# Content Workflow

## Manual Writing

Write in Workbench or a local editor, then commit reviewed MDX files under `apps/web/src/content`.

Raw notes and logs can be staged under `automation/raw/inbox` before conversion. Keep sensitive files out of Git; use `automation/raw/private` for local-only scratch material.

## Collections

- Projects: systems implementation records.
- Notes: reusable technical references, operational logs, deployment runbooks, troubleshooting, and paper reading notes.
- Research: computer science, electrical/electronic engineering, systems engineering, AI infrastructure, software engineering, algorithms, and embedded/system-level engineering notes.
- Archive: temporary notes, experiments, and reviewed archive material.

## Taxonomy

Top-level collections describe the content type. Keep navigation simple and use metadata inside collections for finer organization.

- `area`: study or technical field, such as `Computer Networks`, `Algorithms`, `Kubernetes`, or `Registry/Nexus`.
- `type`: writing format, such as `concept`, `troubleshooting`, `problem-solving`, `runbook`, `paper-review`, `research-note`, `implementation-note`, `decision-record`, or `experiment-note`.
- `series`: learning path, grouped sequence, or ongoing topic.
- `tags`: specific keywords.
- `problemId`: optional problem identifier for coding-test or Baekjoon notes.

Notes areas include Algorithms, Baekjoon, Computer Networks, Operating Systems, Databases, System Software, Digital Circuits, Computer Architecture, Cloud Infrastructure, Kubernetes, Networking, Troubleshooting, Programming, and Security.

Operational material is grouped under Notes using areas such as Kubernetes, Networking, CI/CD, Registry/Nexus, Storage, and Troubleshooting.

Research areas are limited to computer science and electrical/electronic engineering topics: Computer Architecture, Systems, Distributed Systems, AI Infrastructure, Embedded Systems, and Electronic Engineering.

Placement rules:

- Concept study notes go to Notes.
- Algorithm and Baekjoon notes go to Notes.
- Computer networks, operating systems, databases, system software, and digital circuits study notes go to Notes.
- Real operational logs, deployment notes, troubleshooting, and incident notes go to Notes.
- Built systems and tools go to Projects.
- Paper reading notes go to Notes; original research experiments go to Research.
- CS/EE research ideas and experiments go to Research.
- Old drafts or low-confidence generated material goes to Archive.

## Drafts

Drafts use:

```yaml
draft: true
reviewed: false
reviewStatus: "needs-review"
```

Drafts are excluded from public routes.

Visibility is controlled only by `draft`.

- `draft: true` is hidden from public listing and detail pages.
- `draft: false` is visible on public listing and detail pages.
- `reviewed`, `autoGenerated`, `generatedAt`, `source`, and `sourceUrl` do not control visibility.
- If an automation-created entry should remain hidden, keep `draft: true`.

## Project chronology

For published Projects, `date` is the documented **work reference date**, not the date a retrospective was authored. Prefer the dated incident, experiment, report, or other meaningful milestone supported by the original record. A multi-incident article may use a representative dated milestone while retaining the full `period`. Do not infer a particular day from a month-only source or imply that all work took place on that milestone.

- `datePrecision: "day"`: a specific day is supported by the evidence.
- `datePrecision: "month"`: only a month is supported; use its first day internally for sorting and display only the year and month.
- `datePrecision: "period"`: only an interval is supported; use a consistent month-start ordering anchor within that interval and display the existing period text, not its synthetic date. Historical completed projects use their completion month when known; broad ongoing projects use their supported period start.
- `recordedAt`: date of the earliest non-draft revision found in the public source repository (or the date of the first public record for a newly authored project). This is not a claim about the precise time the site was deployed. Keep it stable after edits.
- `updated`: date of the latest substantive article revision. A metadata-only chronology correction need not overwrite this date.

Projects lists use work chronology. RSS uses the first public record for Projects so retrospective work dates do not backdate publication metadata. Preserve Notes, Research and Archive dates from their original authoring/source records unless there is concrete evidence that those dates are incorrect. Imported study notes are maintained in their source repository rather than edited in generated copies.

When changing a Project's frontmatter, update its English source hash so the independent Korean edition remains synchronized. The same date precision must be visible in both languages.

## Public Metadata Policy

Internal workflow fields are kept in frontmatter, but public pages must not label posts as generated, manual, reviewed, or in-review.

Public pages may display:

- title
- description
- date
- updated date
- tags
- category
- content type
- source or source URL when useful and non-sensitive

Do not display these workflow fields on public pages:

- `autoGenerated`
- `generatedAt`
- `reviewed`
- `reviewStatus`
- `sourceKind`
- `sensitivity`

Once a draft has been reviewed and published, it should appear as a normal article. `autoGenerated` remains only for internal tracking because a draft may later be substantially edited by hand.

## Generated Draft Metadata

Generated content should normally start unpublished:

```yaml
draft: true
autoGenerated: true
generatedAt: "2026-05-13"
reviewed: false
reviewStatus: "needs-review"
contentType: "deployment-note"
sourceKind: "raw-note"
sensitivity: "sanitized"
source: "source system or workflow"
sourceUrl: "https://example.com/source"
```

## Raw Note To Draft

Use the local generator for a first-pass structure:

```bash
npm run draft:from-note -- --source automation/raw/inbox/example.md --collection notes --type deployment-note --tags "deployment,github-pages"
```

The generator:

- reads one raw note or log file
- redacts obvious IPs, emails, bearer [REDACTED], and key/value secrets
- infers a collection and content type when not supplied
- writes an MDX draft into the existing Astro content collections
- never publishes content

Manual review is still required before changing `draft` or `reviewStatus`.
