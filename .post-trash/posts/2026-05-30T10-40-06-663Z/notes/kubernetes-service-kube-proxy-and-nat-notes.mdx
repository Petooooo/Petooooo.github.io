# Kubernetes Service와 kube-proxy, NAT 정리

## 핵심 요약

Kubernetes Service는 단순히 "Pod를 묶는 객체" 정도로 이해하기 쉽지만, 실제로는 다음과 같은 구조에 가깝다.

```text
가상 IP(VIP) 기반의 L4 로드밸런싱 추상화
```

그리고 이를 Linux kernel networking stack 위에서 구현하는 핵심 요소 중 하나가 `kube-proxy + iptables(netfilter)` 조합이다.

---

# Pod IP vs Cluster IP

## Pod IP

각 Pod가 실제로 가지는 네트워크 주소.

예시:

```text
Pod A -> 10.x.x.x
Pod B -> 10.x.x.x
```

특징:

- 실제 endpoint
- Pod 재생성 시 변경 가능
- Pod마다 개별적으로 존재

---

## Cluster IP

Service에 부여되는 가상 IP(VIP).

예시:

```text
Service web-svc
ClusterIP = 10.x.x.x
```

중요한 점:

- 실제 NIC(Network Interface)에 붙어있는 IP가 아님
- iptables/ipvs가 가로채기 위한 "가상 목적지" 개념에 가까움
- 실제 backend Pod로 rewrite되기 위한 진입점 역할

직관적으로는 다음처럼 이해 가능:

```text
Client
  ↓
ClusterIP
  ↓
실제 Ready Pod 중 하나
```

---

# Service는 무엇을 묶는가?

보통 Deployment/ReplicaSet이 동일 label을 가진 Pod들을 생성한다.

예시:

```yaml
selector:
  app: nginx
```

그러면 Service는:

```text
app=nginx
```

label을 가진 Pod들을 backend endpoint로 사용한다.

즉 결과적으로:

```text
ReplicaSet의 여러 Pod를 하나의 Service로 묶는 형태
```

처럼 동작한다.

---

# kube-proxy의 역할

자주 오해되는 부분:

```text
"kube-proxy가 직접 트래픽을 전달한다"
```

하지만 iptables mode 기준으로는 조금 다르다.

보다 정확하게는:

```text
kube-proxy는 Service/Endpoint 상태를 감시하고
iptables rule을 생성/수정/삭제하는 controller 역할에 가깝다.
```

즉 실제 forwarding은:

```text
Linux kernel의 netfilter/iptables
```

가 수행한다.

---

# NodePort 트래픽 흐름

예시:

```text
외부 클라이언트
→ NodeIP:NodePort
→ iptables PREROUTING
→ KUBE-SVC chain
→ backend Pod 선택
→ DNAT
→ PodIP:TargetPort
```

직관적으로 표현하면:

```text
외부에서 들어온 목적지를
실제 Pod 주소로 rewrite
```

하는 과정이다.

---

# NAT(Network Address Translation)

NAT은:

```text
패킷의 IP/Port 정보를 중간에서 수정하는 기술
```

이다.

주로 다음 정보를 수정한다.

- Source IP
- Destination IP
- Source Port
- Destination Port

즉:

```text
L3(IP) + L4(Port)
```

수준에서 rewrite를 수행한다.

---

# DNAT

Destination NAT.

목적지를 변경하는 NAT.

예시:

원래 목적지:

```text
dst = NodeIP:30080
```

변경 후:

```text
dst = PodIP:8080
```

즉:

```text
NodePort/ClusterIP
→ 실제 backend Pod
```

로 목적지를 변경한다.

Kubernetes Service의 핵심 동작 중 하나.

---

# SNAT

Source NAT.

출발지를 변경하는 NAT.

예시:

```text
src = PodIP
↓
src = NodeIP
```

주로:

- 외부 통신
- 응답 경로 유지
- masquerade

등에 사용된다.

---

# iptables와 netfilter

Linux kernel에는 패킷 흐름 중간에 hook 지점이 존재한다.

대표적으로:

```text
PREROUTING
INPUT
FORWARD
OUTPUT
POSTROUTING
```

iptables는 여기서:

- NAT
- filtering
- redirect
- marking

등을 수행한다.

---

# Kubernetes에서의 DNAT 직관

예시:

```text
ClusterIP = 10.x.x.x:80

Ready Pod:
10.x.x.x:8080
10.x.x.x:8080
```

클라이언트가:

```text
10.x.x.x:80
```

으로 요청하면 iptables가:

```text
dst = ClusterIP:80
↓
dst = PodIP:8080
```

으로 rewrite한다.

즉 Service는 사실상:

```text
iptables 기반 NAT 추상화
```

라고 볼 수 있다.

---

# kube-proxy와 Ready Pod

kube-proxy는 API Server로부터:

- Service
- EndpointSlice
- Pod readiness

정보를 watch한다.

그리고 Ready 상태인 backend Pod만 대상으로 iptables rule을 구성한다.

즉:

```text
Ready 상태가 아닌 Pod는
Service backend에서 제외
```

된다.

---

# kube-proxy는 실제 프록시인가?

iptables mode 기준으로는 일반적인 의미의 프록시와는 다르다.

오히려:

```text
네트워크 정책 관리자
```

또는:

```text
data plane을 구성하는 control agent
```

에 더 가깝다.

실제 패킷 forwarding은 kernel이 담당한다.

---

# 정리

현재 이해 기준에서 Kubernetes Service는 다음처럼 정리 가능하다.

```text
Service
=
Pod 집합에 대한
가상 IP 기반 L4 로드밸런싱 추상화
```

그리고 kube-proxy는:

```text
Service 상태를 기반으로
iptables/ipvs rule을 관리하는 controller
```

로 이해할 수 있다.

---

# 헷갈리기 쉬운 포인트

## ClusterIP가 실제 NIC에 붙는가?

아님.

일반적으로:

```text
iptables가 가로채기 위한 VIP 개념
```

에 가깝다.

---

## kube-proxy가 직접 패킷을 forwarding하는가?

iptables mode에서는 일반적인 의미의 forwarding proxy는 아님.

실제 패킷 처리는:

```text
Linux kernel networking stack
```

가 담당한다.

---

## Service는 Pod를 직접 소유하는가?

아님.

Service는 selector를 통해 Pod를 선택한다.

보통 ReplicaSet/Deployment가 Pod를 생성하고, Service는 이를 backend endpoint로 사용한다.
