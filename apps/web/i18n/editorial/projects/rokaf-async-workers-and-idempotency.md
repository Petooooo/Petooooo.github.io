사용자가 요청한 일이 몇 초 만에 끝나지 않을 때가 있다. 특히 파일 처리나 다른 서비스에 의존하는 작업은 HTTP 연결을 계속 붙잡아두는 것보다 요청을 먼저 접수하고 백그라운드에서 처리하는 편이 나을 때가 많다.

내부 서비스에 RabbitMQ를 사용하면서 처음에는 API와 Worker를 분리하는 구조 자체에 집중했다. 하지만 운영 관점에서 더 중요한 질문은 따로 있었다. **Worker가 작업 결과를 저장한 직후, 메시지에 Ack를 보내기 전에 죽는다면 어떻게 될까?**

Broker는 Ack를 받지 못한 메시지를 다시 전달할 수 있다. Worker가 이미 했던 일을 그대로 반복한다면 사용자의 요청 하나가 결과물 두 개로 남을 수 있다. 큐를 도입했다고 문제가 끝나는 것이 아니라, 큐 때문에 생기는 실패 지점을 설계해야 했다.

## 요청을 받아들이는 시간과 실행하는 시간을 분리했다

RabbitMQ를 이용하면 API는 작업을 접수하고 상태를 전달하는 일에 집중할 수 있다. Worker는 실제 처리 속도에 맞춰 큐에서 메시지를 가져간다. 호출자가 연결을 끊어도 작업을 이어갈 수 있고, 여러 Worker로 소비를 분산하는 구조도 만들 수 있다.

다만 큐는 실패를 없애지 않는다. 작업이 아직 대기 중인지, Worker가 처리 중인지, 중간 결과가 남았는지, 재시도가 필요한지, 영구적으로 실패했는지 판단할 상태가 추가로 필요하다.

{{figure /figures/journals/rabbitmq-idempotency.svg | 메시지 전달과 Ack, 작업 결과의 영속 상태를 분리한 개념도다. 큐가 작업을 다시 보내더라도 결과까지 중복 생성하지 않는 조건이 핵심이다.}}

## Ack는 결과의 정확성을 보장하지 않는다

메시지의 생애를 따라가 보면 취약한 구간이 여러 곳에 있다.

| 구간 | 실제로 일어날 수 있는 일 |
| --- | --- |
| Publish 응답 전 | Broker에 메시지가 들어갔지만 호출자는 성공을 못 받았을 수 있음 |
| 메시지 수신 전 | 작업은 대기 중이지만 아직 결과 없음 |
| 처리 중 | 일부 파일이나 데이터만 만들어졌을 수 있음 |
| 결과 저장 후, Ack 전 | 결과는 이미 있는데 같은 작업이 다시 배달될 수 있음 |
| Ack 이후 | 전달은 끝났지만 애플리케이션의 최종 결과가 정확한지는 별도 문제 |

이 중 특히 네 번째 구간이 중요했다. Ack를 늦게 보내면 메시지 손실 위험을 줄이는 데 도움이 되지만, 작업의 중복 실행 가능성이 생긴다. 반대로 결과를 확인하기 전에 Ack부터 보내면 Worker가 죽었을 때 작업을 잃을 수 있다.

따라서 최소 한 번 전달되는 방식(At-least-once Delivery)을 사용한다면 **같은 메시지를 다시 받아도 논리적 결과가 중복되지 않게 만드는 것**은 애플리케이션의 책임이다. Broker의 Ack만으로 정확히 한 번 효과가 발생했다고 보장할 수 없다.

## 시도 ID보다 작업 ID가 중요했다

사용자가 파일 하나를 변환해 달라고 요청했다고 생각해보자. API 응답이 Timeout이 나서 사용자가 다시 요청할 수 있다. Worker도 재전송된 메시지를 다시 받을 수 있다.

이때 시도할 때마다 새로운 작업으로 취급하면 결과 파일이 여러 개 만들어질 수 있다. 반면 사용자가 의도한 한 번의 작업을 식별하는 안정적인 ID가 있으면, 이미 완료한 작업인지, 중간부터 재개해야 하는지, 실패한 상태인지 판단할 근거가 생긴다.

내가 검토한 상태 모델은 `pending` → `processing` → `completed` 또는 `failed`였다. 자동 재시도를 더 이상 진행할 수 없는 경우에는 별도의 실패 대기 상태를 두고 운영자가 확인할 수도 있다.

문제는 상태 변경과 실제 작업 결과가 언제나 하나의 트랜잭션에 속하지 않는다는 점이다. DB에 `completed`를 기록하는 작업과 S3 객체를 쓰는 작업은 서로 다른 시스템에 걸쳐 있을 수 있다. 한쪽만 성공한 시점에 Worker가 죽으면 다시 실행할 때 무엇을 믿어야 할지 결정해야 한다.

그래서 결과 객체의 Key를 안정적으로 정하거나, DB의 유일성 제약을 이용하거나, 기존 결과를 조회해 재사용하는 방식 같은 대안을 검토했다. 작업 종류에 따라 적합한 방식이 달라진다. 이 모두를 동일한 형태로 배포했다는 뜻은 아니다.

## Worker를 늘린다고 처리량이 계속 증가하지는 않는다

메시지가 쌓이면 Worker 수를 늘리는 일이 가장 먼저 떠오른다. 하지만 Worker가 데이터베이스나 객체 저장소를 기다리고 있다면, 수를 늘리는 것이 병목에 더 큰 압력을 줄 수도 있다.

큐의 길이만이 아니라 가장 오래 기다린 메시지의 나이, 처리 완료 속도, 재전송 횟수, Worker의 메모리 사용량, 최종 결과를 함께 살펴야 한다.

Queue Depth가 계속 늘어난다면 입력 속도가 소비 속도보다 높다는 뜻일 수 있다. Worker는 바쁜데 DB 지연이 크다면 소비자를 더 만드는 것이 올바른 대응인지 의심해야 한다. Poison Message가 반복해서 재시도된다면 일반적인 처리량 그래프에서는 잘 드러나지 않는 장애가 생길 수도 있다.

그래서 Worker 동시성은 무작정 최대치로 늘리기보다 **하위 시스템이 감당할 수 있는 수준으로 제한**해야 했다.

## 어떤 테스트가 있어야 안심할 수 있을까

내가 재현해보고 싶었던 장면은 단순하다. 논리 작업을 하나 발행한 다음, Worker가 실제 결과를 저장했지만 Ack를 보내기 전에 중단시킨다. 메시지를 재전송한 뒤 최종 상태를 비교한다.

여기서 성공 조건은 Worker가 두 번 실행됐는지가 아니다. **사용자가 의도한 결과가 한 번만 남았는가**다.

정상 작업, 재시도된 작업, 영구 실패한 작업을 구분해 상태를 조회할 수 있어야 하고, 작업 완료 후 API가 같은 작업 ID로 일관된 결과를 보여줄 수 있어야 한다.

남아 있는 기록은 큐와 비동기 처리, 멱등성에 관한 설계와 운영 고민을 뒷받침하지만, 이 모든 실패 주입 실험을 완료하거나 구체적인 처리량 개선 수치를 측정했다는 자료는 없다. 그래서 성능 향상을 만들어 내기보다 실패 가능성을 어떻게 다뤘는지 남긴다.

RabbitMQ를 운영하며 중요하게 생각하게 된 것은 큐 자체보다 **작업의 영속적인 정체성과 상태**였다. 호출자는 이미 기다리기를 포기했을 수 있고, 메시지는 다시 배달될 수 있다. 그때도 결과가 정확하려면 메시지와 별도로 유지되는 작업 기록이 필요하다.
