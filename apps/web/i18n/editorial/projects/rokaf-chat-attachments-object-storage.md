채팅방도 남아 있었고, 사용자 계정도 정상적으로 보였다. 오래된 대화 내역을 스크롤하면 이전에 올렸던 사진과 파일의 흔적도 있었다. 그런데 정작 파일을 열어보면 실패했다.

Rocket.Chat을 다른 환경으로 옮기면서 MongoDB 데이터를 복원한 뒤 마주한 상황이다. 처음에는 데이터베이스 복원이 잘못됐다고 생각했다. 하지만 새로 업로드한 파일은 MinIO에 정상적으로 저장됐고, 다시 내려받을 수도 있었다. **새 파일은 열리는데 예전 파일만 열리지 않는 것**이었다.

이 차이를 보고 조사 방향을 바꿨다. MinIO 연결 자체가 끊겼다면 새 파일도 실패했을 것이다. 채팅 메시지가 사라졌다면 복원 과정부터 살펴야 했겠지만, 문제의 메시지들은 그대로 있었다. 그렇다면 메시지와 첨부파일의 실제 바이트가 서로 어떤 방식으로 연결되는지 확인해야 했다.

## 메시지 하나가 파일 하나를 온전히 담고 있지는 않다

Rocket.Chat 화면에서는 파일을 올린 메시지 하나로 보이지만, 실제 데이터는 여러 곳에 나뉘어 있다.

메시지에는 첨부파일에 대한 참조가 남는다. 업로드 정보를 관리하는 MongoDB 레코드에는 파일 식별자와 이름, 저장 위치를 찾는 데 필요한 정보가 담긴다. 예전에 사용하던 GridFS는 파일 정보를 관리하는 Collection과 바이너리 조각을 담는 Collection을 따로 사용한다. 반면 MinIO로 옮긴 파일은 S3 객체의 Key로 찾게 된다.

따라서 메시지나 업로드 레코드를 복원하는 것과 파일의 실제 데이터를 옮기는 것은 서로 다른 작업이다. GridFS에서는 파일 정보가 남아 있어도 그 파일을 구성하는 Chunk가 없으면 원래 바이트를 재구성할 수 없다. MinIO에서도 객체 자체가 존재하더라도 Rocket.Chat이 다른 Key를 요청한다면 해당 파일은 열리지 않는다.

{{figure /figures/journals/chat-attachment-identity-map.svg | 화면에서 보이는 첨부파일 하나가 메시지, 업로드 메타데이터, GridFS 원본 데이터, S3 객체 Key에 걸쳐 연결되는 관계를 그렸다. 실제 저장소 배치도는 아니다.}}

Rocket.Chat 문서에도 저장소 유형을 변경한다고 과거 파일이 자동으로 새 저장소에서 열리는 것은 아니라고 안내돼 있다. 당시 내 상황이 딱 그랬다. 이미 쌓인 파일과 앞으로 업로드할 파일은 서로 다른 저장 방식을 바라보고 있었다.

## 새로 업로드한 파일이 기준이 됐다

우선 정상적으로 동작하는 쪽부터 살펴봤다. 새 파일을 하나 올리고, Rocket.Chat이 MinIO에 어떤 이름으로 객체를 만드는지 확인했다.

당시 새로 만들어진 S3 객체 Key는 대략 다음과 같은 구조였다.

`<workspace-prefix>/uploads/<room-id>/<user-id>/<upload-id>`

여기서 중요한 것은 각 식별자 자체가 아니다. 기존 GridFS 파일을 아무 이름으로 버킷에 복사해서는 안 되고, **현재 실행 중인 Rocket.Chat이 기대하는 Key의 구조**를 따라야 한다는 점이었다.

확인해야 할 값도 하나가 아니었다.

| 항목 | 어떤 의미로 구분했나 |
| --- | --- |
| S3 Object Key | MinIO 버킷 안에서 실제 파일 데이터를 찾는 위치 |
| `AmazonS3.path` | Rocket.Chat 업로드 레코드가 참조하는 S3 Key |
| `path` | 애플리케이션이 노출하는 업로드 경로 |
| `url` | 미리보기나 다운로드에 사용되는 파일 URL |
| GridFS 파일 ID | 예전 저장소에서 원본 바이트를 찾는 식별자 |

당시 환경에서는 `path`가 `/file-upload/<id>/<name>` 형태였고, `url`에는 `/ufs/AmazonS3:Uploads/<id>/<name>` 형식이 사용됐다. 비슷해 보여도 서로 다른 역할을 하는 값이다. 특히 `AmazonS3.path`를 다른 Key로 적어두면 올바른 바이트를 MinIO에 올려도 기존 메시지에서는 찾지 못할 수 있다.

이 URL 형식은 **당시 사용하던 버전에서 관측한 것**이다. Rocket.Chat의 이후 버전에서는 파일 접근 경로가 달라질 수 있으므로, 다른 버전에 같은 문자열을 그대로 적용해서는 안 된다.

## GridFS에서 꺼내는 일과 MinIO에 놓는 일

원본 파일을 가져오는 작업에서도 고민이 있었다. GridFS는 파일을 일반 디렉터리 구조로 저장하지 않는다. 파일 레코드의 ID와 Chunk의 순서를 따라 바이트를 재구성해야 한다. 원본에서 파일을 꺼낸 다음에도 어느 메시지에 속한 파일인지, MinIO에서는 어떤 Key가 되어야 하는지 따로 알아야 했다.

그래서 작업을 두 부분으로 나누어 생각했다. **먼저 원본 파일을 정확히 꺼내고, 그다음 새로운 저장소의 주소 규칙에 맞게 배치하는 것**이다.

당시에는 파일 ID 목록을 텍스트로 뽑아 최근 파일부터 확인하는 방법을 검토했다. `recent_files.txt`에서 ID만 추출해 한 디렉터리에 파일 ID를 이름으로 저장해두고, 파일이 모이면 `mv`로 필요한 디렉터리 구조를 만드는 방식이었다. 그다음 MinIO Client로 객체를 옮기면 원본 파일 추출과 S3 Key 매핑을 따로 점검할 수 있었다.

이 순서를 생각한 이유는 단순하다. 파일을 잘못 꺼냈다면 경로를 아무리 고쳐도 원본이 돌아오지 않는다. 반대로 파일을 제대로 꺼냈는데 Key를 잘못 만들었다면 같은 GridFS 추출을 계속 반복할 필요가 없다.

`mongofiles`와 `mc`를 이용한 추출·업로드 절차도 구체적으로 검토했다. 다만 작업을 설명하기 위해 정리한 절차와 **전체 과거 파일의 이전·검증이 끝났다는 결과**는 구분해야 한다. 현재 남아 있는 자료만으로 모든 파일이 정상 이전됐다고 말할 수는 없다.

## MongoDB 접속 오류는 또 다른 문제였다

마이그레이션을 진행하던 중 MongoDB Replica Set 쪽의 문제도 있었다. 일부 연결에서는 `getaddrinfo ENOTFOUND`가 발생했고, MongoDB 클라이언트가 `ReplicaSetNoPrimary` 상태를 보였다.

처음에는 같은 “파일이 안 열린다”는 증상으로 묶기 쉽다. 하지만 MongoDB 멤버의 이름을 해석하지 못해 파일을 읽어오지 못하는 것과, MinIO에 있는 파일을 잘못된 Key로 요청하는 것은 전혀 다른 문제다.

Replica Set이 설정돼 있다는 사실만으로 모든 Pod에서 멤버의 주소를 올바르게 찾을 수 있는 것은 아니다. 또한 멤버 간 연결과 Primary 선출 상태를 확인하지 않은 채 연결 문자열만 바꾸면 진단이 더 어려워질 수 있다.

이 MongoDB 오류가 예전 첨부파일 문제 전체의 원인이었다고 판단하지는 않았다. **원본을 읽는 데 실패한 단계와 새 저장소에서 찾는 데 실패한 단계를 구분**해야 했다는 것이 중요했다.

## 개수만 맞으면 끝났다고 할 수 있을까

파일 복사를 마치면 버킷에 객체가 몇 개 있는지 먼저 세어보게 된다. 하지만 객체 수가 같아도 참조가 잘못됐을 수 있다. 같은 내용이 다른 Key에 올라갔을 수도 있고, 객체의 크기나 바이트가 달라졌을 수도 있다. 계정 권한이 달라 실제 사용자는 다운로드하지 못할 수도 있다.

그래서 필요한 것은 총량을 비교하는 표보다는 **업로드 ID마다 검증 상태를 남기는 대조표**라고 생각했다.

{{figure /figures/journals/chat-attachment-reconciliation-matrix.svg | 새 업로드의 정상 동작과 과거 첨부파일 접근 실패는 당시 확인한 사실이다. 나머지는 원본 파일, 메타데이터, S3 객체와 실제 다운로드를 확인해야 하는 검증 항목이다.}}

대조표를 만든다면 적어도 원본 GridFS 파일 ID, 예상 S3 Key, 추출 여부, MinIO에서의 객체 존재 여부, 크기·체크섬, 실제 Rocket.Chat 다운로드 결과를 나누어 적어야 한다.

여기서 MinIO의 객체 조회가 성공한 것과 Rocket.Chat에서 정상적으로 열리는 것은 별개의 조건이다. `mc stat`으로 Key가 존재하는지 확인해도, 실제 사용자가 요청하는 URL이 다른 파일을 가리키거나 권한 검사에서 막힐 수 있다. 반대로 파일 URL이 보인다고 실제 바이너리가 완전하다는 뜻도 아니다.

체크섬도 조심해야 한다. S3의 ETag를 모든 파일의 MD5라고 가정하면 Multipart Upload 등에서 잘못된 비교를 할 수 있다. 서로 비교 가능한 체크섬이 있는지 확인하거나, 필요한 경우 원본과 대상의 바이트를 직접 읽어 비교하는 편이 더 확실하다.

## 저장소 설정을 바꾸는 순간에도 파일은 계속 생긴다

가장 어려운 문제는 언제 새 저장소를 기준으로 삼을 것인지였다.

앞으로 올라올 파일은 MinIO에 정상적으로 저장되는데, 오래된 파일의 본문은 여전히 GridFS에만 남아 있을 수 있다. 이 상태에서 저장소 설정만 바꾸면 화면의 메시지는 살아 있어도 첨부파일을 찾는 경로는 달라진다.

복사 중에도 사용자가 새 파일을 올릴 수 있다. 첫 번째 파일 목록을 뽑은 뒤 생성된 파일은 어떻게 처리할지, 어떤 시점에 원본 쓰기를 멈추고 마지막 차이를 맞출지 정해야 한다. 문제가 생겨 이전 설정으로 돌아갈 경우 새로 생긴 파일을 잃지 않으려면 어떤 메타데이터와 객체를 보존해야 하는지도 생각해야 했다.

그래서 롤백을 단순히 설정을 되돌리는 작업으로 볼 수 없었다. 이전 GridFS 데이터와 새 S3 객체, 그 사이에 바뀐 메타데이터가 함께 맞아야 한다.

당시 전체 첨부파일을 대상으로 바이트 단위 비교와 다운로드 검증을 모두 수행했다는 증거는 남아 있지 않다. 원본 GridFS를 제거해도 괜찮다고 판정한 최종 감사 결과나 완전한 롤백 테스트도 확인되지 않는다. 그런 결과는 만들어 넣지 않으려 한다.

## 결국 파일의 주소를 옮기는 작업이었다

처음에는 GridFS에 있던 파일을 MinIO에 복사하면 끝날 줄 알았다. 하지만 메시지에 남아 있는 식별자, 업로드 레코드의 메타데이터, GridFS에서 실제 바이트를 찾는 방식, S3의 객체 Key가 모두 맞아야 예전 첨부파일 하나를 다시 열 수 있었다.

가장 도움이 됐던 단서는 **새 파일은 열리고 예전 파일은 열리지 않는다는 차이**였다. 덕분에 저장소 자체가 동작하지 않는 문제와 과거 데이터의 참조가 맞지 않는 문제를 나눌 수 있었다.

나중에 같은 종류의 이전 작업을 다시 한다면 총 파일 수보다 먼저 하나의 논리적인 파일 ID를 따라가고 싶다. 메시지에서 참조한 파일이 어떤 업로드 레코드로 이어지는지, 원본 GridFS에서는 어떤 바이트가 나오는지, MinIO의 어느 Key에 놓이는지, 마지막으로 실제 사용자가 그 파일을 열 수 있는지까지.

남은 검증은 메시지의 파일 참조부터 업로드 메타데이터, GridFS 원본 바이트, MinIO Object Key, 최종 다운로드 응답을 하나씩 연결해 확인하는 작업이었다.
