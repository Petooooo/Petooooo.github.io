처리 시간이 긴 문서 변환 작업을 돌리던 중 RabbitMQ 연결이 먼저 끊긴 적이 있었다. Broker에서는 메시지를 다시 전달할 수 있는 상태가 됐는데, 정작 파일을 처리하던 Worker는 계속 일을 하고 있었다. 같은 문서를 두 Worker가 동시에 처리할 수도 있다는 뜻이었다. 연결이 끊겼다는 사실과 작업이 끝났다는 사실을 같은 것으로 취급하면 문제가 생겼다.

이 경험을 떠올리며 2026년 6월 비동기 문서 번역 서비스를 설계하고 구현했다. 문서 하나를 번역하려면 파일을 받아 저장하고, 형식에 맞게 내용을 추출한 다음, 번역된 내용을 다시 문서에 넣어 결과물을 만들어야 했다. PDF와 DOCX, HWPX는 중간에 거치는 과정도 달랐다. 어떤 단계는 HTTP 요청 하나가 기다리기에는 너무 오래 걸렸고, 중간 실패가 곧 사용자 작업 전체의 실패를 뜻하지도 않았다.

그래서 HTTP 요청이 맡는 일은 작업을 접수하고 식별자를 반환하는 데까지로 줄였다. 이후에는 RabbitMQ가 단계별 실행 명령을 전달하고, 별도로 유지하는 작업 상태를 기준으로 어떤 Worker가 무엇을 처리해야 할지 결정하도록 했다. **이 구조는 로컬 구현과 계약 테스트, 형식별 E2E Smoke Test 및 별도 설치 리허설에서 확인했다.** 실제 운영 환경에서 모든 문서를 정확하게 번역하고 장애 후에도 복구된다는 수준까지 검증한 것은 아니다.

## HTTP 요청이 문서 한 건을 끝까지 붙잡지 않도록

문장을 하나 번역하는 API라면 요청을 보내고 응답을 받는 과정이 비교적 단순하다. 문서에는 다른 일이 붙는다. 표 안의 텍스트를 바꿔야 하고, 번역문이 길어지면 줄바꿈이나 페이지 배치가 달라질 수 있다. 텍스트를 모두 번역해도 원래의 파일 형식으로 다시 조립하지 못하면 사용자가 받을 결과물은 없다.

한 요청 안에서 업로드, 변환, 추출, 번역, 치환, 내보내기를 모두 처리하는 방식은 실패 지점도 한데 묶는다. 클라이언트 연결이 끊겼을 때 실제 변환은 어디까지 진행됐는지 알기 어려워진다. 사용자가 다시 업로드하면 새 작업이 하나 더 만들어질 수도 있다.

우선 사용자의 문서 작업을 RabbitMQ 메시지 하나와 분리했다. 입력 파일과 각 단계에서 만들어진 파일은 객체 저장소에 두고, Job ID와 현재 단계, 시도 횟수와 작업 상태는 DB에 남겼다. RabbitMQ는 그 기록을 대신하는 저장소가 아니라 다음에 실행할 일을 전달하는 수단으로 사용했다.

작업의 다음 단계를 정하는 역할은 Job Service에 두었다. 파일 변환 Worker가 스스로 다음 Queue를 고르는 방식은 피했다. 각 Worker는 자신이 맡은 단계의 결과를 보고하고, Job Service가 그 결과가 지금도 유효한지 확인한 뒤 다음 단계를 진행한다. 이 선택 덕분에 순서를 판단하는 곳은 한 군데로 모을 수 있었지만, 중복 이벤트와 오래된 결과를 무시할 책임도 그쪽에 생겼다.

{{figure /figures/journals/document-translation-architecture.svg | API는 작업을 접수하고 Job Service는 단계의 상태를 보존한다. RabbitMQ는 실행 명령을 전달하며 PDF·DOCX·HWPX Worker는 각 형식의 처리 결과를 객체 저장소에 남긴다. 실제 내부 시스템 배치가 아닌 역할 분담 개념도다.}}

## PDF, DOCX, HWPX를 같은 변환기로 다루기 어려웠다

문서의 구조를 바꾸지 않고 텍스트만 교체하면 될 것 같았지만, 파일 형식에 따라 그 가정이 성립하지 않았다.

DOCX는 문단·Run·표 같은 요소를 구조적으로 다룰 수 있다. 다만 추출한 문장을 번역한 뒤 다시 넣었다고 해서 Run의 스타일이나 표의 높이, 페이지 배치가 보존됐다는 의미는 아니다. 텍스트 길이가 바뀌면 구조를 유지한 채로도 화면에 보이는 결과는 달라질 수 있다.

PDF는 편집 가능한 문서와 다른 문제를 가지고 있었다. 당시 구현한 경로에서는 중간 DOCX 표현으로 변환해 텍스트를 추출·치환하고, 요청한 출력 형식에 맞춰 다시 내보내는 흐름을 시험했다. 중간 변환 단계가 늘어나면 글꼴과 페이지 나눔, 그림·표의 위치가 달라질 가능성도 늘어난다. Worker가 정상 종료했다는 것은 결과 파일을 만들었다는 뜻에 가깝지, 화면까지 원본과 같다는 보증이 아니다.

HWPX는 패키지 구조와 자체 문서 요소를 다뤄야 했다. 전용 추출·치환 경로를 두었고, 초기 내보내기 작업에는 호환성을 맞추기 위한 임시 처리도 있었다. 이후 형식별 E2E Smoke Test는 단계가 끝까지 연결되고 결과물이 전달되는지 확인했다. **다양한 실사용 HWPX 문서의 모든 기능을 보존했다는 시험은 아니었다.**

세 경로가 각자 별개의 서비스 전체를 갖고 있는 것은 아니었다. 작업 접수와 상태 관리, 번역 연결, 결과 통지는 공유하고 형식마다 실제 파일을 다루는 Worker만 달라졌다. 공통 기능과 예외가 많은 파일 처리 기능의 경계를 나누는 편이 문제가 발생한 구간을 찾기 쉬웠다.

| 문서 형식 | 별도로 처리한 부분 | 당시 검사에서 확인한 범위 |
| --- | --- | --- |
| DOCX | 구조 기반 추출·치환 | 단계별 전달과 결과 생성 경로 |
| PDF | 편집 가능한 중간 표현을 거치는 변환 | 변환 Worker와 전체 경로의 완료 |
| HWPX | 패키지 구조에 맞춘 추출·치환 | 전용 경로의 전달과 Smoke Test 완료 |

형식별 테스트를 통과한 뒤에도 남은 일은 분명했다. 실제 문서 모음을 모아 서식, 표, 이미지, 복잡한 레이아웃을 비교해야 했다. 그런 품질 평가 결과가 없으므로 문서 충실도가 검증됐다고 기록하지 않는다.

## RabbitMQ Ack 시점을 바꾸면서 생긴 책임

예전 방식에서는 Worker가 파일 변환을 모두 마칠 때까지 메시지를 Ack하지 않았다. 처리 도중 Worker가 종료되면 Broker가 메시지를 다시 전달할 수 있다는 장점이 있다. 하지만 작업은 오래 걸리고 AMQP 연결은 그보다 먼저 끊길 수 있었다. 연결이 사라지면 Broker는 다시 전달을 결정하는데, 원래 Worker의 파일 처리까지 자동으로 중단시키지는 못한다.

반대로 메시지를 받자마자 Ack하면 문제가 없어질까. 그렇게 하면 Worker가 아무런 상태도 남기지 못한 채 죽었을 때 Broker는 작업을 다시 전달할 이유를 잃는다.

6월에 구현한 방식은 그 사이에 영속 상태를 두었다. Worker가 현재 Stage를 확인하고 Job Service에 Claim을 기록한다. Claim에는 Attempt와 Lease가 연결된다. **상태 저장이 성공한 다음 RabbitMQ 명령을 Ack**하고 오래 걸리는 작업을 수행하도록 했다.

이제 Ack 이후 Worker가 죽어도 작업이 사라져서는 안 된다. Broker에는 Ack한 Delivery가 남아 있지 않으므로, Lease가 만료됐는지 살피는 Reconciler가 새로운 시도를 허용해야 한다. 늦게 끝난 이전 Worker가 결과를 보내더라도 현재 Stage와 Claim이 맞지 않으면 그 완료 이벤트를 그대로 받아들이면 안 된다.

{{figure /figures/journals/document-translation-job-state.svg | Pending에서 Claim·실행·완료로 이어지는 상태와 재시도·Lease 만료·최종 실패를 구분했다. RabbitMQ Ack는 결과 파일의 완료와 다르며, 복구는 영속된 Stage 상태를 기준으로 판단한다. 실제 운영 Queue 설정을 나타내는 그림은 아니다.}}

여기서 해결하려 했던 문제는 RabbitMQ가 메시지를 정확히 한 번 전달하게 만드는 것이 아니었다. Broker가 같은 명령을 여러 번 전달하거나 Worker가 사라지더라도 하나의 **논리적인 문서 작업**이 잘못된 단계로 넘어가지 않게 하는 일이었다.

## PostgreSQL, 객체 저장소와 RabbitMQ 사이의 빈틈

Job Service가 PostgreSQL에 기록을 남기고 Worker가 MinIO에 결과물을 저장하는 동안 RabbitMQ는 명령을 전달한다. 이 세 시스템의 작업을 한 번의 원자적 Transaction으로 묶을 수는 없었다.

가령 Worker가 결과 파일을 객체 저장소에 올린 직후 종료됐다고 하자. DB의 Stage는 아직 완료되지 않았고, RabbitMQ에는 이미 Ack를 보낸 상태일 수 있다. 이후 재시도한 Worker가 앞선 결과를 확인하지 않고 새 파일을 만들면 같은 사용자의 결과가 중복될 가능성이 있다.

반대도 문제다. DB에서는 완료됐다고 표시했는데 객체 저장소에 해당 파일이 없다면 사용자는 결과물을 받을 수 없다. 그래서 완료 이벤트를 받을 때 현재 Stage와 Claim, 결과 파일의 식별자를 대조하고, 재시도 시 기존 결과물이 있는지 다시 확인하는 방향으로 설계했다.

재시도에는 횟수와 Backoff가 있어야 했다. 실패가 계속되는 작업은 무한히 돌리기보다 사람이 원인을 확인할 수 있도록 상태를 남기는 편이 적절했다. 로컬 Reliability Test에서는 Claim, 오래된 Lease의 복구, Retry·Backoff, 오래된 이벤트나 중복 이벤트 처리, 논리적인 Dead-letter 상태를 검사했다.

다만 RabbitMQ 자체의 DLX·DLQ까지 모든 환경에서 활성화한 것은 아니었다. Helm 통합 과정에서 기존 Queue의 선언 인자와 새로운 DLX 설정이 달라 `PRECONDITION_FAILED`가 발생했고, 물리적 DLQ 연결은 지원하되 기본으로 켜지 않는 형태가 됐다. **DB에 실패 상태를 남기는 기능과 실제 RabbitMQ Dead-letter Queue가 구성된 상태는 다르다.**

## 번역과 결과 통지는 별도의 계약으로 남겼다

문서 처리 경로에서 중요한 것 중 하나는 파일 변환 Worker가 번역 모델의 내부 구현을 알 필요가 없도록 하는 일이었다. 번역을 요청할 때 세그먼트의 식별자와 원문, 번역 방식을 전달하고, 결과가 어느 부분에 대응하는지 다시 연결할 수 있어야 했다.

통지도 마찬가지였다. 결과 파일을 저장했다고 해서 문서 처리 Worker가 사용자에게 보낼 링크를 직접 만들 필요는 없었다. 통지 어댑터가 수신 대상과 결과물 정보를 다른 서비스에 넘기도록 경계를 두었다. Mock API와 계약 테스트는 이런 정보가 올바르게 전달되는지 확인할 수 있다. 하지만 실제 번역문이 전문 용어에 맞는지, 운영 환경에서 통지와 파일 다운로드가 끝까지 가능한지는 별도의 시험이 필요하다.

## 어느 부분까지 구현하고 검증했는가

6월의 개발 기록에는 아키텍처만 남은 것이 아니다. Python 테스트와 API Contract 검증 기록이 있고, 그중 한 단계에서는 단위 테스트 **121개 통과**가 확인됐다. PDF·DOCX·HWPX 각각의 경로를 따라가는 E2E Smoke Test와 장시간 작업·Retry·Lease 관련 시험도 수행했다. Helm Lint와 설치 리허설에서는 외부 PostgreSQL·RabbitMQ·MinIO를 사용하는 구성을 포함해 상태 확인과 형식별 작업을 검증했다.

이 숫자와 성공 기록은 **해당 시점의 로컬 개발 환경에서 실행한 검사 결과**다. 지금 소스 전체를 다시 받아 동일 버전으로 모든 검사를 재현한 결과도 아니고, 실제 운영 환경에서의 장기 신뢰성을 검증한 결과도 아니다.

특히 문서 품질 측정, 변환 오류 시점별 Failure Injection, 실제 서비스 의존성과의 전체 End-to-end 검증, 장애 뒤 파일 무결성 점검은 여전히 남아 있다. 그 작업을 끝냈다는 근거가 없는 상태에서 '완성된 번역 시스템을 안정적으로 운영했다'고 표현하지 않으려 한다.

## 남은 확인 사항

다시 이 서비스를 시험한다면 PostgreSQL에 Claim을 저장한 직후, 객체 저장소에 결과 파일을 쓰고 완료 이벤트를 보내기 직전, 완료 상태를 적용한 뒤 통지를 보내기 전에 각각 Worker를 중단해 볼 것이다. 그다음 같은 Job ID가 복구되는지, 늦게 도착한 이전 시도의 결과가 무시되는지, 기존 파일을 재사용하거나 정리할 수 있는지 확인해야 한다.

PDF와 DOCX, HWPX마다 표·이미지·각주·복잡한 스타일을 포함한 문서를 준비하고 결과물을 직접 비교하는 검사도 필요하다. Queue의 메시지 수나 Pod의 `Ready` 여부만으로 문서 한 건이 제대로 끝났다고 판단해서는 안 된다.

현재 확인된 것은 **로컬에서 단계형 문서 처리와 일부 복구 동작을 시험했고, 형식별 경로 및 설치 리허설이 완료됐다는 범위**다. 운영 환경의 최종 배포와 전체 문서 충실도 검증은 확인되지 않았다.
