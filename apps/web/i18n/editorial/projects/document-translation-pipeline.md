문서 변환 Worker가 아직 파일을 처리하는데 RabbitMQ 연결이 먼저 끊긴 적이 있었다. Broker는 해당 메시지를 다시 전달할 수 있는 상태가 됐지만, 먼저 실행된 Worker의 작업은 계속되고 있었다. 다음 Worker가 같은 요청을 받으면 하나의 문서를 두 번 처리할 수도 있었다. 메시지를 소비했다는 사실과 문서 처리가 끝났다는 사실은 서로 달랐다.

이 문제는 비동기 문서 번역 서비스를 만들 때도 중요했다. PDF·DOCX·HWPX를 받아 내용을 추출하고 번역한 뒤 다시 문서로 만드는 과정에는 시간이 오래 걸리는 단계가 많았다. 나는 이를 하나의 HTTP 요청이나 RabbitMQ 메시지에 묶지 않고, **작업 상태를 영속적으로 관리하는 파이프라인**으로 설계·구현했다. 개발 단계에서 형식별 처리와 복구 로직을 시험한 뒤, 실제 내부망 환경에 배포해 운영했다.

핵심은 단순히 Queue를 붙이는 일이 아니었다. 파일을 처리하던 Worker가 중간에 사라지거나 같은 명령이 다시 도착하더라도, **사용자가 요청한 문서 작업이 현재 어느 단계에 있는지** 판단할 수 있어야 했다.

## 비동기 Job 처리 구조

문장 몇 개를 번역하는 API와 문서 한 건을 번역하는 서비스는 처리 시간이 다르다. 문서에는 표와 문단, 스타일, 이미지 같은 구조가 있고, 원문을 추출한 뒤 번역문을 다시 삽입하고 파일로 내보내는 작업이 필요하다. 이 모든 과정을 동기 HTTP 요청에서 수행하면 클라이언트 연결과 Timeout이 실제 작업 수명에 영향을 주게 된다.

그래서 API는 문서를 접수하고 Job ID를 반환하는 역할에 집중하도록 했다. 이후 단계는 Worker가 비동기로 처리하고, 클라이언트는 저장된 작업 상태를 조회할 수 있도록 나눴다.

원본과 중간 산출물, 최종 결과물은 MinIO에 저장하고, PostgreSQL에는 Job ID와 Stage, Attempt, Lease, 작업 진행 상태를 기록했다. RabbitMQ는 단계별 작업 명령과 완료 이벤트를 전달하는 데 사용했다. RabbitMQ에 메시지가 남아 있는지만으로는 사용자 작업의 현재 상태를 판단할 수 없었기 때문이다.

다음 단계를 결정하는 책임은 Job Service에 모았다. 변환 Worker가 다음 Queue를 임의로 선택하는 대신 자신이 수행한 단계의 결과를 보고하면, Job Service가 현재 상태와 맞는 결과인지 확인하고 후속 작업을 전달한다. 이렇게 하면 중복 메시지나 늦게 도착한 완료 이벤트를 어느 지점에서 걸러야 하는지도 분명해졌다.

{{figure /figures/journals/document-translation-architecture.svg | Job Service는 작업 상태와 단계 전이를 관리하고, RabbitMQ는 실행 명령을 전달한다. PDF·DOCX·HWPX Worker는 형식별 처리를 수행하며 결과 파일은 객체 저장소에 남긴다. 실제 내부 시스템 배치가 아닌 구성 요소 간 역할을 나타낸 개념도다.}}

## PDF·DOCX·HWPX 처리 경로

처음부터 모든 문서를 같은 변환 코드로 처리하지는 않았다. 세 형식은 텍스트를 추출하는 방식부터 번역 결과를 삽입하는 과정까지 차이가 컸다.

**DOCX**는 문단과 Run, 표 같은 구조를 다룰 수 있어 텍스트 추출과 치환을 구분하기 좋았다. 다만 번역문이 길어지면 Run 구조를 유지하더라도 줄바꿈과 표 높이, 페이지 배치가 달라질 수 있었다. 문서의 구조를 유지하는 문제와 출력 화면의 레이아웃을 맞추는 문제는 별개였다.

**PDF**는 편집 가능한 중간 표현이 필요했다. 당시 구현한 경로에서는 DOCX로 변환해 텍스트를 추출·치환한 뒤, 요청한 출력 형식에 맞춰 다시 내보냈다. 변환 단계가 추가되는 만큼 글꼴이나 페이지 나눔, 이미지와 표의 위치도 확인해야 했다.

**HWPX**는 파일 내부의 패키지 구조를 고려해 전용 추출·치환 경로를 구성했다. 초기에 내보내기 호환성을 맞추기 위한 임시 처리도 있었고, 이후 전용 Worker를 전체 Job 흐름에 연결해 형식별 E2E Smoke Test를 진행했다.

세 형식을 별개의 시스템으로 개발한 것은 아니다. Job 접수, 상태 관리, 번역 호출, 결과 알림은 공통으로 두고 **실제 파일 형식을 다루는 Worker만 분리**했다. 덕분에 특정 형식의 변환 문제를 조사하거나 라이브러리를 수정할 때 다른 경로와 책임을 구분하기 쉬웠다.

| 형식 | 처리 방식 | 확인한 개발 테스트 |
| --- | --- | --- |
| DOCX | 문서 구조를 이용한 텍스트 추출·치환 | 단계별 Worker 전달과 결과 파일 생성 |
| PDF | DOCX 중간 표현을 거치는 추출·치환·내보내기 | PDF 변환 경로의 E2E Smoke Test |
| HWPX | 패키지 구조에 맞춘 전용 추출·치환 | HWPX Worker 연동과 결과물 전달 |

## RabbitMQ Ack와 작업 상태

오래 실행되는 작업을 처리하면서 가장 중요하게 다룬 것은 Ack 시점이었다.

작업이 완전히 끝날 때까지 메시지를 Ack하지 않으면 Worker가 죽었을 때 Broker가 다시 전달할 수 있다. 하지만 변환이 길어지는 동안 RabbitMQ 연결이 끊길 수 있었고, 그 사이 파일 처리는 계속될 수 있었다.

그렇다고 메시지를 받자마자 Ack하는 방식도 적절하지 않았다. 작업 상태를 남기기 전에 Worker가 종료되면 Broker에는 다시 전달할 메시지가 없고, 애플리케이션에도 복구할 근거가 남지 않는다.

새 구조에서는 Worker가 현재 Stage를 확인하고 **Job Service에 Claim을 영속화한 뒤 메시지를 Ack**하도록 했다. Claim에는 Attempt와 Lease를 함께 기록했다. 변환 자체는 그다음에 실행한다.

Ack 이후 Worker가 종료되면 RabbitMQ가 같은 명령을 자동으로 되살리지는 않는다. 이때는 Reconciler가 만료된 Lease를 확인하고 재시도를 허용해야 한다. 이전 Worker가 늦게 결과를 보내더라도 현재 Stage와 Claim에 맞지 않으면 작업을 다음 단계로 넘기지 않는다.

{{figure /figures/journals/document-translation-job-state.svg | Job의 대기·Claim·실행·완료 상태와 Lease 만료, 재시도, 최종 실패를 구분했다. 메시지 Ack와 결과 파일의 완성은 서로 다른 사건이며, 복구는 영속 Job 상태를 기준으로 진행한다.}}

이 방식의 목적은 RabbitMQ가 메시지를 반드시 한 번만 전달하도록 만드는 게 아니었다. **메시지 전달이 반복되더라도 하나의 Job을 일관되게 진행하는 것**이었다.

## 재시도와 결과 파일의 일관성

작업 상태는 PostgreSQL, 결과물은 MinIO, 명령은 RabbitMQ에 나뉘어 있다. 세 시스템을 한 번의 Transaction으로 묶을 수 없기 때문에 각 단계의 완료 시점을 따로 다뤄야 했다.

예를 들어 Worker가 MinIO에 결과 파일을 저장한 직후 종료되면, 실제 파일은 있지만 DB에는 해당 Stage가 완료되지 않은 상태가 남을 수 있다. 다시 실행된 Worker가 이전 산출물을 확인하지 않으면 같은 작업의 결과 파일이 중복 생성될 수 있다. 반대로 DB에는 완료라고 기록했는데 결과 파일이 없다면 사용자는 번역 결과를 받을 수 없다.

그래서 완료 이벤트에는 현재 Stage와 Claim이 맞는지 확인하는 절차를 넣고, 재시도할 때 기존 산출물을 어떻게 다룰지 고려했다. 재시도 횟수와 Backoff도 제한해 계속 실패하는 작업이 무한히 반복되지 않도록 했다. 개발 과정에서는 중복 이벤트, 오래된 완료 이벤트, Lease 만료와 재시도, 논리적인 실패 상태를 테스트했다.

Helm 통합 과정에서는 RabbitMQ의 기존 Queue 선언 인자와 새로운 DLX 설정이 달라 `PRECONDITION_FAILED`가 발생한 적도 있었다. 그 문제를 다루면서 애플리케이션이 DB에 기록하는 최종 실패 상태와 RabbitMQ의 실제 DLX·DLQ 구성은 별개로 유지했다. 물리적인 DLQ 연결은 지원하되 기본으로 활성화하지 않는 구성이었다.

## 번역 서비스와 결과 알림 연동

문서 변환 Worker가 특정 번역 모델의 API 구현까지 알고 있을 필요는 없었다. 파일에서 추출한 문장에는 원문뿐 아니라 세그먼트 식별자도 필요했다. 번역 결과가 돌아왔을 때 어떤 문단이나 위치에 대응하는지 알아야 원래 문서에 다시 넣을 수 있기 때문이다.

번역 호출은 별도 어댑터를 통해 처리하도록 했다. Worker는 번역을 요청하는 데 필요한 데이터와 결과를 주고받고, 번역 서비스의 구체적인 호출 방식은 그 경계 안에 두었다.

결과 알림도 문서 변환과 분리했다. 최종 파일을 저장하는 Worker가 사용자에게 보낼 알림까지 직접 처리하게 하지 않고, 결과 파일의 식별자와 수신 대상 정보를 알림 처리 쪽에 넘기도록 구성했다. 계약 테스트에서는 세그먼트 매핑과 결과 메타데이터, 오류 전달이 올바른지 확인했다.

이렇게 분리해 두면 번역 모델이나 알림 시스템의 구현이 바뀌어도 PDF·DOCX·HWPX 변환 코드를 함께 고칠 필요가 줄어든다.

## 내부망 배포와 운영

개발한 파이프라인은 로컬에서 테스트만 하고 끝낸 프로젝트가 아니다. **내부망 환경에 배포해 실제로 운영했다.** 문서 처리 API, Job 상태 관리, RabbitMQ, 형식별 Worker와 저장소를 연결하는 과정까지 맡았다.

외부 패키지와 이미지 저장소를 자유롭게 이용할 수 없는 환경이었기 때문에 각 Worker의 라이브러리와 실행 환경, 컨테이너 이미지, 서비스 간 의존성을 나누어 관리하는 일이 중요했다. PDF 변환에 필요한 구성과 HWPX 처리에 필요한 구성, Job Service의 의존성이 모두 같지는 않았다. 기능을 여러 서비스로 분리한 대가로 관리해야 할 배포 단위가 늘었지만, 형식별 처리 문제를 독립적으로 살펴볼 수 있는 구조를 만들었다.

개발 기록에는 Python 단위 테스트 **121개 통과**가 확인된 시점이 있다. API Contract 검사, PDF·DOCX·HWPX 경로별 E2E Smoke Test, 장시간 Stage와 Retry·Lease 관련 검사도 수행했다. Helm Lint와 설치 리허설에서는 PostgreSQL·RabbitMQ·MinIO 같은 외부 의존성을 연결하는 구성도 확인했다.

이 테스트 기록과 실제 내부망 배포·운영 경험은 함께 이 프로젝트의 구현 범위를 보여준다. 다만 121개라는 수치는 당시 개발 단계의 테스트 결과이지, 운영 중 처리한 문서 수나 장애 없는 가동 시간을 의미하지 않는다.

| 구분 | 수행한 내용 |
| --- | --- |
| 설계·구현 | 비동기 Job 관리, Stage 전이, RabbitMQ 명령 처리와 형식별 Worker |
| 개발 테스트 | 121개 단위 테스트, API 계약 검사, PDF·DOCX·HWPX E2E Smoke Test |
| 장애 대응 설계·검증 | Claim·Lease, Retry·Backoff, 중복·오래된 이벤트 처리 |
| 배포 준비 | 컨테이너 이미지, Helm 구성, 의존 서비스 연동과 설치 리허설 |
| 실제 운영 | 내부망 환경에 서비스 배포 및 운영 |

## 이후 개선할 부분

운영 중인 비동기 서비스에서는 Queue에 메시지가 쌓인 개수만으로 작업 상태를 알기 어렵다. Job이 접수된 뒤 얼마나 오래 기다렸는지, 어느 Stage에서 시간이 걸리는지, Attempt가 몇 번 발생했는지, 최종 결과 파일이 실제로 준비됐는지를 함께 살펴야 한다.

복구 로직을 더 강하게 검증하려면 Claim 저장 직후, 결과 파일 업로드 직후, 완료 이벤트 전송 직전처럼 저장소 사이의 경계마다 Worker를 종료하는 시험이 유용하다. 번역 품질도 실제 PDF·DOCX·HWPX 문서 묶음을 대상으로 표·이미지·글꼴·페이지 구성이 어떻게 바뀌는지 별도로 비교할 수 있다. 아직 측정하지 않은 처리 속도나 서식 보존율을 임의의 숫자로 제시할 필요는 없다.

비동기 문서 번역 서비스의 **설계와 구현, 형식별 Worker 개발, 작업 상태·재시도 처리, 내부망 배포와 운영**까지 직접 맡았다. RabbitMQ의 메시지 전달 상태와 실제 문서 작업 상태를 분리하고, PDF·DOCX·HWPX 처리를 독립적으로 관리할 수 있도록 구성했다.
