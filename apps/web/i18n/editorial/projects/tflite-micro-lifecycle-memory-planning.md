임베디드 디바이스에서 신경망을 실행할 때 가장 먼저 부딪히는 제약 중 하나는 메모리다. TensorFlow Lite Micro(TFLM)처럼 작은 메모리 환경을 겨냥한 추론 런타임은 이미 여러 텐서가 같은 버퍼 공간을 재사용하도록 설계돼 있다.

그런데 2024년 학부 프로젝트에서 Greedy Memory Planner의 배치 결과를 직접 살펴보면서 한 가지 질문이 생겼다. **텐서의 생존 기간이 겹친다는 이유만으로 두 버퍼가 메모리에서도 완전히 분리돼야 할까?**

어떤 연산에서는 입력의 앞부분을 이미 소비한 뒤 출력의 일부를 생성할 수 있다. 그 입력 영역을 이후에 다시 읽지 않는다는 사실을 보장할 수 있다면, 출력 버퍼가 그 영역을 일부 재사용할 가능성이 생긴다. 이 관계를 Memory Planner에 알려주는 것이 프로젝트의 핵심이었다.

이 글은 당시 작성한 8쪽 분량의 보고서를 기준으로 알고리즘과 실험을 다시 정리한 것이다. 보고서의 원래 측정값과 아직 검증하지 못한 부분을 구분해 두었다.

## Greedy Memory Planner는 무엇을 이미 잘하고 있었을까

TFLM의 Greedy Memory Planner는 모든 텐서에 독립적인 공간을 영구적으로 할당하지 않는다. 텐서마다 크기와 활성 기간(Lifetime)을 고려하고, 동시에 살아 있는 버퍼끼리 겹치지 않는 위치를 찾아 하나의 메모리 Arena에 배치한다.

당시 먼저 확인했던 것도 이 기존 배치 방식이었다. 각 텐서의 크기, Offset, Lifetime을 출력하고 실제로 메모리를 어떻게 재사용하는지 비교했다. Planner는 `AddBuffer()`로 버퍼 정보를 받고, `GetOffsetForBuffer()`에서 필요한 Offset 계산을 수행한다. 내부의 `CalculateOffsetsIfNeeded()`가 공유 메모리 배치를 계산하고, `GetMaximumMemorySize()`로 최대 점유 범위를 알 수 있다.

이 방식은 이미 합리적이다. 하지만 입력과 출력 텐서의 Lifetime이 겹친다는 사실만으로 같은 메모리 영역의 모든 바이트가 동시에 필요하다는 뜻은 아니다. **연산이 입력을 어떤 순서로 소비하는가**까지 알면 더 좁은 배치를 시도할 수 있었다.

## 입력과 출력이 일부 겹쳐도 안전한 조건

입력 텐서 A와 출력 텐서 B를 생각해보자. 일반적인 Planner는 두 버퍼가 동시에 활성 상태라면 서로 다른 메모리 영역에 배치하려 한다. 하지만 연산 과정에서 A의 일부를 더 이상 읽지 않고 B가 그 영역을 덮어써도 결과가 달라지지 않는다면, 그 부분의 중복 사용은 허용할 수 있다.

이 프로젝트에서는 그런 관계를 **Conflict Data**로 표현했다. 보고서의 예시는 `{ A, B, -L }` 형태다. `L`은 입력이 소비된 범위와 출력의 배치에 따라 허용할 수 있는 상대 위치의 제약을 나타낸다. 반대쪽 경계는 입력 크기를 이용해 알 수 있으므로 모든 값을 별도로 저장할 필요가 없었다.

{{figure /figures/redrawn/tflm-lifetime.svg | 텐서 A와 B의 실행 시점 및 메모리 주소 관계를 그린 원본 보고서의 개념도다. L은 연산 순서가 허용하는 겹침 제약을 뜻한다.}}

여기서 조심해야 할 점은 모든 합성곱 연산이 무조건 입력을 덮어써도 된다는 뜻이 아니라는 것이다. 어떤 연산에서는 앞에서 소비한 입력을 뒤에 다시 읽을 수도 있다. **실제 연산의 접근 순서로 안전하다고 확인된 관계**에 대해서만 부분 겹침을 허용해야 했다.

## 첫 번째 변화: 버퍼를 놓는 순서

기본 Greedy Planner에서는 크기가 큰 버퍼를 먼저 고려하는 휴리스틱을 사용한다. 우리는 Conflict Data가 없는 버퍼에는 이 접근을 유지하고, Conflict Data가 있는 버퍼에는 관계 그래프를 이용한 별도의 순서를 적용했다.

보고서의 예시에서 A → B, B → C, C → E, D → E 같은 의존 관계가 있다면, 끝에 있는 출력 E를 먼저 두고 입력 쪽으로 거꾸로 탐색한다. 출력에서 입력으로 향하는 Reverse BFS 방식이다. 같은 깊이의 후보는 크기가 큰 버퍼를 우선했다.

{{figure /figures/redrawn/tflm-conflict-graph.svg | 출력에서 입력 방향으로 역방향 탐색해 배치 우선순위를 정하는 Conflict Graph의 예시다.}}

왜 출력부터 놓을까? Planner는 낮은 Offset부터 빈 자리를 찾는다. 출력 버퍼의 위치를 먼저 잡아두면, 뒤이어 놓는 입력 버퍼가 **출력과 얼마나 겹칠 수 있는지**를 Conflict Data의 제약에 맞춰 계산하기 쉬워진다.

물론 Reverse BFS가 모든 입력에서 최적의 Peak Memory를 보장하는 것은 아니다. 당시에는 합리적인 배치 순서를 얻기 위해 채택한 휴리스틱이었다.

## 두 번째 변화: 다음 Offset을 찾는 방법

기존 Planner에서는 동시에 활성 상태인 버퍼를 만나면 보통 기존 버퍼의 끝을 넘는 다음 위치를 후보로 삼는다.

Conflict Data를 이용하는 버전은 이미 배치한 버퍼가 현재 입력과 안전한 입출력 관계에 있는지 확인한다. 그런 관계가 있으면 전체 버퍼 크기만큼 건너뛰지 않고, 기록된 겹침 제약을 반영한 위치도 후보로 고려할 수 있다.

{{figure /figures/redrawn/tflm-offset.svg | 입력과 출력의 겹침 제약이 있을 때 후보 Offset을 계산하는 과정을 보여주는 원본 보고서 기반 그림이다. 거리 비율은 예시다.}}

이때 다른 활성 버퍼와의 충돌까지 무시해서는 안 된다. 하나의 입출력 관계가 안전하더라도 다른 텐서가 같은 메모리를 필요로 한다면 그 배치는 사용할 수 없다. Planner는 모든 관련 제약을 함께 만족시켜야 한다.

이 프로젝트는 단순히 최대 메모리 크기에서 일정량을 빼는 방식이 아니라, **어느 바이트를 어떤 시점 이후에 다시 쓸 수 있는지**를 배치 과정에 반영한 시도였다.

## C++ Planner를 바꾸고 TFLM에 연결하기

처음에는 직접 구성한 버퍼 목록을 이용해 기존 Greedy Planner와 수정한 Planner의 Offset과 최대 사용 주소를 비교했다. 새로운 배치가 의도대로 일어나는지 확인하기에 가장 단순한 출발점이었다.

이후 C++ Planner의 정렬과 후보 Offset 계산을 변경하고, TFLM Interpreter 초기화 과정에서 Conflict Data 배열과 개수를 전달할 수 있도록 연결했다.

다만 중요한 역할 구분이 있다. 실험에서 사용한 Conflict Data는 자동으로 추론한 것이 아니라 **수동으로 작성한 정보**였다. 그 데이터 준비는 다른 팀원이 맡았다. 내가 중점적으로 수행한 작업은 원래 Planner 분석, Conflict를 고려한 정렬·배치 알고리즘 구현, TFLM 통합과 메모리 사용량 평가였다.

Compiler나 연산 실행을 분석해 Conflict Data를 자동 생성하는 것은 앞으로 발전시킬 수 있는 방향이지만, 당시 완성한 자동 분석 파이프라인이라고 소개할 수는 없다.

## 실제로 얼마나 줄었을까

보고서에는 직접 만든 버퍼 테스트와 두 TFLM 모델에 대한 메모리 사용량 비교가 있다.

| 평가 대상 | 기존 Greedy Planner | 수정한 Planner | 보고서에 기재된 감소율 |
| --- | ---: | ---: | ---: |
| 구성한 버퍼 테스트 | 4,101 bytes | 3,585 bytes | 12.58% |
| Person Detect | 55,296 bytes | 39,636 bytes | 28.33% |
| Tiny U-Net | 230,416 bytes | 198,120 bytes | 14.06% |

Person Detect에서 더 큰 감소가 나왔고 Tiny U-Net에서도 배치에 필요한 최대 버퍼 공간을 줄일 수 있었다. 하지만 두 모델이 완전히 같은 수준으로 개선되는 것은 아니었다. 어떤 텐서 사이에 안전한 겹침 관계가 존재하는지, 배치 순서가 어떻게 결정되는지에 따라 결과는 달라진다.

수치에 대해서도 한 가지 남겨둘 점이 있다. 보고서는 모델별 감소율을 28.33%와 14.06%로 제시하지만, 같은 표의 Bytes 값으로 직접 계산하면 대략 28.32%와 14.02%가 나온다. 원본에 있는 차이를 설명 없이 고쳐 쓰기보다 둘 다 기록해 두는 편이 정확하다고 생각한다.

무엇보다 위 결과는 **계획된 Peak Buffer 사용량의 감소**다. 실제 MCU 전체 메모리 사용량, 추론 지연시간이나 에너지 소비가 같은 비율로 줄었다는 실험 결과는 아니다.

## 메모리 배치가 작아졌다고 정답이 보장되지는 않는다

이 알고리즘에서 마지막으로 중요했던 질문은 정확성이었다. 입력의 일부가 이미 소비됐다고 가정했지만 실제 Operator가 그 영역을 나중에 다시 읽는다면, 메모리를 절약한 대신 입력을 손상시킬 수 있다.

따라서 최종적으로는 수정한 Planner를 사용하는 추론 결과가 기존 Planner와 동일한지 확인해야 한다. 보고서에서도 실제 In-place 업데이트를 적용한 후 추론 결과를 대조할 필요가 있음을 남겼다.

또한 Conflict Data 자동 추출, 전역 Peak Memory를 최소화하는 더 정교한 탐색은 별도의 연구 과제다. Reverse BFS는 좋은 배치를 찾기 위한 방법이지 최적해를 증명하는 알고리즘은 아니었다.

이 프로젝트를 하며 텐서의 크기보다 **앞으로 어떤 데이터가 정말 다시 읽혀야 하는가**가 메모리 관리에서 더 흥미로운 질문이라는 생각을 했다. Lifetime과 연산의 실행 순서를 함께 보면, 겉으로는 동시에 살아 있는 두 버퍼에서도 안전하게 재사용할 수 있는 공간을 찾을 수 있었다.
