Langfuse를 v4로 옮기던 중 마이그레이션 화면에 `Timeout error.`가 떴다. 오래 걸리던 작업이 끝내 실패한 줄 알았다. 그런데 PostgreSQL에 남은 진행 기록을 열어보니 예상과 달랐다. Phase는 `completed`, 완료된 청크는 9개, 실패한 청크는 0개였다.

화면이 실패라고 말하는데 데이터베이스에는 완료됐다는 기록이 있었다. 둘 중 하나가 틀렸다고 단정하기 전에, 서로 무엇을 보고 있는지부터 따져봐야 했다. 화면은 요청에 대한 응답을 기다리고 있었고, 백그라운드 작업은 그보다 오래 실행됐을 수도 있었다.

이 일은 최종적으로 끝내지 못한 업그레이드의 기록이 아니다. 이후 작업을 계속해 **2026년 11월 17일에는 마이그레이션 Step 1–5를 마치고, `events_only` 모드에서 과거와 신규 데이터 검증까지 통과**했다. 그 사이에 마주친 오류들이 왜 서로 다른 의미였는지, 그리고 어디까지 확인한 뒤에야 완료라고 부를 수 있었는지를 남겨두려 한다.

## Langfuse v4 업그레이드와 데이터 이전

이전에도 Langfuse를 업그레이드해봤지만, 이번에는 애플리케이션 버전만 맞춘다고 끝나지 않았다. Trace와 Observation처럼 오래 쌓인 데이터를 새로운 분석 구조에서 읽을 수 있어야 했고, 그 과정에서 PostgreSQL의 작업 상태와 ClickHouse의 데이터, Keeper의 조정 상태가 함께 중요해졌다.

Helm 배포가 성공해도 백그라운드 마이그레이션이 끝났다는 뜻은 아니다. 애플리케이션 Pod가 실행 중이어도 옛 데이터를 새 구조로 옮기는 작업은 따로 진행될 수 있다. 특히 데이터를 대량으로 다시 쓰는 동안에는 목적지의 저장 공간과 쓰기 가능한 Replica가 필요했다.

나는 이번 작업을 하나의 긴 업그레이드 명령이 아니라, 각각 증거가 남아야 하는 여러 단계로 다뤘다. 이전 버전의 데이터를 옮기는 일, 새 버전에서 실제로 읽고 쓰는 일, 마지막 임시 구조를 정리하는 일은 완료 조건이 달랐다.

## Step 2 Timeout과 영속 진행 상태

Step 2는 기존 Observation을 마이그레이션용 `observations_pid_tid_sorting` 테이블로 백필하고 정렬하는 과정과 연결돼 있었다. 이 단계에서 받은 `Timeout error.`를 그대로 '데이터 복사 실패'로 받아들이면, 이미 진행된 작업을 다시 실행할 수도 있었다.

당시 직접 확인한 값은 다음과 같다.

| 관측 지점 | 남아 있던 기록 |
| --- | --- |
| 호출자·화면 | 실패, `Timeout error.` |
| PostgreSQL의 Phase | `completed` |
| 완료된 청크 | **9개** |
| 실패한 청크 | **0개** |

이 기록은 화면이 시간을 초과했다는 사실과 데이터 처리가 어디까지 진행됐는지를 구별해줬다. 물론 청크 수가 맞는다고 새 애플리케이션에서 모든 결과가 정확하다는 보장은 없다. 다만 아무것도 완료되지 않았다는 가정으로 처음부터 되돌아갈 이유도 없었다.

진행 상태를 대조한 뒤에는 해당 단계의 재시도를 통해 문제를 해결하고 다음 단계로 넘어갔다. 여기서 말하는 재시도는 **관측된 영속 상태를 확인한 뒤 진행한 작업**이지, 타임아웃이 날 때마다 무조건 전체 백필을 다시 실행했다는 뜻이 아니다.

{{figure /figures/journals/langfuse-migration-evidence.svg | Step 2에서는 호출자에게 보인 Timeout과 데이터베이스에 저장된 완료 기록이 달랐다. 이후 별도의 단계 검증과 정리를 마친 시점까지 구분해 그렸다.}}

## 다른 시점에 나타난 Read-only와 공간 부족

업그레이드 과정에서 ClickHouse Replica가 Read-only 상태에 들어갔을 때는 Keeper와 복제 상태를 별도로 확인해야 했다. 애플리케이션 컨테이너가 실행 중이라는 이유만으로 ClickHouse가 쓰기를 받아들인다고 할 수 없었다.

또 다른 시점에는 Remote Insert가 저장 공간 부족으로 실패했다. 평소 데이터가 차지하는 크기와 마이그레이션에 필요한 여유 공간은 같지 않다. 기존 데이터를 읽어 새 구조에 다시 쓰는 동안에는 원본 외에 추가 공간이 필요할 수 있다. 저장 공간이 부족한 채 같은 Insert를 반복하면 같은 문제를 되풀이할 뿐이다.

과정 중에는 JSON과 Date 상태를 처리하는 코드에서 오류가 나타난 기록도 있다. 예전 조사 메모에는 이것이 'Step 6'으로 표기돼 있었지만, **최종적으로 완료한 다섯 개 마이그레이션 단계와 같은 번호 체계라고 단정할 자료는 없다.** 그 오류를 Step 5 이후에 또 다른 필수 마이그레이션이 실패했다는 의미로 옮겨 적지는 않았다. 중요한 것은 저장된 상태를 파싱하는 코드의 오류와 Replica·디스크 상태의 오류를 구별하는 일이었다.

이 증상들을 모두 같은 원인으로 설명하려고 하면 판단이 흐려진다. Timeout은 호출자의 대기 시간과 실제 작업의 수명이 어긋난 것일 수 있고, Read-only는 조정 계층이나 Replica의 문제이며, 저장 공간 부족은 물리적인 용량 제약이다. 하나를 고쳤다고 나머지가 자동으로 해결되는 구조가 아니었다.

## Step 1–5 완료와 데이터 조회 검증

Step 2를 넘긴 뒤에도 바로 '전환 완료'라고 쓰지 않았다. 후속 Step 3–4에서는 v4 이벤트 데이터의 백필과 검증을 진행했다. 이후 실제로 과거 데이터를 조회하고 새 데이터를 기록해 읽을 수 있는지 확인했다.

최종 확인 시점은 **2026년 11월 17일**이다. 그때의 상태는 다음과 같았다.

| 항목 | 최종 확인 상태 |
| --- | --- |
| Helm Chart / 애플리케이션 | **2.1.3 / 4.46.0** |
| 데이터 기록 모드 | **`events_only`** |
| 마이그레이션 단계 | **Step 1–5 완료** |
| 과거 데이터 조회·신규 데이터 기록 | **검증 통과** |
| Step 5 | 임시 `observations_pid_tid_sorting` 테이블 정리 완료 |

마지막 Step 5는 무턱대고 오래된 원본을 삭제하는 단계가 아니었다. 마이그레이션 도중 사용한 임시 테이블을 정리하는 일이었다. 기존 `traces`와 `observations` 원본 테이블을 지우는 작업으로 이해해서는 안 됐다. 실제 정리 전에 앞선 단계와 데이터 검증을 먼저 확인했던 이유다.

이 정도의 기록이 있으므로 이제는 초기의 '진행 중인 마이그레이션'이라고만 쓸 필요가 없다. **확인한 범위에서 v4 전환과 기존·신규 데이터 검증을 마쳤다**는 것이 더 정확하다. 그렇다고 모든 형태의 과거 데이터, 예외적 조회 경로, 장애 복구 상황을 빠짐없이 검증했다는 뜻까지 넓히지는 않는다.

## 타임아웃과 완료 사이에 남은 것

처음 `Timeout error.`를 봤을 때 가장 쉽게 할 수 있는 일은 실패한 것으로 판단하고 재시작하는 것이었다. 하지만 진행 테이블을 확인하고 나서는 질문이 달라졌다. 요청이 끝난 것인가, 데이터 작업이 끝난 것인가. 둘은 같은 사건의 서로 다른 시점일 수 있었다.

나중에 실제 검증을 마치고 임시 테이블까지 정리한 뒤 돌아보니, Step 2에서 멈춰 확인했던 일이 전환 과정 전체를 다루는 방식에도 영향을 줬다. 완료 여부를 화면 한 줄에 맡기지 않고, 영속 기록과 실제 읽기·쓰기 결과를 나눠 확인하게 됐다.

Step 2의 Timeout 직후 PostgreSQL에는 완료 9개·실패 0개의 기록이 남았다. 이후 Step 1–5를 마치고 `events_only`에서 과거·신규 데이터 조회를 검증했으며, 마지막 임시 테이블 정리까지 확인했다.
