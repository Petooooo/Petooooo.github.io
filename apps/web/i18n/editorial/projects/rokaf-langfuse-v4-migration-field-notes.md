Langfuse를 v4로 업그레이드하던 중 마이그레이션 Step 2가 `Timeout error.`를 반환했다. 일반적으로는 실패한 작업이라고 생각하고 다시 실행하기 쉽다. 나도 처음에는 같은 방향으로 접근할 뻔했다.

그런데 PostgreSQL에 저장된 백그라운드 마이그레이션 상태를 확인하니 다른 모습이 보였다. Phase는 `completed`였고, 완료된 청크는 9개, 실패한 청크는 0개였다.

화면에 나타난 실패와 영속화된 작업 상태가 다른 말을 하고 있었다. 이후에는 어느 하나의 표시를 진실로 삼기보다 **각 상태가 무엇을 관측한 결과인지**부터 구분하려 했다.

## 업그레이드할 대상은 애플리케이션만이 아니었다

Langfuse는 애플리케이션 코드뿐 아니라 PostgreSQL, ClickHouse, Keeper 등 여러 상태 저장 시스템에 의존한다. 새 버전의 이미지를 배포하는 것과, 이전 버전에서 생성한 Trace와 Observation을 새 데이터 구조로 옮기는 것은 분리된 작업이다.

특히 백그라운드 마이그레이션은 대량의 과거 데이터를 읽고 다시 쓰기도 한다. DB Replica나 Coordinator가 불안정하거나 목적지 저장 공간이 부족하면, 앱 Pod가 정상으로 표시돼도 작업을 끝낼 수 없다.

이 때문에 마이그레이션을 한 번의 업그레이드 명령으로 보지 않고 여러 독립적인 상태 전이로 나누어 살펴야 했다.

{{figure /figures/journals/langfuse-migration-evidence.svg | 호출자에게 보인 오류, 영속화된 Phase, ClickHouse·Keeper 상태, 저장 공간은 서로 다른 증거다. 이 그림은 실제 내부 구성도가 아니라 검증할 계층을 정리한 것이다.}}

## Step 2의 Timeout을 어떻게 해석할 것인가

당시 남아 있는 확인 결과는 다음과 같다.

| 항목 | 확인한 값 |
| --- | --- |
| 화면에 표시된 상태 | 실패, `Timeout error.` |
| 영속화된 Phase | `completed` |
| 완료된 청크 | **9개** |
| 실패한 청크 | **0개** |

이 결과를 보고 “마이그레이션이 성공했다”고 바로 결론 내릴 수는 없다. 다만 **모든 청크가 실패했으니 처음부터 다시 실행해야 한다**는 판단도 맞지 않을 수 있다는 사실은 확인됐다.

클라이언트나 API 호출자가 Timeout을 받은 시점에도 Worker가 작업을 이어갔을 수 있다. 반대로 진행 상태 기록이 완료됐다고 해서 그 결과가 실제 애플리케이션의 모든 조회에서 올바르게 사용된다는 보장은 없다.

그래서 먼저 구분할 것이 생겼다. UI가 시간 안에 응답을 받았는가. 백그라운드 작업은 실제로 어디까지 진행됐는가. 목적지 데이터는 새 코드가 기대하는 상태로 바뀌었는가. 새 애플리케이션은 그 데이터를 읽고 쓸 수 있는가.

이 질문들을 하나씩 확인하지 않고 전체 작업을 반복하면 이미 끝난 데이터 변환을 다시 수행할 위험이 있었다.

## ClickHouse와 Keeper를 보던 시점

다른 작업에서는 ClickHouse Replica가 Read-only 상태를 보이거나 Keeper의 조정 상태를 확인해야 했다. 이것은 앞서 본 UI Timeout과는 다른 문제다.

데이터베이스가 쓰기를 받아들이는지 확인하려면 Coordinator와 Replica 상태를 따로 보아야 한다. 컨테이너 하나를 다시 실행했다고 Keeper와 ClickHouse 테이블의 상태가 올바르게 회복되는 것은 아니다.

또 다른 시점에는 Remote Insert에서 공간 부족이 발생했다. 데이터 재작성은 원본을 읽고 새 테이블에 기록하는 동안 추가 공간을 사용할 수 있다. 용량 조건이 그대로인데 같은 INSERT를 재실행하면 문제를 되풀이할 뿐이다.

이때부터 증상을 하나의 “업그레이드 장애”로 묶지 않으려 했다. Timeout은 호출 시간 문제일 수 있고, Read-only는 Replica 또는 조정 상태 문제일 수 있으며, 공간 부족은 물리 저장 자원의 제약이다. 각각 다른 증거와 조치가 필요하다.

## Step 6에서는 또 다른 문제가 나왔다

이후 v4 단계에서는 영속화된 마이그레이션 상태를 읽고 처리하는 과정에 JSON·Date 변환 문제가 나타났다. 앞서 Keeper나 스토리지 문제를 살펴봤다고 해서 이런 유형의 오류까지 해결되는 것은 아니었다.

문제의 층위가 바뀐 것이다. 저장된 상태의 자료형을 애플리케이션이 어떻게 파싱하고 직렬화하는지, 해당 단계가 기대하는 값과 실제 기록이 맞는지 확인해야 했다.

이처럼 서로 다른 오류가 한 업그레이드 과정에서 이어졌기 때문에, 어느 한 오류를 고치면 전체 마이그레이션이 정상으로 돌아왔다는 식으로 기록하고 싶지 않았다.

## 서로 다른 상태가 모순되어 보일 때

내가 가장 신뢰하려 했던 것은 개별 상태 표시가 아니라 **그 상태를 만들기까지의 증거**였다.

| 증거 | 알려주는 것 | 그것만으로 알 수 없는 것 |
| --- | --- | --- |
| UI와 HTTP 응답 | 호출자가 제시간에 결과를 받았는가 | Worker 작업이 실제로 끝났는가 |
| 영속 진행 테이블 | 어떤 Phase와 청크가 기록됐는가 | 모든 목적지 Row가 올바른가 |
| ClickHouse·Keeper | Replica와 조정 계층이 읽기·쓰기를 지원하는가 | 애플리케이션의 데이터 해석이 올바른가 |
| 실제 기능 검사 | 현재 애플리케이션의 주요 읽기·쓰기 동작 | 모든 과거 데이터의 예외 사례까지 포함한 정확성 |

Step 2에서는 호출자에게 Timeout이 표시됐지만, 영속 상태에서는 완료된 Phase와 9개 청크를 확인했다. 다른 시점의 공간 부족이나 Read-only 오류를 그 Timeout의 원인이라고 단정할 근거는 없다.

재시도를 결정할 때는 현재 작업이 살아 있는지, 이미 기록된 완료 청크를 다시 실행해도 안전한지, 새로운 데이터를 확인할 방법이 있는지 먼저 검토해야 한다.

## 무엇을 확인해야 완료라고 말할 수 있을까

내가 생각한 검증은 화면의 상태 표시에서 끝나지 않는다.

영속화된 Phase와 청크에 모순이 없는지 확인하고, ClickHouse Replica와 Keeper가 정상적인 읽기·쓰기를 지원하는지 살펴야 한다. 저장 공간도 충분해야 한다. 기존 Trace와 Observation을 대표적으로 조회한 뒤 새로운 기록을 쓰고 다시 읽는 검사도 필요하다. 애플리케이션 재시작 이후 백그라운드 작업이 정상적으로 이어지는지도 확인하고 싶었다.

이 항목을 당시 전부 수행했다는 기록은 남아 있지 않다. 따라서 이 글은 **Langfuse v4 업그레이드 완료 보고서가 아니라 진행 중 확인한 상태와 아직 열려 있는 문제의 기록**이다.

결과가 지저분하게 남아 있어도 그 기록을 지우고 깔끔한 성공 이야기로 바꾸지는 않으려 한다. 화면의 실패 표시와 백그라운드 데이터 작업의 상태가 다를 수 있다는 사실, 그리고 각 저장 계층이 서로 다른 실패를 낼 수 있다는 사실이 오히려 이후 작업에서 도움이 됐다.

이 문제는 자연스럽게 영속 쓰기, 장애 직후의 상태 복구, 파일시스템의 보장 범위 같은 질문으로 이어졌다. **중단된 작업이 어디까지 실제로 끝났는지 무엇으로 판정할 것인가**는 애플리케이션 바깥에서도 계속 나타나는 문제다.
