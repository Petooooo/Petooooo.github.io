2023년 10~11월에는 **STM32 보드 세 대와 FreeRTOS를 사용해 Mini-Desktop을 구축**했다. 커서와 창을 조작하고 여러 애플리케이션이 함께 동작하는 임베디드 시스템이었다. 전체 아키텍처를 설계하고 **10개 Task의 동작, 보드 간 UART 통신, 우선순위와 Mutex**를 함께 다뤘다.

지금 읽으면 데스크톱이라는 이름이 조금 과하게 느껴질 수도 있다. 하지만 마이크로컨트롤러 위에서는 키 입력이나 화면 상태를 처리하는 동안 다른 작업이 멈추지 않도록 만드는 일부터 직접 설계해야 했다.

이 글은 2023년 프로젝트 기록을 2026년 11월에 다시 정리한 것이다. 게시 시점과 당시 수행 기간은 구분했다.

## 하나의 반복문 대신 여러 Task로 나누기

단순한 임베디드 프로그램은 하나의 Loop에서 입력을 읽고, 상태를 바꾸고, 출력하는 방식으로도 만들 수 있다. 하지만 Mini-Desktop처럼 사용자 입력과 화면 갱신, 애플리케이션 동작, 보드 간 통신이 함께 진행되면 특정 작업이 오래 걸릴 때 다른 작업까지 영향을 받기 쉽다.

그래서 기능별로 **FreeRTOS Task를 구성하고 동작 우선순위를 지정**했다. 시스템 전체에서 10개 Task가 동시에 관리됐고, 작업마다 언제 CPU를 사용해야 하는지 고려해야 했다.

## 세 보드 간 GPIO·UART 통신

보드 안에서 직접 입출력 신호를 처리할 때는 **GPIO**, 보드 사이에 정보를 주고받을 때는 **UART**를 활용했다. 보드 하나의 함수 호출과 달리 다른 보드로 전달한 데이터는 수신 시점과 처리 시점이 달라질 수 있다.

이 차이를 고려해 어떤 상태를 어느 기능이 관리하고, 입력이 전달됐을 때 어떤 Task가 반응해야 하는지 설계했다. 커서와 창, 실행 중인 애플리케이션 상태가 서로 맞지 않으면 사용자는 바로 이상한 동작을 보게 된다.

## 우선순위와 Mutex

여러 Task가 동작한다고 공유 상태 문제가 없어지는 건 아니다. 두 Task가 같은 값을 수정하거나, 한쪽이 사용하는 데이터를 다른 쪽이 갱신하는 경우에는 실행 순서를 고려해야 한다.

**Mutex로 공유 자원 접근을 보호**하면서도 우선순위가 높은 Task가 불필요하게 오래 기다리지 않도록 작업 범위를 나누었다. 실시간 시스템에서 중요한 것은 Task가 많다는 사실보다, 필요한 동작이 제때 실행되도록 책임과 동기화 경계를 정하는 일이었다.

## 커서·창·애플리케이션과 절전 상태

구현한 인터페이스에는 **커서와 창의 상호작용**, 여러 애플리케이션의 동작, **Sleep/Resume**이 포함됐다. CPU나 보드가 동작 중이라고 해서 사용자의 작업 상태가 올바르게 유지되는 것은 아니기 때문에, 화면과 입력, 각 Task가 공유하는 상태를 함께 확인해야 했다.

Sleep/Resume에서도 일시적으로 동작을 중단하는 것과, 다시 실행할 때 필요한 상태를 복구하는 것을 구분했다.

이후 시스템 개발에서 여러 실행 주체가 **같은 상태를 언제 어떻게 바꿀 수 있는지**를 먼저 살펴보게 됐다. FreeRTOS에서 다뤘던 동기화 문제는 규모가 달라져도 계속 등장했다.
