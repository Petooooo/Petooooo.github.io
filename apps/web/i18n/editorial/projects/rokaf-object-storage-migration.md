대용량 데이터를 다른 MinIO 환경으로 옮기던 중 복사 작업이 끝났다는 메시지를 보았다. 그런데 원본과 대상의 객체 수와 사용량을 비교하자 수치가 맞지 않았다. 작업이 성공했다고 생각했던 순간부터 진짜 검증이 시작된 셈이었다.

당시에는 Standalone MinIO와 그 아래 Longhorn 볼륨을 사용하던 구조를 분산 MinIO로 옮기는 작업을 하고 있었다. 단순히 서버 하나를 늘리는 것이 아니라, **어느 계층이 데이터의 중복 저장과 복구를 책임질지** 바꾸는 일이었다.

그 과정에서 데이터 전송 실패, 일부 객체의 누락, Multipart Upload의 미완료 상태, IAM 설정 이전, Lifecycle 정책까지 마주했다. 복사가 얼마나 진행됐는지보다 **새 저장소가 기존 애플리케이션에 같은 의미의 객체 공간을 제공하는지**가 더 어려운 문제였다.

## 블록 복제와 객체 분산은 다른 이야기다

기존에는 하나의 MinIO 인스턴스가 객체 API를 제공하고, Longhorn이 그 아래 영속 볼륨을 복제하는 역할을 맡았다. 볼륨 데이터에 복제본이 있다는 것은 유용하지만 MinIO 프로세스 하나의 가용성 문제까지 해결해주지는 못한다.

분산 MinIO는 다른 방식이다. 여러 저장소 구성원이 하나의 객체 서비스를 만들고, Erasure Coding으로 데이터와 패리티를 분산한다. 그러면 중복성의 일부 책임이 블록 스토리지 계층에서 객체 스토리지 계층으로 옮겨간다.

{{figure /figures/journals/minio-storage-ownership.svg | Standalone MinIO와 Longhorn의 블록 복제, 분산 MinIO의 객체 단위 Erasure Coding이 각각 무엇을 책임지는지 비교한 개념도다. 실제 노드 수나 데이터 배치, 장애 허용 개수를 나타내지는 않는다.}}

어떤 방법이 무조건 더 좋다는 뜻은 아니다. 블록 복제는 볼륨 단위의 복구와 재구축 비용이 있고, 분산 MinIO는 멤버 사이의 설정 일치와 Erasure Set의 쿼럼, 객체 힐링을 고려해야 한다. Pod 개수만으로 허용 가능한 장애 수를 계산할 수도 없다.

실제로 분산 운영 단계에서 환경변수 불일치 문제를 접한 적도 있다. 구성원들이 서로 독립적인 Standalone 서버가 아니라 하나의 분산 시스템에 속한다는 점을 보여준 별도의 운영 문제였다. 다만 그 설정 문제가 앞서 발생한 모든 데이터 복사 차이의 원인이라고 추정하지는 않았다.

## 파일을 복사하는 것과 S3 공간을 옮기는 것은 다르다

처음에는 모든 파일을 복사한 뒤 클라이언트가 바라보는 주소만 바꾸면 될 것 같았다. 하지만 애플리케이션은 임의의 디렉터리를 읽는 것이 아니라 S3 API를 사용하고 있었다.

버킷과 객체 Key, 버전, 삭제 마커, 접근 권한, Lifecycle 규칙이 함께 의미를 갖는다. 데이터의 바이트를 복사하더라도 이 중 일부가 달라지면 애플리케이션에는 이전과 다른 저장소가 된다.

그래서 이 작업을 세 갈래로 나누어 생각했다.

첫째, **객체 자체가 옮겨졌는가**. 복사가 중간에 끊긴 객체가 없는지, 나중에 원본에 생긴 새 객체가 남아 있지는 않은지 확인해야 한다.

둘째, **객체의 식별과 메타데이터가 같은가**. 현재 보이는 Key가 같더라도 버전 관리와 삭제 마커가 다른 경우에는 이전 읽기 동작이 유지되지 않을 수 있다.

셋째, **기존 사용자가 여전히 필요한 객체에 접근할 수 있는가**. IAM 정책은 객체 데이터를 복사한다고 함께 이전되는 것이 아니다.

한 번에 여러 요소를 바꾸면 어디에서 차이가 생겼는지 확인하기 어려웠다.

## 전송은 끝났는데 목록은 같지 않았다

데이터 이동에는 MinIO Client를 사용했고, 이후 `mc mirror`와 `mc diff`로 원본과 대상을 비교했다. 대규모 전송 중에는 Gateway Timeout이나 Client Closed Request 같은 오류도 발생했다. 실패한 항목을 별도로 추적했던 이유는 전체 진행률 숫자만으로 완료된 객체 목록을 믿을 수 없었기 때문이다.

Timeout은 특히 애매하다. 클라이언트는 응답을 기다리다 포기했지만 서버에서는 이미 일부 작업이 처리됐을 수 있다. 반대로 요청 자체가 반영되지 않았을 수도 있다. **HTTP 요청의 결과와 객체가 실제로 저장된 상태를 같은 증거로 취급하면 안 된다.**

더 어려운 점은 복사하는 동안에도 원본이 바뀔 수 있다는 것이었다. 전체 복사가 성공한 직후 새로운 객체가 생성되거나 기존 객체가 덮어써졌다면, 두 저장소의 목록이 달라지는 것은 이상하지 않다. Bulk Copy 이후 마지막 차이를 맞추거나 쓰기를 멈추는 시점을 정하는 전략이 필요했다.

그런 마지막 동기화와 쓰기 정지, 전체 객체의 차이가 0이라는 검증을 모두 끝냈다는 기록은 남아 있지 않다. 이 글에서는 검증 방법과 실제 확인된 차이를 구분한다.

## 합계보다 중요한 것은 누락된 한 개의 객체였다

객체 수나 전체 용량이 다르다는 것은 좋은 경고다. 그러나 원인을 알려주지는 않는다. `mc diff` 결과에서 원본에만 존재하는 항목을 발견했을 때 비로소 조사할 구체적인 대상이 생겼다.

“원본에만 있다”는 사실은 비교 시점에 대상에서 그 논리 객체가 보이지 않았다는 뜻이다. 복사 실패인지, 복사 이후 생성됐는지, 접근 정책 때문에 목록에 나오지 않았는지, 다른 이유로 삭제됐는지는 별도의 기록을 대조해야 한다.

{{figure /figures/journals/minio-object-reconciliation.svg | 원본과 대상의 객체를 어떻게 분류해 비교할지 나타냈다. 원본에만 있는 객체는 실제 관측한 차이이며, 다른 행은 완전한 비교 도구라면 구분해야 할 사례들이다.}}

내가 생각한 객체 비교의 기준은 다음과 같았다.

| 비교 결과 | 바로 할 수 있는 판단 |
| --- | --- |
| 양쪽에 있고 속성이 같음 | 목록 수준의 일치. 바이트가 같다는 증명은 아님 |
| 원본에만 있음 | 대상에서 누락됐거나 보이지 않는 객체. 전송 기록 확인 필요 |
| 대상에만 있음 | 추가 객체의 출처 확인 필요. 곧바로 삭제하면 위험 |
| 양쪽에 있지만 속성이 다름 | 크기·버전·메타데이터 중 무엇이 달랐는지 확인 |
| Multipart Upload 미완료 | 완성된 객체 목록과 따로 관리 |
| 요청 실패나 권한 부족 | 일치 또는 불일치가 아니라 아직 모르는 상태 |

이렇게 나눠 기록하면 “복사 실패 0개” 같은 하나의 숫자보다 실제 다음 행동을 결정하기 쉽다.

## ETag가 같다고 모든 바이트가 같은 것은 아니다

객체 무결성을 확인하려 할 때 ETag도 주의해야 한다. S3의 ETag는 모든 경우에 전체 객체의 MD5 해시가 아니다. Multipart Upload와 암호화 방식 등에 따라 그 의미가 달라질 수 있고, 같은 데이터를 다른 Part 구성으로 올리면 ETag도 달라질 수 있다.

따라서 `mc diff`가 알려주는 목록과 메타데이터의 차이는 매우 유용하지만, 그것을 모든 대상 객체의 바이트를 읽어 비교한 결과로 확대 해석하면 안 된다.

검증의 강도를 나눌 필요가 있었다. 버킷·Key·Version의 존재 여부를 보는 단계, 크기와 메타데이터를 비교하는 단계, 비교 가능한 체크섬을 확인하는 단계, 필요한 경우 원본과 대상을 실제로 읽어 해시를 계산하는 단계다. 마지막으로 애플리케이션이 실제로 필요한 객체를 정상적으로 읽는지도 확인해야 한다.

쓰기 작업이 계속 일어나는 환경이라면 비교 기준이 되는 시점부터 고정해야 한다. 그렇지 않으면 정교한 비교 프로그램도 계속 움직이는 대상을 추적하게 된다. 전체 데이터에 대해 버전 단위 검증과 읽기 검증을 마쳤다는 증거는 확보하지 못했다.

## Multipart Upload가 차지하는 별도의 공간

조사 중에는 완료되지 않은 Multipart Upload도 확인했다. 큰 파일을 여러 Part로 나눠 전송하다 중단되면, 완성된 객체로 보이지 않는 데이터가 저장 공간을 점유할 수 있다.

따라서 “객체가 몇 개 있는가”와 “미완료 Upload가 얼마나 남아 있는가”를 한 숫자로 합칠 수 없다. Multipart Part가 남아 있다고 해서 애플리케이션이 읽을 수 있는 객체가 있다는 뜻은 아니다.

그렇다고 모든 미완료 Upload를 즉시 지우는 것도 위험하다. 지금 진행 중인 전송인지, 정말 버려진 전송인지 구분해야 한다. Cleanup과 만료 정책은 사용하는 MinIO 버전과 Lifecycle 설정의 영향을 받으므로 별도의 관리 문제로 봤다.

## IAM을 이전할 때 막힌 문제

객체가 모두 있어도 애플리케이션의 계정과 정책이 달라졌다면 마이그레이션은 끝나지 않는다.

IAM 설정을 옮기는 과정에서는 Export Archive 형식과 Import 권한에서 문제가 생겼다. 콘솔에 로그인할 수 있다는 사실만으로 관리용 Import를 실행할 권한까지 확보되는 것은 아니었다. 어떤 사용자 권한으로 요청하고 있는지, Archive가 기대한 형식인지부터 확인해야 했다.

더 조심스러웠던 것은 대상 저장소에도 이미 설정이 있다는 점이다. Import가 기존 사용자와 정책을 병합하는지, 대체하는지, 충돌을 일으키는지 모르고 적용하기는 어려웠다. 선택한 설정만 이전하거나 기존 설정을 보존하는 방향을 검토했지만, 모든 IAM 주체가 정확히 이전됐다는 결과까지 기록으로 남아 있지는 않다.

마지막으로 확인해야 할 것은 명령어의 종료 코드가 아니라 실제 애플리케이션의 권한이다. 필요한 객체를 읽고 쓰는가, 허용되지 않은 객체에는 여전히 접근하지 못하는가. **데이터 무결성과 권한의 정확성은 독립적인 조건**이다.

## Lifecycle 규칙도 데이터 정합성의 일부였다

저장된 객체 중에는 오랫동안 남겨둬야 하는 데이터가 있고, 일시적인 처리 결과도 있다. 임시 파일을 자동으로 정리하면 공간이 줄겠지만 버킷 전체에 짧은 TTL을 적용하면 아직 참조되는 객체를 지울 수도 있다.

당시에는 Prefix별 Lifecycle과 만료 기간을 검토했다. 핵심은 “몇 일 뒤에 삭제할까”보다 **어떤 작업이 끝나야 그 객체를 버려도 되는가**였다. 이후 작업의 재시도 가능 기간도 함께 고려해야 한다.

버전 관리가 켜져 있다면 현재 버전의 만료와 과거 버전의 삭제도 다르다. 따라서 Lifecycle은 복사나 IAM 이전에 슬쩍 포함할 설정이 아니라 별도의 검증 대상으로 남겼다. 전체 버킷에 안전한 최종 정책이 적용됐다는 뜻은 아니다.

## 접속 주소를 바꾸기 전에 확인하고 싶었던 것

새 MinIO 콘솔이 열리는 것만으로는 Cutover를 결정할 수 없다. 적어도 원본과 대상의 버킷·Key·Version을 같은 시점에서 비교하고, 누락되거나 불명확한 항목을 별도로 기록해야 한다. 대표적인 객체를 실제로 읽어 확인해야 하며, IAM 권한은 허용과 거부 동작 모두 검사해야 한다.

새 쓰기와 덮어쓰기, 삭제, Multipart Upload 완료 동작도 실제 애플리케이션 관점에서 확인하는 편이 좋다. 마지막으로 문제가 발견됐을 때 원본을 얼마나 오래 유지하며 어떤 경로로 되돌릴지 정해둬야 한다. 롤백은 DNS 주소를 되돌리는 것만으로 끝나지 않는다. **그사이에 달라진 데이터와 권한을 어떻게 취급할지**가 더 중요하다.

이 모든 조건을 당시 통과했다고 주장하지는 않는다. 실제로 진행한 대량 전송과 오류 조사, `mc diff`의 차이, 미완료 Upload와 IAM 문제는 남아 있지만 완전한 무결성 검증 보고서는 없다.

대량 전송 이후에도 원본·대상 객체 수와 크기가 일치하지 않는 시점이 있었다. 실패한 전송 목록, 미완료 Upload, IAM 정책을 따로 살폈지만 객체 단위 재검증과 실제 클라이언트 다운로드를 모두 통과한 최종 무결성 보고서는 남아 있지 않다.
