인터넷에 연결된 환경에서 컨테이너 이미지를 만드는 일은 비교적 단순하다. Dockerfile에서 베이스 이미지를 지정하고 필요한 패키지를 설치한 뒤 Registry로 Push하면 된다. 그런데 공용 Registry와 패키지 저장소에 접근할 수 없는 환경에서는 그 평범한 과정의 숨겨진 전제가 하나씩 드러난다.

나는 GitLab Runner와 Kaniko, 사설 Nexus3 Registry를 이용해 Git의 변경사항을 내부 이미지로 만들고 배포할 수 있는 경로를 구축했다. 목표는 단지 CI Job이 한 번 성공하는 것이 아니었다. **어제 성공한 빌드를 같은 입력으로 내일도 재현할 수 있는가**가 더 중요했다.

## 무엇을 미리 준비해야 빌드할 수 있을까

폐쇄망에서 필요한 베이스 이미지는 승인된 경로로 미리 반입하고, 내부 Registry에서 접근할 수 있도록 준비해야 한다. 애플리케이션 패키지도 내부 미러에 필요한 버전이 있어야 한다. 빌드 도구 자체도 이미지로 준비돼야 한다.

그래서 Dockerfile만이 빌드의 입력이라는 생각을 버렸다. Runner가 사용하는 Job 이미지, Kaniko 실행 파일, 베이스 이미지의 정확한 버전, 패키지 미러, 사설 CA, Registry에 Push할 권한까지 모두 입력이었다.

{{figure /figures/journals/ci-dependency-map.svg | 폐쇄망 이미지 빌드가 의존하는 실행 환경과 공급 경로를 정리했다. 실제 내부 서버 배치나 Registry 주소를 나타내는 그림은 아니다.}}

가능하다면 `latest` 태그보다 고정된 Tag나 Digest를 사용하고 싶었다. 외부에서 바뀌는 이미지를 다시 받을 수 없는 환경에서는 입력의 정확한 버전이 재현성의 핵심이기 때문이다.

## Kaniko가 있는데 실행 파일이 없었다

GitLab Runner를 Kubernetes Executor로 구성했을 때 가장 먼저 막힌 부분 중 하나는 Kaniko 실행 환경이었다.

Kaniko를 사용하는 이미지가 지정돼 있어도 실제 Job에서 기대한 `/kaniko/executor`가 존재하지 않거나, Runner가 필요로 하는 셸 환경과 이미지의 Entry Point가 맞지 않을 수 있었다. 표면적으로는 CI 파이프라인 실패였지만 바로 Registry 문제라고 생각하면 엉뚱한 설정을 바꾸게 된다.

실제 이미지 안에 실행 파일이 있는지, 어떤 Entry Point가 적용되는지부터 확인했다. 이후 Runner가 사용하는 셸과 Kaniko 실행 파일을 함께 준비한 Wrapper 이미지로 실행 환경을 맞췄다.

이 문제는 권한이 아니라 **패키징과 실행 계약**의 문제였다. 없는 실행 파일은 Kubernetes 권한을 더 줘도 생기지 않는다.

비슷하게 프런트엔드 빌드에서 `storybook: not found`나 `spawn ENOENT`가 발생한 경우도 있었다. 그때도 미러에서 패키지를 받지 못한 것인지, 실제 빌드 Workspace에 필요한 CLI가 설치되지 않은 것인지 구분해야 했다.

## 401이 떴다고 비밀번호부터 바꾸지 않았다

Nexus3에서는 어떤 Repository로는 Push가 되는데 다른 Repository에서는 401이 발생하는 사례를 조사했다. CI 설정이 비슷하다고 해서 동일한 권한 경로를 타는 것은 아니다.

Registry까지 네트워크 요청이 도달한 상황이라면 TLS 연결 자체의 실패와 다르다. 이때는 실제로 어떤 이미지 경로로 요청했는지, Job 변수는 무엇인지, Docker 인증 설정이 어떤 Credential을 사용하는지, Nexus의 Repository 권한이 어떻게 적용되는지 살펴야 한다.

인증이 성공했다는 사실과 특정 경로에 Push할 권한이 있다는 사실도 다르다. 이름이 여러 단계로 중첩된 이미지 경로에서는 이 구분이 더 중요했다.

오류를 없애기 위해 CI 계정에 관리자 권한을 일괄 부여하는 것보다는 **요청에 필요한 권한이 어느 범위까지인가**를 먼저 확인하고 싶었다. 민감한 변수를 진단 로그에 그대로 출력하지 않는 것도 중요했다.

남아 있는 조사에는 Repository별 401 원인을 좁혀간 과정이 있지만, 모든 사례가 최종적으로 같은 방식으로 해결됐다고 주장할 수는 없다.

## 빌더와 노드는 서로 다른 CA를 신뢰한다

사설 Registry를 HTTPS로 사용하면서 인증서 신뢰 문제가 나타났다. 여기서 가장 자주 놓치기 쉬운 점은 **인증서를 검증하는 주체가 여러 개**라는 사실이다.

Kaniko가 이미지를 Push할 때 검증하는 CA와 K3s 노드의 Container Runtime이 이미지를 Pull할 때 검증하는 CA는 서로 다른 실행 환경에 있다. 개발자 PC의 브라우저가 Registry에 접속할 수 있다는 사실도 이 둘을 대신하지 않는다.

따라서 `x509` 오류가 발생했다면 어디에서 발생했는지 먼저 확인해야 했다. 빌드 이미지의 신뢰 저장소가 문제인지, 노드 런타임의 설정이 문제인지, 요청한 이름과 인증서 SAN이 맞지 않는지에 따라 조치가 달라진다.

또한 같은 Job이 어느 Runner 노드에서 실행됐는지에 따라 네트워크 연결 결과가 달라질 수 있었다. 특정 노드에만 배치하면 급한 작업은 통과할 수 있지만, 그것으로 다른 노드의 접근 경로까지 정상이라는 결론을 내릴 수는 없다.

## Registry가 자기 자신을 복구해야 하는 상황

사설 Registry는 모든 이미지 공급을 한곳에서 관리할 수 있어 편리하다. 하지만 Registry 자신도 같은 K3s 플랫폼에서 실행된다면 장애 복구에서 순환 의존성이 생길 수 있다.

Registry를 되살리는 데 필요한 이미지가 오직 고장 난 Registry에만 있다면, 복구 과정에서 가장 먼저 필요한 리소스를 가져올 수 없게 된다.

그래서 정상 배포 경로와 별개로 최소한의 부트스트랩 입력을 어떻게 확보할지 고민했다. 중요한 서비스의 이미지와 설정을 독립적인 경로에 보관하거나, Registry 없이도 최소 복구를 시작할 수 있어야 한다는 방향이었다.

이것을 완성된 재해복구 체계로 표현하고 싶지는 않다. 다만 **복제본이 많다는 사실과 복구에 필요한 의존성을 제거했다는 사실은 같지 않다**는 점은 분명했다.

## 장애를 나눠 보니 다음 행동도 달라졌다

지금은 CI 실패를 하나의 범주로 보지 않는다.

| 나타난 증상 | 먼저 확인할 곳 |
| --- | --- |
| `/kaniko/executor`가 없음 | 실제 Job 이미지 내용, Entry Point |
| 빌드 도구를 찾지 못함 | Workspace와 패키지 설치 상태 |
| `x509` 인증서 오류 | 해당 클라이언트의 CA 신뢰와 SAN |
| HTTP 401 | Token 교환, 이미지 경로, Repository 권한 |
| 일부 Runner에서만 실패 | 노드별 네트워크와 실행 환경 |
| 이미지 Pull 실패 | K3s Container Runtime, Registry 접근 경로 |
| Registry 자체 복구 실패 | 독립적인 부트스트랩 이미지 공급 경로 |

이 기준은 실제 문제를 분류하며 정리한 것이지 내부 CI 설정 전체를 공개한 매뉴얼은 아니다.

폐쇄망에서 CI를 운영하면서 가장 오래 남은 것은 특정 도구의 사용법보다 **빌드가 성공하기 위해 미리 존재해야 하는 것들을 하나씩 찾아낸 과정**이었다. 모든 의존성이 명시돼 있어야 재현 가능한 빌드가 되고, 어느 단계가 실패했는지 알아야 안전하게 고칠 수 있었다.
