브라우저에서는 Plane 화면이 열렸다. 배포 자체는 끝났고 이제 계정을 만들기만 하면 될 것 같았다. 그런데 초기 설정 화면으로 들어가면 다시 `/god-mode`로 돌아왔고, 로그인 과정은 좀처럼 다음 단계로 넘어가지 않았다.

이때 보였던 오류는 한 가지가 아니었다. `/auth/email-check` 요청은 처음에 HTTP 405를 반환했고, 다른 시점에는 400을 반환했다. 화면에는 **Instance not configured**라는 메시지도 나타났다.

폐쇄망 Kubernetes에 Plane CE v1.2.0을 설치하면서 겪었던 문제다. 서비스가 실행 중이고 첫 화면도 보인다는 사실이 그다지 도움이 되지 않았다. 실제로 필요한 것은 **최초 사용자 등록을 끝내고 Workspace까지 만들어 정상적으로 사용할 수 있는 상태**였다.

결국 요청을 어느 서비스로 전달하는지 다시 정리한 뒤 초기 설정이 진행됐고, 사용자 계정과 Workspace를 만들 수 있었다. 며칠 뒤에는 Plane Pages에서 실시간 연결이 끊기는 문제가 나타났는데, 이번에는 빠져 있던 `/live` 경로를 추가한 뒤 정상화됐다. 화면 하나가 열리는 것과 여러 서비스가 협력하는 기능 하나가 끝까지 동작하는 것은 다른 일이었다.

## 설정이 안 됐다는 메시지를 그대로 믿기 어려웠다

`Instance not configured`라는 문구를 보면 데이터베이스의 초기화가 실패했거나 Instance 설정이 잘못 저장됐다고 생각하기 쉽다. 그래서 설정 상태와 외부 접속 주소도 확인할 대상으로 두었다.

하지만 화면에 그 오류가 표시되는 경로부터 따져봐야 했다. 프런트엔드가 설정 정보를 가져오는 API를 호출했는데, 그 요청이 정작 API 서버가 아닌 다른 서비스로 향했다면 어떻게 될까? 서버에서 필요한 설정이 존재하더라도 브라우저는 올바른 응답을 받지 못할 수 있다.

`/auth/email-check`의 405와 400도 같은 맥락에서 보게 됐다. 405는 요청을 받은 대상이 해당 HTTP Method를 허용하지 않았다는 뜻이고, 400은 요청을 처리하는 쪽에서 내용이나 상태를 받아들이지 않았다는 뜻이다. 하지만 그 결과만으로 올바른 API에 도착했는지, 세션이 유효한지, 초기 설정이 끝났는지를 단정할 수는 없다.

처음에는 오류 메시지를 하나씩 고치려고 했다면, 어느 순간부터는 **브라우저가 보낸 경로를 실제로 누가 받아 처리했는지**를 먼저 확인하게 됐다.

## 같은 주소 아래에 서로 다른 서비스가 있었다

Plane은 하나의 웹사이트처럼 보이지만, 초기 설정 화면과 일반 웹 화면, API, 실시간 기능 등이 모두 같은 프로세스에서 실행되는 것은 아니다.

Ingress에서 요청을 나눠주는 방식이 중요했다. 모든 경로를 기본 웹 프런트엔드로 넘겨버리면 첫 화면은 정상적으로 보일 수 있다. 하지만 인증 API나 관리자 화면이 다른 서비스를 필요로 한다면 실제 기능은 실패한다.

{{figure /figures/journals/plane-route-ownership.svg | Plane의 기능별 경로와 해당 요청을 처리해야 하는 서비스를 나누어 표시했다. 실제 내부 Ingress 설정이나 서버 주소는 포함하지 않은 개념도다.}}

당시 문제를 이해하기 위해 요청 경로를 기능별로 나눠봤다.

| 요청 경로의 예 | 맡는 기능 | 잘못 연결될 때 나타날 수 있는 문제 |
| --- | --- | --- |
| `/god-mode/*` | 최초 설정·관리자 화면 | 초기 설정으로 진입하지 못하거나 반복 이동 |
| `/auth/*`, `/api/*` | 인증 및 애플리케이션 API | 사용자 확인, 세션, 설정 정보 요청 실패 |
| `/graphql/*`, `/internal/*` | 배포 버전에 따라 API가 맡는 경로 | 해당 기능의 API 요청 실패 |
| `/live/*` | 실시간 통신 | WebSocket·실시간 협업 기능에 문제 발생 가능 |
| `/spaces/*` | 별도 공개 페이지 | 공유 페이지 조회 실패 |
| 객체 저장소 접근 경로 | 파일 업로드·다운로드 | 브라우저에서 파일을 올리거나 열지 못함 |
| `/` | 일반 웹 프런트엔드 | 기본 화면 렌더링 |

이 표는 **실제 폐쇄망 IngressRoute를 옮긴 설정표가 아니다.** Plane과 Helm 차트의 버전에 따라 경로 및 구현은 달라질 수 있다. 특히 `/god-mode`는 관리자 인터페이스의 경로이지, 무조건 일반 웹 화면이나 API로 연결할 주소가 아니다.

가장 신경 썼던 것은 기본 경로가 다른 요청을 가리지 않도록 만드는 일이었다. `PathPrefix("/")`처럼 모든 요청과 일치하는 규칙만 있으면 API나 관리 화면을 위한 구체적인 규칙이 있어도 요청이 예상과 다르게 처리될 수 있다.

이 과정에서는 URL뿐 아니라 Host와 Forwarded Header도 구분해서 봐야 했다. 외부에서 보이는 주소와 애플리케이션이 알고 있는 주소가 다르면 로그인이나 Redirect 경로에 영향을 줄 수 있다. 다만 이 가능성을 모든 오류의 원인으로 단정하지는 않았다.

## 화면이 열리는 것을 넘어서 실제 계정을 만들기까지

라우팅을 수정한 뒤에는 상황이 달라졌다. 이전에 반복되던 초기 설정을 벗어나 사용자 등록을 진행할 수 있었고, 새 계정을 만들면서 Workspace도 생성됐다.

이 결과는 의미가 있었다. 적어도 브라우저, 관련 화면, API, 초기 설정 과정이 서로 연결되어 하나의 실제 사용자 동작을 완료했다는 뜻이기 때문이다.

{{figure /figures/journals/plane-bootstrap-statechart.svg | 처음 화면이 열린 상태부터 초기 설정 실패, 라우팅 수정, 계정·Workspace 생성까지의 관측된 상태를 나누었다. 뒤에 나타난 프록시·스토리지 문제는 별도 조사로 표시했다. 실시간 연결 복구는 별도로 확인된 결과다.}}

그렇다고 모든 Plane 기능이 정상적으로 운영됐다고 말할 수는 없다. 계정 등록과 Workspace 생성이 성공했다고 해서 파일 업로드, 외부 인증, WebSocket 연결, 장애 복구까지 검증한 것은 아니기 때문이다.

Instance의 도메인·접속 주소와 초기화 상태를 확인하는 방법도 검토했다. 다만 데이터베이스의 특정 필드를 직접 변경한 것이 유일한 원인이었음을 입증하는 변경 전후 기록은 남아 있지 않다. 실제로 확인된 결과는 **라우팅을 바로잡은 뒤 최초 사용자 등록과 Workspace 생성이 가능해졌다**는 것이다.

## 다른 접속 주소에서는 다시 404가 났다

한번 초기 설정에 성공했다고 끝난 것은 아니었다. 이후 별도의 Nginx Reverse Proxy를 거쳐 다른 주소로 접속하도록 시도했을 때는 로그인 화면조차 나타나지 않았다. HTTP 404가 돌아왔다.

그 과정에서 URL과 환경 설정값도 조정했지만, 기록상 그 404가 해결됐다는 확인은 없다.

앞에서 성공했던 초기 설정과 이번 문제를 같은 사건으로 취급할 수 없는 이유다. 하나의 접속 경로에서 계정 생성이 성공했다는 것은 다른 프록시를 하나 더 거쳤을 때도 모든 요청 경로가 올바르게 전달된다는 보장이 아니다.

중간에 프록시가 늘면 확인할 대상도 늘어난다. 요청의 Host를 유지했는지, 사용자가 보는 프로토콜과 Forwarded Header가 맞는지, 경로를 잘라서 전달하는지, 어느 서비스로 프록시되는지에 따라 404의 의미가 달라진다.

이후의 404에 대해서는 최종 원인을 증명한 기록이 부족하다. 따라서 해결된 것처럼 쓰지 않고 남겨두었다.

## Pages는 열리는데 연결은 끊겨 있었다

초기 설정을 끝내고 계정을 사용할 수 있게 된 뒤에도 문제가 하나 남아 있었다. Plane Pages에서 **Connect lost**라는 메시지가 보였다. 사이트가 아예 열리지 않는 상황은 아니었다. 실시간으로 연결돼 있어야 하는 기능만 정상적으로 움직이지 않았다.

처음에는 WebSocket의 Upgrade 처리가 떠올랐다. Nginx에는 이미 HTTP/1.1과 `Upgrade`, `Connection` 헤더를 전달하도록 설정해둔 상태였다. 그렇다면 헤더를 다시 넣는 것보다 **그 요청이 정말 WebSocket을 처리하는 서비스로 가고 있는지**를 확인하는 편이 먼저였다.

Plane에서 실시간 연결은 `/live` 경로를 이용한다. 확인해보니 당시 IngressRoute에 그 경로가 빠져 있었다. 일반 Web 서비스를 보여주는 `/` 규칙이 있더라도 Live 서비스의 역할까지 대신할 수는 없다.

**`/live`를 Live 서비스로 보내도록 수정하자 Pages에서 연결이 끊겼다는 문제가 해결됐다.** 이번에는 단순히 HTTP 200이 돌아왔다는 식의 테스트가 아니었다. 실제로 실패하던 Pages 기능의 연결 상태가 달라졌다는 점을 확인했다.

WebSocket 문제라고 해서 Upgrade 헤더나 Timeout만 조정하면 되는 것은 아니었다. 브라우저에서 프로토콜을 올리는 과정이 허용돼야 하고, 그 연결이 **실제로 해당 프로토콜을 구현한 Backend로 전달돼야 한다.** 어느 하나만으로는 충분하지 않다.

## MinIO에서는 서버의 성공이 브라우저의 성공은 아니었다

파일 업로드도 비슷한 문제를 보여줬다. Plane 백엔드가 Kubernetes 내부 주소를 이용해 MinIO에 접근하는 것은 가능했는데, 브라우저에서 파일을 올리려고 하면 오류가 발생했다.

그렇다면 MinIO 자체가 고장 난 것일까? 반드시 그렇지는 않다. 서버에서 내부 DNS 이름을 찾을 수 있는 것과, 사용자의 브라우저가 같은 주소에 접근할 수 있는 것은 다르다.

나중에는 외부에서 접근할 수 있는 HTTPS 저장소 주소를 사용하는 방법도 검토했다. 이때는 SSL 인증서 검증 실패가 나타났다. 이후 Nginx를 통해 MinIO에 접근하도록 실험했을 때에는 Plane API에서 **Bucket에 접근할 권한이 없다**는 오류가 나왔다. 인증서 검증과 S3 권한은 서로 다른 단계의 문제이므로, 한쪽의 오류가 사라졌다고 다른 쪽까지 해결됐다고 판단할 수는 없었다.

| 요청을 보내는 곳 | 필요한 조건 |
| --- | --- |
| Plane 백엔드 | 내부 저장소 주소의 DNS·네트워크 연결과 올바른 S3 인증 정보 |
| 사용자의 브라우저 | 실제 접근 가능한 URL, TLS 인증서 신뢰와 이름 일치, 필요한 CORS 조건 |
| 중간 프록시 | 객체 저장소까지 이어지는 경로, 적절한 Header와 요청 크기 처리 |

브라우저가 객체 저장소에 직접 요청하는 구조인지, Plane 서버가 대신 파일을 중계하는 구조인지에 따라서도 실패할 수 있는 곳이 달라진다. Plane 공식 문서에는 Storage Proxy를 사용하는 선택지가 있지만, 당시 내가 그 기능을 성공적으로 활성화해 검증했다는 자료는 없다.

여기서 생각할 점은 단순했다. **백엔드 Pod에서 파일 저장이 가능했다는 결과를 브라우저 업로드까지 성공했다는 뜻으로 확대할 수 없다.** 실제로 파일을 보내는 쪽이 누구인지 알아야 그쪽의 DNS, 인증서, 네트워크 경로를 확인할 수 있다.

## 어디까지 성공했다고 말할 수 있을까

Plane을 운영 가능한 상태로 판단하려면 적어도 몇 가지 기능은 실제로 사용해봐야 한다.

첫 화면과 관리자 화면이 각각 열리는지, 인증 API가 올바르게 응답하는지, 새 계정으로 로그인해 Workspace를 사용할 수 있는지 확인할 필요가 있다. 실시간 협업 기능을 사용한다면 WebSocket도 검사해야 한다. 파일 업로드는 서버 쪽 설정만 보지 말고 사용자가 실제로 접근하는 브라우저에서 올리고 다시 받아봐야 한다.

그중 당시 실제로 확인한 것은 **초기 설정을 통과해 계정과 Workspace를 만든 것**, 그리고 **`/live` 라우팅 수정 후 Pages의 연결 오류가 사라진 것**이다. Nginx를 추가한 다른 접속 경로의 404와 MinIO 브라우저 업로드의 TLS·권한 문제는 별도 조사 대상이었다. OAuth 연동을 완료했다는 기록도 없다.

이 구분을 남겨두는 편이 글을 조금 덜 매끄럽게 만들 수는 있다. 그래도 실제 운영 기록이라면 그쪽이 더 낫다고 생각했다.

## 같은 주소라도 요청마다 목적지가 달랐다

이번 일을 겪으며 Ingress를 단순히 도메인 하나를 Service 하나에 연결하는 설정으로 보면 곤란하겠다고 느꼈다.

화면, 관리자 기능, API, 파일 저장소가 서로 다른 서비스를 이용한다면 한 번의 사용자 동작에서도 여러 경계를 넘나든다. 브라우저에 첫 화면이 나타나는 것은 그중 하나의 경로가 열렸다는 의미일 뿐이다.

초기 설정 문제는 라우팅을 정리한 뒤 계정과 Workspace가 만들어지는 것으로 확인했다. Pages 연결 문제도 `/live` 라우팅 수정으로 해결했다. 반면 다른 프록시 경로와 저장소 연결에서 마주친 오류들은 별도의 조사 대상으로 남았다.

첫 화면을 가져오는 요청과 로그인 요청, 실시간 연결 요청, 파일 업로드 요청은 서로 달랐다. **정상 화면 하나보다 실제로 실패했던 사용자 동작이 다시 성공하는지를 확인하는 것**이 이번 작업에서 더 믿을 만한 기준이었다.
