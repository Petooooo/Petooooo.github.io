데이터베이스를 고가용성으로 만들고 싶을 때 가장 먼저 떠오르는 방법은 Replica를 늘리는 것이다. 하지만 실제로 MongoDB와 PostgreSQL, ClickHouse를 운영하면서, **프로세스가 여러 개 있다는 것과 클라이언트가 정상적으로 읽고 쓸 수 있다는 것은 별개의 문제**라는 점을 자주 확인했다.

그 차이는 Langfuse 업그레이드에서 더 선명하게 드러났다. 애플리케이션 Pod가 정상으로 보이더라도 마이그레이션은 아직 진행 중일 수 있었고, 반대로 화면에 Timeout이 떴지만 내부 진행 기록은 완료 상태일 수 있었다.

## 고가용성은 데이터 복제만으로 끝나지 않는다

MongoDB Replica Set을 생각하면 이해하기 쉽다. 각 서버가 살아 있다는 사실만으로 쓸 수 있는 Primary가 존재한다고 말할 수는 없다. 멤버 상태와 선출 조건, 클라이언트의 연결 및 재시도 동작을 함께 확인해야 한다.

PostgreSQL과 Pgpool은 또 다른 문제를 만든다. Pgpool이 클라이언트에게 안정적인 접속 주소를 제공하더라도, 실제로 연결한 PostgreSQL이 쓰기 가능한 노드인지 확인되지 않으면 요청이 실패할 수 있다. Pgpool 자체가 데이터를 영속화해주는 것은 아니다.

ClickHouse는 자체 복제와 Keeper 조정 메타데이터를 사용한다. Replica 프로세스가 실행 중이더라도 Keeper 상태나 복제 테이블의 상태 때문에 쓰기를 제한할 수 있다.

이렇게 보면 고가용성에는 서로 다른 조건이 있다. 프로세스가 살아 있는가. 데이터 복제본이 존재하는가. 어떤 서버가 쓰기를 받아야 하는지 정해졌는가. 요청이 올바른 서버로 전달되는가. 장애 뒤에도 필요한 데이터가 남아 있는가. 결국 애플리케이션에서 실제 읽기·쓰기가 가능한가.

이 조건을 하나의 “HA 성공” 표시로 묶어두면 어떤 계층이 잘못됐는지 알아내기 어렵다.

{{figure /figures/journals/db-migration-state.svg | 데이터베이스 가용성에는 Replica 상태, 연결 경로, 저장 공간, 애플리케이션 데이터 버전이 함께 관여한다. 실제 내부 배치도나 검증 결과를 나타내는 그림은 아니다.}}

## Langfuse는 이미지 버전만 바꾼다고 끝나지 않았다

Langfuse를 업그레이드할 때는 애플리케이션과 PostgreSQL, ClickHouse, Keeper가 함께 얽혀 있었다. 이전 버전에서 쌓인 Trace와 Observation을 새 분석 구조에 맞게 재작성하는 과정도 필요했다.

Helm Chart를 업데이트하고 새 Pod가 실행돼도 이전 데이터까지 바로 새 코드가 이해할 수 있다는 보장은 없다. 마이그레이션은 단순한 배포보다 더 복잡한 상태 전이다.

내가 구분하려 한 것은 애플리케이션 코드·스키마 버전, PostgreSQL에 저장된 마이그레이션 진행 상태, ClickHouse의 실제 데이터와 Keeper 상태, 목적지 저장 공간, 새 코드의 대표적인 읽기·쓰기 결과였다.

이 중 하나가 정상이라고 나머지가 정상이라는 결론을 내릴 수는 없었다.

## Timeout이 떴는데 완료된 청크가 있었다

가장 기억에 남는 것은 Langfuse 마이그레이션 Step 2였다. 작업 화면에는 `Timeout error.`가 표시됐지만, 영속화된 마이그레이션 정보를 직접 확인하니 다른 결과가 나왔다.

| 확인한 항목 | 당시 기록 |
| --- | --- |
| 사용자에게 보인 단계 상태 | 실패 및 Timeout |
| 영속화된 Phase | `completed` |
| 완료된 작업 청크 | **9개** |
| 실패한 작업 청크 | **0개** |

이 기록은 화면의 상태와 실제 백그라운드 작업의 진행이 다를 수 있다는 직접적인 증거였다.

그렇다고 청크 9개가 완료됐다는 사실만으로 모든 데이터가 정확히 변환됐다고 말할 수도 없다. UI와 호출자가 Timeout을 받았더라도 Worker가 계속 실행됐을 가능성을 확인한 것이지, 새 애플리케이션이 모든 데이터를 정상적으로 읽는지까지 검증한 것은 아니었다.

그래서 바로 마이그레이션을 처음부터 다시 실행하는 대신, **영속된 진행 기록을 기준으로 어떤 작업이 이미 끝났고 다음에 무엇을 확인해야 하는지**를 구분하려 했다. 중복으로 재실행하면 이미 반영된 결과를 다시 처리할 위험도 있다.

## Read-only와 공간 부족은 전혀 다른 원인이다

다른 시점에는 ClickHouse가 Read-only로 동작하거나 Keeper 조정 상태를 확인해야 하는 문제도 있었다. 이때 애플리케이션 Pod를 다시 시작하는 것으로 데이터베이스가 자동으로 쓰기 가능 상태가 되지는 않는다.

또한 Remote Insert에서 저장 공간 부족 오류가 발생한 경우도 있었다. 새로운 테이블을 만들고 기존 데이터를 재작성하는 과정은 평소 서비스에서 사용하는 용량 외에 임시 공간을 필요로 한다. 공간이 부족한 상태에서 같은 Insert를 다시 실행하면 실패만 반복할 수 있다.

이것들은 모두 “마이그레이션이 안 된다”로 표현할 수 있지만, 해결해야 할 계층은 서로 다르다.

- Timeout은 호출자와 백그라운드 작업의 시간 경계 문제일 수 있다.
- Phase는 영속 상태 기록이 어떤 단계를 완료했다고 보는지 알려준다.
- Read-only는 Replica나 Coordinator의 쓰기 가능 상태를 확인해야 한다.
- 공간 부족은 저장 용량의 제약이다.
- 새 스키마를 읽지 못하는 문제는 애플리케이션 코드나 데이터 변환 단계와 관련될 수 있다.

한 가지 원인으로 모두 설명하려고 하면 저장 공간만 늘렸는데도 마이그레이션이 실패하는 상황을 이해하기 어려워진다.

## 재시도도 새로운 작업이다

마이그레이션 작업은 보통 데이터를 읽고 다시 쓰는 무거운 배치 작업이다. 중간에 오류가 발생하면 다시 실행하고 싶지만, 어느 청크까지 완료됐는지 모른 채 재시도하면 결과가 겹칠 수 있다.

그래서 나는 재시도 전에 어떤 상태가 영속화됐는지 확인하는 편이 안전하다고 생각했다. 청크가 시작됐는지, 완료됐는지, 다른 Worker가 아직 소유하고 있는지, 데이터 변환 결과가 이미 반영됐는지를 구분해야 한다.

또한 복제본의 Repair 트래픽과 마이그레이션 데이터 재작성은 같은 디스크와 네트워크 자원을 사용할 수 있다. 스토리지 여유 공간이 충분하지 않다면 둘을 동시에 진행하는 것이 복구를 더 어렵게 만들 수도 있다.

## 마지막에 남는 질문은 애플리케이션 동작이다

데이터베이스 HA를 판단할 때 프로세스 수와 Leader 상태가 필요하지만, 그것은 시작점일 뿐이다. 마이그레이션이 끝났다고 판단할 때도 화면의 초록색 상태만으로는 부족하다.

나는 완료 여부를 다음처럼 확인하고 싶었다. 영속된 마이그레이션 단계에 누락이나 실패 청크가 없는가. Replica와 Keeper가 정상적인 읽기·쓰기를 지원하는가. 목적지 저장 공간에 여유가 있는가. 기존 Trace와 Observation이 조회되는가. 새로 쓴 데이터가 다시 읽히는가. 애플리케이션을 재시작한 뒤에도 백그라운드 작업이 정상적으로 이어지는가.

남아 있는 자료에는 Step 2의 Timeout과 완료 기록, 공간 부족, Read-only, 이후 JSON/Date 상태 처리 문제까지 구체적인 단서가 있다. 하지만 Langfuse v4 전체 마이그레이션이 모든 항목을 통과했다는 완료 보고서는 없다.

이 글에서 중요한 것은 “HA를 구축했다”보다 **누가 어떤 상태를 결정하고 그 상태를 어떻게 검증하는가**였다. 데이터베이스가 실행 중인지, 복제가 진행 중인지, 읽기·쓰기가 가능한지, 애플리케이션이 실제 데이터를 사용할 수 있는지를 분리해서 이해해야 장애가 발생했을 때도 더 정확한 다음 행동을 선택할 수 있다.
