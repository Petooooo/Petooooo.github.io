Rocket.Chat의 이전 데이터를 다루던 중 MongoDB 연결에 `ReplicaSetNoPrimary`가 나타난 적이 있다. 일부 멤버 주소를 찾지 못하는 `getaddrinfo ENOTFOUND`도 확인했다. 데이터베이스 Pod가 실행 중이라는 사실만으로 애플리케이션이 쓰기 가능한 Primary를 찾을 수 있는 것은 아니었다.

비슷한 간극을 ClickHouse에서도 봤다. 테이블을 복제 구조로 옮기는 과정에서 프로세스는 살아 있었지만 Replica는 Read-only 상태에 들어갔다. Langfuse 업그레이드 때는 반대처럼 보이는 일도 있었다. 화면에는 `Timeout error.`가 남았는데, PostgreSQL에 기록된 마이그레이션 진행 상태는 `completed`였다.

모두 같은 장애는 아니었다. 다만 서로 다른 시스템을 다룰 때마다 비슷한 질문으로 돌아왔다. **지금 정상이라고 표시된 것은 정확히 무엇이고, 그 상태가 실제 사용자의 읽기·쓰기까지 보장하는가.**

## MongoDB가 떠 있어도 Primary를 찾지 못했다

처음에는 고가용성을 구축한다는 말을 단순하게 생각하기 쉬웠다. 인스턴스를 여러 개 두고 하나가 내려가도 나머지가 살아 있으면 된다는 식이다. 하지만 MongoDB에서는 각 프로세스의 생존과 Replica Set 전체의 쓰기 가능 상태가 다르다.

Rocket.Chat의 첨부파일 이전을 조사하던 시기에는 Replica Set 멤버의 이름을 해석하지 못하는 오류와 `ReplicaSetNoPrimary`를 만났다. 이 두 메시지가 모든 첨부파일 문제의 원인이었다고 말할 수는 없다. 실제로 과거 파일이 열리지 않던 문제에는 GridFS 바이너리와 MinIO 객체 경로, Rocket.Chat의 업로드 메타데이터가 일치하는지도 따로 확인해야 했다.

그럼에도 연결 오류는 중요한 경계 하나를 드러냈다. MongoDB 멤버가 실행되고 Service 주소가 존재하더라도, 클라이언트가 멤버를 찾고 Primary를 선택해 필요한 연산을 수행할 수 있어야 한다. 구성 파일에 Replica Set이 적혀 있다는 것과, 애플리케이션에서 그 구성을 실제로 사용할 수 있다는 것은 다른 이야기였다.

## 연결을 받아주는 곳과 데이터를 쓰는 곳

PostgreSQL과 Pgpool을 살필 때는 같은 문제를 조금 다른 방향에서 보게 됐다. Pgpool은 애플리케이션이 접속할 창구를 제공하지만, 그 창구가 살아 있다는 사실이 뒤에 있는 PostgreSQL의 쓰기 가능 상태나 데이터 내구성을 대신 증명하지는 않는다.

내가 구분하려 했던 것은 Pgpool 프로세스의 상태, 실제 Primary·Standby의 역할, 요청이 전달되는 대상, 그리고 장애 이후 애플리케이션의 연결이 어떻게 회복되는가였다. 기록에 남아 있지 않은 자동 장애 조치 성공 사례를 덧붙일 생각은 없다. 당시의 검토는 **접속점을 이중화하는 것과 올바른 데이터베이스로 요청을 보내는 일을 별개의 조건으로 취급해야 한다**는 판단에 가까웠다.

MongoDB의 Primary 선출과 PostgreSQL의 쓰기 노드 라우팅은 같은 방식으로 구현되지 않는다. Kubernetes의 Pod 수나 Leader라는 이름 하나로 두 시스템을 묶으면 오히려 판단이 흐려졌다.

## ClickHouse에서는 두 번째 Pod보다 테이블의 상태가 중요했다

기존 단일 ClickHouse를 복제 구성으로 옮길 때는 더 직접적으로 부딪혔다. 두 번째 Pod를 띄워도 기존 MergeTree 테이블이 저절로 ReplicatedMergeTree가 되지는 않는다. 각 Replica에 보관되는 데이터 Part와 Keeper가 관리하는 복제 메타데이터는 서로 다른 역할을 가진다.

나는 기존 백업과 테이블 정의를 바탕으로 MergeTree 계열의 저장 테이블을 복제형 엔진으로 전환했다. 일반 View와 Materialized View는 처음부터 같은 방식으로 처리하지 않고 의존 관계를 따로 봤다. 중간에는 기존 테이블을 Attach할 때 `KEEPER_EXCEPTION`이 발생했고, Replica가 Read-only로 표시되기도 했다.

이후 `system.replicas`에서 `is_readonly = 0`, `queue_size = 0`을 확인한 시점이 있었다. 상태가 개선됐다는 분명한 단서였다. 그렇지만 한쪽 Replica에 데이터가 먼저 쌓이고 다른 쪽이 뒤따라가는 모습도 봤다. 큐가 비었다고 해서 모든 과거 Row와 View 결과가 일치한다는 결론까지 내릴 수는 없었다.

이 경험 이후에는 상태 표시를 볼 때 그 값이 어디까지 말해주는지 먼저 따지게 됐다. `is_readonly = 0`은 그때 확인한 Replica가 Read-only가 아니라는 뜻이고, `queue_size = 0`은 그 순간 대기 중인 복제 작업이 없다는 뜻이다. 실제 데이터의 일치 여부와 애플리케이션의 조회 결과는 다시 확인해야 한다.

{{figure /figures/journals/db-migration-state.svg | 프로세스 상태, Replica 조정, 저장 공간, 애플리케이션 데이터 버전은 같은 상태 표시로 묶을 수 없다. 실제 클러스터 배치도가 아닌 개념도다.}}

## Langfuse의 Timeout은 어디에서 난 실패였을까

Langfuse를 새 버전으로 옮길 때도 이 구분이 필요했다. Helm Chart와 애플리케이션 이미지를 바꾸는 일은 배포 과정의 일부일 뿐이었다. 이전 버전에서 쌓인 Trace와 Observation을 새로운 데이터 구조로 옮기는 백그라운드 작업은 PostgreSQL의 진행 기록, ClickHouse의 쓰기 상태, Keeper의 조정 상태와 저장 공간에 영향을 받았다.

Step 2에서 `Timeout error.`가 나타났을 때, 오류만 보고 전체 작업을 처음부터 반복하는 것은 조심스러웠다. PostgreSQL에 남아 있는 마이그레이션 상태를 직접 확인하니 다음과 같았다.

| 확인한 곳 | 기록된 상태 |
| --- | --- |
| 화면과 호출자에게 보인 결과 | 실패, `Timeout error.` |
| 영속화된 Phase | `completed` |
| 완료된 청크 | **9개** |
| 실패한 청크 | **0개** |

화면이 기다리던 응답을 제때 받지 못한 것과 백그라운드 데이터 작업이 실패한 것은 같은 말이 아니었다. 이 기록은 적어도 9개 청크가 완료 상태로 남아 있음을 보여줬다. 반대로 그 수치만으로 모든 목적지 데이터가 정확하게 변환됐거나 새 버전의 Langfuse가 과거 데이터를 모두 정상 조회한다고 주장할 수도 없었다.

그래서 먼저 확인할 것은 재시도 버튼이 아니라 이미 저장된 진행 상태였다. 어떤 작업이 끝났는지, 아직 실행 중인 작업이 있는지, 새 코드가 그 결과를 실제로 읽고 쓸 수 있는지를 나눠 봐야 했다. 이 Step 2 사례의 세부 기록은 별도 글에 남겨두었다.

## 비슷하게 보인 오류들이 서로 다른 곳에서 나왔다

또 다른 시점에는 ClickHouse의 Remote Insert가 공간 부족으로 실패했다. 데이터를 재작성하면서 원본과 목적지, 임시 작업 공간을 함께 고려해야 했고, 공간 조건이 바뀌지 않은 채 같은 Insert를 반복한다고 나아질 문제는 아니었다.

Read-only 상태는 Replica와 Keeper 쪽에서, 저장 공간 부족은 디스크 용량 쪽에서 원인을 찾아야 했다. 이후 Langfuse의 다른 단계에서는 JSON·Date 상태 처리 오류도 나타났다. 데이터베이스가 쓰기를 받을 수 있는가와 마이그레이션 코드가 영속 상태를 올바른 자료형으로 읽는가는 또 별개의 문제였다.

여러 오류를 모두 '업그레이드 실패'라고 묶으면 편하기는 하다. 하지만 그렇게 적고 나면 어디까지 확인했고 무엇을 바꿔야 하는지 오히려 보이지 않았다. 당시 서로 다른 시점에 나타난 증상을 하나의 원인과 한 번의 복구로 연결하지 않은 이유다.

마이그레이션 중에는 평소 요청 외에도 데이터 재작성과 복제본 동기화가 디스크와 네트워크를 사용한다. 따라서 복구와 이전을 동시에 진행할 때 자원 여유와 작업 소유권을 확인해야 한다는 판단도 남았다. 이를 정량적으로 측정한 공개 벤치마크가 있는 것은 아니다.

## 마지막에는 애플리케이션으로 돌아와야 했다

데이터베이스가 정상이라는 말을 하려면 여러 단계의 확인이 필요했다. 프로세스가 떠 있는지, Primary나 Replica가 기대한 역할을 수행하는지, 클라이언트 요청이 올바른 곳에 도달하는지, 데이터가 실제로 남아 있는지, 그리고 애플리케이션이 그 데이터를 사용할 수 있는지가 서로 이어져야 한다.

Langfuse라면 과거 Trace와 Observation이 조회되는지, 새로 기록한 데이터를 다시 읽을 수 있는지, 재시작 뒤에도 백그라운드 작업이 진행되는지 확인해야 한다. ClickHouse라면 쓰기 가능한 상태와 복제 큐 외에 데이터 자체의 비교가 필요하고, MongoDB라면 애플리케이션이 원하는 읽기·쓰기 정책 아래 Primary와 통신할 수 있어야 한다.

이 글을 처음 정리하던 때에는 Langfuse v4 마이그레이션에도 끝나지 않은 단계가 있었다. 하지만 그 상태가 최종 결과는 아니었다. **2026년 11월 17일에는 Step 1~5를 모두 마쳤고, `events_only` 모드에서 과거와 신규 데이터 검증을 통과했다.** 마지막에는 이전을 위해 사용한 임시 정렬 테이블을 정리했으며, 기존 `traces`와 `observations` 원본 테이블을 삭제한 것은 아니었다. 중간 장애와 최종 검증의 차이는 [Langfuse 이전 기록](/projects/rokaf-langfuse-v4-migration-field-notes/)에 따로 남겨두었다.

그렇다고 이 글에서 다룬 모든 데이터베이스 장애와 모든 예외적인 복구 상황이 검증됐다는 뜻은 아니다. 검증한 범위를 넘어서 성공을 넓혀 쓰지 않으려 한다.

처음에는 복제본이 몇 개인지부터 보곤 했다. 이제는 그 숫자를 확인한 다음에 한 가지를 더 묻는다. **그 복제본들 중 실제 요청을 받아서, 필요한 데이터를 올바르게 돌려줄 수 있는 것은 무엇인가.** 고가용성을 운영하면서 끝내 확인해야 할 것은 그쪽에 더 가까웠다.
