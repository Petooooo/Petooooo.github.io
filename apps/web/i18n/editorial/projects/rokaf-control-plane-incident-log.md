Control Plane 장애는 나중에 설명하기가 오히려 쉽다. 모든 것이 복구된 뒤에는 “etcd가 문제였고 조치해서 정상화했다”는 식으로 정리하고 싶어지기 때문이다. 하지만 실제로는 **서비스를 먼저 살려야 해서 원인을 다 확인하지 못한 채 넘어간 순간**들이 있었다.

K3s 운영 중 etcd의 불안정 또는 손상 의심, 디스크의 Read-only 상태, API 접근 장애를 조사했다. 이들을 같은 시기에 봤다는 이유로 모두 하나의 원인에서 시작됐다고 단정하고 싶지는 않다.

## 여러 컴포넌트가 함께 실패할 때

Control Plane에 문제가 생기면 API 요청이 느려지거나 실패하고, Controller가 새로운 Pod를 만들지 못하거나 Scheduler가 예상대로 동작하지 않을 수 있다. 그 아래에서 실행되는 애플리케이션에도 연쇄적으로 문제가 나타난다.

이때 여러 Pod를 동시에 재시작하면 일단 서비스가 돌아올 수는 있다. 하지만 **처음 문제가 생긴 위치**를 알아낼 단서는 사라질 수 있다.

내가 관심을 둔 것은 어느 시점에 어떤 상태가 먼저 변했는지였다. etcd가 응답하지 않았는가. 노드의 디스크 쓰기가 먼저 실패했는가. API Server에 도달하는 네트워크 경로가 막혔는가. 아니면 API가 unavailable해지면서 다른 컴포넌트들이 뒤따라 실패한 것인가.

{{figure /figures/journals/control-plane-incident-evidence.svg | 디스크 I/O, etcd 멤버와 쿼럼, API Server, Controller, 애플리케이션은 서로 다른 증거를 제공한다. 실제 장애 타임라인이나 내부 인프라 토폴로지는 아니다.}}

## Read-only라는 단어를 그대로 믿지 않았다

장애 로그에 Read-only가 보이면 디스크가 고장 난 것으로 생각하기 쉽다. 하지만 그 표현은 여러 상황을 가리킬 수 있다.

파일시스템이 오류 이후 스스로 Read-only로 Remount됐을 수 있다. 원래 의도적으로 Read-only로 Mount한 경로일 수도 있다. 데이터베이스가 복제 상태 때문에 논리적으로 쓰기를 제한했을 수도 있고, 권한이 없는 애플리케이션이 Read-only처럼 보이는 오류를 받았을 수도 있다.

따라서 DB의 Read-only 상태를 Linux 파일시스템의 Read-only Remount라고 단정할 수 없다. 반대로 파일시스템 오류가 있었다는 사실만으로 물리 디스크의 손상 원인까지 확정할 수도 없다.

이 구분은 etcd에서 더 중요했다. etcd는 클러스터의 상태를 영속적으로 기록하고 멤버끼리 일관성을 유지해야 한다. 로컬 디스크의 쓰기와 응답 지연이 etcd 상태에 영향을 줄 수 있고, etcd가 쿼럼을 형성하지 못하면 Kubernetes API의 상태 변경도 영향을 받는다.

**etcd 프로세스 한 개가 살아 있다는 사실은 클러스터 쿼럼이 정상이라는 증거가 아니다.** 마찬가지로 API 요청이 실패했다는 결과만으로 etcd 데이터가 손상됐다고 결론 낼 수도 없다.

## 복구와 원인 규명은 별도의 작업이었다

장애 당시에는 서비스를 다시 사용하는 것이 급선무였을 수 있다. 그렇더라도 원인 분석 기록에는 무엇을 복구했다고 확인했는지 남기고 싶었다.

| 복구 단계 | 확인할 내용 | 아직 알 수 없는 것 |
| --- | --- | --- |
| 프로세스 재시작 | 해당 서비스가 다시 실행되는가 | 디스크의 데이터가 정확한가 |
| etcd 조정 상태 | 멤버와 쿼럼이 동작하는가 | 모든 API와 클라이언트가 복구됐는가 |
| API Server | 대표적인 읽기·쓰기 요청에 응답하는가 | 애플리케이션 데이터까지 복구됐는가 |
| Controller | 필요한 리소스를 다시 만들고 조정하는가 | 사용자의 실제 요청이 성공하는가 |
| 애플리케이션 | 대표적인 기능을 사용해볼 수 있는가 | 전체 과거 데이터의 무결성까지 확인됐는가 |

Kubernetes API가 다시 열리는 순간은 중요하지만, 그것만으로 장애를 완료 처리하기에는 부족했다. 특히 Stateful 서비스라면 실제 쓰기와 데이터 복구까지 살펴야 한다.

Rollback이나 Restore가 필요한 경우에도 상태 저장 시스템의 복구 절차와 Backup을 고려해야 한다. 아무 근거 없이 이전 데이터를 지우거나 컴포넌트를 반복 재시작하는 방식은 오히려 문제를 크게 만들 수 있다.

## 결국 파일시스템 쪽으로 관심이 향했다

Control Plane의 여러 계층을 들여다보면서 오히려 더 아래쪽이 궁금해졌다. etcd처럼 분산된 상태 저장소도 각 멤버의 로컬 파일시스템과 블록 장치에 의존한다.

`fsync` 지연, 쓰기 순서, 파일시스템 메타데이터, I/O 오류, Read-only Remount가 상위 데이터베이스와 오케스트레이터에 어떤 모습으로 전달되는지 알아야, “etcd가 불안정했다”는 사실을 넘어 더 구체적인 설명을 할 수 있을 것 같았다.

모든 사건이 파일시스템에서 시작됐다고 주장하려는 것은 아니다. 그런 결론을 내리기 위해 무엇을 관측해야 하는지 더 분명해졌다는 뜻이다.

## 남겨두고 싶은 기록

다시 비슷한 장애를 만나면 첫 번째 API 실패 시간, 각 etcd 멤버의 상태, 호스트 디스크 오류와 Mount 상태, 실제로 적용한 변경 시간, 클라이언트 요청이 다시 성공한 시간을 함께 기록하고 싶다. 중요한 것은 로그를 많이 모으는 것보다 **어떤 증거가 어떤 판단을 가능하게 하는지**다.

남아 있는 자료는 etcd 불안정·손상 의심과 Read-only 현상을 조사했고 일부 상황에서 가용성을 회복했다는 것을 뒷받침한다. 하지만 특정 호스트 I/O 오류가 이 모든 현상을 일으켰다고 시간 순서와 상태 기록으로 입증한 자료는 없다.

실제 복구 조치와 별개로, etcd 로그와 호스트 I/O 오류·파일시스템의 Read-only 전환을 같은 시간축에서 비교한 자료가 더 필요했다. 현재 기록은 일부 가용성 회복을 보여주지만 공통 원인을 확정하지는 못한다.
