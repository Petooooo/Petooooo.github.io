## 개요

**DevOps**는 개발자가 운영을 대신하거나 운영자가 배포 스크립트만 작성하는 방식을 의미하지 않는다. 핵심은 개발, 운영, 테스트, 보안, 비즈니스 요구사항을 하나의 흐름으로 연결하여 애플리케이션을 더 빠르고 안정적으로 전달하는 것이다.

소프트웨어는 단순히 코드를 작성한다고 끝나지 않는다. 요구사항이 정리되고, 코드가 작성되고, 빌드되고, 테스트되고, 배포되고, 운영 중 문제가 관찰되며, 그 피드백이 다시 다음 개발로 돌아온다. DevOps는 이 전체 흐름을 **delivery pipeline**으로 보고, 그 안의 수동 작업과 대기 시간, 책임 단절, 피드백 지연을 줄이는 접근이다.

Kubernetes 환경에서는 DevOps의 의미가 더 분명해진다. 애플리케이션은 container image로 패키징되고, 배포 상태는 manifest나 Helm chart로 선언되며, 운영 상태는 metrics, logs, traces를 통해 관찰된다. 즉, 개발과 운영의 경계가 코드, pipeline, cluster 상태로 연결된다.

## DevOps가 필요한 이유

전통적인 조직에서는 개발팀과 운영팀의 관심사가 분리되어 있었다.

| 구분 | 주요 관심사 | 흔한 목표 |
|---|---|---|
| 개발팀 | 기능 구현, 버그 수정, 코드 리뷰, 테스트 | 변경을 빠르게 반영 |
| 운영팀 | 배포, 인프라 관리, 장애 대응, 안정성 유지 | 서비스를 안정적으로 운영 |

이 구조 자체가 항상 나쁜 것은 아니다. 문제는 두 팀의 목표가 서로 충돌하기 쉽다는 점이다.

개발팀은 새로운 기능을 빠르게 배포하고 싶어 한다. 반면 운영팀은 안정성을 위해 변경을 조심스럽게 다루고 싶어 한다. 이때 개발팀은 운영팀이 배포를 막는다고 느끼고, 운영팀은 개발팀이 불안정한 코드를 넘긴다고 느낄 수 있다.

이런 구조에서는 배포가 협업 흐름이 아니라 단순한 **handoff**가 된다.

```text
요구사항 정리
  -> 개발팀 구현
  -> QA 검증
  -> 운영팀 배포
  -> 장애 발생
  -> 원인 분석 요청
  -> 다시 개발팀 수정
```

단계가 나뉠수록 다음 문제가 커진다.

- 변경 사항이 production까지 도달하는 시간이 길어진다.
- 배포 실패 시 어느 단계에서 문제가 생겼는지 추적하기 어렵다.
- 운영 중 얻은 피드백이 다음 개발 계획에 늦게 반영된다.
- 수동 배포와 수동 검증이 많아져 작업 재현성이 낮아진다.
- 개발팀과 운영팀 사이의 책임 경계가 모호해진다.

DevOps는 이 문제를 해결하기 위해 등장한 방식이다. 개발과 운영을 하나의 연속된 software delivery system으로 보고, 변경 사항이 안전하게 흘러가도록 협업 구조와 자동화 체계를 만든다.

## DevOps의 정의

DevOps는 하나의 도구 이름이 아니다. 특정 직무 하나로만 설명하기도 어렵다. 더 정확하게는 다음 네 가지 요소가 결합된 운영 방식이다.

| 요소 | 의미 | 핵심 질문 |
|---|---|---|
| Culture | 개발, 운영, 보안, 비즈니스가 같은 제품을 함께 책임지는 문화 | 배포 후 문제까지 함께 책임지는가? |
| Process | planning부터 monitoring까지 이어지는 반복 가능한 흐름 | 변경 사항이 어떤 단계를 거쳐 production에 도달하는가? |
| Automation | 빌드, 테스트, 배포, 인프라, 검증의 자동화 | 사람이 반복하던 작업을 pipeline이 재현 가능하게 수행하는가? |
| Feedback | 운영 중 얻은 정보를 다시 개발로 되돌리는 구조 | 장애, 성능, 사용자 반응이 다음 개선으로 이어지는가? |

짧게 정리하면 다음과 같다.

```text
DevOps = Culture + Process + Automation + Feedback
```

DevOps의 목표는 단순히 배포 속도를 높이는 것이 아니다. 더 중요한 목표는 **작은 변경을 자주, 자동 검증을 거쳐, 관찰 가능한 상태로, 필요하면 빠르게 복구할 수 있게 만드는 것**이다.

## DevOps는 팀 이름이 아니라 작동 방식이다

현업에서는 `DevOps Engineer`, `DevOps Team`이라는 표현을 자주 사용한다. 그러나 DevOps를 특정 팀 하나가 담당하는 작업으로만 이해하면 본질을 놓치기 쉽다.

DevOps Engineer가 CI/CD pipeline, Kubernetes manifest, Helm chart, Infrastructure as Code, monitoring stack을 구축할 수는 있다. 하지만 제품팀 전체가 동일한 delivery pipeline과 운영 지표를 공유하지 않으면 DevOps가 조직의 작동 방식으로 자리 잡기는 어렵다.

주의할 점은 다음과 같다.

| 오해 | 실제 의미 |
|---|---|
| Jenkins를 쓰면 DevOps다 | 도구 사용만으로 DevOps가 되는 것은 아니다. |
| Kubernetes를 쓰면 DevOps다 | Kubernetes는 DevOps를 가능하게 하는 실행 환경 중 하나다. |
| DevOps는 운영팀을 없애는 것이다 | 운영 책임을 없애는 것이 아니라 운영 지식을 개발 흐름에 더 일찍 포함하는 것이다. |
| DevOps Engineer 한 명을 뽑으면 된다 | 개인 역할보다 조직의 delivery system이 더 중요하다. |

DevOps의 핵심은 팀 이름이 아니라 다음 질문에 있다.

> 변경 사항이 얼마나 빠르고 안전하게 production까지 도달하며, 운영 중 얻은 피드백이 얼마나 빠르게 다음 개발로 돌아오는가?

## Delivery Pipeline의 큰 흐름

DevOps에서 중요한 관점은 애플리케이션을 **ideation부터 production까지 이동시키는 전체 흐름**으로 보는 것이다.

일반적인 delivery pipeline은 다음 순환 구조를 가진다.

```text
아이디어
  -> 계획
  -> 코드 작성
  -> 빌드
  -> 테스트
  -> 릴리스
  -> 배포
  -> 운영
  -> 모니터링
  -> 피드백
  -> 다시 계획
```

이 흐름은 한 번 실행되고 끝나는 절차가 아니다. 운영 중 관찰된 문제와 사용자 피드백이 다시 backlog에 들어가고, 다음 변경 사항으로 이어지는 반복 구조다.

예를 들어 사용자가 특정 API의 응답 속도가 느리다고 느낀다면, DevOps 관점에서는 이를 단순 장애 처리로 끝내지 않는다. 먼저 latency, error rate, resource usage, dependency 상태를 관찰한다. 이후 병목 후보를 정리하고, 개선 작업을 작은 단위로 나누어 pipeline을 통해 검증하고 배포한다.

## DevOps Lifecycle

DevOps lifecycle은 여러 방식으로 표현할 수 있지만, 핵심 단계는 다음과 같이 정리할 수 있다.

| 단계 | 목적 | 주요 작업 |
|---|---|---|
| Plan | 무엇을 바꿀지 결정 | 요구사항 정리, backlog 관리, 작업 분해 |
| Code | 변경 사항 구현 | 코드 작성, branch 관리, pull request, code review |
| Build | 실행 가능한 산출물 생성 | compile, package, container image build |
| Test | 변경 검증 | unit test, integration test, static analysis, security scan |
| Release | 배포 가능한 변경 확정 | versioning, artifact 관리, release note |
| Deploy | 환경에 반영 | staging 배포, production 배포, rolling update |
| Operate | 서비스 운영 | 장애 대응, scaling, backup, patching |
| Monitor | 상태 관찰과 학습 | metrics, logs, traces, alerting, feedback |

이 단계들은 직선형으로 한 번만 흐르지 않는다. 실제 운영에서는 계속 순환한다.

```text
Plan -> Code -> Build -> Test -> Release -> Deploy -> Operate -> Monitor
  ^                                                                  |
  |------------------------------------------------------------------|
```

이 순환이 짧고 안정적일수록 조직은 더 빠르게 학습하고 더 안전하게 변경할 수 있다.

## Planning: 작업을 작게 나누는 단계

Planning은 단순 회의가 아니다. 사용자 피드백, 장애 기록, 비즈니스 요구사항, 기술 부채, 보안 요구사항을 모아 다음 변경 단위를 정리하는 단계다.

DevOps에서는 큰 변경을 한 번에 배포하기보다, 작은 변경을 자주 배포할 수 있도록 작업을 나누는 것이 중요하다. 작은 변경은 다음 장점이 있다.

- code review가 쉽다.
- 테스트 범위를 명확히 잡기 쉽다.
- 배포 실패 시 원인 후보가 줄어든다.
- rollback 또는 fix forward 판단이 쉬워진다.
- 운영 지표 변화와 코드 변경을 연결하기 쉽다.

예를 들어 "업로드 기능 개선"이라는 큰 작업은 다음과 같이 나눌 수 있다.

| 작업 단위 | 목적 |
|---|---|
| 업로드 latency 측정 지표 추가 | 현재 병목 확인 |
| 이미지 처리 로직 분리 | 동기 처리 구간 축소 |
| 업로드 API timeout 조정 | 사용자 경험 개선 |
| storage dependency 모니터링 추가 | 외부 의존성 상태 관찰 |
| canary 배포 적용 | 변경 영향 범위 제한 |

이처럼 planning 단계에서 작업을 작게 나누면 pipeline의 검증 결과와 production의 관찰 결과를 더 쉽게 연결할 수 있다.

## Coding: 운영 가능성을 고려한 코드 작성

DevOps에서 coding은 기능 구현만 의미하지 않는다. 코드를 작성하는 단계부터 운영 가능성을 함께 고려해야 한다.

확인할 포인트는 다음과 같다.

- 오류 발생 시 원인을 추적할 수 있는 로그가 남는가?
- 환경별 설정값이 코드와 분리되어 있는가?
- secret, token, password, 내부 IP, private hostname이 코드에 들어가지 않는가?
- API 변경이 기존 client를 깨뜨리지 않는가?
- 장애 발생 시 retry, timeout, fallback 전략이 있는가?
- 배포 후 metrics로 상태 변화를 확인할 수 있는가?
- rollback 또는 feature flag 기반 비활성화가 가능한가?

운영 가능성을 고려하지 않은 코드는 production에서 문제를 만들기 쉽다. DevOps에서는 이 문제를 줄이기 위해 개발 단계부터 observability, configuration, security, deployment strategy를 고려한다.

> 내부 IP, token, password, private hostname, secret은 문서와 repository에서 반드시 `[REDACTED]`로 처리해야 한다.

## Build: 재현 가능한 산출물 만들기

Build 단계에서는 source code가 실행 가능한 형태로 변환된다. 언어와 환경에 따라 산출물은 다를 수 있다.

| 환경 | 일반적인 build 산출물 |
|---|---|
| Java | JAR, WAR |
| Node.js | bundled artifact, package |
| Go | binary |
| Python | wheel, container image |
| Kubernetes | container image, Helm chart, manifest |

DevOps에서 중요한 것은 사람이 로컬에서 임의로 빌드한 결과물을 운영 환경에 올리지 않는 것이다. 같은 commit은 같은 pipeline에서 빌드되어야 하고, 산출물은 추적 가능한 위치에 저장되어야 한다.

Kubernetes 환경에서는 보통 다음 흐름이 사용된다.

```text
Git commit
  -> CI pipeline
  -> test
  -> container image build
  -> image registry push
  -> manifest 또는 Helm chart update
```

이렇게 하면 production에서 문제가 발생했을 때 다음을 추적할 수 있다.

- 현재 배포된 image tag는 무엇인가?
- 해당 image는 어떤 commit에서 만들어졌는가?
- 어떤 test를 통과했는가?
- 이전 image로 rollback 가능한가?
- 배포 전후 metrics 변화는 어땠는가?

Build 자동화의 핵심은 속도보다 **재현성**과 **추적 가능성**이다.

## Test: 검증을 뒤로 미루지 않기

DevOps에서 test는 마지막에 한 번 수행하는 절차가 아니다. 변경이 pipeline을 통과하는 동안 여러 단계에서 반복적으로 수행된다.

| 테스트 종류 | 목적 |
|---|---|
| Unit test | 작은 코드 단위의 동작 검증 |
| Integration test | 모듈 또는 서비스 간 상호작용 검증 |
| Static analysis | 코드 품질, 타입, 취약 패턴 점검 |
| Security scan | dependency, container image 취약점 확인 |
| Smoke test | 배포 직후 기본 기능 동작 확인 |
| End-to-end test | 사용자 흐름 기준 검증 |
| Canary analysis | 일부 트래픽에서 production 영향 확인 |

중요한 것은 test를 빠르게, 반복 가능하게, 자동으로 실행하는 것이다. 변경 사항을 자주 배포하려면 사람이 매번 전체 기능을 수동으로 검증할 수 없다.

따라서 DevOps에서 test automation은 단순 편의 기능이 아니라 배포 속도와 안정성을 동시에 확보하기 위한 핵심 장치다.

## Release와 Deploy 구분

DevOps에서 **release**와 **deploy**는 구분해서 이해하는 것이 좋다.

| 구분 | 의미 |
|---|---|
| Deploy | 코드를 특정 환경에 반영하는 행위 |
| Release | 사용자에게 기능을 공개하는 행위 |

예를 들어 새로운 기능이 production 환경에 이미 배포되어 있지만 feature flag로 꺼져 있다면, deploy는 되었지만 release는 아직 되지 않은 상태다.

이 둘을 분리하면 운영 안정성을 높일 수 있다.

- production에 먼저 안전하게 배포한다.
- 일부 사용자 또는 내부 사용자에게만 기능을 연다.
- metrics와 logs를 확인한다.
- 문제가 없으면 release 범위를 넓힌다.
- 문제가 있으면 feature flag를 끄거나 rollback한다.

Kubernetes 환경에서는 rolling update, canary deployment, blue-green deployment 같은 전략이 이 구분과 연결된다.

| 전략 | 특징 | 주의할 점 |
|---|---|---|
| Rolling update | pod를 순차적으로 교체 | readinessProbe 설정이 중요 |
| Canary deployment | 일부 트래픽만 새 버전으로 전달 | 관찰 지표가 충분해야 함 |
| Blue-green deployment | 기존 환경과 새 환경을 분리 | resource 사용량이 증가할 수 있음 |
| Feature flag | 배포와 기능 공개를 분리 | flag 관리 복잡도 증가 |

## Kubernetes 환경에서의 DevOps 흐름

Kubernetes 기반 DevOps 흐름은 다음과 같이 이해할 수 있다.

```text
1. 개발자가 Git에 코드를 push한다.
2. CI가 test와 build를 수행한다.
3. container image가 registry에 저장된다.
4. Helm chart 또는 Kubernetes manifest가 갱신된다.
5. CD 도구가 cluster에 변경 사항을 반영한다.
6. Kubernetes가 rolling update를 수행한다.
7. readinessProbe를 통과한 pod만 traffic을 받는다.
8. metrics, logs, traces를 통해 상태를 관찰한다.
9. 장애 또는 성능 문제가 발견되면 다시 backlog로 돌아간다.
```

이 구조에서 Kubernetes는 단순 실행 환경이 아니다. DevOps의 여러 원칙을 실제 운영에 연결해주는 platform 역할을 한다.

| Kubernetes 요소 | DevOps 관점의 의미 |
|---|---|
| Deployment | 원하는 replica 상태를 선언 |
| Service | pod 변경과 무관한 안정적인 접근 지점 제공 |
| Ingress | 외부 트래픽 진입 경로 관리 |
| ConfigMap | 환경별 설정 분리 |
| Secret | 민감 정보 분리 관리 |
| readinessProbe | traffic을 받을 준비가 되었는지 확인 |
| livenessProbe | 비정상 container 재시작 |
| resource requests/limits | scheduling과 resource isolation |
| Helm chart | 배포 설정의 template화 |
| Namespace | 환경 또는 팀 단위 격리 |

DevOps 관점에서 중요한 것은 Kubernetes 객체를 단순히 만들고 끝내는 것이 아니다. 변경 사항이 Git, CI/CD, registry, cluster, observability stack까지 이어지는 하나의 흐름으로 관리되어야 한다.

## Automation의 역할

Automation은 DevOps의 핵심이다. 사람이 반복적으로 수행하는 작업은 느리고, 실수하기 쉽고, 추적하기 어렵다.

예를 들어 수동 배포는 다음과 같은 위험을 가진다.

- 잘못된 서버에 접속할 수 있다.
- 다른 버전의 artifact를 복사할 수 있다.
- 설정 파일을 누락하거나 잘못 수정할 수 있다.
- rollback 절차가 사람의 기억에 의존할 수 있다.
- 실제로 어떤 변경이 적용되었는지 기록이 남지 않을 수 있다.

DevOps에서는 이런 작업을 pipeline과 코드로 옮긴다.

| 자동화 대상 | 예시 |
|---|---|
| Build | source code를 artifact 또는 container image로 변환 |
| Test | unit test, integration test, security scan |
| Deploy | manifest apply, Helm upgrade, rolling update |
| Infra | Infrastructure as Code 기반 resource 생성 |
| Verification | smoke test, health check, canary metric 확인 |
| Monitoring | alerting, dashboard, log aggregation |

Automation의 목적은 단순히 사람의 작업을 줄이는 데 있지 않다. 더 중요한 목적은 같은 작업을 같은 방식으로 반복하게 만드는 것이다.

```text
같은 commit
  -> 같은 build process
  -> 같은 artifact
  -> 같은 deployment process
  -> 추적 가능한 production state
```

이 재현성이 있어야 장애 분석과 rollback이 가능해진다.

## Observability와 Feedback Loop

DevOps는 production 배포에서 끝나지 않는다. 운영 중 얻은 정보가 다시 개발로 돌아와야 한다.

이를 위해 필요한 것이 **observability**다. Observability는 단순 monitoring보다 넓은 개념이다. 시스템 외부에서 관찰 가능한 signals를 통해 내부 상태를 추론할 수 있어야 한다.

대표적인 signals는 다음과 같다.

| Signal | 설명 |
|---|---|
| Metrics | latency, error rate, throughput, CPU, memory 등 수치형 지표 |
| Logs | 요청 처리 과정, 오류 메시지, 상태 변화 기록 |
| Traces | 분산 시스템에서 요청이 여러 서비스를 거치는 경로 |
| Events | 배포, 재시작, scaling, 장애 발생 같은 상태 변화 |

DevOps에서 observability가 중요한 이유는 다음과 같다.

- 배포 후 실제 영향도를 확인할 수 있다.
- 장애 원인을 빠르게 좁힐 수 있다.
- 성능 저하가 특정 변경과 관련 있는지 볼 수 있다.
- 사용자 경험과 시스템 상태를 연결할 수 있다.
- 운영 피드백을 다음 backlog로 되돌릴 수 있다.

좋은 DevOps 흐름에서는 장애 대응이 수동 조치로 끝나지 않는다. 같은 문제가 반복되지 않도록 test, alert, runbook, resource 설정, deployment strategy를 개선한다.

---

## DevOps의 운영상 검증 포인트

DevOps가 실제로 잘 작동하는지 보려면 도구 목록보다 운영 지표와 흐름을 확인해야 한다.

| 검증 포인트 | 확인 질문 |
|---|---|
| 변경 추적성 | production에 배포된 artifact가 어떤 commit에서 왔는지 확인 가능한가? |
| 빌드 재현성 | 같은 commit을 다시 빌드하면 같은 결과를 얻을 수 있는가? |
| 테스트 자동화 | 변경 사항이 병합되기 전에 자동 검증되는가? |
| 배포 안정성 | readinessProbe, rolling update, rollback 전략이 준비되어 있는가? |
| 운영 관찰성 | metrics, logs, traces로 배포 전후 상태를 비교할 수 있는가? |
| 피드백 반영 | 장애와 사용자 피드백이 다음 planning으로 돌아가는가? |
| 보안 처리 | secret, token, 내부 IP, private hostname이 노출되지 않는가? |
| 책임 공유 | 개발과 운영이 같은 지표와 pipeline을 기준으로 협업하는가? |

이 질문에 답할 수 없다면, 도구는 많아도 DevOps 흐름은 아직 약할 수 있다.

## 자칫 실수하기 쉬운 부분

### 도구 도입을 DevOps로 착각하는 경우

Jenkins, Docker, Kubernetes, Terraform, Ansible을 도입했다고 해서 자동으로 DevOps가 되는 것은 아니다. 도구는 DevOps를 가능하게 하는 수단이다. 중요한 것은 변경 사항이 안전하게 production까지 흘러가는 구조다.

### 배포 속도만 강조하는 경우

DevOps는 무작정 빨리 배포하는 방식이 아니다. 작은 변경을 자주 배포하되, 자동 테스트와 관찰 지표, rollback 전략이 함께 있어야 한다. 속도만 있고 검증과 관찰이 없으면 장애를 더 빠르게 production에 전달할 뿐이다.

### 운영 책임을 뒤로 미루는 경우

DevOps에서는 개발 단계부터 운영 가능성을 고려해야 한다. 로그, metrics, timeout, retry, configuration, secret 처리, deployment strategy는 코드 작성 이후에 붙이는 부가 기능이 아니다.

### 배포와 release를 구분하지 않는 경우

기능을 production에 deploy하는 것과 사용자에게 release하는 것은 다르다. 이 둘을 분리하지 않으면 문제가 생겼을 때 영향 범위를 줄이기 어렵다.

### 피드백 루프가 없는 경우

모니터링 dashboard만 있다고 피드백 루프가 만들어지는 것은 아니다. 운영 중 발견된 문제가 backlog, test, alert, runbook, pipeline 개선으로 이어져야 한다.

## Kubernetes DevOps의 간단한 mental model

Kubernetes 환경에서 DevOps를 다음과 같이 생각할 수 있다.

```text
Git은 변경의 출발점이다.
CI는 변경을 검증하고 artifact를 만든다.
Registry는 실행 가능한 산출물을 보관한다.
Manifest와 Helm chart는 원하는 배포 상태를 선언한다.
CD는 선언된 상태를 cluster에 반영한다.
Kubernetes는 실제 상태를 원하는 상태에 맞추려 한다.
Observability는 실제 상태가 안전한지 확인한다.
Feedback은 관찰 결과를 다음 변경으로 되돌린다.
```

이 mental model에서 핵심은 **원하는 상태**와 **실제 상태**의 연결이다.

- Git에는 원하는 애플리케이션 코드와 배포 설정이 있다.
- Registry에는 해당 코드에서 만들어진 image가 있다.
- Kubernetes에는 실제 실행 중인 workload가 있다.
- Observability stack에는 실제 운영 상태가 있다.
- Backlog에는 다음에 개선할 작업이 있다.

DevOps는 이 요소들을 따로 보는 것이 아니라 하나의 delivery system으로 연결한다.

## 정리

DevOps는 개발과 운영을 단순히 합치는 것이 아니다. 소프트웨어가 아이디어에서 production 운영까지 이동하는 전체 흐름을 하나의 system으로 보고, 그 안의 병목과 수동 작업, 책임 단절, 피드백 지연을 줄이는 접근이다.

핵심은 다음과 같다.

- DevOps는 culture, process, automation, feedback의 결합이다.
- 목표는 빠른 배포만이 아니라 빠르고 안전한 가치 전달이다.
- CI/CD는 DevOps를 실행 가능하게 만드는 핵심 엔진이다.
- Kubernetes는 선언형 배포와 운영 자동화를 통해 DevOps 흐름을 구체화한다.
- Observability는 production 상태를 다시 개발로 연결하는 feedback loop의 기반이다.
- 도구보다 중요한 것은 변경 사항이 안전하게 흐르는 delivery pipeline이다.

결국 DevOps를 잘 운영한다는 것은 다음 질문에 답할 수 있다는 뜻이다.

> 현재 production에 적용된 변경은 어디서 왔고, 어떻게 검증되었으며, 문제가 생기면 어떻게 관찰하고 복구할 수 있는가?
