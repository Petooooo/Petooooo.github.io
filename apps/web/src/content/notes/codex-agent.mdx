## 개요

Codex 같은 coding agent를 기존 프로젝트에 적용할 때 핵심은 단순히 "코드를 잘 작성하게 하는 것"이 아니다.  
더 중요한 것은 agent가 프로젝트 구조를 먼저 파악하고, 변경 범위를 작게 나누고, 검증 가능한 단위로 구현하며, 필요 시 쉽게 되돌릴 수 있도록 작업 흐름을 통제하는 것이다.

이 노트는 다음 목표를 기준으로 agent 활용 방식을 정리한다.

- 오류 가능성 줄이기
- 쓰레기 코드와 임시 패치 누적 방지
- 기존 아키텍처 유지
- 성능 개선을 측정 기반으로 수행
- 작업 단위 rollback을 쉽게 만들기
- Codex 전역 `AGENTS.md`와 repo별 지침을 분리해서 운영하기

## 기본 관점

Agent는 프로젝트의 최종 의사결정자가 아니라, 구조 조사와 반복 구현을 수행하는 작업자에 가깝게 다루는 것이 안전하다.

```text
사람 = 제품 방향, 아키텍처 방향, 승인, 최종 책임
Agent = 코드베이스 조사, 계획 초안, 최소 단위 구현, 검증, 요약
```

따라서 agent에게 바로 "구현해줘"라고 지시하기보다는 다음 순서가 더 안전하다.

```text
구조 파악
→ 현재 동작 이해
→ 문제 정의
→ plan.md 작성
→ 사람의 승인
→ 최소 기능 단위 구현
→ 검증
→ local commit
→ 다음 작업
```

## 바로 구현시키면 생기는 문제

Agent에게 처음부터 구현을 맡기면 다음과 같은 흐름이 발생하기 쉽다.

```text
요청
→ 여러 파일을 한 번에 수정
→ 오류 발생
→ 임시 패치
→ 또 다른 오류 발생
→ 기존 구조와 다른 코드 누적
```

이때 가장 위험한 것은 단순한 문법 오류가 아니라 다음과 같은 구조적 부작용이다.

- 기존 아키텍처 무시
- 과한 추상화
- 중복 코드 추가
- 임시 예외 처리
- TODO, placeholder, debug print 잔류
- 검증되지 않은 성능 최적화
- 테스트 회피
- public API 또는 설정 형식의 의도치 않은 변경

## 전역 AGENTS.md와 프로젝트별 AGENTS.md 분리

전역 지침에는 모든 프로젝트에 적용할 공통 작업 방식을 작성한다.

```text
~/.codex/AGENTS.md
```

전역 지침의 역할은 다음과 같다.

- 작업 전 구조 파악
- 최소 기능 단위로 쪼개기
- spec-first 기본 적용
- test-first는 가능한 경우에만 적용
- 위험 명령 제한
- 쓰레기 코드 방지
- 성능 개선은 측정 기반으로 수행
- 검증 후 요약

반면 프로젝트별 지침은 각 repo의 루트에 둔다.

```text
repo/AGENTS.md
```

프로젝트별 지침에는 다음 내용을 넣는 것이 좋다.

- 프로젝트 구조
- 주요 실행 명령
- lint/typecheck/test/build 명령
- 아키텍처 경계
- 금지된 변경
- dependency 추가 정책
- 배포 또는 운영 관련 주의사항

## 권장 디렉터리 구조

복잡한 작업은 채팅 로그에만 의존하지 말고 repo 내부에 agent 작업 문서를 남기는 것이 좋다.

```text
docs/agent/
  research.md
  plan.md
  implementation-log.md
  verification.md
```

각 파일의 역할은 다음과 같다.

| 파일 | 역할 |
| --- | --- |
| `research.md` | agent가 코드베이스를 조사한 결과 |
| `plan.md` | 구현 전 계획과 승인 대상 |
| `implementation-log.md` | 실제 변경 내용 기록 |
| `verification.md` | 실행한 테스트, lint, typecheck, manual check 결과 |

이 구조를 사용하면 새 세션에서 다시 작업하더라도 현재 프로젝트 상태와 작업 방향을 복구하기 쉽다.

## Research 단계

처음 보는 repo나 unfamiliar area에서는 바로 코드를 수정하지 않는다.  
먼저 구조를 파악한다.

확인할 항목은 다음과 같다.

- 프로젝트 타입
- 주요 언어
- package manager 또는 build system
- framework 또는 runtime
- entry point
- 관련 source directory
- test/lint/typecheck/build 명령
- 변경 가능성이 있는 파일 주변의 기존 패턴
- 현재 git status

Agent에게 줄 수 있는 프롬프트 예시는 다음과 같다.

```text
이 repo의 구조를 먼저 조사해줘.

아직 코드는 수정하지 마.
관련 파일을 읽고 docs/agent/research.md에 정리해줘.

- 프로젝트 구조
- 주요 entry point
- 이 기능과 관련된 파일
- 현재 데이터 흐름
- 기존 패턴
- 테스트/빌드/실행 명령
- 위험 요소
- 아직 불확실한 점

구현 계획은 아직 작성하지 말고, 리서치만 해줘.
```

## Plan 단계

구조 파악 이후에는 바로 구현하지 않고 `plan.md`를 작성하게 한다.

`plan.md`에는 다음 내용이 포함되어야 한다.

- 목표
- 기대 동작
- 바꾸지 않을 것
- 변경 파일 목록
- 단계별 구현 계획
- 테스트 또는 검증 방법
- 위험 요소
- rollback 방법

예시 프롬프트는 다음과 같다.

```text
research.md를 기반으로 plan.md를 작성해줘.

아직 코드는 수정하지 마.

plan.md에는 다음을 포함해줘.

- 목표
- 기대 동작
- 바꾸지 않을 것
- 변경 파일 목록
- 단계별 구현 계획
- 테스트 또는 검증 방법
- 위험 요소
- rollback 방법

작업은 최소 기능 단위로 쪼개고, Phase 1만 구현 가능한 수준으로 계획해줘.
```

## 승인 전 구현 금지

Agent 활용에서 중요한 규칙은 다음과 같다.

```text
계획이 승인되기 전까지 코드를 수정하지 않는다.
```

계획을 사람이 검토한 뒤, 범위를 줄이거나 파일 변경 대상을 제한해야 한다.

예시 피드백은 다음과 같다.

```text
이 계획에서 src/auth/session.ts는 건드리지 마.
현재 문제는 UI 메시지 매핑만 바꾸면 될 것 같아.
계획을 더 작게 줄여줘.
아직 구현하지 마.
```

수정된 계획이 적절하면 구현을 승인한다.

```text
plan.md의 Phase 1 구현을 승인한다.

Phase 1만 구현해줘.
계획에 없는 파일은 수정하지 마.
구현 후 가장 좁은 관련 테스트/typecheck/lint를 실행해줘.
마지막에 변경 파일, 변경 이유, 검증 결과, 남은 리스크를 요약해줘.
```

## 최소 기능 단위로 작업하기

Agent에게는 큰 기능을 한 번에 맡기기보다 최소 기능 단위로 작업하게 해야 한다.

최소 기능 단위의 예시는 다음과 같다.

- 하나의 bug fix
- 하나의 UI behavior
- 하나의 endpoint 변경
- 하나의 component 변경
- 하나의 command 변경
- 하나의 testable path
- 명시적으로 요청된 작은 refactor

좋지 않은 작업 단위는 다음과 같다.

- 기능 변경과 리팩토링을 한 번에 수행
- UI 수정과 API 변경을 한 commit에 포함
- dependency 추가와 구조 변경을 동시에 수행
- mass-format과 bug fix를 섞기
- plan에 없던 cleanup을 함께 수행

## Spec-first와 TDD/SDD 기준

전역 지침에는 "무조건 TDD"보다는 다음 원칙을 넣는 것이 좋다.

```text
Spec-first by default.
Test-first when practical.
Do not invent fake tests.
Use the narrowest meaningful verification.
```

즉, 기본은 SDD 또는 spec-first에 가깝게 두고, TDD는 테스트 인프라가 있는 경우에 우선 적용한다.

### Spec-first

비 trivial 변경 전에는 기대 동작을 먼저 정의한다.

- 무엇이 바뀌어야 하는가
- 무엇은 유지되어야 하는가
- input/output은 무엇인가
- edge case는 무엇인가
- user-visible behavior는 무엇인가
- failure behavior는 무엇인가
- 어떻게 검증할 것인가

### TDD가 적합한 경우

TDD는 다음 작업에서 유용하다.

- bug fix
- business logic
- parser
- API
- data transformation
- validation
- 계산 로직
- 재현 가능한 실패 케이스가 있는 문제

흐름은 다음과 같다.

```text
기대 동작 정의
→ 가장 작은 관련 test 추가/수정
→ 가능하면 실패 확인
→ 최소 수정 구현
→ 관련 test 재실행
→ 필요 시 작은 refactor
```

### TDD를 강제하지 않아야 하는 경우

다음 작업에서는 무리하게 테스트를 만들면 오히려 쓰레기 코드가 생길 수 있다.

- CSS만 수정하는 UI 변경
- 간단한 문서 수정
- 설정 파일의 작은 값 변경
- Kubernetes manifest 수정
- Helm values 수정
- CI/CD 설정 수정
- 테스트 인프라가 전혀 없는 프로젝트

이 경우에는 test 대신 다음 검증을 사용한다.

- typecheck
- lint
- build
- dry-run
- diff
- template rendering
- static inspection
- manual reproduction steps

## 성능 개선 정책

성능 개선은 추측 기반으로 하면 위험하다.  
Agent에게 성능 개선을 맡길 때는 반드시 baseline과 비교 기준을 요구해야 한다.

권장 흐름은 다음과 같다.

```text
병목 후보 식별
→ 측정 또는 재현 경로 확보
→ baseline 기록
→ 하나의 focused change 적용
→ 결과 비교
→ trade-off 요약
```

주의할 점은 다음과 같다.

- 근거 없이 caching을 추가하지 않는다.
- 근거 없이 concurrency를 추가하지 않는다.
- 근거 없이 memoization을 추가하지 않는다.
- 근거 없이 queue, background job, streaming을 추가하지 않는다.
- speculative optimization 때문에 가독성을 떨어뜨리지 않는다.
- 성능 개선을 측정하지 않았다면 "개선됨"이라고 단정하지 않는다.

## Cleanup과 dead code 제거 기준

Cleanup은 behavior-preserving이어야 한다.  
기능 변경과 broad cleanup을 섞으면 diff review와 rollback이 어려워진다.

삭제 전 확인 기준은 다음과 같다.

- unreachable code인가
- 참조가 없는 코드인가
- 기존 구현과 중복되는가
- commented-out dead code인가
- temporary debug code인가
- 현재 코드와 모순되는 obsolete documentation인가
- commit하면 안 되는 generated artifact인가

주의할 점은 다음과 같다.

- public API를 쉽게 삭제하지 않는다.
- exported function을 쉽게 삭제하지 않는다.
- migration을 삭제하지 않는다.
- script를 삭제하지 않는다.
- test를 삭제하지 않는다.
- 호환성 유지용 코드를 근거 없이 삭제하지 않는다.

## 위험 명령 제한

`AGENTS.md`에는 위험 명령을 실행하지 말라는 정책을 넣고, 가능하면 Codex rules로도 제한하는 것이 좋다.

위험 명령의 예시는 다음과 같다.

```text
rm -rf
git reset --hard
git clean
git push
git push --force
docker system prune
docker volume prune
kubectl delete
kubectl apply against production-like resources
helm uninstall
helm upgrade against production-like releases
database drop
database truncate
destructive migration
```

기본 원칙은 다음과 같다.

```text
inspection before mutation
dry-run before apply
local commit before risky change
no push without explicit approval
```

## Commit 단위 관리

작업마다 local commit을 남기면 rollback이 쉬워진다.  
다만 "매 수정마다 commit"이 아니라 "검증된 최소 기능 단위마다 commit"이 좋다.

권장 흐름은 다음과 같다.

```text
새 작업 시작
→ git status 확인
→ 작업용 branch 생성
→ 구조 파악
→ plan.md 작성
→ 사람의 승인
→ 최소 기능 단위 구현
→ test/typecheck/lint 실행
→ diff self-review
→ local commit
→ 다음 작업
```

좋은 commit 단위의 예시는 다음과 같다.

```text
검색 API timeout 처리 추가
ProductCard hover 스타일 수정
Nexus upload 중복 GAV 처리 로직 추가
Kubernetes manifest dry-run 검증 스크립트 추가
```

좋지 않은 commit 단위는 다음과 같다.

```text
fix
update
이것저것 수정
리팩토링 + 기능 변경 + 포맷팅 혼합
```

Agent에게 commit을 허용할 때는 push를 금지해야 한다.

```text
이번 작업은 완료 후 검증이 통과하면 local commit까지 만들어줘.
push는 하지 마.
commit message는 작업 내용을 간결하게 작성해줘.
```

전역 지침에는 다음 원칙을 넣는 것이 좋다.

```text
Do not create commits unless the user explicitly asks.
When the user asks for commits, create local commits only.
Never push commits unless the user explicitly asks.
Prefer one commit per verified minimal functional unit.
```

## Branch 기반 운영

작업 단위 branch를 만들면 reset을 자주 쓰지 않아도 된다.

```bash
git checkout -b agent/task-name
```

작업이 마음에 들면 merge한다.

```bash
git checkout main
git merge agent/task-name
```

작업 방향이 잘못되었다면 branch를 삭제한다.

```bash
git checkout main
git branch -D agent/task-name
```

이 방식은 `git reset --hard`보다 안전하다.  
다만 branch 삭제 역시 현재 변경 내용과 필요한 파일이 없는지 확인한 뒤 수행해야 한다.

## 잘못된 방향으로 진행된 경우

Agent가 잘못된 방향으로 여러 파일을 수정했다면, 나쁜 diff 위에 계속 패치하지 않는 것이 좋다.

이때 사용할 수 있는 프롬프트는 다음과 같다.

```text
현재 변경 방향이 잘못됐다.
이 diff를 기준으로 추가 패치하지 마.

먼저 변경된 파일과 문제점을 요약해줘.
그다음 안전하게 되돌릴 수 있는 범위를 제안해줘.
내 승인 전에는 reset이나 삭제 명령을 실행하지 마.
```

필요하면 plan을 다시 작성한다.

```text
승인한다.
현재 잘못된 변경을 되돌리고, plan.md를 더 작은 범위로 다시 작성해줘.
아직 구현하지 마.
```

## UI 작업에서의 주의점

UI 작업은 말로만 설명하면 agent가 구조를 과하게 바꿀 수 있다.  
가능하면 현재 화면과 원하는 화면을 스크린샷으로 제공하고, 변경하면 안 되는 부분을 명확히 적는다.

예시 프롬프트는 다음과 같다.

```text
현재 화면 스크린샷은 A이고, 원하는 화면은 B다.

수정 목표:
- 검색창은 상단 중앙 유지
- 버튼 높이는 그대로
- hover 색상만 변경
- 레이아웃 구조는 변경하지 말 것

먼저 관련 컴포넌트를 찾아서 plan.md를 작성해줘.
아직 구현하지 마.
```

UI 작업의 검증은 단순 compile 여부보다 user-visible behavior를 기준으로 한다.

## Infrastructure 작업에서의 주의점

Kubernetes, Docker, Helm, CI/CD, registry, database 관련 작업은 production impact가 생길 수 있다.

이런 작업에서는 다음 순서가 안전하다.

```text
현재 설정 inspect
→ target environment 확인
→ dry-run/diff/template/plan 실행
→ 변경 영향 요약
→ 승인 후 적용
```

주의할 점은 다음과 같다.

- namespace 삭제 금지
- persistent volume 삭제 금지
- database drop/truncate 금지
- registry data 삭제 금지
- production-like resource에 apply/patch/delete 금지
- rollback path 확인 전 배포 금지

## 전역 AGENTS.md에 넣을 핵심 문장

전체 지침을 한 문장으로 줄이면 다음과 같다.

```text
Improve the project by making small, verified, directionally consistent changes. Do not create new architecture, abstractions, dependencies, or performance mechanisms unless the need is proven.
```

또 다른 핵심 문장은 다음과 같다.

```text
Spec-first by default. Test-first when practical.
```

그리고 구현 전 통제 원칙은 다음과 같다.

```text
Do not edit before understanding the structure.
Do not implement before the plan is approved for non-trivial work.
Do not push without explicit approval.
```

## 실제 작업 프롬프트 모음

### 리서치 전용

```text
이 repo의 구조를 먼저 깊게 조사해줘.

아직 코드는 수정하지 마.
관련 파일을 읽고 다음 내용을 docs/agent/research.md에 정리해줘.

- 프로젝트 구조
- 주요 entry point
- 이 기능과 관련된 파일
- 현재 데이터 흐름
- 기존 패턴
- 테스트/빌드/실행 명령
- 위험 요소
- 아직 불확실한 점

구현 계획은 아직 작성하지 말고, 리서치만 해줘.
```

### 계획 작성

```text
research.md를 기반으로 plan.md를 작성해줘.

아직 코드는 수정하지 마.

plan.md에는 다음을 포함해줘.

- 목표
- 기대 동작
- 바꾸지 않을 것
- 변경 파일 목록
- 단계별 구현 계획
- 테스트 또는 검증 방법
- 위험 요소
- rollback 방법

작업은 최소 기능 단위로 쪼개고, Phase 1만 구현 가능한 수준으로 계획해줘.
```

### 계획 수정

```text
plan.md에 남긴 피드백을 반영해서 계획을 수정해줘.

아직 구현하지 마.
범위를 더 줄이고, 기존 구조를 최대한 유지하는 방향으로 다시 작성해줘.
```

### 구현 승인

```text
plan.md의 Phase 1 구현을 승인한다.

Phase 1만 구현해줘.
계획에 없는 파일은 수정하지 마.
구현 후 관련 테스트나 typecheck를 실행하고 결과를 요약해줘.
검증이 통과하면 local commit까지 만들어줘.
push는 하지 마.
```

### 실패 시 중단

```text
지금 방향이 잘못된 것 같다.

추가 구현하지 마.
현재 변경된 파일과 문제점을 먼저 요약해줘.
그다음 되돌릴 부분과 유지할 부분을 제안해줘.
내 승인 전에는 git reset, 삭제, 강제 변경을 실행하지 마.
```

## 요약

Agent는 코드를 자동으로 작성하는 도구라기보다, 기존 프로젝트의 구조를 읽고 작은 단위로 검증 가능한 변경을 수행하는 작업자로 다루는 것이 좋다.

안전한 운영 방식은 다음과 같다.

```text
전역 AGENTS.md 설정
→ repo별 AGENTS.md 설정
→ docs/agent/research.md 작성
→ docs/agent/plan.md 작성
→ 사람의 승인
→ 최소 기능 단위 구현
→ 검증
→ local commit
→ 다음 작업
```

핵심은 다음 세 가지다.

1. 구현 전 구조 파악과 계획 수립
2. 검증 가능한 최소 기능 단위 구현
3. rollback 가능한 git 작업 단위 유지
