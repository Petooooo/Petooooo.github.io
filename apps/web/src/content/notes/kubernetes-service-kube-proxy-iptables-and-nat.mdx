# Kubernetes Service의 핵심 개념

## Pod IP

각 Pod는 고유한 IP를 가진다.

예시:

```text
Pod A -> 10.42.1.7
Pod B -> 10.42.2.3
```

특징:

* 실제 endpoint 역할 수행
* Pod 재생성 시 변경 가능
* scale up/down 시 개수가 변함
* 직접 의존 시 안정성이 낮음

---

## ClusterIP

`Service`에 부여되는 가상 IP(VIP).

예시:

```text
Service: web-svc
ClusterIP: 10.43.0.15
```

특징:

* 실제 NIC에 바인딩된 IP가 아님
* iptables/ipvs에서 가로채기 위한 논리적 주소
* Service 단위로 고정된 접근 지점 제공

즉:

```text
Client
→ ClusterIP
→ 실제 Pod 중 하나
```

구조를 제공한다.

---

# Service와 Pod 선택 방식

Service는 일반적으로 label selector를 통해 Pod를 선택한다.

예시:

```yaml
selector:
  app: nginx
```

이 경우:

```text
app=nginx
```

label을 가진 Pod들이 backend endpoint가 된다.

보통 Deployment/ReplicaSet이 동일 label의 Pod를 생성하므로 결과적으로:

```text
ReplicaSet Pod 집합
→ Service backend
```

처럼 동작한다.

# kube-proxy의 실제 역할

## 흔한 오해

다음 표현은 학습용으로는 이해 가능하지만 기술적으로는 부정확하다.

```text
kube-proxy가 트래픽을 Pod로 전달한다
```

---

## 실제 역할

kube-proxy는:

* Service
* EndpointSlice
* Pod readiness 상태

를 Kubernetes API에서 watch한다.

그리고 이를 기반으로:

* iptables rule 생성
* iptables rule 수정
* iptables rule 삭제

를 수행한다.

즉:

```text
kube-proxy = 규칙 관리자(control agent)
```

에 가깝다.

실제 패킷 forwarding은 Linux kernel networking stack이 수행한다.

---

# NodePort 트래픽 흐름

예시:

```text
NodeIP:30080
↓
PodIP:8080
```

외부 클라이언트가:

```text
[REDACTED_NODE_IP]:30080
```

으로 요청하면 대략 다음 흐름으로 처리된다.

```text
외부 클라이언트
→ NodeIP:NodePort
→ iptables PREROUTING
→ KUBE-SVC chain
→ backend endpoint 선택
→ DNAT 수행
→ PodIP:TargetPort
```

---

# DNAT 개념

## 정의

DNAT(Destination NAT):

```text
패킷의 목적지 주소(IP/Port)를 변경하는 것
```

---

## Kubernetes 예시

원래 패킷:

```text
dst = ClusterIP:80
```

변환 후:

```text
dst = PodIP:8080
```

즉:

```text
ClusterIP
→ 실제 PodIP
```

로 rewrite된다.

---

## iptables 예시

```bash
-A KUBE-SVC-XXXXX \
  -j KUBE-SEP-YYYYY

-A KUBE-SEP-YYYYY \
  -j DNAT --to-destination 10.42.1.7:8080
```

의미:

```text
Service로 들어온 패킷의 목적지를
10.42.1.7:8080으로 변경
```

---

# SNAT 개념

## 정의

SNAT(Source NAT):

```text
패킷의 출발지 주소(IP/Port)를 변경하는 것
```

---

## 대표 사례

가정용 공유기:

```text
192.168.x.x
↓
공인 IP
```

변환.

Kubernetes에서는 다음 상황에서 자주 사용된다.

* 외부 통신
* 응답 경로 유지
* cross-node traffic

iptables에서는 보통:

```text
POSTROUTING
```

단계에서 수행된다.

# NAT의 본질

NAT는 본질적으로:

```text
중간 네트워크 장비가
패킷 주소를 수정하여
다른 대상처럼 보이게 만드는 기술
```

이다.

대표 사용 사례:

* 가정용 공유기
* Kubernetes Service
* 클라우드 LoadBalancer
* Ingress
* 포트포워딩
* 일부 프록시 시스템

---

# Linux netfilter와 iptables

Linux kernel은 패킷 처리 과정에서 여러 hook 지점을 제공한다.

대표적인 hook:

```text
PREROUTING
INPUT
FORWARD
OUTPUT
POSTROUTING
```

iptables는 이 지점들에서:

* NAT
* filtering
* marking
* redirect

등을 수행한다.

# Kubernetes Service를 본질적으로 표현하면

다음 표현이 비교적 정확하다.

```text
Service =
Pod 집합에 대한
가상 IP 기반 L4 로드밸런싱 추상화
```

그리고:

```text
kube-proxy =
그 추상화를
iptables/IPVS 규칙으로 구현하는 관리자
```

라고 볼 수 있다.

# 주의할 점

## kube-proxy가 직접 프록시 역할을 수행하는 것은 아님

iptables mode에서는:

```text
실제 패킷 처리
→ Linux kernel
```

이다.

kube-proxy는 주로 control 역할 수행.

---

## ClusterIP는 실제 인터페이스 IP가 아님

자칫 실수하기 쉬운 부분:

```text
ClusterIP = 실제 네트워크 인터페이스에 존재하는 IP
```

라고 이해하는 것.

실제로는:

```text
iptables/ipvs에서 처리되는 논리적 VIP
```

에 가깝다.

---

## Ready 상태 기반 endpoint 관리

kube-proxy는 Ready Pod 기준으로 endpoint를 구성한다.

즉:

```text
NotReady Pod
→ backend endpoint 제외
```

가 수행된다.

단, 상태 전파 및 failure detection에는 지연이 존재할 수 있다.

검증 필요:

* kubelet probe interval
* node failure detection timeout
* EndpointSlice update propagation delay
