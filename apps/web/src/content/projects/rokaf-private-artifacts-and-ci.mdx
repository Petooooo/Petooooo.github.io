I had built a path for source code to become a container image without asking a public registry for help. GitLab Runner started a build in Kubernetes, Kaniko built the image, and Nexus kept the artifact inside the network. That made ordinary deployments much easier to manage.

But when Nexus and cluster DNS were unavailable during a later incident, some Pods could not pull the images they needed to come back. Even `IfNotPresent` was not enough to rescue every workload. The recovery mechanism I had counted on depended on services that were themselves down.

This was not the first time an apparently small CI failure had sent me looking at the wrong layer. I had previously seen `/kaniko/executor: No such file or directory` even though the intended image contained the binary. A different failure occurred before Kaniko could run at all: Kubernetes rejected the job image's registry certificate. Nexus itself could also show a working administrative UI while Docker clients were still failing at a different connector.

These were separate investigations spanning early 2026, not a single outage with a tidy fix. What links them is a question I kept returning to: **which component must already work before this step can even begin?**

The original private addresses, port assignments, registry paths, credentials and node identities are omitted. I distinguish confirmed changes from proposals and from recovery scenarios that were never fully exercised.

## The first contract was the job's actual runtime

I used a GitLab Runner with the **Kubernetes executor** rather than requiring a privileged Docker daemon for every build. A job image still had to satisfy two different consumers: GitLab Runner's script execution and Kaniko's image-building executable.

In January, one of the first failures was blunt:

`exec: "sh": executable file not found in $PATH`

The bare Kaniko executor image did not provide the shell expected by the job environment. I built a small, shell-capable **wrapper image** that included a shell and preserved the `/kaniko` executor files. After that change the previously failing Kaniko CI job began to execute. This was a concrete fix to the image/runtime contract, not a change in Nexus permissions.

The next failure appeared at a different boundary: a Docker-configuration file variable was unset when the script tried to copy it. The script could now run, but it did not yet have the registry credentials/configuration delivered in the form it expected. Making an executable available and giving that executable the right credentials are independent accomplishments.

In February, the missing-executor symptom returned after server restarts. The intended image showed `/kaniko/executor` when examined interactively, while the failing job claimed the path was missing. A missing path in a log was no longer sufficient evidence that the image lacked the file.

The decisive question became: **which Runner, executor and filesystem actually ran this job?**

During a March investigation, the environment reported a hostname and filesystem consistent with a different execution context from the Kubernetes job image I expected. The Runner identifiers also did not match the intended setup. The Helm values did not pin jobs with the expected `runners.tags` / `runUntagged` policy, leaving selection ambiguous. That was a strong reason to investigate Runner assignment rather than rebuild Kaniko yet again.

I do not have a preserved comprehensive audit proving every subsequent job landed on the correct Runner. The evidence supports an earlier wrapper-image fix **and** a later Runner-selection/environment investigation. Those two episodes should not be collapsed into one permanent "Kaniko binary missing" root cause.

| What I saw | What I had to identify first | Supported outcome |
| --- | --- | --- |
| `sh` missing | Whether Runner could execute a script in this image | Shell-capable wrapper got the job running |
| `/kaniko/executor` missing after restart | Actual Runner, executor, container and mounts | Environment mismatch investigated; universal fix not proved |
| Empty Docker-config file variable | Whether a File-type CI variable existed in that job | Missing runtime configuration identified |
| Push fails after build starts | Destination TLS, credential and repository scope | Separate registry investigation needed |

GitLab's Kubernetes-executor documentation and Kaniko's debug-image guidance explain why an image suitable for executing a binary does not necessarily satisfy a CI runner's shell contract. These are general mechanisms; the actual Runner selection remains an operational fact to check on each failed job.

## An x509 error can occur before Kaniko exists

I encountered registry-certificate problems at more than one stage. It was tempting to say "Kaniko does not trust the CA" whenever a CI job contained an `x509` error, but that diagnosis only makes sense if Kaniko had actually started and was making the connection.

In one March failure, the x509 verification error appeared while Kubernetes was **pulling the CI job image**, before the Kaniko script had begun. A certificate added inside the Kaniko image could not help: the node's container runtime needed to pull that image in order to start the container.

A different connection occurred after the build began, when Kaniko pushed the resulting image to Nexus. In that case the **builder container's trust store** mattered. I had addressed a build/push certificate problem by preparing a CA-aware builder image; that did not imply that every K3s node also trusted the same CA.

There was a third caller: a workstation or another machine using Docker to log in, pull or push. Docker maintained its own trust configuration for registry endpoints. An HTTPS connection could fail because the signing root was unknown, or because the certificate did not contain the IP address or DNS name actually used by the client.

I also worked through a certificate-generation issue in which a Java certificate parser rejected duplicate extensions. That reinforced the need to verify the actual certificate chain and Subject Alternative Names rather than assuming a generated keystore was correct. A useful test order was: inspect the certificate and verify its issuer, confirm the requested identity is in the SAN, then test the intended caller. A Docker `/v2/` probe returning `401 Unauthorized` may mean HTTPS reached a protected registry API; an `x509` failure occurred earlier, before application authorization.

K3s documents node-specific registry trust through `registries.yaml`, including a CA file, while Docker clients have their own endpoint-scoped CA mechanism. This is why I would not solve certificate problems by disabling verification globally: it hides the exact trust boundary that is still broken.

## The Nexus homepage was not the registry protocol

Nexus had another distinction that was easy to miss. The management UI and Docker Registry API could be exposed through different connectors and ports. I wanted a small, controlled external surface: one route for the UI, another for the Docker API, and restricted node exposure rather than every Kubernetes node accepting all traffic.

This led me through Helm Service configuration, connector listeners, NodePort and TCP routing choices. But making the UI load was not equivalent to making a Docker client's `/v2/` request reach the correct repository. A `404` after a proxy or connector change was a reason to inspect the request's destination and URL mapping; an `x509` error pointed at a different, earlier trust problem.

I also investigated a case where one repository could be pushed to while another returned `401`. Reaching Nexus proved the network path was alive, but it did not establish that the active credential had the right repository-scoped privileges. A working username does not imply authorization for every hosted Docker repository or every image path.

I did not retain final, independently verified push/pull results for every connector, repository and client. The useful success criterion would have been a complete **tag → login → push → digest verification → pull** for the specific endpoint, then the same test from the actual Kubernetes nodes. The observed error codes alone do not constitute that test.

The site’s earlier [service-integration record](/projects/rokaf-self-hosted-services-integration/) covers the UI/API distinction more briefly. Here it matters because a pipeline can be correctly built and still have no usable artifact destination.

## MinIO could hold blob data without becoming Nexus's entire state

I wanted Nexus binary artifacts on a shared S3-compatible store while its application state remained on persistent storage. The Helm values needed to enable persistence; the chart also brought operational helper-image dependencies such as `bashImage` that had to be available inside the isolated network.

For the object-store integration I enabled **path-style S3 addressing** against MinIO. The observed endpoint then resolved correctly, and objects were created in the chosen bucket under a prefix incorporating the Blob Store's name. This was real evidence that Nexus wrote objects through the configured MinIO path.

It was not evidence of a fully tested **Nexus high-availability** design. A functional S3 Blob Store does not make Nexus metadata, scheduled tasks, database state and connector configuration independently recoverable. Moving the binary payload changes its storage failure domain; it does not automatically make every other part stateless.

Nor did I establish by benchmark that MinIO-backed blob reads were faster than local HDD in this specific deployment. Storage latency, concurrency, object size, erasure coding and network overhead mattered. I was constrained to hardware with spinning disks for that placement, so "use a fast SSD" was not an available shortcut.

The practical question became what to restore together. If the object store survived but Nexus metadata was inconsistent with it, the registry could still fail to serve an artifact. Conversely, a healthy UI and metadata database would be of little use if the Blob Store were inaccessible. I treated `persistence.enabled`, the object store and the Docker connector as three different operational contracts.

## The cycle I could not restart my way out of

A later incident put these dependencies in a more uncomfortable light. When Nexus and CoreDNS were unavailable at the same time, some workloads encountered image-pull failures during recovery. I had expected `imagePullPolicy: IfNotPresent` to help, but that policy only allows reuse when the requested image is actually present and usable **on the node trying to start the Pod**. It is not a shared-cluster cache, an artifact backup or a guarantee after rescheduling.

The failure mode is straightforward:

- A node needs a critical platform image.
- The configured image reference points to Nexus.
- Nexus is unavailable, and the normal DNS/registry path may also be unavailable.
- Nexus's own recovery Pod or its dependencies may need an image from that unavailable source.

I evaluated keeping a **small, independent inventory of recovery images**, using node-local preloads or a bootstrap source that did not depend on the failing Nexus instance. K3s supports importing images into its containerd store, but the exact cache placement and recovery procedure still need to be tested on the actual nodes. I also considered a separate minimal registry; placing that registry inside the same cluster without independently available dependencies would just move the cycle.

This is a dependency **cut**, not automatically a high-availability solution. A second registry that depends on the same DNS, storage or control-plane failure domain may still be unavailable when needed. I cannot claim that the complete alternative recovered the cluster in a simulated simultaneous failure; the preserved evidence establishes the outage symptoms and the architecture I evaluated in response.

## I began checking where the failure occurred before choosing a fix

The incidents changed the order in which I investigated a failed CI run:

| Observation | First boundary to inspect | What it does **not** prove |
| --- | --- | --- |
| `sh` unavailable in a Kaniko job | Actual job image / Runner script contract | Nexus permissions are broken |
| `/kaniko/executor` missing although image contains it | Runner selection, runtime filesystem and mounts | Binary missing in every environment |
| `x509` while pulling job image | K3s node/containerd and registry certificate | Kaniko itself has started |
| `x509` during Kaniko push | Builder CA and endpoint certificate identity | Every node trusts the same CA |
| `401` from Docker registry | Auth token, scope, repository permissions | Wrong password is the only cause |
| `404` on registry route | Connector/path mapping and requested API | Nexus metadata is necessarily lost |
| UI and object writes work | Administrative path and configured S3 blob access | Docker push/pull and recovery have passed |
| `IfNotPresent` but pull still fails | Exact image presence on selected node, DNS, registry path | Cluster-wide cached images exist |

If I were packaging the system again, I would preserve the identity of the **source revision, builder image, base images, internal package mirror, registry certificate, published image digest and the manifest that consumes it**. That is a reproducibility inventory, not a claim that all of those identities were automatically promoted by the GitOps controller.

A build succeeding does not automatically update desired state. The companion [offline GitOps record](/projects/rokaf-offline-gitops-delivery/) examines that separate promotion and reconciliation boundary.

During the later Nexus/CoreDNS outage, some Pods could not retrieve the images required for restart. That made cached-image coverage and independent access to recovery images specific operational requirements, separate from the earlier Kaniko runtime and registry TLS fixes.
