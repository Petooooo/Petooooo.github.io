I wanted a pipeline in which a change could move from Git to an image in our private registry and finally into an internal service **without relying on a successful call to the public internet**. This sounds like ordinary CI/CD until the environment cannot simply fetch a missing base image, package, certificate chain, or build tool.

The platform had a GitLab Runner, an internal Nexus3 service and K3s workloads. I was responsible for making their interactions actually work. My first concern was **reproducibility**: an image that built yesterday must not fail tomorrow merely because an upstream `latest` tag moved or a public package repository disappeared.

## 1. Why the usual build recipe was not enough

In a connected environment, a Dockerfile can fetch its base image and the package manager can resolve dependencies as needed. In a restricted network, every dependency becomes an explicit **supply-chain input**. I therefore approached image building in separate stages: prepare compatible source images in a connected setting, transfer them through an approved path, mirror them internally, and build against fixed image references.

I preferred **fixed tags or digests** over `latest` for the parts that would otherwise be difficult to reproduce. A build's success depends not only on the Dockerfile but on the builder image, CA trust, package mirror content and destination registry privileges.

| Component | The question I asked |
| --- | --- |
| Runner | Which Kubernetes executor and job image actually starts the work? |
| Kaniko | Is `/kaniko/executor` present, executable and compatible with the job entry point? |
| Base images | Is every stage reachable from an internal source? |
| Package manager | Does the internal mirror contain the precise packages the lockfile requires? |
| Nexus3 | Can the job authenticate **and** push to the intended hosted repository path? |
| Runtime | Can K3s nodes verify certificates and pull the final image? |

## 2. The build environment that looked correct but was not

At one stage I encountered a job image that appeared suitable for Kaniko but did not expose the expected `/kaniko/executor` at runtime. It was easy to assume that the pipeline syntax or the runner itself was wrong. Instead, the immediate diagnostic question was much smaller: **what binary and entry point were actually present in the container?**

I inspected the packaged executor path and image behavior, then adjusted the build image packaging and entry-point handling before focusing on registry pushes. This was a useful reminder that an orchestration error may originate **inside the image**, before any infrastructure-level permission is involved.

A related dependency problem appeared with a frontend build: a workspace-based Storybook image failed with errors such as `storybook: not found` and `spawn ENOENT`. The first useful distinction was between an unavailable network mirror and dependencies that had simply **not been installed into the image's effective workspace**. Those require different fixes; retrying the registry would not restore a missing local CLI.

## 3. A 401 response was not necessarily a bad password

Later, one repository pushed images while another failed with a **401**, despite similar CI configuration. Because the transport reached the registry, I treated that as different from a TLS handshake failure.

I compared the successful and failing contexts across **destination path, job variables, builder Docker configuration and repository permissions**. Nexus3 has separate concepts of identity, Docker registry token exchange, and repository-scoped grants. A credential can be valid but lack the correct push action for one image path.

That distinction was especially important when the target image name included nested repository components. Instead of immediately granting broad administrative rights to make the error disappear, I considered which token, path and repository permission were actually being exercised. The investigation also taught me to avoid printing secrets while checking which variable was effective in a job.

## 4. TLS and node placement were separate failure planes

Internal HTTPS required the clients involved in build and deployment to recognize the private CA and the identity on the certificate. The builder, container runtime and developer workstation can have different trust stores. An image push failing on certificate verification is not the same problem as a registry authorization error.

I also observed that a pipeline could behave differently depending on **which worker node received the job**. Connectivity and policy at the host layer mattered even though the YAML was unchanged. Node placement was useful to isolate a failing environment; it was not a substitute for understanding the connectivity asymmetry.

## 5. The bootstrap problem that made me rethink recovery

A registry hosted by the same platform it supplies can become a circular dependency: the registry service needs an image to recover, but the only image source is the unavailable registry. I investigated separating a **minimal bootstrap source** from the general artifact supply so essential services would not depend exclusively on themselves.

The design decision is subtle: more replication of a single dependency is not the same as removing that dependency from the **recovery path**. This led me to think about what must already exist before the first job, first container pull or first rebuild can succeed.

## 6. Reconstructing the actual dependency graph

The most useful exercise was to ask what **must already be working** before a new image can be built and deployed. In a connected environment that dependency graph is often hidden by package registries and public image mirrors. In a closed network it becomes an operational requirement.

| Artifact | Producer/source | Needed by | Failure if missing |
| --- | --- | --- | --- |
| Builder image | Approved image preparation process | GitLab Runner job | The job cannot start its own build tooling |
| Kaniko executor | Content of the actual builder image | Build script | Command not found / non-executable path |
| Base image | Private image repository | Dockerfile stage | Build cannot resolve the parent layer |
| Dependency packages | Internal package mirror/cache | Application build step | Tool or package unavailable |
| Internal CA trust | Approved certificate distribution | Builder and runtime | TLS handshake or verification failure |
| Registry authorization | Nexus repository policy and job credential | Image push | Token exchange or push denied |
| Target image | Completed CI job | K3s runtime | Image pull or startup failure |

The table also shows why a successful job on one runner could not prove that every worker node or runtime had the same dependencies available.

### Why I separated packaging from authorization

The Kaniko executor issue was resolved by inspecting **the actual contents and entry point of the image**, not by expanding CI permissions. I treated the missing executable as a packaging defect. Later, registry authorization problems belonged to another layer entirely.

This sounds obvious in retrospect, but without a dependency graph an operator can spend hours changing tokens when the binary itself does not exist—or rebuilding images when the request actually reached Nexus but was denied.

## 7. A reproducibility checklist

For a representative, non-sensitive CI pipeline I would record:

1. **Source revision:** the Git commit or reproducible source package.
2. **Builder identity:** exact image reference or digest and known executor path.
3. **Dependency closure:** all base stages, OS packages and application packages resolvable internally.
4. **Credential scope:** the job can perform only required registry actions.
5. **Trust chain:** the builder trusts the registry certificate and the runtime separately trusts the image source.
6. **Result:** image digest and the workload revision that consumed it.
7. **Recovery input:** a minimal set of images/configuration that exists independently of the service being recovered.

This is a **design checklist derived from the experience**, not a published copy of the actual operational pipeline.

## 8. Why a registry error cannot be one diagnosis

| Symptom | Likely boundary | Evidence I would request |
| --- | --- | --- |
| `/kaniko/executor` missing | Builder image packaging | Executable existence and image metadata |
| Package manager cannot find a tool | Dependency installation/mirror | Lockfile, workspace and installed packages |
| TLS unknown issuer | Trust root | Presented certificate and trusted issuer set |
| Certificate name mismatch | Endpoint identity | Requested host/IP versus SAN |
| Registry returns HTTP 401 | Authentication/authorization | Token exchange, repository path and scoped action |
| Some runners work, others fail | Node/network/environment | Controlled placement comparison |
| Registry recovery depends on itself | Bootstrap architecture | Minimal dependency path without registry |

For the repository-specific 401 cases, I would not label every instance fully resolved unless the exact repo permissions and active job credentials had been correlated. **Reaching the registry, authenticating successfully and being authorized to push are three distinct milestones.**

## 9. What I would measure in a future isolated lab

A small testbed could deliberately remove one dependency at a time and record whether a clean build succeeds. The controlled variables would include builder digest, base image availability, CA trust, write permission and runner placement. A comparable result should specify which dependency was changed, how the job failed, and whether it recovered after restoring that dependency.

I would use this to test a concrete reliability question: **Can an essential platform component be restored without depending on the same component's own repository endpoint?**

That question is more durable than any individual image name or CI tool version.

## What changed in my approach

I stopped treating an image-push failure as one generic CI problem and instead classified **packaging, package availability, authentication, authorization, TLS trust, node connectivity and bootstrap availability**. That made the diagnostic sequence more disciplined and made the overall delivery process easier to reason about.

The public record does not include internal endpoints or production credentials. A few repository-specific 401 cases were still being narrowed down when I recorded them; where I had a confirmed fix I distinguish it from cases where I had only isolated the likely layer.
