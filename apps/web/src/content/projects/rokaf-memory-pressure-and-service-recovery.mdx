In March, one of the K3s hosts became almost unresponsive in the early hours of the morning. Memory use was approaching 100%, and even basic inspection was painfully slow. I ended up rebooting the host. What I wanted to know afterward was which process had consumed the memory. But the previous boot's journal was no longer available: `journalctl --list-boots` showed only the current boot.

I had no preserved kernel OOM-killer event from the incident. That did **not** establish that no OOM event had happened. Severe memory pressure and slow reclaim can make a machine almost unusable before the kernel chooses or kills a process. With the earlier journal missing, I could not reconstruct which of those conditions came first.

I investigated installing earlyoom as a guard against another prolonged stall. The first definite failure I encountered, however, was not the host's memory accounting. It was the **earlyoom systemd service itself**. Later incidents added a different problem: earlyoom had selected a process to terminate, but that process's memory footprint did not explain the spike in host-wide usage.

These are observations from different dates, not a single recovery sequence.

## A full memory graph did not establish an OOM event

The host had been severely delayed, but overall memory utilization alone could not explain the behavior. Linux uses otherwise available RAM for reclaimable page cache, and the meaningful amount of available memory is not simply total minus used. When available pages are scarce, reclaim and swap I/O can produce very high latency even without a preserved kernel OOM event.

The observations I needed at the time were `MemAvailable`, `SwapFree`, the rates of swap-in and swap-out, reclaim and pressure stalls, and the ownership of anonymous and kernel memory. I did not retain that synchronized snapshot before rebooting the host.

Other host checks also showed swap close to fully occupied. Swap *occupancy* and continuing swap *traffic* are different measurements. A high used-swap figure does not by itself prove that the host was actively thrashing at that moment. I would need the page activity and pressure measurements from the same interval to make that claim.

The recorded March result is therefore narrow: **the machine became extremely slow as memory utilization approached its limit, and I rebooted it**. The original consumer, kernel OOM activity, and extent of reclaim pressure were not conclusively established.

## earlyoom 1.9.0 started manually but failed under systemd

I compiled earlyoom 1.9.0 from source for the host. The extracted source had no Git metadata, and the build environment lacked `pandoc`; the logs nevertheless showed that the executable was compiled.

While configuring a systemd drop-in, the service entered a restart loop. Its status included exit code **`16`**. Another retained error was:

`Failed to stop EXEC spawning /usr/local/sbin/earlyoom: No such file or directory`

Running `earlyoom -d` manually did work. The `-d` option is **debug logging**, not “daemonize”; the direct invocation did not reproduce the environment variables, executable path, service manager directives or effective command-line options used by systemd.

The [earlyoom 1.9.0 manual](https://sources.debian.org/src/earlyoom/1.9.0-1/MANPAGE.md) defines exit code `16` as **invalid parameters for the swap threshold**. That makes the actual swap-related arguments in the service invocation an important place to inspect. It does not tell me the exact malformed argument from the retained logs alone.

The `Failed to stop EXEC spawning` message describes another failure boundary: systemd could not find the executable named by a **stop operation**. It is evidence about the configured executable path, but it cannot by itself establish why an earlyoom process exited with code `16`. I should not merge the two errors just because they were visible while debugging the same service.

At the time I reviewed the `ExecStart` override under `/etc/systemd/system/earlyoom.service.d/override.conf` and the `EARLYOOM_ARGS` supplied from `/etc/default/earlyoom`. The effective unit, all drop-in fragments and the command actually received by the binary needed to be compared. I also considered returning to the supplied service unit rather than maintaining an unnecessarily broad override.

I do not have a preserved final unit and long-running service test proving that every startup and restart problem was eliminated. A manual foreground process and a stable, supervised system service are different checkpoints.

## A running earlyoom process was not a guarantee against stalls

By default, earlyoom checks **available memory and free swap together** against configured thresholds. When both fall below the configured limits, it may send `SIGTERM`; at lower thresholds it can escalate to `SIGKILL`. It is a userspace monitor with its own victim-selection logic, separate from the kernel's OOM killer and memory-cgroup limit enforcement.

That makes the effective unit configuration important. Seeing a service named earlyoom is not the same as verifying that it is running continuously with the intended thresholds. The real `ExecStart`, effective environment, swap options and actual signal logs matter. The `-r` flag changes how often periodic memory reports are printed; it does not set the frequency of the low-memory checks themselves.

In July I searched the surviving logs for earlyoom `SIGTERM` or `SIGKILL` entries and kernel OOM events, but the search returned no matching records. That established only the absence of those messages **in the retained and searched interval**. It did not prove that the host never experienced memory pressure or that the daemon had prevented every incident.

## An earlyoom victim did not explain the later memory spike

In August I examined a separate sharp rise in host memory use: the reported level climbed from roughly one fifth of the system toward saturation. Prometheus data covered the interval, but the Kubernetes container metrics I inspected did not show a corresponding jump. The application containers in those charts continued to look near their usual levels.

I did find an earlyoom victim record. The selected process had a reported **`VmRSS` of approximately 608 MiB**. That number was far smaller than the host-wide change. It did not account for the increase by itself. It also did not prove earlyoom selected an incorrect victim.

By default, earlyoom evaluates processes using an **OOM score**, not simply by sorting every process by RSS. Its `--sort-by-rss` option changes that choice. The RSS value logged for one selected process is not a record of every anonymous page, shared-memory allocation, page-cache entry, kernel allocation or other process and container on the machine.

A K3s container chart also does not necessarily account for all consumers on a Linux host. Host processes, other container runtimes, shared memory and kernel memory can sit outside the chart's selected series. To narrow the discrepancy I needed time-aligned host metrics such as `AnonPages`, `Shmem`, `Cached`, `Slab` and `SUnreclaim`, plus the relevant cgroup's `memory.current`, `memory.stat` and `memory.events`. The latter counters would help distinguish reclaim pressure or cgroup OOM activity from an earlyoom userspace kill.

Those measurements were avenues for investigation, not a completed attribution. The evidence supports **a host-wide spike, an earlyoom process selection, and a mismatch with the sampled Pod metrics**. It does not identify the actual source of the host's extra memory consumption.

## Memory Pressure Evidence Capture

The difficulty in these cases was not finding a single command to reduce memory use. It was having enough evidence from **before** the system became unresponsive or was rebooted.

| Evidence source | What it could clarify | Missing from the retained incidents |
| --- | --- | --- |
| Host `/proc/meminfo` | Available RAM, swap and memory composition | Synchronized accounting of the full rise |
| `vmstat` and memory PSI | Swap traffic, reclaim and time stalled under pressure | Pressure and latency at the failure instant |
| Kubernetes and non-Kubernetes cgroups | Workload ownership and memory event counters | Source of the unaccounted host usage |
| Effective earlyoom systemd unit | Actual executable, thresholds, restart behavior | Verified final configuration and stability |
| Kernel and earlyoom journals | Kernel OOM events and userspace process kills | Pre-reboot history and complete event chain |

I would rather preserve compact periodic measurements and the service's effective configuration than generate artificial pressure on a production host just to reproduce an OOM.

In March I encountered **host memory saturation, severe slowdown and a reboot**; during earlyoom 1.9.0 setup I traced a systemd exit status `16` and an executable-path problem while manual execution worked. A later log search in July found no retained kill, and August logs recorded an earlyoom victim during another host-memory spike. The initiating process or cgroup behind that spike remains unidentified, making time-aligned host and cgroup memory capture the next priority.
