GPU workloads introduced a familiar-looking but difficult trade-off: **maximize utilization** or **preserve predictable behavior under load and failure**. In a shared on-premises system, both goals matter, and a device plugin's ability to advertise resources does not automatically settle the question.

I worked on AI service placement in K3s and considered **whole-GPU assignment, device-plugin behavior, time-slicing and MIG where supported**, as well as how services should behave when a GPU host becomes unavailable.

## 1. A GPU request is only as meaningful as what Kubernetes advertises

Scheduling decisions depend on resources visible to the cluster. I investigated issues where **GPU Operator and Node Feature Discovery labels/resources were not appearing as expected**. The existence of a physical GPU did not mean that Kubernetes correctly recognized a schedulable accelerator.

The useful sequence was to separate hardware/driver recognition from device-plugin registration, node labels, Pod resource requests and application startup. Jumping directly to the inference container could misidentify an infrastructure discovery issue as a model bug.

## 2. Full GPU versus sharing: what is actually isolated?

It is tempting to see a GPU as a pool of interchangeable fractions. In practice, **time-slicing**, **MIG** and **whole-device allocation** have different guarantees.

| Choice | What made it attractive | What I needed to question |
| --- | --- | --- |
| **Whole device** | Predictable access to device memory and execution | Lower consolidation and possible idle capacity |
| **Time-slicing** | Higher apparent concurrency for tolerant workloads | Shared memory and contention; logical slots are not physical partitions |
| **MIG (compatible hardware)** | Hardware-backed partitions with stronger boundaries | Availability, partition sizes and model memory requirements |
| **Multiple replicas** | Service continues if one workload or node fails | Where remaining capacity comes from and how requests are rerouted |

Some inference workloads require a substantial working set or show latency variation under contention. For those, using the entire GPU can be the simpler, more reliable choice even if the utilization chart looks less impressive.

## 3. Failover versus graceful degradation

The second question was what happens when a host with an active GPU service disappears. A replica can keep the endpoint reachable, but if one of two serving paths is gone, the remaining deployment may have **less throughput and higher tail latency**.

I considered **degraded-capacity service** as a more realistic objective than claiming full-capacity, zero-interruption failover. This led me to think about placement, how load balancing discovers healthy replicas, and the capacity margin needed to absorb a failure.

## 4. Why placement constraints were not a long-term solution

When a workload runs only on particular nodes, an affinity or selector may isolate an immediate problem. But restrictive placement can make recovery harder by leaving fewer choices after a node failure. With GPU workloads, compatibility sometimes requires explicit placement; the trick is to avoid accidentally encoding a temporary diagnostic workaround as a permanent availability policy.

The same problem appears in CPU/memory and storage scheduling: more operational constraints can mean less freedom for the scheduler.

## 5. The questions that remain open

I still had verification work around certain hardware-discovery labels and the exact behavior of possible GPU-sharing configurations. I did not turn those evaluations into claimed production benchmark results.

The direction I want to pursue is clearer: performance and isolation claims should come from **device memory behavior, measured latency and actual failure testing**, not the fact that a Kubernetes manifest contains a GPU resource request.
