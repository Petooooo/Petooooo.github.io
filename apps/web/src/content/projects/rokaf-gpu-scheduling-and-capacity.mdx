When I started placing AI workloads on a shared Kubernetes cluster, the first number to look at seemed obvious: GPU utilization. But an idle-looking device is not necessarily wasted capacity. A model can reserve most of its memory while using relatively little compute, and a second model can fail to start even though the utilization graph looks quiet.

I configured GPU sharing with time-slicing and spent time separating two problems that are easy to conflate: **whether Kubernetes sees a schedulable resource** and **whether the application can actually run within its memory and latency budget**. I also evaluated whole-GPU assignment and MIG where the hardware supports it. Those are different ownership models, not successive optimization steps.

This was one part of the larger system I built: **a centrally managed GPU platform with KAI Scheduler and JupyterHub deployed and operating in the internal environment**. The [central GPU platform record](/projects/rokaf-central-gpu-platform-kai-jupyterhub/) covers scheduling and user notebook access; this article concentrates on the device-sharing and capacity choices.

## A logical GPU slot is not a GPU partition

A Kubernetes device plugin advertises extended resources to the scheduler. With ordinary whole-device allocation, a GPU request generally corresponds to exclusive placement on the advertised device. With time-slicing enabled, the plugin can advertise multiple *replicas* of one physical GPU as allocatable units.

That increases the number of Pods that the scheduler can place. It **does not multiply physical SMs or device memory**. A request for one replicated GPU does not reserve a fixed fraction of VRAM, guarantee a percentage of compute time, or give the Pod a separate fault domain.

This distinction mattered whenever I had to decide whether a workload was small enough to share a card. The right question was not simply, "Can another Pod be scheduled?" It was, "What happens when both processes allocate their peak working set and execute kernels at the same time?"

## Three allocations that solve different problems

### Whole-device assignment

A single workload owns the device allocation. It has the largest available pool of memory and compute capacity, and it does not compete with another Pod that has been assigned the same GPU through the time-slicing mechanism.

That simplicity is attractive for models with large weight sets, variable KV-cache growth or strict response-time expectations. The cost is consolidation: an application might reserve a GPU while leaving much of its compute capability idle. Dedicated placement also does not eliminate other failure modes such as driver faults or host loss.

### Time-slicing

Time-slicing multiplexes workloads onto the **same physical GPU**. The additional resource advertisements act like admission opportunities, not hard quotas. The processes share the GPU memory pool, and runtime execution is interleaved by the device scheduling machinery.

That distinction creates two independent risks:

- **Memory contention:** separately scheduled Pods can each allocate memory from the same physical pool. A configuration with several replicas does not imply that each receives one equally sized memory slice.
- **Performance and fault interference:** execution and memory-bandwidth contention can affect tail latency, and the replicated workloads are not hardware fault-isolated from one another.

Time-slicing is useful when several relatively small, bursty workloads would otherwise leave an accelerator idle. It is a poor substitute for predictable memory isolation. The workload mix, not the number of advertised replicas, determines whether it helps.

### MIG, on supported GPUs

Multi-Instance GPU (MIG) changes the physical partitioning model. Supported devices can expose GPU instances with specified compute and memory resources, including stronger isolation of their memory-system paths. Unlike time-slicing, one instance cannot simply consume the other instance's allocated memory.

That predictability comes with constraints. MIG support depends on the actual accelerator and its mode; available instance profiles impose discrete sizes. A workload whose memory footprint exceeds a profile cannot be made to fit by merely asking the Kubernetes scheduler for another logical replica. Partitioning can also strand capacity if demand is not aligned with the available shapes.

I treated MIG as a **hardware-dependent design alternative**, not as something I could claim to have deployed on every GPU. The record of implementing time-slicing and the evaluation of MIG must stay separate.

| Question | Whole GPU | Time-slicing | MIG on compatible hardware |
| --- | --- | --- | --- |
| Does the Pod share the same physical compute resource with other allocated workloads? | Not through this allocation | Yes, interleaved on one device | Separated into hardware instances |
| Is GPU memory hard-partitioned between the allocations? | No co-tenant in this allocation | **No** | **Yes, per instance** |
| Is there hardware-backed isolation between co-tenants? | No co-tenant in this allocation | **No** | **Yes, within MIG's specified boundaries** |
| Can small models consolidate onto one device? | Only if another mechanism is used | Yes, with interference risk | Yes, if a profile fits and the GPU supports MIG |
| What capacity can be guaranteed from the resource request alone? | The allocation, not an end-to-end latency SLA | No proportional compute or VRAM share | Instance resources, not an application latency SLA |

## The placement decision was really a workload decision

I found it more useful to classify workloads by their operating requirements than to rank GPU-sharing modes as universally better or worse.

| Workload characteristic | First option to evaluate | What could change the decision |
| --- | --- | --- |
| Large model weights or unpredictable KV-cache growth | Whole device | A verified smaller model/profile or stricter admission control |
| Several lightweight, bursty services | Time-slicing | Combined memory peak, queueing and interference |
| Independent tenants requiring strong resource boundaries | MIG, if supported | Available profiles and per-instance capacity |
| Service must remain available after a GPU host is lost | Multiple eligible serving paths with spare capacity | Headroom, routing health checks and degraded throughput policy |
| GPU is physically present but not advertised to Kubernetes | Repair discovery/registration first | Sharing mode cannot fix a missing device-plugin resource |

A successful scheduling event is only the first gate. A representative inference request must still fit in memory, initialize successfully and meet the intended response-time budget.

## The earlier problem: discovery and scheduling were mixed together

I also encountered GPU Operator and Node Feature Discovery behavior where expected labels or resources were missing or inconsistent. The debugging sequence could not start with the model server: if the node never advertises a suitable resource, the inference process may never run.

I separated the investigation into these boundaries:

**Hardware recognition.** Is a compatible device visible to the driver and container runtime?

**Device plugin registration.** Does Kubernetes advertise the expected extended resource and allocatable count?

**Node metadata.** Are node labels or feature-discovery rules missing, and are workload placement constraints depending on those labels?

**Pod allocation.** Is the resource request valid for the advertised type, and does the container actually receive device access?

**Application behavior.** After allocation, can the model load and serve representative requests without exhausting memory or violating latency expectations?

A label problem, a device-allocation problem and a model-memory problem can produce similarly unhelpful symptoms at the application layer. They require different evidence and different repairs. My separate [GPU discovery investigation](/projects/rokaf-gpu-discovery-open-investigation/) retains unresolved observations rather than assigning every symptom to one cause.

## Why I did not equate more schedulable replicas with better capacity

Consider a physical GPU with a fixed amount of memory. The device plugin may advertise additional replicated allocations, but the combined worst-case memory demand of all admitted workloads can still exceed that one pool. It is possible to raise the number of Pending Pods that become Running and simultaneously lower the fraction of user requests that complete successfully.

Compute contention is different. Two models may individually fit in VRAM and still interfere with one another's execution and memory bandwidth. In interactive serving, that often matters most at the tail of the latency distribution, not at average GPU utilization.

I would therefore evaluate sharing against four budgets rather than one:

- **Resident memory:** model weights plus maximum observed runtime workspace and cache growth.
- **Compute and memory-bandwidth contention:** how co-located workloads change actual service behavior.
- **Tail latency and errors:** p50, p95, p99 and out-of-memory or initialization failures under a controlled workload mix.
- **Failure headroom:** whether remaining healthy devices can accept traffic after one serving path becomes unavailable.

This is an evaluation framework, not a claim that the military environment produced a publicly reportable benchmark. I have not retained a sanitized set of comparative throughput or latency results, so the article does not assign invented percentages to time-slicing or MIG.

## Availability means having somewhere useful to fail over

Replicas can preserve an endpoint but not necessarily its normal capacity. If one GPU-backed instance disappears, the remaining serving paths may handle a larger share of requests, and their queues and tail latencies may change. A scheduler may be able to place an additional Pod while that Pod has insufficient usable device memory to load the model.

The design question I returned to was: **what service level is acceptable when capacity is degraded?** For some workloads, rejecting excess jobs is preferable to allowing queues to grow without bound; for others, a slower response may be acceptable. Either decision must be explicit.

That trade-off also affected placement constraints. Pinning an application tightly to one class of nodes can repair a short-term compatibility problem while making the system less resilient to a later node failure. I tried to keep temporary discovery workarounds distinct from long-term availability policy.

| Work | Evidence boundary |
| --- | --- |
| Shared GPU resource configuration using time-slicing | **Implemented/configured** as part of the cluster work |
| GPU Operator, NFD and resource-advertisement troubleshooting | **Observed and investigated**; some root-cause questions remained open |
| Whole-device allocation for capacity reasoning | **Compared as an option**; not a published workload benchmark |
| MIG profile selection and isolation analysis | **Evaluated alternative** conditional on GPU support; not claimed as universally deployed |
| Repeated, controlled latency/throughput comparison among all three policies | **Not publicly verified** |
| Zero-interruption failover with full performance after host loss | **Not claimed** |

I configured time-slicing and evaluated MIG on supported hardware as a different allocation model. Choosing between them requires measured peak VRAM use, workload interference and latency; a larger advertised replica count does not provide those measurements.
