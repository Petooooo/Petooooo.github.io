When an internal service stopped responding from a Pod, CoreDNS was an obvious component to suspect. Some Pods had trouble reaching DNS or a Service virtual IP, and startup operations that depended on those paths could fail. Other access paths appeared to behave differently. From a user's perspective, the result was simply an unavailable service.

The host state was harder to interpret. **A Flannel interface was up, routes to Pod networks were present, and Service-related NAT entries existed.** Those observations did not show the packet traversing the rules, reaching a ready CoreDNS endpoint or returning to the caller. I could see pieces of the network configuration without proving that the particular request had crossed them.

I also investigated intermittent reachability concerns involving MetalLB VIPs. But an external client reaching a LoadBalancer address and a Pod sending a DNS query to a ClusterIP are not the same request path. I did not have synchronized evidence tying the two symptoms to one cause, so I kept their investigations separate.

## The DNS request failed; the interface still existed

The retained notes describe failures involving DNS or Service-IP access from some Pods. I inspected Flannel, local Pod routes and NAT rules related to Kubernetes Services. The interface was up and the rules were present, yet that did not settle whether the DNS query had reached its intended destination.

An interface being UP says something about its local state. It does not verify cross-node encapsulated traffic, the host firewall's forwarding decision or the return path. Likewise, a Service NAT rule being installed does not show that a packet matched it, selected a working EndpointSlice address or completed a round trip.

At one point, the troubleshooting included ICMP attempts against the DNS Service's virtual IP. That was not a reliable DNS acceptance test. A Kubernetes ClusterIP is a virtual destination for a Service's configured protocols and ports; it does not promise an ordinary host's ICMP echo behavior. **A failed ping to a DNS ClusterIP cannot by itself establish that UDP or TCP DNS queries are failing.**

This was not evidence of one broken CoreDNS instance. It was evidence that I needed to separate the resolver's behavior from the Service datapath carrying the resolver request.

## Was CoreDNS unable to answer, or unable to receive the request?

For an affected Pod, the most useful comparison would be two DNS queries carrying the same question and using the intended protocol: one to the DNS Service's ClusterIP and another to an appropriate CoreDNS Pod endpoint. The queries would need to originate from the same network context and be recorded close together in time.

If the direct endpoint answered but the Service-IP query did not, I would investigate Service translation, endpoint selection, filtering and return traffic before blaming DNS application logic. If both failed, the direct Pod datapath and resolver process would need attention. Repeating the same test from a known unaffected Pod could then reveal whether the problem depended on its source node.

I did not retain a complete paired set of these measurements from the original incident. They are **follow-up tests**, not results I can retrospectively mark successful or failed.

| Comparison to record | What it could distinguish |
| --- | --- |
| Affected Pod → DNS ClusterIP, UDP/TCP port 53 | Whether the actual DNS Service path completes |
| Same Pod → suitable CoreDNS endpoint, same query | Whether bypassing Service translation changes the result |
| Affected and unaffected Pods → same destination | Whether the failure depends on the source or node |
| EndpointSlice readiness and a real DNS response | Whether a listed endpoint can serve the request |
| Service rule counters and packet observations at the failure time | Whether a specific forwarding path is actually traversed |

A failing DNS name resolution and a failing network connection can also coexist. The test should record which resolver answered, what answer it returned, and whether the client then reached the returned destination. An application log that only says “connection timed out” does not make that distinction for me.

## NAT entries did not prove which rule handled the packet

Once I saw Service-related NAT rules, it would have been easy to write that kube-proxy was correctly configured and the failure must lie elsewhere. But the host can have a valid-looking rule that was never applied to the affected traffic. Other rules may filter packets after destination translation; connection tracking and source-dependent routing may affect the return leg.

I considered whether `iptables`, the active proxy backend or `conntrack` state could explain the partial failures. A conntrack table at capacity can be relevant to intermittent transport errors, but **the available incident evidence did not establish a measured exhaustion event**. I had no basis to call it the root cause.

Docker and K3s could both manage host-network rules in the operating environment. Their coexistence made rule ownership an important question, but it did not prove that Docker overwrote a particular Kubernetes rule during the DNS incident. Nor would blindly flushing rules or switching CNI implementations count as a validated repair. Such actions could destroy the state I needed to inspect and disrupt unrelated workloads.

The more detailed Pod-IP versus ClusterIP investigation remains a separate local draft while its evidence and public-disclosure boundaries are reviewed. I do not convert that draft's unconfirmed hypotheses into resolved findings here.

## The VIP investigation needed a different set of observations

A MetalLB VIP exposes a Kubernetes LoadBalancer Service to clients outside the Pod-to-Service DNS path. Depending on deployment, MetalLB can advertise an external address using layer-2 ARP/NDP or BGP. The relevant evidence depends on the configured mode and the client's network location.

The notes record concerns about apparently intermittent access through VIPs. They do **not** give me a consistent timeline identifying who advertised the address at each failed request, whether that advertiser changed, or whether the packet reached the receiving node. It would be too strong to say that the VIP repeatedly failed over or that a MetalLB speaker was the proven cause.

Before investigating advertisement changes, I would establish what the client actually experienced. Did name resolution return the expected VIP? Did the client reach a listening TCP endpoint? Did TLS finish? Did Traefik select the intended router? Was an EndpointSlice ready? A successful DNS response for a VIP is not evidence that the VIP is reachable.

There was one **different incident with stronger evidence**. Adding a LoadBalancer Service caused K3s's built-in ServiceLB to create `svclb-*` resources that requested a host port already used by another exposure path. Altering or deleting that Service removed the contention and restored the older path. MetalLB address advertisement and K3s ServiceLB host-port ownership were separate mechanisms. The [ServiceLB host-port case](/projects/rokaf-service-lb-hostport-conflict/) documents that reversible sequence. It does not establish a cause for the other suspected VIP or ClusterIP failures.

## What a restart would and would not tell me

Restarting a DNS or network component might be necessary to restore service, but it also changes transient state: caches, connection tables, timing and controller reconciliation may all shift. A request succeeding afterward demonstrates the endpoint was accessible at the time of the retest. It does not, by itself, identify which earlier component failed.

The missing evidence in this case was a repeated request with a consistent caller and a common timeline for the response, resolver status, Service endpoints and—if external VIP traffic was involved—advertisement and transport reachability.

Adding CoreDNS replicas can improve tolerance to an individual Pod failure when those replicas actually cover independent failure domains. It cannot automatically correct an unreachable upstream resolver, a broken Service forwarding path or a host-level packet drop. I have not recorded a before/after test establishing that a replica change permanently corrected this incident.

## Current status

The surviving observations establish that **some Pods experienced DNS or Service-IP access problems**, and that **Flannel interfaces/routes and Service NAT entries existed** when networking was inspected. They also establish that I investigated separate concerns around VIP reachability. They do **not** establish a shared root cause, a measured MetalLB speaker-failover event, conntrack exhaustion or a reproducible low-level fix.

My next controlled test would compare real DNS queries to a ClusterIP and its backend endpoint from affected and unaffected Pod locations. For external VIP traffic I would record the same client's transport result alongside the advertisement mode, network neighbor or routing state, and ready backends. Those paired observations are necessary before a final cause can be reported.
