I changed a Longhorn volume's desired replica count from **two to one** and watched its status turn **Healthy**. The change looked like a fix, at least on the dashboard. But I could still see two replica objects, and one of them had not returned to a usable state.

Longhorn had become healthy **against the new target**, not against the original redundancy requirement. I could not conclude that it had rebuilt the second copy, that its disk contents were current, or that another disk failure would be survivable.

This was one of several persistent-storage incidents I investigated on a closed-network K3s platform in early 2026. Other episodes involved a replica stuck in `Stopped` despite an existing data file, a node that stopped reporting its status, and an instance-manager process that could not finish stopping while a volume remained `Detaching`. They surfaced as similar application failures, but they were **different incidents on different dates**, not one clean recovery narrative.

I have removed volume sizes, PVC identifiers, hostnames, node numbers, operational disk paths and other internal details. The surviving observations are more specific than a general tutorial but not enough to claim a complete rebuild or full data-integrity audit of every volume.

## The green label measured the target I had just reduced

In late January, one volume was `Degraded`. Its intended replica count was two. One replica was `Healthy`; another was `Unknown`. The UI did not provide the useful replica log view I expected, leaving me with a status whose underlying reason still required investigation.

I reduced the configured replica count to one. The volume promptly changed to `Healthy`, yet the old replica object still appeared alongside the remaining healthy replica. It would have been easy to count the rows and assume two copies were still present. That was not what I had observed.

There were at least three separate variables:

| Signal | Before the change | After the change | What it actually established |
| --- | --- | --- | --- |
| Desired replica count | 2 | 1 | The configured redundancy target changed |
| Volume status | `Degraded` | `Healthy` | Longhorn evaluated health against that target |
| Replica objects shown | One `Healthy`, one `Unknown` | Two objects still visible; one remained suspect | An object being listed did not prove it was a usable, current copy |
| Two healthy data copies | Not demonstrated | Not demonstrated | Original failure tolerance was **not** verified as restored |

During the same investigation, the one known healthy replica showed a `Deleting Snapshot` operation that I had not started manually. I could not establish that the operation caused the degradation or damaged the data. But it did make another destructive intervention harder to justify: the last known good source was busy, and I did not have a validated second source to fall back to.

The more important question was not whether the interface could be made tidy. It was **which data copy I would trust if the next operation failed**.

## A replica file on disk was not a healthy replica

In a related follow-up, the node holding a problematic replica was running, and its replica `.img` file still existed on disk. Nevertheless, Longhorn showed `Stopped`. I enabled **Offline Replica Rebuilding**, but the replica remained Stopped during the observed check.

That was not proof that Longhorn had lost the bytes. It also was not proof that the bytes could be reintroduced safely. File existence does not establish that the snapshot chain is valid, that the bytes match the latest committed writes, or that the engine recognizes this replica as eligible to join the active set.

Offline rebuilding has prerequisites. Longhorn's documentation describes eligibility for detached degraded volumes, a reusable failed replica or schedulable disk candidate, and a ready instance manager. The exact behavior depends on the installed release. Enabling a setting **permits a mechanism**; it cannot make an ineligible replica rebuild instantly.

At another point I tried to delete a replica and Longhorn refused, warning that no other healthy replica was available and this copy might still hold data needed for recovery. The refusal was useful evidence, not an obstacle to bypass blindly. If a replica may be the last recovery candidate, deleting it to remove an error marker can eliminate the only remaining path back to the original data.

My preserved notes do not show a completed rebuild, a valid second copy and a successful byte-for-byte comparison after this operation. What I can confirm is that the file remained, the replica was still Stopped, the offline rebuild setting did not visibly change it, and a deletion guard protected potentially valuable data.

## The data plane and the process manager

The V1 data engine provides a useful model for the file-based replicas discussed here. I have not retained the exact installed engine release, so the following is an explanation of the documented architecture, not a reconstructed instance inventory. The manager reconciles Kubernetes custom resources; the instance manager supervises engine and replica processes. The engine exposes the volume frontend and coordinates I/O to participating replicas. A replica process serves the data represented by its own disk files and snapshot metadata. An instance manager is not itself a copy of the volume.

The engine replicates writes synchronously to its participating healthy replicas. Failed replicas can be excluded from service; the remaining set can continue if the engine can serve I/O. This is not a Raft majority vote per block. The frontend, filesystem and storage flush contracts still matter: an application write returning from the page cache is not evidence that every intended replica has durably stored the data. The [writeback investigation](/projects/linux-disk-io-journaling-writeback/) explains that boundary. In a separate [control-plane record](/projects/rokaf-control-plane-incident-log/), quorum describes voting members rather than replica disks.

Three state dimensions are useful when investigating a failure. Volume robustness describes the controller's assessment of usable redundancy; attachment state describes whether and where the volume is presented; replica process state describes the lifecycle of an instance. For an active V1 engine, the per-replica modes RW, WO and ERR describe its data-plane participation. A rebuilding WO replica is not yet a valid read source. A stopped process can retain its disk files, and a healthy detached volume need not have a running engine. I would therefore compare the desired replica count, the actual engine mode map when attached, replica conditions and current process state rather than count objects in the UI.

## Snapshot dependencies and the rebuilding window

A V1 replica maintains a writable head and a chain of sparse snapshot disk images. An older snapshot can provide a block that was not changed in newer layers. Deleting a snapshot logically and reclaiming its allocated data are distinct operations: purge may have to coalesce data into a surviving layer before the old file can be removed. That can require extra temporary space and I/O. The exact on-disk layout, backing images and metadata must be interpreted with the matching engine version. File size or a file's mere presence does not identify a consistent recovery source.

I tested the dependency principle with a tiny in-memory sparse-block model. A base holds A, B and C; an intermediate layer changes B to B1; the head changes C to C2. The visible result is A, B1, C2. Dropping the intermediate layer without preserving its contribution changes the visible B back to B. Merging its unshadowed changes into the head preserves the result. The model verifies those outcomes, not Longhorn's file format, purge code or crash safety.

In the documented V1 rebuilding process, the engine adds a target in WO mode and establishes a snapshot reference point. The source and destination synchronize required snapshot data while new writes are coordinated with the rebuilding replica. The target becomes RW only after the rebuild completes successfully. Depending on version and available data, full transfer, delta comparison or checksum-based fast rebuilding can reduce transfer work. Fast rebuilding relies on the supported checksum metadata and is not a fresh audit of every block. The original stopped replica did not demonstrate any of these completed checkpoints.

Offline rebuilding can attach a detached degraded volume for maintenance, rebuild it and detach it again. It requires a usable source and an eligible destination; the current documentation excludes faulted volumes. Availability of the option and its precise checks depend on release and engine. Turning the setting on did not establish those prerequisites in the original incident.

A capacity calculation illustrates why I did not regard free disk space as sufficient evidence. If a hypothetical rebuild must transfer 4 TiB at a sustained 100 MiB/s, the transfer alone takes about 11.65 hours. At 50 MiB/s it takes about 23.30 hours. Those are idealized transfer times, not predictions for the original volume. Sparse blocks, snapshot history, new writes, compression, local reuse and contention can change the actual bytes and effective rate. Admission must also account for scheduling constraints and free-space thresholds; nominal cluster-wide capacity does not guarantee a suitable target.

## Node Ready and volume Ready answered different questions

During a separate node-health incident, Kubernetes marked a node's conditions `Unknown` with `Kubelet stopped posting node status`. The K3s agent journal did not expose an equally obvious error, and important Longhorn replica data still physically occupied the node's disk.

After an authorized reboot, the node returned to `Ready`.

That was a meaningful recovery of kubelet-to-control-plane communication. It did **not** verify that every Longhorn replica on that host could rejoin, that the volume was attached and writable, or that application-level data remained consistent. I learned to treat the host coming back as one checkpoint in a larger investigation.

Before resetting node state or cleaning directories, preserving the physical replica data mattered. A scheduler, a storage controller and a filesystem do not share exactly the same notion of what has recovered.

## A different volume could not finish detaching

Another large volume had previously shown a repeating `Detaching` condition, along with `Faulted` and `NotReady` symptoms. The consuming workload could not get a usable attachment.

One instance-manager log line gave the incident a sharper shape:

`failed to unregister process ... since it is state stopping rather than stopped`

I have replaced the original process identifier with an ellipsis. The message was about a **process-state transition**. Something Longhorn wanted to unregister had not advanced from `stopping` to `stopped`. That is different from the scheduler simply failing to place a Pod, and different again from finding a corrupt file on disk.

To reason about it I separated the owners of the operation: the application requests I/O through its mounted filesystem; kubelet and CSI manage mount and staging actions; Kubernetes and Longhorn track attachment state; the instance manager supervises engine and replica processes; and the underlying host retains devices, mounts, open resources and replica files.

In later troubleshooting I also encountered a force-detach followed by a **port-in-use** error, and in another node cleanup a Longhorn CSI `globalmount` directory could not be removed because the device or resource was busy. These are evidence of resources still being held or contested. They do not prove that the earlier process-manager incident had the same root cause.

Similarly, missing containerd snapshot paths or CSI metadata files in a separate node incident were not proof of Longhorn block corruption. It mattered to preserve those boundaries in the write-up.

For the instance-manager `stopping` log, I do not have a final trace demonstrating a clean reattach, restored two-replica set and application-wide data verification. An instance-manager restart was discussed as a possible intervention; a suggestion is not a recorded successful result.

### Ownership must converge before detachment is complete

For an ordinary single-writer CSI filesystem volume, stopping the consumer, removing its publication, unstaging and releasing controller attachment are distinct actions. Longhorn also reconciles its own VolumeAttachment tickets; CSI is one requester, and other controllers can request attachment for maintenance. The Kubernetes VolumeAttachment object and Longhorn's custom resource are different records. The installed version and access mode determine the actual sequence.

The historical unregister error tells me that the process manager rejected a state transition while the instance was still stopping. It does not show whether a signal was delivered, a child process exited, an I/O request stalled or a port was held by that same process. The later port conflict and busy directory are separate observations. The [VFS record](/projects/linux-vfs-mount-lifecycle/) distinguishes a mountpoint removal error from an explicit unmount failure.

I would preserve the attachment requests and matching CSI events, process state and logs, the device and mount identities in the relevant namespaces, and any socket owner evidence before considering a forced transition. The absence of an object in the API does not prove that an old writer is fenced. An instance-manager restart can affect other volumes supervised by it. Neither removing a ticket nor restarting a manager is a substitute for verifying that the old owner no longer has access. No such full verification trace survives for this incident.

## What should be checked before touching a volume?

A PVC being `Bound` does not demonstrate that its Pod has a mounted block device. A Pod being scheduled does not prove that a former writer has detached safely. A volume label being green does not establish that its initial redundancy target has been restored.

I found it useful to turn each signal into a narrower question:

| Observation | Next evidence I would look for | What I would **not** conclude |
| --- | --- | --- |
| Pod scheduled / PVC Bound | CSI events, attach and mount results | Data ready |
| `Detaching` / `Faulted` | Longhorn volume and attachment ticket state, engine logs | Every replica is corrupt |
| Instance-manager stuck at `stopping` | Process lifecycle, owner, logs and existing writers | Force cleanup is automatically safe |
| Busy `globalmount` | Active mount references and device users | A replica file should be deleted |
| Node returned to `Ready` | Replica engine and workload read/write state | Volume fully recovered |
| `Healthy` after target 2 → 1 | Actual usable replica membership and future rebuild plan | Original two-copy failure tolerance restored |

A forced detach can be dangerous if a workload still owns the writer. I would first capture the existing volume and attachment evidence and decide whether the operation could discard the only remaining access path. The Longhorn attachment-ticket model is useful here; arbitrary force operations do not replace inspecting ownership.

## The hidden cost of a one-copy workaround

Lowering the desired replica count solved a status problem. It also reduced the amount of hardware failure the volume could tolerate until redundancy was restored. That interval was itself a reliability exposure.

Rebuilding requires more than a second empty directory. It needs capacity on an eligible disk, a valid data source, network and disk I/O, and enough time to reconcile snapshots and writes. A cluster may have free space for current logical data but lack the headroom to rebuild a missing replica while the workload continues using the volume.

I was especially cautious while the sole known healthy source showed a snapshot-deletion operation. A snapshot operation is not evidence of corruption, but competing repair and snapshot work can make recovery decisions less forgiving. I would measure rebuild progress and source availability rather than invent a completion time.

StorageClass choices matter too. A small single-instance application may benefit from Longhorn's movable replicated block storage. A database with its own replication, such as ClickHouse, has a separate recovery model. A distributed object store such as MinIO may not need the same replica guarantees at every lower layer. Stacking replicas can consume capacity and complicate failure ordering without automatically improving end-to-end durability.

The decision is **which layer is responsible for a recoverable copy**, not which technology looks more redundant on an architecture diagram.

## Replica Recovery and Application Validation

I would want five distinct facts: the host is reachable, the volume is attached and mounted safely, the intended number of **usable** replicas has returned, the application has recovered its own on-disk state, and a representative client can read and write the expected data. A backup restore test and a checksum/integrity audit add further confidence.

After lowering Longhorn's desired replica count from two to one, the volume returned to **Healthy under the new target**. In a separate host incident, the node returned to Ready. Neither event rebuilt the stopped second replica or verified the application's complete data set. Restoring the original redundancy level and testing application reads were separate steps. This also reinforced why a live replica and an independently protected backup solve different failure scenarios.
