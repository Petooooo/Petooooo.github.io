A stateless Pod can often be recreated somewhere else and become useful quickly. The first time I began operating persistent services, I realized that this mental model hides the hardest part: **the replacement process may start long before its data is available and consistent**.

In my K3s environment I worked with Longhorn persistent volumes and MinIO object storage. The recurring engineering decision was not simply “How many replicas?” but **which component owns persistence, what state must be restored, and what failure is actually being tolerated?**

## 1. Separating the four recovery clocks

A node or workload failure can set several different clocks running.

| Clock | Event I needed to observe | What it does *not* prove |
| --- | --- | --- |
| **Scheduling** | A new Pod is placed | The underlying volume is attached |
| **Storage** | Volume attachment and replica state reconcile | The application has recovered its on-disk state |
| **Application** | Database/service process becomes internally ready | External clients can use the intended operation |
| **User-visible** | A representative request succeeds | Every consistency or durability guarantee has been validated |

This distinction changed the way I thought about availability objectives. **RTO** should cover the outage visible to the consumer; **RPO** depends on which data was actually durable or replicated. A healthy Kubernetes object alone answers neither.

## 2. Longhorn made storage transitions visible

Longhorn provided a way to manage replicated volumes without manually managing all storage placement. It also introduced states that matter during a failure: attachment/detachment, replica repair, volume health, actual disk space, and rebuilding after a degraded condition.

During troubleshooting I encountered **read-only storage symptoms**, attachment behavior and replica rebuild concerns. Some failures initially appeared to be application problems because that was where the error surfaced. The more useful approach was to inspect which layer had changed first: was the process blocked because of storage, was a volume waiting to move, or had the application failed independently?

I also learned that **replicas consume capacity during normal operation and repair**. A cluster near its disk limit may have insufficient headroom to rebuild its redundancy, even when the logical amount of user data appears manageable. Replication is not free backup space.

## 3. One storage class should not be used for every stateful application

At first it is tempting to put every database onto a replicated network volume. But a system such as ClickHouse already has database-level replication and recovery logic. Adding an extra network block-replication layer can introduce latency and complicated failure interactions.

I evaluated when **application-managed replicas on local storage** might be better than automatically applying Longhorn to every service. This was not a claim that local disks are universally safer. It is a question of **where durability and failover should be implemented**, and how the layers interact when one fails.

| Workload characteristic | Design question |
| --- | --- |
| One mutable database instance | Is volume movement part of the expected recovery plan? |
| Application-level replicated database | Are replicas independent enough, and does extra block replication help? |
| Analytics engine with heavy writes | Does rebuild traffic or remote I/O affect write latency and capacity? |
| Small internal stateful service | Is operational simplicity more valuable than another replication mechanism? |

## 4. MinIO and lifecycle decisions

Object storage required a different mindset from block storage. Applications may store durable records, temporary uploads, retained artifacts or large generated objects under the same API. With MinIO I considered **S3 compatibility, access permissions, migration dependencies, retention and lifecycle policies**.

A lifecycle rule is not just housekeeping. Deleting objects early may save disk space but break replay or recovery assumptions; keeping everything indefinitely can exhaust capacity. The correct retention period depends on who owns the data and how long an application may still reference it.

## 5. What “volume healthy” really needs to mean

I learned to distinguish **Kubernetes's view of a PVC** from the application's use of data inside that volume. A bound claim states that storage has been provisioned or associated; it says nothing by itself about a recent disk error, a database's recovery log or the consistency of user-facing operations.

The recovery sequence can include several separate points:

1. Scheduler chooses a node that can run the workload.
2. The storage subsystem determines whether the volume can be attached there.
3. The relevant replicas and data path become usable.
4. The filesystem can be mounted with the expected permissions and semantics.
5. The database or application repairs or replays its own persisted state.
6. A representative client read/write operation succeeds.

An operator who checks only step 1 may report success long before the consumer has received service.

### Replication overhead is also recovery overhead

Suppose a storage system normally has several data copies. Losing one copy does not necessarily mean immediate user-visible downtime, but it can produce a **degraded redundancy window**. Rebuilding the missing copy requires disk capacity, read bandwidth, write bandwidth and time; during the rebuild, ordinary application I/O may compete with repair traffic.

| Operating state | Question I would ask |
| --- | --- |
| All replicas healthy | Is the application meeting its latency and durability expectations? |
| One replica unavailable | Can the workload still read/write, and what redundancy remains? |
| Rebuild active | Is there enough free space and I/O bandwidth to finish repair? |
| Rebuild delayed | Is the bottleneck disk space, failed node, scheduling or storage policy? |
| Service recovered | Did the database/application complete its own recovery, too? |

I avoid publishing numerical rebuild times because the actual hardware, failure domain and workload determine them.

## 6. Choosing the layer that owns durability

A database with built-in replication and a replicated block volume can appear “doubly protected.” That does not necessarily mean it has twice the reliability. Both layers may rebuild simultaneously, compete for bandwidth or react differently to a partial failure.

The decision depends on which layer is responsible for:

- Detecting failed replicas.
- Selecting a writable copy or leader.
- Preserving write ordering and consistency.
- Repairing stale state.
- Exposing readiness to the application.
- Providing backup or point-in-time restoration.

In my ClickHouse considerations, this led me to examine **application-managed replication on local storage** rather than mechanically putting every database on a network-replicated volume. This was a workload-specific design choice, not a universal rule for all databases.

## 7. Durability, backup and object lifecycle are different contracts

A replicated volume helps tolerate some hardware failures. It does **not** replace a backup that can recover from accidental deletion or logical corruption. Likewise, MinIO object replication and an S3 lifecycle policy address different concerns.

| Mechanism | Primary purpose | What it does not automatically solve |
| --- | --- | --- |
| Block replica | Keep additional copies of current block state | Recovering an old version of accidentally deleted data |
| Snapshot | Preserve a point-in-time view | Off-cluster disaster recovery without a protected destination |
| Backup | Recover data after logical or infrastructure loss | Immediate online failover |
| Object lifecycle | Bound storage retention and growth | Understanding whether deleted objects are still needed |
| Database replication | Maintain application-aware copies | Unconditional correctness of arbitrary client retries |

A retention period needs to reflect the application's reference lifecycle. Deleting objects after an apparently reasonable interval can break a delayed consumer or historical replay task.

## 8. How I would investigate a read-only symptom

The phrase “read-only volume” can mean a filesystem remount, a storage subsystem state, a database replica state or even an application-level permission issue. My first step would be to identify **which component emitted the error**, not to assume that every layer independently became read-only.

Only then would I compare application logs, mount status, volume state, host I/O evidence and database replica information. A definitive postmortem would need a time-correlated trace; the original public record does not establish such a single root cause.

## 9. An incomplete failure analysis is still useful

I kept several cases in the form of symptoms, hypotheses and checks rather than forcing a neat root cause. For example, **read-only volume behavior** may result from more than one layer; repeated restarts could erase evidence without answering the question.

My preferred order became:

1. Record the application-visible symptom and the point at which it began.
2. Check Pod scheduling independently from PVC/volume health.
3. Inspect whether the database or service sees an I/O error, missing data, or a recoverable restart.
4. Distinguish a temporary workaround from evidence of the actual cause.
5. Record what is still unverified instead of making the incident sound fully resolved.

This way of reasoning is what eventually pushed my interests toward filesystems, block I/O, persistent state and failure ordering.
