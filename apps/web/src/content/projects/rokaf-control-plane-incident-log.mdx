When the K3s control plane stopped responding reliably, ordinary `kubectl` requests became part of the incident. The affected applications were not necessarily all broken in the same way, but the cluster's ability to expose and update their state was in question. I investigated etcd instability and possible corruption during operational incidents; other records involved read-only disk symptoms.

Some services became usable again after recovery work. That was important to operations, but it left an unanswered question: **was the control-plane state failure initiated by an etcd problem, or did storage trouble precede it?** The remaining notes do not supply a synchronized sequence that can settle that question. I do not want a successful recovery checkpoint to become an invented root-cause report.

## An unavailable API was a symptom, not an etcd corruption test

In a K3s installation using embedded etcd, Kubernetes state depends on the etcd cluster, while the API server, controllers and scheduler rely on that state to process new work. A degraded control plane can therefore affect deployments, reconciliation and endpoint updates even when an application process itself is still running.

The API failing to answer a request is not, on its own, evidence that etcd data has been corrupted. The path also depends on K3s process health, member connectivity, storage latency, a functioning API server and the client's network path.

I needed to distinguish a **running etcd member** from a **usable consensus cluster**. A member process may be alive while quorum for new commits is unavailable. Conversely, an individual member can have problems while the remaining voting members still form quorum and serve the cluster. A read or process-health check on one host cannot substitute for a view of the cluster's membership and commit progress.

The surviving notes include investigations of unstable etcd state and suspected corruption. They do not establish a member-by-member, time-correlated storage trace that proves a particular disk event corrupted etcd. The word *suspected* belongs in the record rather than silently becoming *confirmed*.

## What did “read-only” refer to?

A read-only error looked like a storage failure at first glance, but I found it necessary to ask which layer emitted it.

A Linux filesystem may be deliberately mounted read-only. It may also remount read-only after an error, depending on filesystem behavior and configuration. An application can receive a permissions failure even while the underlying filesystem remains writable. A database may report a logical read-only state because of its replication or coordination state—something I had also seen while investigating ClickHouse. Those conditions are different.

The distinction matters for etcd. Its local member state depends on durable writes. A failing or heavily delayed write path can disrupt an etcd member and, depending on quorum, cluster availability. But saying that this *can* happen is not proof that it *did* happen in these incidents.

To establish that connection I would need the filesystem and mount state, relevant kernel and block I/O errors, write and sync behavior, and the etcd member's log at matching times. A message containing “read-only” does not prove physical-disk damage, a particular RAID defect, or a verified etcd data-corruption event.

## March 10: a storage incident and a consensus incident

On March 10, 2026, I reported disk and RAID failures affecting multiple server nodes, difficulty starting K3s and suspected damage to stored etcd snapshots. The recovery discussion then reached a message indicating that managed etcd membership had previously been reset. That message is evidence of a reset marker, not of a successful snapshot restoration, a healthy reconstituted cluster or a complete data audit. I do not have the original array-level status output, the RAID level, device error counters or a final member-by-member inventory. The private topology and device identifiers are omitted.

I wanted to distinguish two forms of redundancy. RAID can keep a local logical block device usable after certain member-device failures. Raft can keep a replicated state machine available after certain voting-member failures. A RAID disk is not a Raft voter, and a server with redundant disks still has a single vote if it is one voting member. Shared storage, power or other dependencies can defeat the assumption that failures are independent.

## Linux MD: logical blocks and redundancy

Linux software RAID exposes an MD block device above its component devices. A filesystem on that device addresses logical blocks rather than choosing a disk for each write. The mapping is determined by the RAID level and layout. RAID1 mirrors data; RAID5 distributes data and single parity across members; RAID6 adds a second independent parity scheme. RAID0 stripes without redundancy. The ability to continue after a failure depends on the layout, which members are missing and whether the remaining data is readable and consistent. RAID10 tolerance also depends on which copies have failed.

For illustration, consider two-way mirroring and a three-member single-parity stripe. If two data blocks are A and B, the parity block is A XOR B. With one known missing block, the remaining two blocks reconstruct it. Losing two blocks leaves insufficient information. An XOR check alone cannot identify which of three present blocks is incorrect. I implemented that small model with deterministic 4096-byte buffers and checked all three single-block loss positions, rejection of two missing blocks and detection of an altered block. This is algebra, not a Linux MD rebuild or a benchmark. RAID5 has additional consistency and write-hole considerations, and actual RAID6 uses a different coding scheme.

A degraded array can remain writable. In Linux MD, the degraded counter describes missing active members; sync_action describes operations such as recover (building a replacement), resync (re-establishing redundancy) and check (checking consistency). An idle synchronization state alone does not mean the array has its expected number of healthy members. Rebuild or resync also consumes device bandwidth, potentially increasing latency for foreground writes. An array returning to its expected member count does not by itself validate the filesystem or the application contents.

The evidence I would retain includes the kernel's block I/O messages, /proc/mdstat, read-only array detail and the matching MD sysfs attributes. I would identify the actual device stack before interpreting a counter: the logical MD device and its member devices are related, not independent sources of workload throughput. I would not initiate repair, assemble an uncertain array forcibly or change membership just to gather evidence. A surviving member may contain the only remaining copy of relevant data.

## Filesystem state above the array

A disk can fail requests, the logical array can expose errors, and a filesystem can react according to its own error policy. For ext4, errors=remount-ro is one supported policy. A read-only mount may also be an intentional mount configuration. Mount-level and superblock-level write permissions are not identical, and a read-only application replica need not have a read-only Linux mount.

An unsuccessful write with EIO is not the same as EROFS, ENOSPC or EACCES. The errno narrows the operation's failure category, but the storage source and relevant kernel messages are still needed. A successful buffered write is also not proof of durable completion; delayed errors can emerge during synchronization. The [JBD2 and writeback investigation](/projects/linux-disk-io-journaling-writeback/) explains that distinction in more detail.

A filesystem check or repair must follow its own offline and storage-consistency requirements; it cannot establish that a member database is logically consistent. Conversely, a database corruption alarm does not locate a physical disk defect. I would preserve the relevant logs and a supported recoverable copy before any destructive repair.

## Raft quorum is not disk redundancy

An etcd write is proposed through the leader, replicated as Raft log entries, committed under the consensus rules and applied to the state machine. The Raft log must be persisted in accordance with the protocol before acknowledging dependent messages. A slow or failing WAL sync can therefore affect proposal progress even if the member process remains alive. Election and heartbeat behavior also depends on scheduling and network latency. The backend commit and WAL sync metrics observe different parts of the storage path.

For a stable voting configuration of N members, the majority is floor(N/2) + 1. Three voters require two, four require three, and five require three. The corresponding maximum unavailable voters while retaining a majority are one, one and two. This arithmetic is necessary but not sufficient for new writes: the remaining voters must be mutually reachable as needed, establish leadership and make durable progress. Learners do not count as voters, and membership changes must follow consensus rules.

The companion model exhaustively enumerates reachable-voter subsets for these three sizes (56 subsets in total) and checks the majority predicate and failure margin. It does not simulate elections, log replication, network partitions or membership changes. It explains why adding a fourth voter to a three-voter cluster does not improve the number of failures it can tolerate. This is also why K3s recommends an odd number of embedded-etcd servers.

## Recovery from a surviving member versus a snapshot

A temporarily unavailable member is different from a permanently lost majority. If quorum remains healthy, restoring or replacing a failed member can be a membership-management problem rather than a full disaster restore. If quorum is lost permanently, recovery from a trusted snapshot or supported surviving-state procedure establishes a new membership context. The choice depends on what is actually available, its consistency and the installed version.

A membership reset is not automatically a restore from a known-good backup. The March reset-marker message did not establish the restored revision or the health of rejoined members. A snapshot should be checked for its provenance, supported integrity verification and revision; for Kubernetes, restoring older revisions also requires attention to watcher caches and version-supported recovery behavior. K3s backups include the server token needed to recover encrypted bootstrap data. An etcd snapshot captures Kubernetes datastore state, not the contents of every application PVC.

A read-only investigation would compare timestamps from kernel and MD status, the actual filesystem serving the datastore, etcd endpoint status and health, alarms, WAL sync and backend commit latency, and API request errors. On an authorized restored environment I would additionally verify expected objects, revision semantics, controller reconciliation and application-specific data. I would keep the old state and backup provenance until the intended recovery scope is verified, not reuse conflicting old member databases indiscriminately.

The partial recovery described in the original notes remains valuable, but the RAID rebuild outcome and final March etcd integrity are unresolved. These are different from the separate node reboot and return to Ready below.

## Another node came back Ready without proving data recovery

There was also a separate Longhorn-related incident worth keeping distinct. A node's Kubernetes conditions became Unknown and its status included `Kubelet stopped posting node status`. The K3s agent logs did not provide an equally clear explanation. After checking the condition and rebooting the node, I observed it return to `Ready`.

That was a real recovery checkpoint. It was **not** evidence that a stopped Longhorn replica on that node had been rebuilt, that its volume had successfully reattached, or that the original application could read and write all its data.

I cannot date this incident to the same event as the etcd instability or assign it the same disk cause. Its relevance is narrower: the Kubernetes node condition tells me when the control plane can once again observe a node as ready. The storage system has its own recovery state. The [Longhorn replica investigation](/projects/rokaf-stateful-storage-and-recovery/) records those observations separately.

## How I separated the recovery checkpoints

Several system statuses can turn green while the overall service is still missing a prerequisite. I wanted each checkpoint to answer one question, not serve as a proxy for the entire incident.

| Boundary | What the observation could establish | What it would not prove |
| --- | --- | --- |
| Host filesystem and block I/O | Whether the sampled mount and device are writable or reporting errors | Whether the storage event initiated the etcd fault |
| etcd member and quorum | Whether members can participate in consensus and commit updates | Correctness of all historical state or application data |
| Kubernetes API | Whether representative API read/write operations succeed | Whether all controllers have reconciled their workloads |
| Controller and scheduler | Whether desired Pods and endpoints can be reconciled | Whether a stateful volume or database has recovered |
| Application request | Whether a representative client operation works | Full historical data integrity or future failover readiness |

This table is a **verification plan**, not a set of tests that I claim to have executed against every member and application in the original incidents. The available records support partial restoration of usable services, plus the separately verified node return to Ready. They do not support a completed, full-cluster data-integrity audit.

For a stateful control plane, this distinction affects recovery choices. Repeatedly restarting components, deleting data files or forcing recovery without preserved state can erase the evidence needed to determine whether the resulting cluster is consistent. I deliberately omit internal topology and the specific etcd recovery procedure; this document is an engineering account, not a runbook for a private cluster.

## Control Plane Root Cause Evidence

The most useful missing evidence was a single time axis. I would preserve the first unsuccessful client API request and record the corresponding K3s and etcd state, member quorum, host mount state, disk I/O messages and the exact intervention time. After recovery I would repeat representative API and application operations and keep the results separate.

Chronology alone would still need interpretation. An I/O error logged shortly after an API failure might explain an earlier stalled write, or it might be an unrelated event. Without the timestamps, member roles, storage signals and repeated behavior, labeling the read-only symptom as the cause of the entire outage would be speculation.

I had also learned from Longhorn that a Node reporting Ready and a stateful Replica reporting Healthy are different assertions. They can recover on different schedules, even if the client-facing failure appears at the same time. I would not allow a repaired API endpoint to stand in for a storage read/write test.

## Observed Recovery and Unresolved Causes

I investigated **etcd instability, suspected corruption and read-only disk symptoms** during K3s control-plane incidents, and recovered usable access in some cases. In a separate episode, a node returned from Unknown to Ready after reboot. The common initiating fault across these events remains unresolved; establishing that link would require time-aligned host I/O, filesystem, etcd member and API-request evidence.
