The queue had one document-conversion task. A worker had already taken it and was still processing. Yet the message appeared ready again, and another worker could start the **same logical operation** while the first one continued.

I had expected the broker to recover a failed consumer. Instead, I was watching two notions of failure diverge. The **AMQP connection had failed**, so RabbitMQ could return an unacknowledged delivery to the queue. The original conversion process had not necessarily stopped. It might continue doing expensive work and writing artifacts long after the broker stopped considering it the message's owner.

That problem came after a RabbitMQ-to-RabbitMQ migration I had completed using Shovel. It later informed a different worker-lifetime model in a document-processing service. These were **separate episodes in March and June 2026**, not one continuous rollout that solved every cause of every disconnect.

The interesting part was not only how to make RabbitMQ more stable. It was deciding how much of a long-running job's lifetime the broker should own.

This account deliberately excludes internal hostnames, port mappings, actual queues, virtual hosts, credentials and deployment topology. It separates observations from proposed explanations and locally validated redesign work.

## Moving messages was one problem; keeping consumers alive was another

In early March, I moved work from an old RabbitMQ broker to a new one with the **Shovel plugin**. I configured a one-way transfer between equivalent source and destination queues. The recorded setup used the `on-confirm` acknowledgement mode: the source delivery is acknowledged after publication to the destination has been confirmed.

I could observe the Shovel running, messages decreasing in the old queue and increasing in the new one. I regarded that migration as successful, then prepared applications to use the new broker's Kubernetes Service endpoint.

Shovel solved the immediate **transport and migration** problem. It did not copy the entire broker configuration, the consumers' process state or the history of which business effects had already occurred. Nor did a successful transfer demonstrate that every consumer could run a multi-hour task safely.

I did not retain a reconciled source-and-destination message-ID inventory, a precise moved-message count or a failover exercise that would support stronger claims. The status and queue-count observations are evidence of the observed transfer, not a blanket exactly-once migration guarantee.

A useful distinction emerged:

| Concern | What the evidence showed | What it did not show |
| --- | --- | --- |
| Shovel migration | Source messages were transferred to the destination queue; Shovel ran and queue counts moved in the expected directions | Exactly-once business effects or every queue definition being copied |
| New broker reachability | Applications could target the Kubernetes Service and the failing connection path was inside the cluster | That a proxy was the cause, or that TCP sessions were stable for hours |
| Worker continuity | A long-running handler could keep working after AMQP connection loss | That the broker still recognized it as the delivery owner |

Shovel and the worker failure were related operationally because both involved RabbitMQ, but their success criteria were different.

## The reset was not coming through the web proxy

In March I was investigating intermittent `Connection reset by peer` during document-processing work. The affected worker called RabbitMQ through the Kubernetes service name from another Pod. This path did not go through the Nginx or Traefik HTTP reverse-proxy chain I used for web applications.

That mattered. It ruled out a simplistic explanation that the web proxy's WebSocket or HTTP timeout had closed the AMQP session. It did **not** prove what did close it.

Some conversions were hundreds of seconds long; others could run for hours. In one investigation the recorded work duration ranged from roughly **500 seconds to three hours**. The consumer was holding its delivery unacknowledged until the expensive operation completed.

The broker logs gave me a much sharper clue than the generic reset message:

`missed heartbeats from client, timeout: 60s`

One log showed an AMQP connection being closed after about three minutes. In the client at that stage, the heartbeat and blocked-connection timeout options had not originally been set explicitly. I experimented with separating the connection's I/O loop and heartbeat work from the long-running handler. Connection loss still occurred.

I later set or observed the RabbitMQ server heartbeat configuration at `86400` seconds, intending to tolerate very long jobs. Yet the disconnect symptoms persisted. The earlier log's `60s` timeout was not thereby disproved, and the record does not include a successful inspection of the **effective negotiated heartbeat for the failing connection**.

RabbitMQ's heartbeat timeout is negotiated between client and server; a server-side number alone is not proof of the value actually used on a connection. The official documentation explains why both sides matter and why very large timeouts are generally a poor substitute for a live connection event loop.

There was another setting in the investigation: `consumer_timeout` appeared to be `1800000` milliseconds (30 minutes). That concerns delivery acknowledgement timeout, **not the same mechanism as a negotiated AMQP heartbeat**. The recorded `missed heartbeats ... 60s` event should not be relabeled as a thirty-minute acknowledgement timeout. Those mechanisms can both matter to long-running consumers, but the logs distinguish which one was observed.

I considered heartbeat negotiation, blocked client I/O, network-idle behavior and service-level connection handling as hypotheses. I could not establish one final network root cause or a proven permanent fix for the March resets.

## The most damaging consequence was two workers doing one job

A broken AMQP connection has a predictable consequence for an **unacknowledged delivery**: RabbitMQ can requeue and redeliver it. But the worker's processing function need not immediately notice that the transport has gone away.

That was the failure mode I observed. A worker could lose its connection while continuing a long conversion. The queue then showed the task as ready again. Another available consumer could start the same job before the old worker ended.

This was a more important reliability problem than a dashboard's connection count. Two workers might both create output, update a database or send a completion event for one document request. Even if their result files had different names, they could race to set the same job's final state.

A larger heartbeat timeout would not by itself make two simultaneous workers safe. Even perfect heartbeat handling cannot eliminate crashes between committing a side effect and acknowledging a delivery. That race must be handled at the application layer.

## An acknowledgement can be early, late or simply unrelated to the result

The old model kept one RabbitMQ delivery unacknowledged throughout a potentially lengthy conversion. Its advantage was simple: if the consumer truly died before an Ack, the broker could redeliver the task. Its weakness was that the delivery's transport lifetime was tied to a conversion that might take hours. After a connection loss, that model could grant the same logical job to another worker even while the original work continued.

A tempting opposite was to Ack as soon as the message arrived. This kept the broker connection's role brief, but **an unconditional early Ack could lose the job** if the worker then crashed before saving progress. The broker would have no outstanding delivery to replay.

The later design did neither. It first **claimed the logical stage in durable application state**, then acknowledged the RabbitMQ command, and only then proceeded with the long-running work. Once the broker command had been acknowledged, RabbitMQ no longer owned recovery of that stage; a job service and lease reconciler did.

That transfer of responsibility was deliberate. It did not mean the job had finished when the Ack was sent.

| Moment | Broker's knowledge | Durable job service's knowledge |
| --- | --- | --- |
| Command delivered | One consumer has an unacknowledged delivery | Stage may still be pending |
| Claim recorded | Delivery is still outstanding until Ack | Stage and attempt are owned under a lease |
| Ack sent | Broker command is complete | Work is **not** yet complete |
| Conversion continues | Broker has no outstanding copy of this command | Heartbeats / lease keep ownership current |
| Worker disappears | Broker cannot redeliver an already-Acked command | Stale lease triggers reconciliation and a bounded new attempt |
| Output committed, completion accepted | Ack says nothing about the result | Job service verifies relevant stage and durable artifact identity |

The DB-backed claim must be acquired with concurrency control, not with a casual read followed by an unguarded write. The durable job identity and attempt/claim token make it possible to reject stale completion events even if an earlier worker wakes up after a replacement has taken over.

## A new processing attempt is not a new document job

A RabbitMQ redelivery, a user retry and a recovered stale lease can all refer to the **same logical job**. I needed a stable job ID that did not change with each attempt.

The newer worker-runtime design distinguished the accepted job, its active stage, the command ID, the current attempt and lease, and the artifact identity. The job service had the authority to accept or reject stage results. A repeated command for a completed stage should not advance the workflow again; a stale completion from a superseded worker should not overwrite a newer result.

The most important boundary was across three persistent systems: job state in PostgreSQL, artifacts in MinIO, and command delivery in RabbitMQ. There is no ordinary atomic transaction that commits all three together.

A worker might upload a valid file to MinIO and lose its connection before its completion event is applied to PostgreSQL. A retry should check for the existing artifact under a deterministic identity and reconcile it; blindly making another output can duplicate the effect. Conversely, a database row marked completed while its expected artifact is missing is not a successful document job.

The same distinction applied to retries and dead-letter handling. The later local reliability suite exercised retry/backoff, stale-lease recovery and logical dead-letter state. **Physical RabbitMQ DLX/DLQ wiring was not universally enabled by default** because a queue-declaration mismatch appeared in the Helm integration. An application-level terminal failure is not proof that a production dead-letter queue was correctly installed.

I kept stage ownership in the central job service instead of asking each format worker to select and publish its own next processing stage. That made it easier to reject duplicate or out-of-order events; it also made reconciliation a necessary part of the system.

## The tests supported the redesign, not a universal success claim

The June work had more than a diagram behind it. Retained development notes describe local tests covering durable claims, stale leases, bounded retry and duplicate/stale-event handling. Controlled route-level tests exercised PDF, DOCX and HWPX processing paths, and an isolated Helm rehearsal brought up the necessary service dependencies.

Those are meaningful results. They show that the new lifetime model could execute and that selected recovery behavior was tested under controlled conditions.

They do **not** demonstrate that every March reset root cause had disappeared, that every possible race was eliminated or that a full production failure-injection campaign passed. I have no reliable throughput improvement percentage to publish. Nor should I describe the newer Claim → Ack model as if it were the configuration that produced the original March heartbeat logs.

The tests I would keep next to the implementation are concrete:

- Kill the worker **after durable claim and Ack** but before output; ensure the stale lease eventually becomes retryable without changing the job identity.
- Kill it **after artifact upload but before completion event**; ensure another attempt reconciles the object instead of creating a second logical result.
- Deliver the same command or a stale result twice; ensure it does not advance the wrong stage.
- Exhaust retries; ensure the failure is discoverable through job state, irrespective of physical DLQ wiring.
- Compare user-visible result availability with what MinIO and the job database actually contain.

These are the failure boundaries that matter more to a document user than a single green RabbitMQ health indicator. Some of them had targeted tests in June; I do not present the list as evidence that every operational environment passed all five.

## What Shovel could move, and what it could not

Looking back, the Shovel migration and the later worker redesign addressed two different meanings of "moving work."

Shovel moved **messages from one broker to another**. With `on-confirm`, the source acknowledgement follows confirmation from the destination, which is a useful transfer boundary. RabbitMQ's Shovel documentation is explicit about these semantics. But a confirmed publication is still not the same as the document being converted once.

The job-service redesign moved **ownership of a long-running logical operation** away from an AMQP delivery and into durable state. The message was allowed to be transient. The job was not.

During the incident, the same logical job could appear queued while an earlier worker was still processing it. The durable claim was intended to prevent a later delivery from writing a competing result; broker acknowledgement alone could not enforce that rule.
