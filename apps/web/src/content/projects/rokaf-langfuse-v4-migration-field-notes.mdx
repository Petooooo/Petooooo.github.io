I was migrating Langfuse to v4 when a step reported `Timeout error.` My first reading was that a long-running job had failed. But when I inspected its persistent state in PostgreSQL, the result was different: the phase was `completed`, with nine completed chunks and zero failed chunks.

The UI and the progress record were describing different things. One was the response that a caller had waited for; the other was evidence left by the work itself. Before retrying anything, I needed to know which lifetime had actually ended.

This is not the story of an upgrade abandoned at that timeout. I continued the migration. **By November 17, 2026, Steps 1–5 were complete, Langfuse was running in `events_only` mode, and checks of historical and newly written data had passed.** Looking back, the important part of the work was how I got from an ambiguous failure message to a result that I could test.

## A running application was not the whole migration

The upgrade touched application code and several kinds of persistent state: PostgreSQL for progress and metadata, ClickHouse for analytics data, and Keeper for the coordination required by replicated tables. An image update or a successful Helm rollout did not automatically convert old Traces and Observations into structures the new application could use.

Historical data backfills had their own work to finish, and those writes needed a writable destination with enough free space. Rather than call the rollout one operation, I treated data transformation, application behavior, and cleanup as separate milestones.

## Step 2: the caller stopped waiting before the recorded work said it was done

Step 2 involved backfilling and sorting existing Observations into the migration's intermediate `observations_pid_tid_sorting` table. The apparent failure needed more than another look at the UI.

| Observation | Recorded value |
| --- | --- |
| Caller-visible status | Failed, `Timeout error.` |
| PostgreSQL migration phase | `completed` |
| Completed chunks | **9** |
| Failed chunks | **0** |

These values did not prove that every transformed record was already usable by the new application. They did establish that treating the operation as *nine failed chunks* would be wrong. A timeout in the request path was not a rollback of committed background work.

I checked the durable state before taking the retry path. With that distinction understood, a subsequent retry resolved the step and I moved forward. That was not permission to blindly rerun every backfill on every timeout; the persisted bookkeeping mattered.

## Other errors required other evidence

During the broader upgrade, I also had to investigate ClickHouse replicas entering a read-only state. A healthy application Pod did not establish whether the database could write, and Keeper coordination state had to be considered separately.

At another point, a remote insert hit insufficient storage capacity. A data rewrite can require additional target and temporary space beyond the size of the original dataset. Repeating the same insert while the capacity constraint remains is not meaningful recovery.

An earlier investigation also recorded a JSON/date conversion error in persisted migration-state handling. That old note used the label “Step 6,” but I cannot establish that its numbering referred to the same five-step procedure later completed. I retain it as a distinct debugging episode, **not** as evidence that an additional mandatory sixth step was still failing after the final cutover.

It would be convenient to call these all one upgrade problem with one fix. They were different failure boundaries: request lifetime, stored job state, replication and coordination, available disk capacity, and state parsing. I kept them apart rather than inventing one root cause.

## What changed before I called the migration complete

After Step 2, I continued through the later migration work. Steps 3–4 covered v4 event-data backfill and validation. I did not use their completion alone as the final proof; I also checked historical data access and new data creation and retrieval in the application.

The recorded final checkpoint on **November 17, 2026** was:

| Boundary | Verified state |
| --- | --- |
| Helm chart / Langfuse app | **2.1.3 / 4.46.0** |
| Write mode | **`events_only`** |
| Migration procedure | **Steps 1–5 completed** |
| Historical and new data | **Validation passed** |
| Final cleanup | Intermediate `observations_pid_tid_sorting` table cleaned up |

The last cleanup deserves its own sentence. Step 5 removed an intermediate table used for migration; it did **not** mean deleting the original `traces` and `observations` tables. I wanted the earlier migration steps and functional checks accounted for before treating that cleanup as safe.

This later result changes the conclusion of my early field notes. It is accurate to say I completed the recorded migration procedure and verified the historical and new-data paths in the chosen mode. It would be inaccurate to inflate those checks into an exhaustive audit of every legacy edge case or a fully tested disaster-recovery exercise.

## Which kind of completion did I actually observe?

I used several sources of truth at different points. Each answered a narrower question than the phrase “migration successful” suggests.

| Evidence | What it establishes | What it cannot establish alone |
| --- | --- | --- |
| UI or HTTP status | Whether the caller got a timely response | Whether the background job committed its work |
| Durable phase and chunks | Which work was recorded as finished | Whether every destination record is correct |
| ClickHouse and Keeper state | Whether a sampled data/coordination path is writable | Whether the new application understands all old data |
| Functional read/write tests | Whether tested historical and new-data paths work | Every historical edge case or future failure scenario |
| Cleanup checkpoint | Whether the temporary migration table was removed | A universal data-integrity guarantee |

The Step 2 request timed out while PostgreSQL recorded nine completed chunks and zero failed chunks. I continued the remaining procedure, verified historical and newly created data in `events_only` mode, and completed Steps 1–5 and temporary-table cleanup by November 17, 2026. The timeout alone had not described the final outcome.
