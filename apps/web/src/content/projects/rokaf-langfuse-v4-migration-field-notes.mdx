I kept running into a dangerous assumption while upgrading Langfuse: **a failed status badge and a failed data operation are not the same statement**. The clearest example was a background rewrite step that reported a timeout even though the persisted migration state contained evidence that the underlying work had progressed.

## The upgrade was more than one component

The process involved changes to Langfuse application code and supporting stateful systems, including **PostgreSQL, ClickHouse and Keeper**, with multiple migration phases and data rewrites. I had already moved through an earlier upgrade before starting the v4 path.

The real risk was coupling: a migration may need to insert data into a new analytics schema while a coordinator is unstable or storage space is insufficient. Retrying blindly can increase both I/O and uncertainty about partially completed work.

## Step 2: Timeout error, but phase completed

At one point Step 2 reported **`Timeout error.`**. Looking at the migration record gave a different picture:

| Evidence | Recorded value |
| --- | --- |
| User-facing step status | `failed` / timeout message |
| Persisted phase | `completed` |
| Completed work chunks | **9** |
| Failed work chunks | **0** |

This does not by itself prove every downstream read is correct. It does show why I should not simply restart the step or assume its data transformation did not happen. I treated the timeout as a **caller/worker observation** and the persisted chunk counts as **background-operation evidence**.

The next question was whether follow-on operations saw the rewritten data and whether the application considered the migration usable, not whether a spinner had turned green.

## ClickHouse/Keeper and read-only state

Another part of the upgrade involved **read-only ClickHouse behavior** and coordination/leader concerns. I investigated Keeper health and replication state rather than assuming a writable database could be restored by restarting one application container.

At a different point, a remote insert reported **insufficient space**, introducing a hard resource constraint. Even if the migration logic is correct, a data rewrite needs enough temporary and target capacity to complete.

These incidents led me to separate three questions: **is the coordinator functional?**, **is the replica writable?**, and **is the destination sufficiently provisioned?**

## Step 6: Persisted state serialization

During the later v4 phase I encountered a **JSON/date handling error** in a migration state query. That shifted the investigation from storage coordination to **how background migration code represented and parsed persisted state**.

A failure here does not mean that earlier ClickHouse replica or storage work is irrelevant. It means that the migration pipeline has crossed into another independent failure mode.

## A migration can have multiple, conflicting status reports

One lesson from the Step 2 investigation was that **four different kinds of truth** coexist during a background migration.

| Source | What it says | What it cannot prove alone |
| --- | --- | --- |
| HTTP response or UI badge | Whether the caller received a timely response | Whether the background worker completed |
| Persistent progress table | Which phases and chunks have recorded progress | Whether every destination row is usable |
| Analytics/storage health | Whether ClickHouse/Keeper and volumes can accept work | Whether migration code interpreted every row correctly |
| Functional application test | Whether the current application can read/write | Whether every old historical edge case was exercised |

These sources may disagree temporarily. For Step 2 I observed the caller-facing timeout while the persisted progress record showed completed state, **nine completed chunks and zero failed chunks**. The correct next action was to investigate the consistency of those reports, not automatically repeat every chunk.

### A timeout is not a rollback

A client may stop waiting while a database query or worker continues. That possibility is why durable migration state matters. In some applications a job lease or heartbeat would distinguish an active worker from an abandoned attempt; in others the background migration state machine is the more reliable source.

I did not assume that the exact row counts alone proved success. The decision still needed follow-on reads and writes.

## Different failures need different remedies

I tried to avoid lumping the upgrade's symptoms into one “migration problem.”

| Symptom | Failure layer | Reason an unrelated fix would not help |
| --- | --- | --- |
| `Timeout error.` | Caller/worker timing | Replacing storage may not alter the timeout boundary |
| Phase marked completed | Migration bookkeeping | Restarting from zero may duplicate completed work |
| ClickHouse read-only | Replica/coordination state | Application image retry cannot elect a coordinator |
| Insufficient destination space | Storage capacity | Re-running INSERT without headroom repeats failure |
| JSON/date handling error | State parsing and migration code | Keeper health alone cannot repair type handling |

This decomposition made the sequence easier to reason about. It is also why I avoided changing multiple stateful components at the same time when trying to establish a cause.

## A controlled verification checklist

Once the underlying services are healthy, I would verify the migration through independent milestones:

1. The persisted migration phase matches the expected transition.
2. No chunks remain failed or stuck in a running state.
3. Replica/coordinator health allows consistent reads and writes.
4. Destination storage has adequate free space.
5. Representative historical traces/observations can be queried.
6. A new trace/observation can be written and retrieved.
7. Background tasks continue to make progress after the application restart.

I have not published evidence that every one of these final checks passed for the complete v4 rollout. The case should therefore remain a **field note of verified intermediate states and unresolved final validation**, rather than an invented completion report.

## Why this matters for storage research

The migration combined application schema assumptions, coordination metadata and physical storage limits. A write-heavy data transformation can fail for reasons far below its SQL code. The distinction resembles a broader OS question: **what guarantees does each layer provide, and where must correctness be verified after interruption?**

That question connects this operational record to my interest in crash consistency, persistent writes and filesystem recovery.

## What I know and what I still need to check

**Confirmed from the recorded investigation:** the Step 2 mismatch between timeout and persisted phase/chunks; separate insufficient-space symptoms; ClickHouse/Keeper read-only/coordination problems; a later Step 6 JSON/date error.

**Still requiring full end-to-end verification:** whether every migration stage ultimately completed, how the final application reads historical data, and whether new writes and background jobs behaved correctly after the upgrade.

I will not convert this into a “v4 migration complete” claim until those checks exist. The current record is useful precisely because it preserves what was known at each stage.
