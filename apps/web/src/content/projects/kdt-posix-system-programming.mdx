At the beginning of system programming, I was comfortable thinking in terms of **functions and objects**. The course forced me to think in terms of **processes, kernel-managed resources and events that may occur at inconvenient moments**.

I started asking questions like: if a program creates two workers, who closes their file descriptors? If a thread is waiting on a mutex, why might the program appear idle? If one side of a socket connection disappears, which operation notices first?

## 1. A process is more than its code

I learned to distinguish an executable file from a running **process with its own address space and open resources**. Process creation, execution and exit create lifetimes that the program must manage.

The course moved from memory layout and GDB/Makefile work toward process creation, signals and timers. One lesson I carried away was that code which behaves in a single execution path can fail once a signal, child process or timeout enters the system.

It also changed how I interpret error handling. A system call can fail because of a permission boundary, a missing resource, a transient condition or an interrupted operation. A robust program must decide **which errors are retryable, which should be reported, and which require cleanup**.

## 2. Threads: sharing makes coordination harder

Threads can share address space and process resources. That makes them convenient for cooperating work, but shared state creates races. We studied locking, mutual exclusion, critical sections and synchronization in a way that made the trade-off clear:

- **Too little synchronization:** operations see inconsistent or partially updated state.
- **Too much synchronization:** threads serialize unnecessarily or may wait indefinitely.
- **Wrong lock ordering:** a program can deadlock even if every individual data structure is protected.
- **Unclear ownership:** threads may access state that has already been freed or closed.

What mattered to me was not memorizing pthread function names; it was developing a habit of identifying the **shared invariant** before choosing the lock.

## 3. IPC: a channel is an agreement

I worked through the concepts behind pipes, FIFOs, POSIX message queues, semaphores, shared memory and System V IPC. These mechanisms differ in their data model, visibility and lifetime.

| Mechanism | Useful mental model | Design trap |
| --- | --- | --- |
| Pipe/FIFO | Ordered byte stream between cooperating processes | Framing and EOF depend on reader/writer ownership |
| Message queue | Discrete messages with queue limits | A full queue can block or fail a sender |
| Shared memory | Both sides can address the same data | Data visibility needs synchronization |
| Semaphore/mutex | Ordering and mutual exclusion | Correct ordering does not repair an incorrect protocol |
| `mmap` | A mapped region with specific lifetime/protection | Mapping lifetime and backing object still matter |

This made it easier to understand that **data transfer** and **coordination** are separate concerns. Shared memory may avoid copying data, but it does not make two processes agree when a record is complete.

## 4. File descriptors are the common boundary

One concept kept reappearing: the file descriptor. Files, pipes and sockets all use it as a process-visible handle to kernel-managed objects. Descriptor allocation, blocking behavior and cleanup determine much of the program's behavior under failure.

I learned to think carefully about what happens after a fork, which process keeps which endpoint open, and why forgetting to close one unused descriptor can stop the other side from observing EOF.

The course also introduced alternative I/O models such as **epoll**. The value of event-driven I/O becomes clearer when a server must handle many connections without keeping a thread blocked on every client operation.

## 5. TCP and UDP: different contracts

In the network programming portion, we studied C/Python client/server examples, sockets and I/O multiplexing. I distinguished **TCP's ordered byte stream** from **UDP's datagram model** and learned why message boundaries must be designed at the application layer for TCP.

A simple file server or chat service illustrates the design choices: framing messages, handling partial reads/writes, disconnect detection, timeout behavior and deciding what to do when clients are slow.

My strongest takeaway was that **a socket server is a concurrent state machine**, not merely a loop that calls `recv()`.

## 6. Debugging what the program actually owns

When a program behaves strangely, I find it useful to separate process state, kernel-visible handles, synchronization and network state. Logs from the application are only one perspective. A debugger, process/file-descriptor view and system-call trace each answer different questions.

The course gave me this mindset before I worked with asynchronous internal services and containerized applications. Later, queue workers and database connection pools made the same lessons relevant again: **timeouts, ownership and retries must be part of the design rather than last-minute fixes**.
