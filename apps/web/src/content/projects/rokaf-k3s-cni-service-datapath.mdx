An application kept failing during startup because it could not resolve an internal service name. Not every Pod was affected. I inspected the network on a K3s host and found that its Flannel interface was up, routes to Pod networks existed, and Kubernetes Service-related NAT rules were present.

Those observations looked reassuring but did not explain the failing request. A route to a **Pod IP** and a working connection to a **Service ClusterIP** depend on different packet-processing steps. I had checked that several pieces were installed; I had not shown that the affected DNS request actually crossed them.

The DNS and Service-IP reachability investigation remained a separate packet-path problem: the records did not preserve a synchronized capture identifying its failing rule. **I also worked through an iptables rule-application failure during K3s startup and recovered a successful rule bootstrap**, as the later regenerated rules and `bootstrap done` log showed. The recovered startup and the still-open DNS investigation should not be mistaken for one incident.

## Pod IP routing and Service translation

A destination **Pod IP** identifies an endpoint. In a K3s environment using Flannel, Linux routing and CNI-managed networking determine how packets travel to that Pod. Same-node delivery and cross-node transport may use different paths, depending on the configured Flannel backend.

A **ClusterIP** is a virtual Service address. In the kube-proxy **iptables mode** described by Kubernetes, packets addressed to a Service's IP and port are intercepted and destination-NATed to an eligible endpoint. The translated packet still needs a viable path to the chosen backend. Other kube-proxy modes, or an alternative Service datapath, implement the interception differently.

That is why the absence of a conventional route for a Service CIDR did not immediately explain the incident. I could see routes for Pod networks, but the Service range did not have to appear as another ordinary route. I first needed to establish which Service proxy mode the node actually used and whether the particular query matched its programmed forwarding path.

The first useful comparison would have been to send the **same application request from the same Pod**, once to the appropriate backend Pod IP and once through the ClusterIP. A success on the direct path with failure through the Service would narrow the search toward Service selection, translation or stateful return processing. A failure on both paths would make direct routing, filtering or the endpoint process more relevant.

This is a proposed controlled comparison. I did not preserve a paired result from the original outage that conclusively selected one of those branches.

### Namespace boundaries and the first routed hop

A typical Linux Pod has its own network namespace, including interface, routing and socket state. A veth pair connects two network contexts: transmitting through one end delivers the Ethernet frame to the other. With a bridge-based CNI configuration, the host-side veth is attached to a bridge. Same-subnet Pod traffic can be switched at layer 2; traffic outside that subnet can go through the Pod's default gateway and the host's layer-3 forwarding path. Host-network Pods and other CNI implementations differ.

Network namespaces do not mean that every Pod has its own independent physical NIC. Nor does a bridge imply that every Ethernet frame is routed by the host. With bridge netfilter enabled, bridged traffic can also encounter IP-layer filtering; the relevant kernel settings and chain family matter. A capture on a Pod interface, host veth or tunnel device answers different questions.

## Flannel interface and overlay reachability

I did inspect a Flannel interface in the UP state. That confirmed that the local interface existed and was not administratively down. It did not establish that a packet could travel between every pair of nodes.

With K3s, Flannel is part of the integrated networking setup; it does not necessarily appear as a separately deployed `flannel` Pod with a standalone image. A search for such a Pod returning nothing is therefore not proof that Flannel was absent. The relevant host interface, K3s agent state, routes and forwarding traffic deserve inspection.

A same-node Pod-to-Pod request can work even if a cross-node encapsulated packet is being dropped. A cross-node request may traverse an overlay, host routing and filtering rules. Even if it reaches the destination, its reply can take a different path or fail to match expected connection state.

### VXLAN, routing and encapsulation

For the usual Flannel VXLAN example, the source host's route for a remote Pod subnet points toward a tunnel device. Flannel's VXLAN implementation installs route, neighbor and forwarding-database state for remote nodes. The neighbor entry resolves the remote tunnel endpoint's link-layer identity, and the FDB maps that identity to a remote underlay address. These entries cooperate; an UP flag alone checks none of the remote mappings.

A VXLAN tunnel carries an inner Ethernet frame inside an outer UDP/IP packet. The inner IP destination remains the remote Pod, while the outer IP destination is the receiving node's tunnel endpoint. At the receiving end the outer headers are removed, then the inner frame proceeds toward the backend. Encapsulation adds overhead: for an IPv4 underlay, the conventional Ethernet plus IPv4, UDP and VXLAN headers consume 50 bytes of additional space relative to the inner IP packet, excluding optional tags and other overhead. An illustrative 1500-byte underlay IP MTU therefore permits a 1450-byte inner IP packet. The actual MTU and backend must be inspected rather than inferred from this arithmetic.

The original November 24, 2025 messages included the name of the Flannel interface and the reported route state, but not a complete backend or tunnel inventory. They also contained a separate TCP connection timeout to an address in the Pod range. I retained that as evidence of another failed request, not proof that the VXLAN path was at fault or that the destination was an ordinary Pod.

I separated the readings I actually had from the tests I still needed:

| Evidence | What it supports | What it cannot establish |
| --- | --- | --- |
| Flannel interface UP | Local interface and link state exist | Working cross-node transport |
| Pod network routes visible | A route has been installed | Delivery, filtering and reply path are correct |
| Service NAT entries visible | Service-related rules have been written | The failed packet matched those rules |
| EndpointSlice with ready endpoint | Kubernetes has candidate destinations | An endpoint responds to the actual request |
| DNS request failed from some Pods | Those clients did not complete name resolution | The CoreDNS process itself failed |

The last row was particularly important. An application reporting a DNS timeout identifies a failed operation, not automatically a malfunctioning resolver. I needed to learn whether it could contact the DNS Service, whether that Service forwarded the packet, and whether CoreDNS answered.

### Follow the address tuple rather than the Service name

Consider a fictional UDP client at 192.0.2.10:40000, a DNS Service at 198.51.100.53:53 and a chosen endpoint at 203.0.113.20:8053. These are documentation-only addresses and illustrative ports, not the cluster's configuration. In the ordinary routed iptables Service example, DNAT rewrites the destination to the endpoint before the forwarding route is selected. Assume no hairpin, external source or other masquerade condition; the client source is preserved. The endpoint sees a request to its own address and target port, not to the virtual Service address.

The return packet originates at the endpoint's address and port. It must traverse the translation context where the connection-tracking NAT binding was created. Reverse DNAT then changes the source back to the Service address and port. The client receives the reply from the peer it originally addressed. This is why capturing only the request or only a backend's local response is insufficient to establish that the client received a correct reply.

Connection tracking associates packets with an original-direction and a reply-direction tuple. For stateful NAT, a matching first packet establishes the binding and later packets use it. UDP has no TCP-style handshake, but the kernel can still track its traffic and whether a reply has been observed. A new DNS query can use a different tuple; a counter on a NAT rule is not a count of every packet in a tracked flow.

The optional SNAT case is distinct: if a policy requires source masquerading, the backend receives the translated source tuple. The reply must undo that change to recover the client destination, as well as undo DNAT to restore the Service source. The companion generator checks both round trips and rejects an unrelated reply. It is a tuple transformation model, not a live kube-proxy or kernel NAT experiment.

## ICMP probes and DNS request paths

During troubleshooting I attempted to ping the DNS Service IP. The result was not a sufficient DNS test. A Service virtual IP is not an ordinary host required to respond to ICMP echo requests; its configuration defines traffic through specific ports and protocols.

For CoreDNS, the meaningful test was a DNS query over UDP port 53, and TCP where appropriate. The same question could be sent directly to an appropriate CoreDNS endpoint from the affected Pod to distinguish resolver behavior from Service translation.

A minimal inventory before performing that comparison would look like this:

```bash
kubectl -n kube-system get service kube-dns
kubectl -n kube-system get endpointslices \
  -l kubernetes.io/service-name=kube-dns
```

Those are read-only inspection examples, not commands copied from a successful incident run. The query itself would then be repeated from the **same source network context** against the returned ClusterIP and an eligible endpoint. Protocol, port, question, time and selected endpoint all matter when comparing the outcomes.

In the original notes, I had the failed operations and host-state inspection but did not capture that complete side-by-side experiment. A failed Ping and a missing Service-CIDR route did not fill the gap.

## Netfilter rule ownership

The Service NAT rules I saw were not the only rules a packet might encounter. Docker had also been used on hosts in the K3s environment, with K3s running its containerd-based workloads. Both runtimes could configure parts of the same host networking stack, even though they did not manage each other's containers.

I needed to separate **what a packet traversed** from **who installed the rules**. For forwarded traffic, a simplified iptables-based path includes destination translation at `PREROUTING`, routing and filtering around `FORWARD`, and possible source translation at `POSTROUTING`. Host-generated traffic can instead enter through `OUTPUT`; not every request traverses all three forwarded-packet hooks. The exact rules and their evaluation order depend on the active proxy, firewall backend and chain configuration.

Docker's iptables backend may install `DOCKER-USER`, other Docker-specific chains, masquerading and published-port rules. Depending on its configuration, Docker can also set the default `FORWARD` policy to `DROP`. K3s networking has separate writers: kube-proxy for Service handling in the applicable mode, Flannel/CNI for Pod forwarding or masquerading, and the network-policy controller for workload filtering. The presence of rules from these owners was a reason to inspect their interactions—not evidence that Docker had damaged Kubernetes rules.

### Hook selection and the routing decision

The usual IPv4 forwarded path starts with PREROUTING, then a route decision, FORWARD and POSTROUTING. Connection tracking normally attaches state before destination NAT. If the post-DNAT destination is local, the packet instead follows INPUT; a host-originated request starts through OUTPUT, with a route reconsideration if its destination changes. On a typical forwarded path, source NAT is applied at POSTROUTING after the forwarding filter. These are logical hooks, not a promise that every configuration uses identical chains or priorities.

This distinction explains the value of different counters. FORWARD filtering can see the translated backend destination, not necessarily the original virtual IP. Connection tracking exposes the original tuple, while a capture on the backend interface observes the packet after forwarding decisions. A Service rule may select a backend correctly and yet its packet can be dropped later. Conversely, a missing NAT-rule counter increment can reflect a previously established NAT binding rather than a missing Service rule.

I would check conntrack count and max in the relevant namespace, together with insertion-failure or drop statistics and matching flow state. A high count alone is not proof of table exhaustion. The captured original and reply tuples, timestamps and interfaces must match the actual failed query. There is no preserved measurement of these counters in the original incident.

The rules themselves also change meaning across backends. In Docker's **iptables** backend, `DOCKER-USER` is an early user-policy point in the forwarding chain. Docker's **nftables** backend does not create the same `DOCKER-USER` chain; nftables base chains and priorities matter instead. I did not record enough version-specific host output to say an iptables/nftables frontend mismatch caused this incident.

For the DNS failure, the inspection I actually had showed Service NAT entries, not the complete effective ordering of translation, policy filters and return-state handling. A `KUBE-SVC-*`-style entry being present would not show whether the affected packet matched it. Nor did I have a measured `conntrack` table limit, an exhaustion counter or a packet trace proving a connection-tracking failure.

## K3s iptables Bootstrap Recovery

Another network-related operational record offered firmer evidence, but at a **different point in the lifecycle**. During K3s startup, the log contained an iptables bootstrap failure:

```text
Failed to bootstrap IPTables:
failed to apply partial iptables-restore
```

The accompanying failure indicated that `iptables-restore` could not acquire the xtables lock while another process held it. This was a problem **applying rules**, not proof that an existing Pod packet had been dropped by a Docker chain.

I investigated the lock contention while restoring the K3s network rule initialization. During that work I removed `/run/xtables.lock` and restarted K3s; the lock file appeared again, and the first restore attempts still failed. I continued the recovery until the rules were regenerated and K3s logged **`bootstrap done`**. **The iptables bootstrap interruption was cleared and K3s completed its rule-initialization phase.** The surviving record does not identify which process originally held the lock or prove that deleting the file was the step that fixed it.

The lock file's mere existence is normal: `iptables` uses it to coordinate exclusive access. Removing its pathname is not a general repair procedure and does not establish that the underlying lock holder has stopped. The `iptables-restore` utility supports waiting for the exclusive lock with `-w`, but I did not verify that changing K3s's invocation to use this option was an implemented remediation.

### Why removing a lock pathname is not unlocking

The xtables manual describes an exclusive lock file. Public iptables source uses flock on an open descriptor for the lock. The pathname and open file description are different kernel objects, as in the [VFS investigation](/projects/linux-vfs-mount-lifecycle/). If an existing lock file is unlinked while a writer still holds it, that descriptor can keep the old inode and its lock alive. Recreating the same name can produce a different inode and a separate lock domain. Two writers could then believe they have exclusive access, despite using the same pathname at different times.

I tested this mechanism using an ordinary file in a temporary directory, not the real xtables lock. Two independent opens of the original inode competed for an exclusive lock: the second received a nonblocking contention error. After unlinking the disposable name and creating a new file under that name, the new inode could be locked while the original lock remained held. A further independent open of the new inode was blocked. Releasing the original lock allowed the waiting original-inode descriptor to lock it, without changing the new inode's lock.

The experiment demonstrates why deleting the lock file was not a sound general recovery procedure. The historical success was the regenerated rules and bootstrap completion, not proof that unlinking made competing writers safe. In another incident I would identify the actual lock holder and effective invocation, use supported waiting or coordination where appropriate, and verify rule application separately from traffic delivery.

This was an actual **rule-bootstrap recovery**, not just an architectural hypothesis: K3s progressed from a failed iptables-restore attempt to regenerated rules and a completed bootstrap. It remains distinct from the intermittent **Pod-to-ClusterIP DNS failure**, for which the available packet-path evidence did not determine a single root cause.

## Evidence before rule changes

For a repeat failure, I would record the effective firewall backend and the relevant chain policies on the affected host at the same time as a real test request. Read-only inspection can start with commands such as:

```bash
sudo iptables -S FORWARD
sudo iptables -t nat -S
sudo nft list ruleset
```

These are examples of observations to collect in an authorized maintenance context, **not outputs from the original failure**. Actual rules can disclose internal networks and must not be pasted into the public case study. I would also correlate the packet's incoming interface, the Service's selected Endpoint, policy counters, `conntrack` state and the return path. A rule with a matching name may not be on the packet's active path.

I would not blindly flush `iptables` chains, change the host's default forwarding policy, disable Docker's rule management or swap CNIs as a diagnostic shortcut. Those actions can cut off unrelated services and destroy the very state needed for attribution. The retained packet-path record does **not** establish Docker-caused `FORWARD DROP`, an nftables mismatch or conntrack exhaustion as the cause of the separate DNS incident. This does not undo the observed success of the K3s iptables bootstrap recovery.

The order matters because each request is intended to rule out only part of the stack.

| Comparison from a controlled source | What it could isolate |
| --- | --- |
| Direct backend Pod IP and correct target port | The endpoint process and sampled Pod routing path |
| Service ClusterIP and configured Service port | Service interception, endpoint selection and forwarding |
| DNS query against ClusterIP and endpoint | Transport path versus DNS resolver behavior |
| Same-node and cross-node Pod destinations | Local CNI delivery versus inter-node transport |
| Matching rule counters and conntrack events | Whether the inspected packet-processing path was visited |
| Same request from affected and unaffected Pods | Source node or placement dependency |

A direct backend request and a Service request are not always interchangeable without adjusting their ports: a Service's `port` can map to a different backend `targetPort`. The comparison must preserve the same intended application operation.

No test here supplies a final diagnosis on its own. A direct request that works once does not prove the overlay or endpoint is reliable throughout a longer outage. A packet counter rising on one chain does not prove a response returned to the client.

## Why I did not turn this into a Cilium migration

During later K3s planning I considered what using another CNI, including Cilium, would change. That involved its kernel requirements, Service proxy options, policy model, observability and the practical cost of deploying and upgrading it in an offline environment.

But I did not establish that Flannel's implementation was the cause of this particular DNS failure. Migrating the networking stack would introduce new state and different failure modes before answering the original question. The record supports **Flannel operation and an evaluation of alternatives**, not an implemented Cilium rollout or a demonstrated Cilium-based fix.

This incident is also distinct from [the ServiceLB host-port conflict](/projects/rokaf-service-lb-hostport-conflict/). In that separate case, adding a LoadBalancer Service was followed by `svclb-*` host-port occupation; removing the Service restored the earlier access path. The problem was host-port ownership, not the Pod-to-ClusterIP translation path under investigation here.

## Observed Packet-path Evidence and Next Checks

**Completed operational recovery:** K3s initially failed to apply iptables rules because of xtables lock contention. After troubleshooting and restarting, the rules were regenerated and **`bootstrap done` confirmed the successful bootstrap checkpoint**. The exact lock holder and causal intervention were not retained.

**Separate investigation:** some Pods experienced DNS/Service-IP access failures despite a visible Flannel interface, Pod routes and Service NAT rules. A Pod-range request also timed out. These observations were not collected as one synchronized packet trace.

**Still open for the DNS path:** whether an effective `FORWARD` filter, conntrack, Service proxying or the Flannel return path interrupted the failing traffic. A change to Cilium was evaluated, not deployed as the confirmed repair.

If the incident recurred, I would first capture a real query from an affected Pod, compare it with a direct endpoint request, and then examine the effective proxy and host filtering path on the source node. I would repeat the same request from an unaffected location and keep the return traffic in the trace. Until those observations exist, the cause remains open.
