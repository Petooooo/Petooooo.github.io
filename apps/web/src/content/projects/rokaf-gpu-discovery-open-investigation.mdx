While installing NVIDIA GPU Operator on a GPU-equipped K3s node, I encountered a log message that reduced a complicated-looking issue to one small clue: `no nfd label found`. The server had a GPU, but the Operator was not finding the node metadata it expected. In the configuration I was examining, `nfd.enabled=false` was set.

I could have described this as “Kubernetes did not recognize the GPU” and moved on. But that statement skips a question I eventually had to ask: **what, exactly, had failed to recognize it?** A label used to classify a node is not the same thing as an extended resource advertised to the scheduler. Neither proves that a model will initialize successfully inside a container.

The investigation was not a clean, single-setting recovery story. It became a way to distinguish the evidence at each boundary instead of assigning every later GPU problem to that first message.

## The label that was missing was not the GPU itself

The `nfd.enabled=false` value means the GPU Operator is not deploying its own instance of **Node Feature Discovery (NFD)**. That can be intentional when NFD is already installed and operating independently in the cluster. If no suitable NFD instance is publishing the relevant hardware labels for a node, however, the Operator may be unable to recognize the node through the labels it expects.

So the next question was not simply whether to flip the value to `true`. I needed to establish whether another NFD installation existed, whether it was discovering the intended nodes, and whether its results had appeared on the Node objects.

There is a similarly named but distinct component: **GPU Feature Discovery (GFD)** contributes GPU-specific metadata about products and capabilities. NFD's node-hardware classification and GFD's GPU feature information are related to discovery, but they do not serve identical purposes, and neither is the kubelet's allocatable GPU count.

The missing-NFD-label message was an observed symptom at the discovery and node-selection boundary. I have no preserved, comparable before-and-after inventory proving that changing only the NFD setting fixed every node or completed the resource registration chain.

## A GPU label was not an allocatable GPU

I came to separate several things that can all be called “GPU visibility.”

The host driver needs to recognize the physical device. The container runtime must provide the required device and driver interface to a GPU-enabled workload. Discovery components publish node metadata. Separately, the **NVIDIA device plugin** registers extended resources through the kubelet, which Kubernetes exposes in values such as `status.allocatable["nvidia.com/gpu"]`.

A node label describes a property. An allocatable resource is a quantity the scheduler can account for when a Pod requests a device. It is possible to have labels without the expected allocatable resource; the absence of one kind of GPU feature label also does not by itself establish that the allocatable count is zero. The two should be checked, not inferred from each other.

That distinction changed the diagnostic order I wanted to use:

| Evidence to inspect | The narrow question it answers |
| --- | --- |
| Host driver and device interface | Can the operating system recognize and communicate with the GPU? |
| NFD and GFD node metadata | Is the node classified and labeled as expected? |
| Device plugin and kubelet | Does the node advertise a matching allocatable GPU resource? |
| Scheduler event and Pod specification | Can this request be placed given selectors, taints and remaining resources? |
| Runtime and model initialization | Can the container access the assigned device and actually run the model? |

This table is a **proposed evidence sequence**. It is not a checklist I can mark complete for every production node in the original incident.

## A Pending Pod could be blocked after discovery succeeded

Even with a correctly registered device, the scheduler may not place the Pod. The GPU resource name and quantity must match what the node advertises, and `nodeSelector`, node affinity, taints, tolerations, CPU and memory constraints all participate in the decision.

Pinning a workload to one familiar GPU node can be a tempting workaround. It may provide a short-term route to a working Pod without explaining why another node was not eligible. It can also quietly eliminate alternative placement options when that first node fails.

For a Pending workload, I would examine its scheduling events alongside the node's `capacity` and `allocatable` values before attributing the problem to the GPU driver. A CUDA initialization error cannot explain a Pod that has never been scheduled.

The reverse distinction also matters. A Pod reaching Running does not prove that the assigned device works for its application. The process must initialize the device, load model weights and allocate runtime buffers and KV cache within physical VRAM. A successful scheduling decision is only one of the gates.

## DCGM Exporter taught me the same lesson from another direction

I had a separate GPU observability investigation involving **DCGM Exporter**. In one episode it was scheduled onto non-GPU machines, where the Pods became stuck in `ContainerCreating`. In another, its placement was tied to one GPU machine while a second expected GPU machine was uncovered. A direct connection to the expected exporter endpoint on the uncovered node returned connection refused.

Those observations were about **monitoring coverage**. They were not proof that a GPU device had disappeared or that the device plugin had registered zero resources. Conversely, a running exporter on one host would not establish correct resource registration and scheduling across the fleet.

I preferred to reason about exporter placement using verified GPU-role information rather than an individual node name. I do not have a preserved, comprehensive after-change fleet audit. The separate [observability investigation](/projects/rokaf-observability-and-failure-evidence/) retains those two scheduling episodes and their evidence boundaries.

## Time-slicing was not a cure for a missing device

I also configured GPU time-slicing for shared workloads and compared it with whole-GPU allocation and MIG on supported hardware. That was a **capacity-policy decision**, not a replacement for NFD, GFD or device-plugin registration.

Advertising several logical GPU access slots does not cause an absent GPU resource to appear or multiply its physical memory. MIG partitions resources on supported accelerators, but it likewise does not repair a node-label discovery failure. It would have been a mistake to tune the sharing mode while the earlier discovery and allocation questions remained unanswered.

The [GPU scheduling and capacity record](/projects/rokaf-gpu-scheduling-and-capacity/) covers that later distinction: a schedulable slot and enough real VRAM for a model are different promises.

## The evidence I still needed

If I returned to this problem, I would capture the Operator configuration, independently installed NFD components and actual node labels at the same time. Next I would inspect the device-plugin Pods and the kubelet's capacity and allocatable values, then submit a minimal GPU request and record the scheduler decision and successful device initialization. These are controlled follow-up checks, not a reproduction I can claim to have completed.

The strongest surviving fact is narrow: **the Operator did not find expected NFD labels in the observed configuration**. It was worth investigating, but it did not establish one root cause for every GPU node, validate all GPU sharing settings or produce a benchmarked performance improvement.

The machine's GPU was only the beginning of the story. Between the hardware and a useful model process were node labels, registered resources, placement decisions and runtime behavior—each with a different source of truth. What I wanted from the platform was not simply to report that a GPU existed, but to explain **why Kubernetes could safely treat it as a usable resource**.
