I already had a reason to care about the hardware side of computing: I studied electronic engineering alongside computer science and had worked with FPGA/embedded projects. What I wanted from the embedded Linux part of KDT was a different perspective—**how a general-purpose OS exposes hardware through stable interfaces while hiding device-specific details**.

Working through the course's ARM and Raspberry Pi modules, I found that a driver is as much about **lifetimes, concurrency and execution context** as it is about setting registers.

## 1. A system must boot before it can run my program

The early embedded units connected **bootloader responsibilities**, kernel configuration, root filesystem construction, cross-compilation and remote development.

This made a simple distinction important: application developers usually begin with a running OS; embedded developers may have to establish **the environment in which the OS can run**. The hardware's execution state, boot image, device description and available console all affect what can be debugged.

The ARM material extended this with exception levels, registers, calling conventions and exception handling. It helped me connect instruction-level behavior with the operating system's higher-level notions of process context and protection.

## 2. Describing hardware is not the same as driving it

I studied device-tree concepts, platform devices and the Linux device/driver model. A device description says what hardware exists and how it is wired; a driver supplies the operations that let the kernel and applications use it.

The design question I found interesting was **what belongs in data versus code**. The same logical driver can support several hardware configurations if the hardware-specific resources are described accurately rather than hard-coded throughout the program.

The course also introduced character devices, `sysfs` and `procfs` interfaces, which gave another perspective on how device state is made visible to applications and administrative tools.

## 3. GPIO, SPI and PWM require different models

The curriculum covered GPIO, SPI, PWM, UART/interrupts and USB topics, along with board-level interfaces. I learned not to treat these as interchangeable ways of “talking to hardware.”

| Interface | Question I connected it to |
| --- | --- |
| GPIO | How does software observe or drive a simple digital signal? |
| SPI | How are commands and data exchanged with a peripheral? |
| PWM | How does a periodic signal encode control via duty cycle? |
| IRQ | How is an asynchronous hardware event reported to the CPU? |
| Device tree | Where does the kernel learn about hardware resources and compatible drivers? |

The tricky part is often not reading a value once. It is making interactions robust to **initialization order, resource ownership, interrupted operation and cleanup**.

## 4. Interrupt context changes the rules

The most lasting lesson was understanding why hard-IRQ handlers must remain short and avoid operations that can sleep. Drivers may use **threaded IRQs, workqueues or timers** to process work that should not block interrupt handling.

I thought of the data path as a sequence:

1. Hardware signals an event.
2. The kernel receives it in an interrupt context.
3. The driver acknowledges or captures the minimal necessary state.
4. Deferred execution performs the longer work if needed.
5. The final result reaches a device buffer, driver interface or userspace process.

Concurrency becomes important when interrupts arrive faster than their deferred work completes. The driver must decide what to buffer, coalesce, drop or back-pressure and what state is safe to share across contexts.

## 5. Resource lifetime and error handling

Kernel code must release resources even when an intermediate initialization step fails. I studied how a device driver has to account for hardware mappings, IRQ ownership, kernel allocations, worker teardown and module lifecycle.

This is the same class of engineering discipline I later used with containers and stateful services: **setup is only half the lifecycle**. Shutdown, failure, restart and resource cleanup define how the system behaves over time.

## 6. How this fits my future work

My long-term direction is less about designing a new peripheral and more about improving the **OS interfaces and resource-management mechanisms** between applications and devices.

Still, studying ARM, interrupts and driver models gives me important context for future storage research. SSDs, NVMe controllers and other high-performance devices ultimately depend on carefully designed software/hardware interfaces, I/O queues and completion behavior.

I intend to revisit driver concepts through controlled Linux experiments rather than presenting the course's example drivers as my own published products.
