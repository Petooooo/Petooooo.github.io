> **Source revisited: the original *RTOS를 이용한 Mini Desktop 설계* final report (64 content pages, plus one blank page).** This was a collaborative university project completed in 2023. I worked on the overall architecture, embedded logic and RTOS coordination. The original report includes block diagrams, C code, board photographs, GPIO tables, terminal screenshots and a full source appendix. I reconstructed the accompanying SVGs from those materials; **they are neither unmodified screenshots nor newly measured hardware results**.

The first challenge was deciding what *desktop* should mean on three STM32 microcontrollers. I wasn't trying to recreate a commercial window manager. I wanted a cursor, overlapping windows and small applications to continue behaving sensibly while input, sensing, screen composition and game updates were happening concurrently.

The report describes three requirements behind that goal: controlling the cursor through push-buttons, running multiple application tasks at the same time, and detecting user inactivity to enter and leave a sleep state. We ended up distributing ten FreeRTOS tasks across three boards.

The original system diagram groups the hardware into an ultrasonic/presence board, a button/cursor-input board and a desktop display/logic board. **Board 1 runs Tasks 1, 5 and 8; Board 2 runs Tasks 2, 3 and 4; Board 3 runs Tasks 6, 7, 9 and 10.** Those numbers are not merely diagram decorations: they correspond to the task names and C code in the report's appendix.

I needed to correct one imprecise description from the previous version of this article. **The inter-board control and six-bit sensor data used GPIO signals.** Board 3 then assembled the ASCII desktop and sent it to a PC terminal over **UART2**. Individual board code also contains UART debugging, but that does not make UART the transport between the three boards.

This distinction changes how I think about the failure modes. A GPIO input is read as a collection of signal levels. The serial display is a stream of characters, where an update in the middle of a frame can corrupt what the user sees. Their timing problems are different, even if both are part of the same interaction.

## Board 1: ultrasonic distance and the decision to sleep

Board 1's three tasks were **`ULTRASONIC_Task`**, **`SleepCount_Task`**, and **`SleepButton_Task`**. Their reported creation priorities were 2, 1, and 3 respectively. The manual sleep-button path was deliberately given a high priority so it could react when other sensor or counter logic was running.

<figure className="project-concept-figure">
  <a href="/figures/journals/mini-desktop-03-board1-original.svg" target="_blank" rel="noopener noreferrer" aria-label="Open full-size diagram: Block arrangement for ultrasonic sensing, inactivity counting and sleep-button handling on Board 1.">
    <img src="/figures/journals/mini-desktop-03-board1-original.svg" alt="Block arrangement for ultrasonic sensing, inactivity counting and sleep-button handling on Board 1." loading="lazy" decoding="async" />
  </a>
  <figcaption>Board 1's three reported tasks: ultrasonic sensing, inactivity counting and manual sleep control.</figcaption>
</figure>

The HC-SR04 ultrasonic sensor used `PA5` for TRIG and `PA6` for ECHO through `TIM3` input capture. Sending a HIGH pulse of at least `10µs` on TRIG initiated a reading. The ECHO HIGH duration represented the outward and return travel of sound. Instead of trying to observe the pulse using a coarse task delay, the design captured rising and falling edges in hardware.

<figure className="project-concept-figure">
  <a href="/figures/journals/mini-desktop-04-ultrasonic-input-capture.svg" target="_blank" rel="noopener noreferrer" aria-label="Open full-size diagram: Timing sketch of TIM3 Input Capture, HC-SR04 TRIG/ECHO signals and distance calculation.">
    <img src="/figures/journals/mini-desktop-04-ultrasonic-input-capture.svg" alt="Timing sketch of TIM3 Input Capture, HC-SR04 TRIG/ECHO signals and distance calculation." loading="lazy" decoding="async" />
  </a>
  <figcaption>The timer captures ECHO rising and falling edges before converting pulse width into distance; this is a mechanism diagram, not a measured waveform.</figcaption>
</figure>

With the report's assumed timer resolution of one microsecond and sound-speed approximation, the derived one-way distance was:

`Distance(cm) = Difference(µs) × 0.034 / 2`

The report also discusses timer overflow, falling-edge-first capture cases, and switching input-capture polarity for the next event. These are the details that made the sensor logic more than a call to read a peripheral.

I also found the alternative design discussion worth retaining. We considered using the RTOS tick for pulse timing, but the report records an unsuccessful attempt to increase the tick resolution enough to make that useful. At a **1ms** interval, a single tick represents roughly **17cm** of one-way ultrasonic travel under the same approximation. That error is too large for the centimeter-scale interaction we wanted, so the project kept TIM3 input capture. This is the report's implementation decision, not a universal claim that every FreeRTOS configuration is limited to the same tick rate.

### Turning distance into six GPIO bits

The sensor measurement was then **clamped at 63cm**, because six output bits encode values from 0 through 63. Board 3 received that value by reading six specified pins: PC9, PC8, PB8, PC6, PB9 and PC5, corresponding to distance bits 5 through 0.

We also had to treat proximity and inactivity as different triggers. The report used an ultrasonic presence flag, a timer/counter for inactivity, and a button/Move Enable signal to reset the inactive period. It describes an **approximately 15-second no-input rule** for automatic sleep, plus a direct manual sleep-button path.

A task priority does not by itself guarantee a response-time bound. The report records that the sleep-button task was placed above the other two tasks, and the final system demonstrates the intended screen transition; it does not contain a separate worst-case interrupt-to-display latency measurement.

## Board 2: making five buttons behave like a cursor

Board 2 had a much simpler job electrically, but not necessarily in its scheduling: `CLICK_Task` sampled button B1, `MOVE_Task` interpreted four directional switches, and `NONE_Task` emitted the no-movement state. It drove GPIO outputs including **PC1 (click), PA7/PA6 (direction), and PB6 (Move Enable)** toward the other boards.

<figure className="project-concept-figure">
  <a href="/figures/journals/mini-desktop-06-board2-original.svg" target="_blank" rel="noopener noreferrer" aria-label="Open full-size diagram: Board 2 switch inputs, Click/Move/None tasks and direction, enable and click GPIO outputs.">
    <img src="/figures/journals/mini-desktop-06-board2-original.svg" alt="Board 2 switch inputs, Click/Move/None tasks and direction, enable and click GPIO outputs." loading="lazy" decoding="async" />
  </a>
  <figcaption>Click, Move and None tasks share the button-to-GPIO interface, while Click remains independent of directional movement.</figcaption>
</figure>

A useful trick was to encode four directions with two bits. The Board 3 decoder documented these combinations for PC0, PC1 and PC2/Enable:

<figure className="project-concept-figure">
  <a href="/figures/journals/mini-desktop-07-cursor-direction-encoding.svg" target="_blank" rel="noopener noreferrer" aria-label="Open full-size diagram: Cursor direction truth table reconstructed from the Board 3 GPIO decoding logic.">
    <img src="/figures/journals/mini-desktop-07-cursor-direction-encoding.svg" alt="Cursor direction truth table reconstructed from the Board 3 GPIO decoding logic." loading="lazy" decoding="async" />
  </a>
  <figcaption>Two direction bits select Up, Left, Down or Right only while Enable is asserted.</figcaption>
</figure>

When Enable was 0, the two direction bits should not move the cursor. When Enable was 1, the direction bits selected Up, Left, Down or Right. The click signal could remain active while movement continued, allowing a window to be dragged rather than simply selected.

The report documents a real issue here: without protecting the mutually exclusive Move/None output state, both kinds of GPIO updates appeared together. The project used a shared cursor mutex to arbitrate that output path, while `CLICK_Task` was kept independent so a click could accompany movement.

### An inconsistency I would check again

The prose around the Move/None interaction says **Move should outrank None** when directional input is present. However, the original Board 2 `xTaskCreate` appendix assigns **`MOVE_Task` priority 1 and `NONE_Task` priority 2**, with `CLICK_Task` also at 2. I am not going to silently rewrite the historical code or assert which version was eventually flashed.

The ten-task inventory is still valuable, and so is the disagreement. It is a concrete regression question: read the running binary's actual task priorities and inspect which code path owns the cursor mutex when a button changes. Priority ordering is local to the FreeRTOS scheduler **on each board**, not a global ten-task ordering across three microcontrollers.

## Board 3: four tasks, one terminal desktop

The most visible part of the work lived on Board 3. `PrintNCalculate_Task` controlled cursor coordinates, window positions and the serial screen; `Sleep_Task` switched the display state; `Gomoku_Task` and `Curling_Task` updated their own application arrays.

    <img src="/figures/journals/mini-desktop-08-board3-original.svg" alt="Four Board 3 tasks for ASCII screen composition, sleep coordination, Gomoku and Curling." loading="lazy" decoding="async" />

This board did not display to an LCD. It built **ASCII text frames** and transmitted them over UART2 to a terminal connected to the computer. The source's terminal screenshots show small buttons for Gomoku and Curling and overlapping windows containing dots, grid lines, stones, scores and targets.

That constrained output made two details important. The program needed to decide the frontmost window when two windows overlapped, and it needed a consistent set of characters while constructing and sending the frame. It used state flags such as `gomokuScreen`, `curlingScreen`, `isClick` and `isChange`, and arrays `gomokuArray` and `curlingArray` for the games.

### Only redraw when the screen changes

The renderer composed the background, window layers and cursor according to the current position and active-window state. The report states that coordinate calculations needed a delay around **50ms**, while UART printing needed about **200ms**. It handled this relationship inside the shared PrintNCalculate task with `delayPrint` rather than treating every coordinate update as an immediate full-screen print.

Those are the delays described in the source code discussion, not an independently measured 5fps guarantee or a benchmark of the serial bus. What matters here is the original design decision: input may be handled more frequently than a full ASCII frame can sensibly be printed.

### Why I needed CoordinateMutex

An early failure was especially instructive. If a game task modified the array while PrintNCalculate was partway through printing, the terminal could show a mixture of the old and new screen. This is not a problem that adding a few more tasks would solve.

<figure className="project-concept-figure">
  <a href="/figures/journals/mini-desktop-11-coordinate-mutex-tearing.svg" target="_blank" rel="noopener noreferrer" aria-label="Open full-size diagram: Illustration of a torn ASCII frame compared with a frame protected by CoordinateMutex.">
    <img src="/figures/journals/mini-desktop-11-coordinate-mutex-tearing.svg" alt="Illustration of a torn ASCII frame compared with a frame protected by CoordinateMutex." loading="lazy" decoding="async" />
  </a>
  <figcaption>An illustrative mixed-character frame explains the reported shared-array conflict; it is not a copy of the terminal screenshot.</figcaption>

The report shows the project protecting screen-coordinate and game-array updates with `CoordinateMutex`. The intent was to ensure that a frame was consistent while it was assembled and sent. There is a trade-off here: a long serial transmission can also hold the lock longer than an input task would like. The report documents the need for the mutex and the observed mixed-screen behavior, but does not supply lock-hold-time traces. I therefore treat bounded lock duration as an engineering question, not as a measured property of the original build.

## Gomoku and distance-driven Curling

For Gomoku, a click on an empty grid point placed a stone. The two players alternated O and X markers, and clicking an occupied position did not consume a turn. The task updated the game's shared array, which the renderer later displayed.

Curling used the more unusual hardware link: a game piece or bottle cap moved toward the ultrasonic sensor. Board 1 sent the measured distance as six GPIO bits; Board 3 used the resulting `Distance` to update the displayed Curling ball and score. The report's usage sequence puts the target near **15cm**, describes visible movement within **50cm**, and includes a screen example of Player 1's score changing from **9 to 19 (+10)**.

## Sleep was a shared-state transition, not simply a black screen

Board 3's `Sleep_Task` watched the sleep GPIO signal, changed `screenState` and `isChange`, and used `SleepMutex` to coordinate activity. The source shows that the two games also participate in the sleep synchronization so their work can wait and resume with state preserved.

<figure className="project-concept-figure">
  <a href="/figures/journals/mini-desktop-16-sleep-resume-screen.svg" target="_blank" rel="noopener noreferrer" aria-label="Open full-size diagram: Active-to-blank-to-resumed screen state under Sleep_Task and SleepMutex coordination.">
    <img src="/figures/journals/mini-desktop-16-sleep-resume-screen.svg" alt="Active-to-blank-to-resumed screen state under Sleep_Task and SleepMutex coordination." loading="lazy" decoding="async" />
  </a>
  <figcaption>A blank display and mutex-gated game tasks are documented; a complete halt of all ten tasks is not.</figcaption>

It is tempting to describe this as “all ten tasks paused,” but that would be stronger than the evidence supports. The **screen transition and game-task mutex gating** are documented. The boards still have their own schedulers and housekeeping work; the source does not establish a complete hardware-wide suspended state across three chips.

The result screenshots show the terminal turning blank after the sleep button was pressed during an active Curling session. The important idea was keeping the displayed state and application state in agreement rather than treating sleep as merely clearing a character buffer.

## What the final report can actually prove

The original conclusion shows the three intended behaviors: cursor drag, concurrently open Gomoku and Curling windows, and a button-triggered blank sleep screen. The report additionally includes source code for the three boards, GPIO tables, demonstration photos, scheduling discussion and cases where an unprotected output conflicted.

The report documents **ten task creations**, inter-board GPIO connections and a serial desktop. It does not present formal timing guarantees, a worst-case latency study or a power-saving measurement. The source appendix also contains the **Move/None priority discrepancy** noted above. I have preserved that distinction rather than editing the narrative into an unrealistically flawless implementation.

## What I took from building it

Initially, three STM32 boards felt like three mostly separate programs. When I started passing actual user input, game state and screen output through them, the boundaries became much clearer. A one-bit GPIO level meant something different from an assembled UART frame. A mutex had to protect a real shared resource, not merely exist in the code. A high-priority task was useful only when its interactions with the rest of the system were understood.

It was a small Mini-Desktop, but it was my first clear experience of **scheduling, data ownership and synchronization as one system design problem** rather than three unrelated topics. That way of thinking became useful in later embedded and infrastructure work.
