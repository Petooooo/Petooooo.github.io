## The critical distinction

The most useful question in identity engineering is not just **“Who is this?”** but **“Which operation is this identity entitled to perform on which resource?”** Kubernetes access and user-facing application authorization answer different versions of that question.

| Layer | Identity | Authorization boundary |
| --- | --- | --- |
| Kubernetes API | User or ServiceAccount | API group, resource, namespace, verb and RBAC binding |
| Application login | OAuth/OIDC user | Authentication and session establishment |
| Product object | User / organization / project relation | Domain permissions and relationship-based rules |

## ServiceAccount and Kubernetes RBAC

I worked with ServiceAccounts for clients and workloads accessing the Kubernetes API and investigated permission tiers for **observation, development, and administration**.

A sensible observer can usually inspect workload status, events, and logs without receiving write permissions or access to Secrets. A developer may need namespaced workload operations, but `exec`, Pod creation and Secret access carry privilege-escalation risks. An administrator's cluster-scoped authority must be a deliberate exception rather than a convenient default.

The validation workflow I considered used explicit API scope and `kubectl auth can-i` checks, not the assumption that having a working kubeconfig implies correct least-privilege separation. **Design work and discussion of policy tiers do not by themselves prove that every tier was deployed unchanged.**

## GitLab OAuth2, Keycloak and OpenFGA

I worked with GitLab OAuth2 for sign-in to selected applications and explored central identity and fine-grained authorization through **Keycloak/OIDC** and **OpenFGA/ReBAC**.

These approaches are complementary rather than interchangeable:

- **GitLab OAuth2** is useful when an internal service can reuse a familiar identity provider for login.
- **Keycloak** provides a potential centralized identity, client and token-issuance model.
- **OpenFGA** expresses relationships such as whether a user is a member of a team, owner of a project, or viewer of a resource.

The interesting design trade-off is where to put policy decisions. Kubernetes-native RBAC protects the cluster API; an application's own data objects may need policy that Kubernetes has no knowledge of. I studied and worked on those integration boundaries, but do **not** claim that all applications were migrated to a single IdP or that every OpenFGA model reached production.

## Practical lessons

A successful login is not evidence of appropriate authorization. ServiceAccounts, human identities and service-to-service credentials should have separate lifecycles and auditing requirements. Role review should include dangerous combinations, not only the individual rule names.

This work changed how I thought about infrastructure security: **authorization is part of system architecture**, not a last-minute dashboard setting.
