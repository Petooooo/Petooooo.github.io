At first, the question looked like ordinary access control: *who should be able to operate which service?* As more applications and automation entered the platform, I found that there were actually **three different identity problems**. A CI job needs permission to call Kubernetes; a person needs to authenticate to an application; and a project member may have permission to read one object's data but not another's.

The mistake would have been to answer all three with a single “admin/user” switch. I approached each boundary separately, because **successful authentication is not proof that a particular action is authorized**.

## 1. Kubernetes API access: a ServiceAccount is an identity, not a permission

I worked with **ServiceAccounts** and the Role/ClusterRole and binding model. A ServiceAccount answers *which workload identity is calling?* A Role answers *which API resources and verbs should that identity access?* Bindings join the two at an appropriate scope.

The first practical design question was how to separate observability from mutation:

| Persona / use case | Needed capability | What I tried to avoid assuming |
| --- | --- | --- |
| Operations observer | View service health, selected events and logs | That every observer should read Secrets or exec into Pods |
| CI/deployer | Update a defined set of workloads | That building an image requires unrestricted cluster administration |
| Application workload | Access only the API resources it needs | That the default ServiceAccount is suitable for every service |
| Recovery operator | Perform unusual maintenance operations | That elevated credentials should be permanent in ordinary automation |

I considered **`kubectl auth can-i`** a useful validation tool, but only when interpreted with correct identity, namespace, resource and verb. A permission set can appear minimal and still contain dangerous combinations: creating Pods with attached service accounts, reading Secrets, and interactive `exec` deserve special scrutiny.

## 2. Why scope mattered more than the number of Roles

At the beginning it is easy to think a smaller YAML file is a simpler security policy. In reality, a few broad wildcard rules may grant far more access than many narrow rules. I preferred to reason from actual operations and build an explicit boundary.

The tension was real: an operator trying to restore a broken service needs enough access to act quickly, while a regularly running build job should not inherit that emergency authority. The separation between **day-to-day identities** and **exceptional recovery access** became an architectural concern, not merely a naming convention.

## 3. Application login does not solve business authorization

For selected internal tools I worked with **GitLab OAuth2** for sign-in. That addressed the problem of maintaining yet another password database and offered a familiar authentication path, but did not automatically solve application-specific access rules.

Consider a user who is authenticated and belongs to a team. The remaining questions are: can they view every team's projects? Who may invite other members? Are read-only relationships transitive? Who owns the lifecycle of the permission? These are not Kubernetes RBAC questions because Kubernetes has no knowledge of the application's domain objects.

## 4. Keycloak and OpenFGA: useful, but for different layers

I explored **Keycloak/OIDC** as a way to centralize identity and token issuance, and **OpenFGA** as a relationship-based authorization layer. I treated them as complementary.

- **Keycloak** can provide identity, clients, authentication flows and tokens. It does not on its own define every object's domain authorization.
- **OpenFGA** can express subject–object relationships such as `owner`, `editor`, or `viewer`, with inheritance through teams or organizations.
- **Kubernetes RBAC** still protects the Kubernetes API, independent of those application relationships.

The interesting design problem was *where to ask each policy question*. If each application invents its own role strings, the definitions drift; if every request relies on a shared policy engine without considering failure and latency, centralization can become a new dependency. I considered both consistency and availability when evaluating this direction.

## 5. What worked, and what remained design work

I had concrete Kubernetes API/RBAC and OAuth integration experience. For the wider Keycloak/OpenFGA approach, my records include **modeling and integration work**, but not a complete, independently verified cutover of all applications. I am intentionally keeping that distinction in the history rather than describing a fully uniform identity platform.

I also still wanted a systematic method to **audit effective permissions** across CI, human operators and applications—not just verify that each service could log in.

## 6. How I separated the authorization models

The first mistake in an authorization review is to confuse **the identity that authenticates** with **the resource that identity may modify**. A ServiceAccount accepted by the Kubernetes API, a user logged in through OAuth2 and a user assigned to an application team are not the same principal for every resource.

I drew the boundaries as follows:

| Boundary | Typical subject | Protected resource | Policy question |
| --- | --- | --- | --- |
| Kubernetes RBAC | ServiceAccount / Kubernetes user | API resource and verb | May this identity read/update a Deployment in this namespace? |
| OAuth2 / OIDC | Authenticated application user or client | Login/session/token | Who authenticated, and which token was issued? |
| Application roles | User/team role | Application feature | May this user enter this administrative page? |
| OpenFGA / ReBAC | Subject connected to an object | Project, document, workspace | Is this user an owner/editor/viewer through the relation graph? |

An OIDC token may contain claims used by the application, but **issuing a token does not itself prove the caller is allowed to edit a particular document**. That decision depends on the application's resource model.

## 7. ServiceAccount privilege design

For Kubernetes jobs I wanted permissions based on **the exact verbs and resources the job uses** rather than a cluster-wide role granted simply because the job initially failed with a 403.

An example of questions I would ask before creating a Role:

- Does the job only read Pods, or also create/patch Deployments?
- Is access needed in one namespace or across the cluster?
- Does `get` access suffice, or is `list/watch` required?
- Are Secret contents involved, or can a narrower identity/configuration solve the task?
- Who owns token rotation, revocation and incident auditing?

The principle is least privilege, but the real work is discovering a job's **actual API call surface**. A Role that looks narrow by name may still grant broad access through wildcard verbs or resources.

## 8. Modeling relationships without promising a complete rollout

I investigated Keycloak as an identity service and OpenFGA as a possible relationship policy layer. To evaluate the latter properly, I would start from small application objects:

| Relationship | Example question | Required reasoning |
| --- | --- | --- |
| `owner` | Can the creator modify all project settings? | Direct ownership and transfer semantics |
| `editor` | Can a team member edit one document? | Team membership and object grants |
| `viewer` | Can a user read a shared workspace? | Direct vs inherited access |
| Organization membership | Does removing a member revoke document access? | Inheritance and invalidation |
| Delegated admin | Who can invite another user? | Scope and privilege escalation |

A good ReBAC model must specify what happens when a relation is deleted, inherited, cached or unavailable. **Centralized policy becomes a dependency** and can create latency and availability questions of its own.

I distinguish this model exploration from a fully deployed platform-wide authorization cutover. My public record supports RBAC and OAuth work and Keycloak/OpenFGA consideration; it does not establish that every application used one unified policy backend.

## 9. A useful verification matrix

A role change should be tested with **positive and negative cases**:

1. A designated owner performs an allowed action.
2. An editor attempts an owner-only action and is denied.
3. An unrelated user cannot read a private object.
4. Revoking a relationship affects future requests as intended.
5. An unavailable external authorization service does not silently grant access.
6. Audit records distinguish authenticated identity from denied action.

This is a test-design matrix, not a claim that every case was run across all production applications.

## Takeaway

The most important insight was that **the privilege boundary should match the resource boundary**. A cluster administrator, a logged-in user, and an owner of one application object are not interchangeable identities.
