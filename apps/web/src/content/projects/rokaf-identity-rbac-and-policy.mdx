When I connected GitLab Runner to K3s and built a path for Kaniko to push images to Nexus, I began to use the word *permission* more carefully. The Runner needed to ask the Kubernetes API to create a build Pod. Once that Pod was running, Kaniko needed credentials to push to a registry. Both actions happened inside what looked like one CI job, but they crossed different security boundaries.

I ran into a similar distinction with human sign-in. Outline used GitLab for authentication, yet one investigation ended in an `ETIMEDOUT` while Outline's backend tried to reach GitLab's user information endpoint. The user saw a login failure. That was not evidence that the user lacked permission to read a document.

These experiences left me with three separate questions: **Can an automated job operate the cluster? Can a person sign in to the application? Once signed in, can they access this particular object?** A single administrator/user flag could not answer all three.

## The Runner needed an API identity; Kaniko needed registry credentials

With the Kubernetes executor, GitLab Runner asks Kubernetes to schedule Pods for its jobs. The identity making those requests matters. A Kubernetes **ServiceAccount identifies a workload**; the permissions come from the Role or ClusterRole rules and the bindings that associate them with that identity.

The useful questions were specific. Which namespace contains the build work? Does the Runner need to create a Pod, observe its status, or read particular logs? What permission, if any, does an automated deployment need to change a workload? None of those questions are answered by giving a generic job cluster-wide administrator access.

Then the image-building path crosses a different authority. Kaniko can start successfully and still fail to push an image if Nexus rejects its registry credentials or repository scope. Earlier still, the node's **containerd** must pull the job image before Kaniko exists. A registry certificate rejected at image-pull time cannot be repaired by widening the Runner's Kubernetes Role.

The same pipeline log may contain all of those failures, but they are not interchangeable. Kubernetes API authorization, container-runtime image access, and registry push authorization have different callers and different enforcement points. I worked through these integration boundaries in the [Nexus and Kaniko case study](/projects/rokaf-private-artifacts-and-ci/). That record does not amount to a formal audit proving that one Role fixed every later CI permission problem.

## A short Role was not necessarily a small privilege

A broad wildcard can make a Kubernetes Role easy to write while allowing much more than the job needs. Viewing Pod health and selected events does not require reading every Secret or opening an interactive `exec` session in every container.

I wanted to begin with the actual API operations instead: `get`, `list`, `watch`, `create`, `patch` or whatever was genuinely necessary for the task. Scope matters too. A namespace-scoped Role and binding can be more appropriate than a broad ClusterRoleBinding. Permissions to create Pods deserve particular attention because the resulting Pod may carry a ServiceAccount or access volumes and data with separate privileges.

I also did not want a routine build or deploy job to inherit the exceptional authority a person might need during an incident. Emergency maintenance and ordinary automation have different lifetimes and review needs.

`kubectl auth can-i` is useful for checking the effective decision, provided the tested identity, namespace, resource and verb match the actual request. A single successful `can-i` answer does not describe the entire permission set. Checking that a required operation is allowed is only half the test; unrelated and sensitive operations should still be denied.

## The GitLab sign-in failure was not an authorization denial

When Outline reported `connect ETIMEDOUT` while reaching a GitLab identity endpoint, I needed to trace the backend request, not grant the user a stronger application role. During related troubleshooting, `EAI_AGAIN` appeared as a separate name-resolution failure. A DNS lookup problem and a connection timeout can both look like “login does not work” to the person in the browser, but they happen at different points.

A browser displaying the GitLab authorization page says little about whether the **Outline server** can reach GitLab's token or user-information endpoints. Nor does a successful OAuth exchange imply that the authenticated person may edit every document.

This made the authentication/authorization distinction practical rather than theoretical. GitLab OAuth2 and OIDC help the application establish an identity and session. The application's own resource model still has to answer whether a user may administer a workspace, invite a member or edit a specific document. Kubernetes RBAC cannot see those domain objects.

I kept the observed failures and the unresolved parts of that investigation separate in the [Outline authentication record](/projects/rokaf-internal-app-auth-and-tls/). I do not present the timeout as a denied document policy or claim that every affected login path was subsequently verified.

## A document's owner is not a cluster administrator

Once several applications were in use, a shared sign-in system alone no longer seemed sufficient. A user might be able to view one workspace without being allowed to manage its members; a team member might inherit edit access to one document but not another; and removing a member should revoke access that was granted only through that team.

That is what interested me about **Keycloak and OpenFGA**, though for different reasons. Keycloak provides an identity and OIDC-client/token layer. OpenFGA offers a way to model relationships among a subject, a team or organization, and an object such as a document or project.

A token from an identity provider does not automatically tell a policy engine which document relationships exist. Likewise, an OpenFGA `owner`, `editor` or `viewer` relation does not replace Kubernetes' API authorization. They are different decisions that may need to interact in an application design.

This section describes **an explored identity and relationship-authorization model**, not a completed platform-wide deployment of Keycloak and OpenFGA. The directly supported operational work was the K3s/CI authorization boundary and GitLab OAuth integration; the wider object-policy design was an evaluation.

A shared policy service would also become a new dependency. What happens when team membership is revoked but cached authorization results remain? What should the application do if an external decision service is unavailable? The convenience of one policy model is not worth silently granting access when the decision cannot be obtained.

## Authorization Allow/Deny Tests

It is easy to test only the happy path. If a Runner can create the build Pod it is meant to create, the job appears healthy. But that result says nothing about whether it can also read an unrelated namespace's Secrets. A permission review needs both sides of that boundary.

I would apply the same method to document policies. An owner should be able to perform owner-only actions; an editor should not automatically inherit those actions. An unrelated user should not read a private object. Removing a team relationship should change subsequent access decisions as intended, without stale privileges remaining indefinitely.

My operational work covered **Kubernetes and CI authorization boundaries and GitLab OAuth integration**. Keycloak and OpenFGA were evaluated for object-level authorization rather than deployed as a completed, platform-wide policy service. For that design, I would require both allow and deny checks with the requesting identity, target resource and decision point captured together.
