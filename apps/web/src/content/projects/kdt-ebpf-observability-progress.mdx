One thing I wanted from system monitoring was to answer not only **how much CPU or memory was used**, but also **which event or kernel path explained the change**. The monitoring portion of KDT connected `/proc`, familiar process utilities, performance counters, eBPF/BCC and distributed-system dashboards.

## Metrics and traces ask different questions

A dashboard can show that latency increased after a workload change. It usually cannot identify the exact kernel event, syscall or scheduling decision responsible. A trace can show a fine-grained path, but gathering too much trace data can be expensive and difficult to interpret.

I learned to separate:

| Tool / interface | What I expect from it |
| --- | --- |
| `/proc` and process utilities | Live process and system accounting |
| `perf` and PMU | CPU sampling and hardware/software event evidence |
| ftrace | Kernel event/function tracing |
| eBPF + BCC | Programmable event collection at selected hook points |
| Prometheus and Node Exporter | Collected, time-series metrics |
| Grafana | Exploration and comparison of those metrics |
| ELK-style logging | Searching and correlating application/system logs |

## How I thought about a BCC probe

The syllabus included Python/BCC examples, **kprobe/kretprobe**, target-process observation and a path toward a custom exporter. The important question for me was *which event should be captured*, not just whether the probe printed a line.

For example, if I wanted to understand an unexpectedly slow operation, I would need to identify its entry and exit points, correlate the same operation, consider concurrency, and avoid treating one sample as a meaningful distribution.

A probe must also respect kernel version, hook stability, permissions and the overhead of recording events. More data is not necessarily more useful.

## How it relates to dashboards

The monitoring stack illustrates a complementary approach: metrics capture a repeatable summary, while an event trace helps explain a specific anomaly. My goal became to **use a dashboard to find the interval worth investigating, then collect narrower evidence from the relevant subsystem**.

When I later encountered resource pressure and stateful-service errors in infrastructure work, the same distinction applied. CPU charts, application logs and I/O symptoms could point in different directions; correlation matters more than collecting every signal in isolation.

## What I still want to reproduce

I don't have a preserved public benchmark of my own BCC exporter from the course. The next useful lab is small and measurable: capture one process or syscall event, summarize its frequency or duration, compare the result with a standard Linux metric, and document the overhead and limitations.
