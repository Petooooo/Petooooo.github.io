> **April–May 2024 · an earlier FPGA project, revisited in November 2026.** My project portfolio records that I independently developed a Verilog-based systolic-array matrix multiplication accelerator on FPGA, exploring its use for convolution-oriented computation through IM2COL. The original RTL, testbench traces, synthesis reports and benchmarking conditions are not preserved in the materials available for this article. The numbered diagrams below therefore explain a **new, mathematically verified reference example**. They are not screenshots or cycle traces from the 2024 device.

The idea sounded straightforward when I first encountered it: matrix multiplication contains a large number of independent products, and a grid of Processing Elements (PEs) can distribute the work. Writing a multiplication loop in software, however, hides a question that cannot be ignored in RTL: **which two operands reach each PE on a particular clock?**

That question made this project more interesting than the equation itself. I was not merely looking for a different way to write a dot product. I was trying to understand how computation and data movement should be arranged spatially so that local units can keep processing without individually fetching every element from a shared source.

## A matrix equation does not describe the schedule

For two matrices, the underlying operation is familiar:

`C[i,j] = Σ(k=0..K−1) A[i,k] × B[k,j]`

A software implementation can access the required elements by index. In a Systolic Array, an operand must be **physically delivered** to a PE at the right time, and its partial sum must be retained until every required product has been accumulated.

To make the timing discussion concrete, I constructed a small reference case. It is **not an archival 2024 test vector**.

In this example, each output needs **two Multiply-Accumulate (MAC) steps**. Four outputs therefore require eight products. The array does not magically remove any of those arithmetic operations; it distributes them among PEs whose inputs can be reused and forwarded locally.

## Give each PE one output to accumulate

There is more than one Systolic Array dataflow. For the following explanation, I chose an **output-stationary** 2×2 array: `PE(i,j)` holds the running sum for `C[i,j]`; matrix A values move **rightward**, and B values move **downward**. This is an explicit *teaching model*, not a claim that the archived 2024 implementation used these exact dimensions or stationary policy.

A local PE must perform more than multiplication. It accepts an A operand and a B operand, updates its accumulator when both are valid, and forwards the operands for the next PE. Depending on the implementation, the forwarding values and partial sum are registered, while reset, valid gating, arithmetic width, sign treatment and overflow behavior must be defined in RTL.

This was an important difference from reasoning only about a CPU loop. A result can be arithmetically correct yet arrive in the wrong output slot or become visible before the final term. A useful implementation must define both the **value** and **when that value is valid**.

## Why the edge inputs cannot all begin together

For this reference mapping, imagine the reduction index `k` moving through the array. An A value for row `i` is introduced with an initial offset of `i` logical slots; a B value for column `j` is introduced with an offset of `j`. Each value then advances by one PE per slot. Both operands for the same term meet at:

`t = i + j + k`

This is a **logical MAC-slot model**. Real registered RTL may introduce extra latency, and the actual 2024 implementation schedule has not been recovered.

Notice that `A[1,0]` and `B[0,1]` do not enter at `t=0`. They are delayed until `t=1`. Otherwise a PE at the bottom or right may encounter operands with different reduction indices. **Data alignment is part of the computation**, not a cosmetic controller detail.

## Following the wavefront one logical step at a time

The new model produces the complete arithmetic sequence below.

| Logical step | Active products | Intermediate state |
| --- | --- | --- |
| `t=0` | `PE00: 1×5` | `C00=5` |
| `t=1` | `PE00: 2×7`, `PE01: 1×6`, `PE10: 3×5` | `C00=19`, `C01=6`, `C10=15` |
| `t=2` | `PE01: 2×8`, `PE10: 4×7`, `PE11: 3×6` | `C01=22`, `C10=43`, `C11=18` |
| `t=3` | `PE11: 4×8` | `C11=50` |

The PE contributions are deliberately staggered. `C00` reaches its final value before `C11` even though all four outputs belong to the same matrix multiplication. A design that blindly exposes all accumulators after the same early slot would confuse **a partially accumulated value** with a completed result.

A controller therefore needs a convention for **starting a tile, clearing or initializing accumulators, gating valid operands, and collecting finished outputs**. The appropriate mechanism could use counters, valid propagation or a surrounding FSM. Without the original RTL, I cannot say which precise implementation I used in 2024; what survives in my project record is the Verilog implementation and the focus on Systolic Array matrix multiplication.

This also changes how a testbench should be read. Merely observing an expected number somewhere in the waveform is not enough: the expected number must be associated with the correct element and the correct valid boundary.

## One missing delay can change the multiplication itself

I added a deliberately incorrect injection example to make the failure mode visible. In the working schedule at `t=1`, `PE(0,1)` should combine `A[0,0]=1` with `B[0,1]=6`. If column 1's B stream is not delayed while A still takes a slot to cross from `PE(0,0)`, the same PE can instead combine `A[0,0]` with `B[1,1]=8`.

The wrong result is not caused by faulty multiplication: `1×8=8` is mathematically correct for the wrong operand pair. It is caused by a **transport schedule that violates the algorithm's indices**. This is why I think of the PE array as both a compute design and a timing/data-delivery design.

## Bringing this back to convolution through IM2COL

My original 2024 project record explicitly connects the Systolic Array to convolution through **IM2COL**, which turns spatial input patches into columns of a matrix. The important distinction is that **the conversion and buffering are additional work**; Systolic Array MAC execution does not make those transformations disappear.

For a transparent illustration, I calculated a new 3×3 image and a 2×2 filter. Each of the four input patches is flattened to a column. The resulting matrix product has a four-element result of `[-4,-4,-4,-4]`.

For the explanatory model, the generator computes eight MAC events and asserts the reference result `[[19,22],[43,50]]`, while the IM2COL example is also checked in code. This is enough to verify **the new illustrations**, not enough to certify the unrecovered FPGA implementation.

## What stayed with me

This project taught me to pay attention to the moment when an algorithm becomes a physical schedule. The matrix equation says which values should be multiplied. The PE arrangement determines where that happens. The input skew determines **when** the right values meet, and the output-valid logic determines when someone else may safely use the result.

By the time I moved to a full CNN accelerator, I was thinking less about adding more arithmetic units and more about making sure that the surrounding system could feed them correctly. That change in perspective was more useful to me than any unverified claim of raw speedup.
