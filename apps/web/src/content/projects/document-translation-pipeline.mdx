A document conversion worker could continue processing even after its RabbitMQ connection had been closed. I had seen this in earlier long-running work: the broker no longer held a delivery for the original consumer, yet the file operation might still be running. A second attempt could start before the first had stopped.

In June 2026, I developed a document translation workflow that handled PDF, DOCX and HWPX files through separate processing stages. Each job moved from input storage through extraction, translation, document reconstruction and final artifact delivery. Those steps could outlast an HTTP request, and a failed worker should not force the user to start the document over.

I designed and implemented the asynchronous service, deployed it to an internal offline environment and operated it there. RabbitMQ handled stage commands while persistent job state determined which attempt owned the work. Format-specific workers handled conversion and reconstruction. The development tests covered contract behavior, end-to-end format routes and targeted recovery cases; the internal deployment was a further part of the engineering work, not merely a proposed next step.

This account focuses on the architecture, implementation and operational decisions. Internal endpoints, deployment topology, credentials and service-specific configuration are omitted.

## Request handling and asynchronous execution

A synchronous endpoint that uploads a file, runs conversion, extracts text, translates every segment and generates a new document has an uncomfortable property: the client connection becomes an accidental owner of work that can last much longer than the request budget.

I wanted the API request to own **admission**, not execution. Accept the document once, establish an identity for the logical translation, and let the client discover the result through a separately maintained job status. That split changes what must be durable.

The input document and derived artifacts belong in object storage. The job identifier, format, selected translation mode, owner metadata, stage ownership and completion state need a persistent record. RabbitMQ can transport commands and event notifications between services, but the broker delivery itself is not a sufficient source of truth for the job.

| Boundary | Responsibility | What breaks if ownership is unclear |
| --- | --- | --- |
| Request/API | Validate a new task and return a stable job identity | Client retries can accidentally create independent jobs |
| Job service | Decide the active stage and persist state transitions | Two workers may publish the same next step or accept stale results |
| RabbitMQ | Deliver work commands and completion/failure notifications | A disconnect can cause redelivery, not automatic correction |
| Format workers | Transform one type of artifact or text segment | One long-running format conversion blocks unrelated work |
| Object storage | Hold source, intermediate and final artifacts | A completed database flag can point to a missing object |
| Translation / notification adapters | Invoke other service contracts | API drift or duplicate notifications become workflow failures |

I deliberately kept stage progression with a **central job service**, rather than allowing each worker to decide which queue the next worker should consume. The workers can report their result; the orchestrator checks whether that result belongs to the current stage and decides what to publish next.

That concentrates ordering logic in one place. It also means the job service must survive duplicates and stale events: central coordination simplifies the rule, but does not make distributed state atomic.

## PDF, DOCX and HWPX processing paths

One generic file converter would have been a convenient deployment unit but a poor place to hide format-specific assumptions.

**DOCX** is already structured enough to separate content extraction from replacement, but translating extracted strings does not guarantee that runs, styles or tables remain unchanged. Text length and segmentation can alter layout.

**PDF** usually has to be treated differently. The workflow I validated used an intermediate DOCX representation before text extraction and replacement, with additional export and conversion stages for the requested output. That adds more places where layout fidelity can be lost. A successful worker exit is not equivalent to a visually faithful document.

**HWPX** has its own package and document-structure concerns. The route used dedicated extraction/replacement handling instead of pretending every source document could pass through exactly the same converter. Early HWPX export work included compatibility placeholders; later route-level smoke tests showed that the orchestration path could complete, **not** that every real-world HWPX feature was preserved.

The service did not need three separate applications for three formats. Job admission, durable stage progress, translation integration and result notification stayed shared. I separated the workers where the document format required different libraries, intermediate representations or reconstruction steps.

| Input format | Main structural decision | What a route-level test established | What it did not establish |
| --- | --- | --- | --- |
| DOCX | Extract → translate → replace content → export artifact | The staged route could hand off and complete in an isolated test | Visual equivalence of arbitrary documents |
| PDF | Convert through an editable intermediate, then reconstruct | The PDF-route worker chain and completion path were exercised | Pixel-perfect pagination and complex layout retention |
| HWPX | Parse and replace format-specific structure | HWPX-route orchestration and artifact handoff were exercised | Support for every HWPX construct, font and export edge case |

The distinction mattered in implementation: **finishing the workflow** was one condition for success, while **preserving the document's intended structure** required its own quality checks.

## RabbitMQ acknowledgements and durable stage claims

One difficult failure mode appeared in an earlier consumer model: a worker accepted a long document-conversion task and kept its RabbitMQ delivery unacknowledged while doing the expensive work. During long synchronous processing, the client was unable to service the broker connection reliably. The broker reported missed heartbeats and closed the connection.

This was not simply a matter of making the RabbitMQ heartbeat timeout larger. A longer timeout could hide a stalled consumer; an acknowledgement sent before any durable record could lose responsibility for work; and an acknowledgement sent only at the end could keep the transport connection tied to a long-running conversion.

I separated **broker delivery ownership** from **job-stage ownership**.

The newer command-processing path checks the active stage and claims it durably before acknowledging the broker command. The claimed work is represented by a lease and attempt metadata. The expensive conversion can then run independently of keeping that one delivery open. Completion events update the durable state only if the claim and stage are still relevant.

That creates a different failure window. If the worker disappears after acknowledgement but before completing its artifact, RabbitMQ cannot be asked to redeliver that already-acknowledged command. Recovery needs a reconciler that notices a stale lease and deliberately permits another attempt.

That moved recovery out of the lifetime of one broker delivery and into the application's durable stage state.

## Job state, retries and artifact consistency

A single document translation can contain many steps, and some steps can create multiple intermediate artifacts. A broker message is only one attempted delivery; the logical job must survive retries and stage restarts without changing identity.

I used the job service as the place to validate transitions. A completed or superseded stage should not accept an old completion event as permission to advance. A duplicate command should be harmless when the current claim already covers that work. Retry attempts need to be bounded, and a permanently failing stage must become inspectable rather than loop forever.

There is no one transaction that atomically commits PostgreSQL state, a MinIO object and a RabbitMQ acknowledgement together. That is a distributed consistency boundary, not a missing database flag.

For example, a worker may successfully write a final artifact and then lose contact before reporting the stage result. A retry must inspect durable identity and existing artifacts; blindly generating a new file can duplicate effects. Conversely, a job row marked complete without the expected artifact is not a useful translation.

The design therefore required **progress reconciliation**, rather than relying only on the last HTTP response or message acknowledgement.

### Recovery scenarios covered by the design

- A repeated command or stale completion should not advance the wrong stage.
- A worker that stops after claiming a stage should not leave it permanently owned.
- A retry should preserve the logical job identity and be bounded by policy.
- A failure that exhausted automated handling should remain visible for inspection.
- The client should distinguish accepted, processing, completed and failed work without treating a timeout as definitive proof of failure.

The reliability tests exercised durable claims, stale-lease reconciliation, retry/backoff and logical terminal-failure handling. During Helm integration, a queue-declaration conflict (`PRECONDITION_FAILED`) arose when the desired DLX arguments differed from an existing queue. I retained support for broker-level DLX/DLQ configuration without enabling it by default. The durable job failure state and the broker's physical dead-letter queues remained separate mechanisms.

## Translation and notification integration

The conversion workers were not meant to hard-code one translation provider. A translation adapter had to carry a stable segment identity, text and a task-selected translation mode. That let the orchestration and file-replacement layers remain separate from a provider's HTTP contract.

The notification worker had a similar boundary. It should receive enough information to associate the result with the correct recipient and stored artifact, while the source of truth for completed outputs remains the job state. That prevents a notification step from inventing an output path just because a message arrived.

Contract tests checked segment identity, payloads and error handling without binding the conversion workers to one translation provider or notification implementation. Translation quality and recipient-side delivery remained separate operational concerns, rather than assumptions built into worker completion.

## Worker separation and deployment

I did not split components because microservices were fashionable. The processing stages had genuinely different libraries, execution times, memory footprints and failure surfaces.

A PDF conversion image should not have to carry the same dependencies as a notification adapter. An API accepting job requests should not be blocked by one converter. A broken export route should be identifiable without assuming the translation provider itself is wrong.

This separation also shaped deployment. I had to manage multiple images, broker routing, persistent state, service dependencies and version compatibility in an environment without ordinary public-registry access. I deployed and operated the resulting service on the internal network. Keeping file-format dependencies isolated made it easier to update or troubleshoot one processing route without turning every change into a rebuild of the entire application.

## Implementation, deployment and verification

This project went through implementation, staged testing and **internal deployment and operation**. The tests gave me repeatable checks for individual contracts and failure boundaries; deployment required assembling those components into a running service in an offline environment.

| Python tests and API contracts | Job metadata, adapter payloads and worker behavior; 121 unit tests passed at a recorded development checkpoint |

The important distinction is between the **service being deployed and operated**, which I did, and obtaining benchmark-quality evidence for every possible file or failure scenario. The latter was not the requirement for calling the engineering implementation complete.

## Operational follow-up

The next useful improvement was to make recovery behavior observable across the database, broker and artifact store: job age, active attempts, stale leases, format-specific processing time and failed output generation. For deeper resilience testing, I would inject failures immediately after a durable claim, after object upload but before stage completion, and before result notification.

For document quality, a representative PDF/DOCX/HWPX corpus with tables, images, embedded objects and unusual fonts would make layout regressions measurable. I have not published throughput, latency or fidelity percentages without corresponding measurements.

The deployed service used **durable job ownership and separate PDF, DOCX and HWPX processing paths** in the internal environment. Crash-boundary recovery tests and document-fidelity regression checks would be the next areas to expand.
