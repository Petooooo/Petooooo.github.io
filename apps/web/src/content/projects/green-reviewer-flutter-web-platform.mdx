Green Reviewer (그린리버) grew out of a simple problem: a product can be marketed as environmentally friendly, yet a shopper may have little information about what makes that claim credible. From September to December 2023, I developed the web application, mobile application and backend for a service that combined product listings with structured user reviews. Instead of treating a review as only a star rating, I wanted to make the nature of a reported environmental concern visible alongside the product information.

The original repository retains both the Flutter implementation and the services, together with the original mobile and desktop screenshots. This article follows the actual code at [the retained source revision](https://github.com/Petooooo/green-reviewer/tree/2a3f1328e1beb083aa2de33d0fd4d02bc53c07a6) and distinguishes the 2023 implementation from the improvements I would make today. The screenshots below document the historical interface, not present-day product assessments or a currently running service.

## Separating interactive requests from catalog ingestion

The project was more than a Flutter client. Its backend was organized around three Node.js/Express processes and a MySQL database, with a separate Python path for collecting and importing the product catalog.

| Component | Responsibility in the retained source |
| --- | --- |
| Flutter/Dart | Product browsing, search, detail and review screens, checklist charts |
| FacadeServer | The client-facing HTTP entry point; forwards requests |
| ConversionServer | Maps search terms to catalog categories, combines detail responses, coordinates review writes and deletes |
| DatabaseServer | Exposes SQL-backed catalog, image and review operations |
| MySQL | Product records, detail image URLs, reviews, derived checklist totals |
| Python crawler and JSON uploader | Offline acquisition and initial import of the catalog |

The FacadeServer routes product search, search count, detail and review mutations through ConversionServer. Review content is read directly from DatabaseServer through the facade. That distinction matters: the conversion step is useful where a request needs transformation or several underlying operations, not where the facade can simply return a collection of reviews.

I also separated catalog ingestion from user-facing browsing. The crawler first queried Naver Shopping for a search keyword prefixed with the Korean term for eco-friendly products, then used Selenium to obtain supplemental fields where available. The resulting JSON files were organized by category and product ID. A separate uploader inserted product records and detail image URLs into MySQL, initializing the review count and four checklist totals to zero. The public code and original architecture illustration show this division. They do not establish a scheduled, continuously running ingestion pipeline, and I have not rerun the historical crawler against an external website.

The initial data source was therefore product marketing and shopping metadata, not independently verified environmental certifications. The application used user-contributed flags to organize concerns; it did not certify that a product was environmentally sound or determine that a seller had committed wrongdoing.

## Searching a category-based catalog

The catalog was organized by keywords. A typed search term did not have to match the stored category exactly. ConversionServer obtains the distinct keywords from DatabaseServer, then the Transformer class calculates Levenshtein edit distance from the search word to each candidate.

For strings of lengths m and n, the code initializes the first row and column of a two-dimensional matrix to the number of insertions or deletions required to reach an empty string. For an interior cell it takes the minimum of deletion, insertion and substitution costs.

```text
D[i,0] = i
D[0,j] = j
D[i,j] = min(D[i-1,j] + 1,
             D[i,j-1] + 1,
             D[i-1,j-1] + cost)
cost = 0 when the characters match, otherwise 1
similarity = 1 - D[m,n] / max(m,n)
```

<figure className="project-concept-figure"><a href="/figures/journals/green-reviewer-02-search.svg" target="_blank" rel="noopener noreferrer" aria-label="Open Green Reviewer 02 search diagram"><img src="/figures/journals/green-reviewer-02-search.svg" alt="The edit-distance matrix for cup → cups is calculated from the recurrence in Transformer; the words are illustrative." loading="lazy" decoding="async" /></a><figcaption>The edit-distance matrix for cup → cups is calculated from the recurrence in Transformer; the words are illustrative.</figcaption></figure>

The best candidate is selected only when its similarity is strictly greater than the previous maximum, initially zero. Equal scores therefore retain the first encountered candidate. With a hypothetical search word cup and candidate cups, the distance is one and the normalized similarity is 0.75. This is an explanation of the actual recurrence, not a claim that those English words occur in the archived Korean catalog.

The approach has a clear trade-off. It supports small spelling differences without requiring a separate search engine, at O(mn) time and space for each comparison. But a short distance does not imply similar meaning; the code compares JavaScript string units, rather than Korean morphological or semantic features. It has no explicit minimum relevance threshold above zero, and candidate order can affect ties. A production version would distinguish exact matching, aliases and a ranked set of alternatives, then use relevance evaluation before making automatic category selection.

After selecting a category, ConversionServer sends the keyword, page and size to DatabaseServer. The latter queries matching records and slices the returned rows using the index `(page - 1) * size`. The implementation is consequently one-based even though parts of the older API documentation describe zero-based pages. The search count travels through a separate endpoint. I would move pagination into the database with a deterministic ordering and validate page bounds, rather than load all rows and slice them in JavaScript.

## One product ID across the screens

The MySQL initialization SQL defines three tables. The product ID is the shared key: itemTable holds the product metadata, source link and derived review state; detailpicTable stores supplemental image URLs; reviewTable stores review text and four integer checklist values. The latter two tables have foreign keys referring to the product.

<figure className="project-concept-figure"><a href="/figures/journals/green-reviewer-03-data.svg" target="_blank" rel="noopener noreferrer" aria-label="Open Green Reviewer 03 data diagram"><img src="/figures/journals/green-reviewer-03-data.svg" alt="The original MySQL initialization defines three tables linked by the product ID; itemTable also stores the derived checklist totals." loading="lazy" decoding="async" /></a><figcaption>The original MySQL initialization defines three tables linked by the product ID; itemTable also stores the derived checklist totals.</figcaption></figure>

The detail request illustrates why ConversionServer exists. It requests product content and detail images from DatabaseServer, then combines them into one object. The client therefore receives the detail image list together with the basic item information instead of having to assemble the two responses on every platform.

The Flutter application has a shared GlobalStore extending ChangeNotifier, with fields for the selected product, product and review pages, checklist totals and dialog state. It uses Provider and asynchronous HTTP calls, including FutureBuilder for the product detail and review data. The detail screen displays loading/error states and uses the returned original URL for the purchase-page link. The source contains multiple layout branches at a screen width of 800 logical pixels. Rather than maintain entirely different clients, the same Dart code adjusts layout, image sizes, typography and chart dimensions for narrower and wider screens.

This is a useful separation, but not a perfect client abstraction. The archived database service sometimes sends a JSON-encoded string through a JSON response, while other endpoints return an object or a string directly. The conversion and Flutter code consequently contain nested decoding operations. A single typed response schema and a uniform error envelope would remove that accidental coupling between the services.

## Turning reviews into two different visual signals

The review interface uses four categories chosen from the greenwashing types described in the application's educational text: insufficient evidence, inappropriate certification labels, vague claims and false claims. Each review may select more than one category and also contain free text. The four flags are not a mutually exclusive classification.

The original frontend's `fetchProducts` function derives a color for the catalog card from the review count N and the four accumulated checklist counts S1 through S4:

```text
N = 0                  → grey (no reviews)
r = (S1+S2+S3+S4)/(4N)  when N > 0

r < 0.25               → green
0.25 <= r < 0.60       → yellow
r >= 0.60              → red
```

Assuming every stored flag is binary and the totals are consistent with the review rows, r is the fraction of selected positions among all four positions in every review. It is not the fraction of users who report at least one concern and is not an estimated probability of greenwashing. There is no evidence that the two thresholds were calibrated against a labeled validation dataset.

The detail view renders a different quantity. DonutChart passes each nonzero checklist count to fl_chart as a section value, exposes its count on interaction and suppresses the donut when all four counts are zero. The proportions of the sections are normalized by the sum of the selected flags, not by the review count.

For a hypothetical five reviews with sums [4, 3, 2, 1], the card score is 10/20 = 0.50, hence yellow. The chart shares are 4/10, 3/10, 2/10 and 1/10. This distinction is important when explaining the interface: a product with a single flagged review can have the same chart proportions as a product with hundreds of reviews. Zero reviews and reviews with zero flags also convey different information, even though the latter produces no donut.

If I were designing the display again, I would show the total review count, the count of reviews reporting any issue, and category counts separately, along with the original reports. I would also explicitly mark the difference between no evidence and evidence of no reported concerns, and provide a moderation and verification process before presenting any real-world risk assessment. This would make the numbers easier to interpret without treating them as verified environmental evidence.

## Review mutations and the cost of stored aggregates

The review write path retains an implementation decision that is easy to miss by looking only at the UI. Rather than calculate every category total on each product read, the application stores a review count and four aggregate counts directly on itemTable. The JSON uploader initializes these derived values. ConversionServer retrieves the existing totals, adds the new review's four flags, inserts the review row, requests the new row count, then updates the product's stored totals and count.

<figure className="project-concept-figure"><a href="/figures/journals/green-reviewer-05-review-update.svg" target="_blank" rel="noopener noreferrer" aria-label="Open Green Reviewer 05 review update diagram"><img src="/figures/journals/green-reviewer-05-review-update.svg" alt="The original write path makes four separate requests. The concurrent-write example illustrates a possible lost update, not an observed incident." loading="lazy" decoding="async" /></a><figcaption>The original write path makes four separate requests. The concurrent-write example illustrates a possible lost update, not an observed incident.</figcaption></figure>

Deleting a review follows the reverse direction. The conversion layer obtains the old totals and the review's flags, performs the historical deletion check, removes the review row, and writes the decremented aggregate and count. The intent was to make the catalog display inexpensive to read and to avoid recomputing all review totals on every product listing.

The sequence has an important consistency weakness: these operations are separate HTTP requests, not one database transaction. If two writers read the same old sum of three and each adds one, both can write four while the review rows imply five. A failure after inserting a review but before updating the product can similarly leave the cached values stale. Those are code-level possibilities, not recorded incidents. A transaction in DatabaseServer with a row lock or atomic increment/decrement would give the write operation one consistency boundary; alternatively, an aggregate query over the authoritative review rows could avoid maintaining a second source of truth. The same design must address retry idempotency and checking the relationship between a review and its product.

The screenshots show the original review creation and removal interactions. They are valuable records of the implemented interface, but the historical deletion mechanism and SQL construction do not meet modern production security expectations. I would replace direct string-composed queries with parameterized statements, protect credentials and review ownership with appropriate authentication and password hashing, validate inputs, limit request rates, and expose only the facade. These are retrospective improvements, not changes made to the archived service.

## Packaging the backend and defining its limits

The repository includes a Compose configuration for MySQL 8.1.0 and the three service images at version 1.3. The MySQL initialization directory is mounted into the container. Separate sample environment files document the configuration needed by the services. The client README describes running Flutter in Chrome, and the root README describes a mobile build as well as a historical deployment. AWS and Docker are part of the retained architecture and technology list.

The Compose file provides a concrete local packaging path; it is not proof of a hardened deployment. In the old configuration, database and internal service ports are published, and startup ordering is not a readiness check. If revisiting deployment, I would keep internal endpoints on a private service network, use managed secrets and health checks, configure persistence and migrations deliberately, and make failure handling explicit between services. I have not restarted or tested the original public endpoint, APK or database in this retrospective.

The most useful engineering lesson is that a complete application needs more than separate front and back ends. Catalog ingestion, product identity, API contracts, derived state and the visual meaning of that state must agree. Green Reviewer implemented all of these boundaries in a small application, and the retained code makes their trade-offs visible. Later infrastructure work involved a larger scale, but the distinction between a user-visible result and the underlying state that guarantees it remains the same.
