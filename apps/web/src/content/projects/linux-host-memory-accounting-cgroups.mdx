In August 2026, a host memory graph climbed from roughly one fifth of its capacity toward saturation. The Pod memory charts I inspected did not show a corresponding jump. A separate earlyoom record named a selected process with approximately 608 MiB of resident memory. That selection did not account for the host-wide rise. The earlier [memory-pressure investigation](/projects/rokaf-memory-pressure-and-service-recovery/) focuses on pressure and intervention; here I wanted to understand what the measurements actually counted.

A later August 30–31 investigation retained an OOM task-table row for a host management daemon. Its RSS was 54,101,261 pages, swapents was 2,687,499 pages, and pgtables_bytes was 910,581,760 bytes. For a 4 KiB base page those correspond to approximately 206.4 GiB resident, 10.25 GiB in swap entries and 868 MiB of page tables. These quantities have different meanings and the conversion is conditional on the historical page size. An OOM task dump reports eligible tasks and is not a list of the killed processes. The row makes this daemon a substantial memory-consumer candidate, but does not establish that the two August observations were exactly time-aligned, that all the pages were private, or which allocation path caused the increase. I have not retained a complete per-mapping history or verified a permanent fix. The host identity, PID, management endpoint and other operational details are omitted.

## Resident mappings are not unique physical memory

Virtual size (VSZ or VmSize) describes mapped virtual address space. It includes reservations and mappings that need not be resident. RSS counts pages currently resident in a process's address space, including shared mappings. A shared library page can be counted in more than one process. Summing every RSS can therefore overstate the physical memory represented by those mappings.

PSS distributes each resident page's size across its mapping references: a page mapped once contributes its full size; a page mapped twice contributes half to each mapping. USS is commonly estimated as private clean plus private dirty resident memory in smaps; it is not a complete accounting of the kernel resources that would be freed at process exit. Huge-page fields and special mappings need care. Nor does summing PSS across selected processes count every unreferenced cache page or every kernel allocation.

### A measured shared mapping

I wrote a small Linux experiment that creates a 4 MiB anonymous memory-backed file with memfd_create, maps it with MAP_SHARED, touches each page, forks a child and synchronizes after the child touches the same mapping. Both processes remain alive while the parent reads only the matching mapping in each /proc/PID/smaps. A pipe coordinates cleanup. The experiment uses 4 MiB of shared backing data, not an allocation large enough to stress the host.

| Mapping measurement | Parent | Child | Sum |
| --- | ---: | ---: | ---: |
| Size (KiB) | 4096 | 4096 | 8192 |
| RSS (KiB) | 4096 | 4096 | 8192 |
| PSS (KiB) | 2048 | 2048 | 4096 |
| Private clean + dirty (KiB) | 0 | 0 | 0 |

The measured shared-dirty amount was 4096 KiB in each mapping. The summed RSS was twice the shared resident data, whereas PSS accounted for it once across these two mappings. These are actual smaps results from the companion script, not values from the incident and not whole-process memory usage. The test does not measure physical PFNs, overall host memory or a cgroup charge.

## Host memory counters overlap

I would begin host-level attribution with MemAvailable and changes in AnonPages, Cached, Shmem, Slab, SReclaimable, SUnreclaim, KernelStack, PageTables and SwapFree. MemAvailable estimates what can be used without swapping; it is not a separate disjoint pool of physical pages. Cached includes tmpfs/shared-memory accounting, and Slab includes reclaimable and unreclaimable slab. Page tables and kernel stacks are real memory costs that are not part of a process's ordinary resident mappings.

A rising AnonPages would narrow the investigation toward anonymous resident data; increasing unreclaimable slab would point toward a different set of questions. A single sample of either is insufficient to infer a leak. A mapping can contain both file-backed and anonymous data after copy-on-write. Dirty and Writeback describe page state, not additional independent pools; the [disk I/O record](/projects/linux-disk-io-journaling-writeback/) discusses how they can affect reclaim latency.

## cgroup charges are not process PSS

Containers share the host kernel. The memory controller tracks resource use in a hierarchy rather than isolating RAM into separate physical machines. On cgroup v2, memory.current includes the cgroup and its descendants. The memory.stat breakdown includes anonymous, file and kernel memory; fields such as shmem and slab are related subcategories rather than additional independent totals. Kernel accounting details vary across releases. Swap usage is exposed separately by memory.swap.current.

A charge normally remains associated with the cgroup that instantiated the memory until it is released; moving a process does not retroactively transfer all its old allocations. Shared data used by several cgroups need not be charged proportionally to each of them. PSS and memory.current therefore answer different questions. The former apportions mapped resident pages, while the latter reflects controller accounting, including memory not represented by mapped resident pages.

I would verify whether the node uses cgroup v1, v2 or a hybrid arrangement before interpreting any files. The original investigation does not retain that configuration, so the examples use v2 explicitly. A Pod can have a parent cgroup with several containers beneath it, while system services and other runtime workloads may live elsewhere. Summing Pod parents and their container descendants counts the same charge twice. Even non-overlapping selected subtrees do not account for the entire host.

The limits and event counters add a different dimension. memory.high can induce throttling and reclaim without necessarily triggering OOM; memory.max is a hard charge boundary with possible cgroup-local OOM. memory.events counts hierarchical events, while memory.events.local confines the count to the cgroup itself. Comparing deltas requires a stable identity and interval; a new cgroup after a restart may have new counters. The earlier earlyoom article covers the separate mechanisms for choosing a victim.

## Working set is an estimate, not a conservation law

The Kubernetes resource metrics pipeline reports memory working set. The estimate depends on the statistics provider and operating system. In the familiar cAdvisor implementation, working set is usage minus inactive file cache, floored at zero (using the relevant inactive-file field for the cgroup version). It still includes some reclaimable memory and is not equivalent to RSS, PSS, or a guarantee of unreclaimability.

For example, a synthetic cgroup with 1024 MiB of usage and 384 MiB of inactive file cache yields a 640 MiB working set in that formula. A change in inactive file cache can affect the reported working set even if raw usage does not change. Conversely, growth outside the selected Pod cgroups is invisible to their series. The historical dashboard's exact query, provider and sample alignment were not retained; this calculation does not claim that the dashboard used this precise formula.

## Attribution before selecting a remedy

I would collect the following evidence over the same timestamps and boot, using the node and cgroup identities rather than just a process name. These are read-only example commands, not a transcript of the incident.

```bash
cat /proc/meminfo
cat /proc/pressure/memory
ps -eo pid,comm,rss,vsz --sort=-rss
cat "/proc/$PID/smaps_rollup"
cat "/proc/$PID/cgroup"
findmnt -t cgroup,cgroup2
```

Once a relevant v2 cgroup path is resolved in the host mount namespace, I would inspect memory.current, memory.stat, memory.swap.current, memory.events and memory.events.local if available. The host series should be compared with raw container usage and working set over the same interval, checking for duplicate parent series, label filtering, restarts and missing scrapes. A flat graph can be a consequence of the query scope or stale data. PSI measures stalled execution, not memory ownership. RSS ranking is useful to identify candidates, but smaps is comparatively expensive, so I would sample selected processes rather than continuously scan every mapping under pressure.

The daemon row is a useful lead precisely because the original Pod view was incomplete. The next question is whether anonymous resident pages, shared mappings, kernel charges or some combination account for that row and for the change over time. Restarting a service may restore availability without identifying the allocation path or proving that recurrence is prevented. The distinction I want to retain is between a victim, a large mapped consumer, the cgroup charged for memory, and the root cause of continued growth.
