## Multiple databases, multiple meanings of HA

A cluster that operates analytics, relational, document and cache systems has no single universal failover sequence. I worked with **MongoDB replication, PostgreSQL/Pgpool, ClickHouse with Keeper coordination, and stateful application dependencies**. Each adds separate conditions for healthy service.

| Component | Failure/recovery concern |
| --- | --- |
| MongoDB replica set | Member health and election state versus application read/write availability |
| PostgreSQL / Pgpool | Backend health, client routing, database role, and session impact |
| ClickHouse / Keeper | Replication metadata, leader/quorum behavior, read-only state, and disk availability |
| Application migration | Schema/data rewrite progress, retry behavior, and compatibility across dependent services |

## Why orchestration alone cannot solve database failover

The scheduler manages processes; it does not understand whether the data those processes serve is consistent. A database process being `Running` cannot establish that reads are current, writes are durable, migrations are complete, or dependent applications can use the new schema.

For MongoDB and PostgreSQL I separated **database-level replication/failover** from **persistent-volume movement**. For ClickHouse I also had to account for Keeper and replication status, not just Pod health.

## Langfuse as a cross-component migration problem

During a Langfuse upgrade I worked through changes spanning application containers, PostgreSQL migrations, ClickHouse storage/coordination, and operational dependencies. Several symptoms revealed why a migration should be treated as a **persisted state machine** rather than a single green/red UI badge:

- A reported **timeout** did not necessarily mean that the background migration's recorded phase was incomplete. I checked migration state and completed/failed work units independently.
- A **read-only analytics state** required investigation of coordination and replica status, not merely restarting a writer.
- A **space constraint** could interrupt data movement despite other application components reporting healthy.
- Rewriting and materializing data can require long-running operations whose progress must be verified across separate components.

These are generalized failure classes from my work, not an assertion that every observed symptom had the same root cause.

## Lessons for system design

My biggest takeaway was **cross-component observability**: migrations, object storage, volume capacity, and coordinator state may all be required for one user-facing feature to recover. If those dimensions are not monitored separately, failure analysis becomes guesswork.

I deliberately do not publish version-by-version production commands, internal schemas, or sensitive database configuration here. The published lesson is about **replication, consistency, and recovery prerequisites**.
