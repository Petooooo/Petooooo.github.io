Running a database inside Kubernetes is easy to describe as “replicated” or “highly available.” Operating it made me more careful with those words. The database process can be running while its coordinator is unhealthy; a migration can display a timeout while its recorded work is complete; and a replay can fail simply because a destination volume is out of space.

My work crossed **MongoDB, PostgreSQL/Pgpool, ClickHouse/Keeper and Langfuse**, each with a different idea of leadership, replication and readiness.

## 1. Why HA needs more than replicas

I first separated **process redundancy**, **data redundancy**, **election or routing**, and **application compatibility**. These are different properties:

| System | Availability mechanism | Operational concern |
| --- | --- | --- |
| MongoDB | Replica-set membership and primary election | Can the client still read/write with the desired consistency? |
| PostgreSQL / Pgpool | Replication and connection routing | Does the router target a valid writable backend? |
| ClickHouse / Keeper | Replicated data and coordination metadata | Can the replica access the coordinator and accept writes? |
| Langfuse | Application and background migration logic | Does code expect data structures that have not finished migrating? |

The presence of multiple Pods guarantees none of these by itself. In particular, **a Kubernetes leader and a database leader are not the same role**.

## 2. MongoDB and PostgreSQL: data state versus routing

With MongoDB, the important distinction was between a **healthy individual process** and a replica set that could elect and serve a primary. A service endpoint may still exist while the application cannot complete writes. I considered how member state, quorum and client retry behavior would affect continuity.

With PostgreSQL and Pgpool, routing adds another component that can be healthy as a process while routing to a backend with the wrong role or no usable data. A pooler can preserve a stable client endpoint without itself preserving database durability. I separated backend failure, pooler state and application session behavior when reasoning about HA.

## 3. The Langfuse upgrade was a data migration, not just a Helm upgrade

The more demanding problems appeared while moving Langfuse across major application and analytics changes. A container image and a Helm chart can be deployed quickly; historical traces, observations and analytics tables may need **rewrites, materialization and coordination changes**.

My migration path included an earlier v3 upgrade before the v4 transition. The important change in mindset was to treat the rollout as a sequence of independently verifiable stages:

1. **Application/schema state** — what version of the code and schema is active?
2. **PostgreSQL migration record** — what does the persisted migration table say?
3. **ClickHouse data and coordinator** — do replicated tables and Keeper agree?
4. **Capacity** — is there sufficient storage headroom for insert/rewrite work?
5. **Functional checks** — can the application actually read and write the expected data?

## 4. A better definition of database availability

Operating replicated databases taught me that **redundancy is a property of the whole service path**, not just the count of database Pods.

A useful checklist separates:

1. **Process health** — are individual server processes alive?
2. **Coordination** — can the cluster select or recognize the node that should accept writes?
3. **Replica state** — are replicas synchronized enough for the intended read/write policy?
4. **Routing** — do clients reach a backend with the correct role?
5. **Persistence** — is state durably stored and recoverable after a failure?
6. **Application compatibility** — can the current application use the schema and data version?
7. **Client-visible behavior** — do representative reads and writes succeed?

For example, Pgpool can keep its endpoint alive while the PostgreSQL backend does not accept the desired operation. MongoDB members can exist without satisfying the conditions for a writable primary. A ClickHouse replica may be alive but restricted by coordinator state.

### Distinguishing leader, primary and writer

| System | Relevant concept | What needs verification |
| --- | --- | --- |
| MongoDB | Replica-set primary and election | Does the client target a writable primary and receive expected acknowledgements? |
| PostgreSQL / Pgpool | Primary/standby and pooler routing | Which endpoint accepts writes, and what happens on failover? |
| ClickHouse / Keeper | Replicated table state and coordination | Is the replica writable and does the coordination metadata agree? |
| Langfuse | Schema and background data migration | Are records transformed, and can current code read/write them? |

The important lesson was to identify **which component is authoritative for each state** before deciding whether to retry, restart or restore.

## Migration capacity and idempotency

A data migration is often a new workload that runs alongside the service. It may read historical rows, allocate buffers, write replacement tables, rebuild materialized views and retain old data until cutover.

I therefore think about storage headroom as a **functional precondition** of a migration rather than an afterthought. An `NOT_ENOUGH_SPACE`-style error is different from a SQL incompatibility: retrying it before changing the capacity condition can simply repeat the failure.

A migration is also exposed to retries. If a worker processes part of a batch and the caller times out, restarting all of the work blindly risks duplicate effects or conflicting states unless the migration's own bookkeeping supports it.

| Migration checkpoint | Evidence | Risk of a naive retry |
| --- | --- | --- |
| Stage requested | UI/caller state | Request may not reflect background progress |
| Chunk started | Persisted job record | Another worker may still own it |
| Chunk completed | Durable progress counter/state | Work may already have produced its output |
| Data transformed | Destination schema/rows | Chunk accounting may not verify every record |
| Application check | Read/write behavior | Historical and newly written data may follow different paths |

This model helps explain why I wanted **persisted progress and functional verification**, not a single green status label.

## Separating repair and migration traffic

Database HA can be affected by both normal request traffic and background repair. During a rewrite or replica catch-up, I would monitor storage headroom, queueing delay, coordination health and application error rate separately. The performance cost of repair is part of the operational design, even if repair eventually succeeds.

I do not have a public controlled benchmark quantifying those interactions. The value of this record is the engineering decision to treat each stateful layer separately and to verify data, not just deployment status.

## 5. When a migration said “Timeout error”

One particularly instructive step reported **`Timeout error.`**, yet the persisted migration state showed **`phase = completed`**, with **nine completed chunks and zero failed chunks**. Those observations are not equivalent to a blanket declaration of success, but they directly contradict the simplistic conclusion that every chunk must have failed.

I treated the UI/worker timeout as one observation and the recorded migration progress as another. Before rerunning an expensive operation, the question became: *Did the background work continue and finish despite the caller timing out?* This avoided confusing the lifespan of a client request with the lifespan of the underlying data migration.

## 6. Capacity, read-only states and Keeper

Other work exposed a different class of issue: **remote inserts could fail with insufficient space**. No scheduler setting can compensate for genuinely unavailable storage capacity. I had to think about target storage size, temporary space needed for rewrites, and the consequences of retrying after a partial write.

A ClickHouse replica could also enter a read-only state. In those cases I checked the Keeper coordination layer and leader/quorum behavior instead of attributing all failures to the application. The recovery path depended on understanding whether the replica could safely participate in metadata and writes.

During the v4 transition I also saw a background migration step involving a **JSON date/state conversion error**. The publicly useful lesson was not the internal date value: it was that application-side migration logic can fail on persisted state serialization even after earlier storage coordination problems are resolved.

## 7. Later verification changed the Langfuse conclusion

When I first investigated the v4 migration, several stages were still open. The Step 2 timeout and the persisted nine-completed, zero-failed chunk record were evidence of progress, not a sign-off for the whole upgrade.

**That was an intermediate state, not the final outcome.** By November 17, 2026, I had completed Langfuse migration Steps 1–5, moved to `events_only` on app 4.46.0, and passed checks of historical and newly written data. The last step cleaned up an intermediate sorting table; it did not delete the original `traces` or `observations` tables. The [focused migration record](/projects/rokaf-langfuse-v4-migration-field-notes/) separates those later results from the earlier errors.

Langfuse Steps 1–5 and the tested historical/new-data paths were completed on November 17, 2026. That checkpoint does not verify every historical record or prove failover behavior for the MongoDB, PostgreSQL and ClickHouse incidents discussed above.
