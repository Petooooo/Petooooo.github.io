Running a database inside Kubernetes is easy to describe as “replicated” or “highly available.” Operating it made me more careful with those words. The database process can be running while its coordinator is unhealthy; a migration can display a timeout while its recorded work is complete; and a replay can fail simply because a destination volume is out of space.

My work crossed **MongoDB, PostgreSQL/Pgpool, ClickHouse/Keeper and Langfuse**, each with a different idea of leadership, replication and readiness.

## 1. Why HA needs more than replicas

I first separated **process redundancy**, **data redundancy**, **election or routing**, and **application compatibility**. These are different properties:

| System | Availability mechanism | Operational concern |
| --- | --- | --- |
| MongoDB | Replica-set membership and primary election | Can the client still read/write with the desired consistency? |
| PostgreSQL / Pgpool | Replication and connection routing | Does the router target a valid writable backend? |
| ClickHouse / Keeper | Replicated data and coordination metadata | Can the replica access the coordinator and accept writes? |
| Langfuse | Application and background migration logic | Does code expect data structures that have not finished migrating? |

The presence of multiple Pods guarantees none of these by itself. In particular, **a Kubernetes leader and a database leader are not the same role**.

## 2. MongoDB and PostgreSQL: data state versus routing

With MongoDB, the important distinction was between a **healthy individual process** and a replica set that could elect and serve a primary. A service endpoint may still exist while the application cannot complete writes. I considered how member state, quorum and client retry behavior would affect continuity.

With PostgreSQL and Pgpool, routing adds another component that can be healthy as a process while routing to a backend with the wrong role or no usable data. A pooler can preserve a stable client endpoint without itself preserving database durability. I separated backend failure, pooler state and application session behavior when reasoning about HA.

## 3. The Langfuse upgrade was a data migration, not just a Helm upgrade

The more demanding problems appeared while moving Langfuse across major application and analytics changes. A container image and a Helm chart can be deployed quickly; historical traces, observations and analytics tables may need **rewrites, materialization and coordination changes**.

My migration path included an earlier v3 upgrade before the v4 transition. The important change in mindset was to treat the rollout as a sequence of independently verifiable stages:

1. **Application/schema state** — what version of the code and schema is active?
2. **PostgreSQL migration record** — what does the persisted migration table say?
3. **ClickHouse data and coordinator** — do replicated tables and Keeper agree?
4. **Capacity** — is there sufficient storage headroom for insert/rewrite work?
5. **Functional checks** — can the application actually read and write the expected data?

## 4. When a migration said “Timeout error”

One particularly instructive step reported **`Timeout error.`**, yet the persisted migration state showed **`phase = completed`**, with **nine completed chunks and zero failed chunks**. Those observations are not equivalent to a blanket declaration of success, but they directly contradict the simplistic conclusion that every chunk must have failed.

I treated the UI/worker timeout as one observation and the recorded migration progress as another. Before rerunning an expensive operation, the question became: *Did the background work continue and finish despite the caller timing out?* This avoided confusing the lifespan of a client request with the lifespan of the underlying data migration.

## 5. Capacity, read-only states and Keeper

Other work exposed a different class of issue: **remote inserts could fail with insufficient space**. No scheduler setting can compensate for genuinely unavailable storage capacity. I had to think about target storage size, temporary space needed for rewrites, and the consequences of retrying after a partial write.

A ClickHouse replica could also enter a read-only state. In those cases I checked the Keeper coordination layer and leader/quorum behavior instead of attributing all failures to the application. The recovery path depended on understanding whether the replica could safely participate in metadata and writes.

During the v4 transition I also saw a background migration step involving a **JSON date/state conversion error**. The publicly useful lesson was not the internal date value: it was that application-side migration logic can fail on persisted state serialization even after earlier storage coordination problems are resolved.

## 6. What I still wanted to verify

Some migration stages had reached a consistent recorded state while others were still being investigated. The remaining questions were about **end-to-end correctness after data rewriting**: did the application query the correct dataset, did writes work, were background jobs complete, and was the new state internally consistent?

I would rather keep an accurate record of a stalled or partially verified migration than publish a clean “all successful” upgrade story that hides the uncertainty. The goal is to explain *which layer provided each piece of evidence*.
