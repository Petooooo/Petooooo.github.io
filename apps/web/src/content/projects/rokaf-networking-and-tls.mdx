I opened an internal HTTPS endpoint and got a browser warning: `NET::ERR_CERT_AUTHORITY_INVALID`. I had already supplied a certificate and configured the Traefik `IngressRoute`, so I first returned to the HTTP route. But the certificate the browser received was not the one I had intended. It was `TRAEFIK DEFAULT CERT`.

The error occurred before the route could help me. Traefik had to present a certificate during the TLS handshake, before it could inspect the HTTP request path. Looking at the route again was not the same as looking at the connection that failed.

That incident became a useful reference for other access problems I encountered on a closed-network K3s platform. At a different time, adding a `LoadBalancer` Service interrupted an existing host-port entry point. With Outline, the homepage loaded but a realtime WebSocket connection initially failed. DNS and MetalLB VIP reachability raised other questions I could not fully close. To a user they all looked like variations on “the service is down”; they required different evidence.

## The certificate was selected before the HTTP path existed

The environment could not assume that every service would be given a DNS hostname. Some endpoints had to be accessed by IP address and port. That made two details particularly important: whether the issued certificate's **subject alternative names covered the requested IP**, and whether Traefik **actually selected that certificate** for the connection.

I had already considered HTTP rules such as `PathPrefix('/')`. Changing an HTTP path matcher did not replace a default certificate that had already been sent. Adding a `Host(...)` condition did not turn an IP-only TLS request into a DNS-name-based SNI handshake either. The TLS certificate decision preceded the HTTP routing decision.

I inspected the certificate presented on the actual access path using `openssl s_client` and `openssl x509`, comparing its subject, issuer and fingerprint with the intended certificate. This was more informative than knowing that the certificate Secret existed somewhere in Kubernetes. A Secret that is not selected does not help the client.

The configuration I settled on included an appropriate IP SAN and Traefik's `TLSStore default` for the default certificate selection. I could then inspect whether the endpoint presented the intended certificate instead of `TRAEFIK DEFAULT CERT`. That observation is different from proving that every workstation already trusted the issuing private CA. **Certificate selection, endpoint identity and client trust** are separate checks.

## A new LoadBalancer Service interrupted a different endpoint

Another incident initially pointed me toward the wrong component. I added a `LoadBalancer` Service so MetalLB could provide an external VIP. I had not redeployed the previously accessible application, yet its host-port-based entry point stopped responding.

A separate NodePort route still worked, while the newly expected VIP path initially returned connection refused. That difference mattered. It did not look like evidence that every Pod or every Service had gone down.

K3s was still running its built-in ServiceLB. The new `LoadBalancer` object triggered `svclb-*` resources whose Pods requested a `hostPort` already used by the existing exposure path. Changing the new Service port avoided the overlap; deleting the Service removed its ServiceLB resources and restored the earlier access. These are stronger observations than a vague statement that “MetalLB broke the network.”

MetalLB's address allocation and advertisement are not the same action as ServiceLB's host-port allocation. One component was intended to provide an externally reachable address; another controller was also consuming a scarce host-level resource. I moved toward disabling ServiceLB in that MetalLB-based setup, and later observed the same conflict no longer occurring. I cannot turn that into a claim that every node and future Service passed an audited rollout or long-term failover test.

The complete change–conflict–rollback record belongs in the [ServiceLB host-port investigation](/projects/rokaf-service-lb-hostport-conflict/). Here it answers a broader question: **which controller acquired a resource when I added an apparently unrelated Service?**

## The wiki loaded while its realtime protocol failed

Outline presented a third kind of ambiguity. The wiki page loaded through a reverse proxy, yet collaborative editing was not working properly. The relevant proxy investigation involved Nginx in front of Outline, not merely Traefik's main HTTP routing.

An early realtime request returned HTTP `400`. I investigated how Nginx forwarded the hop-by-hop `Upgrade` and `Connection` headers, the `/realtime` path, HTTP/1.1 and connection timeout/buffering behavior. After those changes, the WebSocket handshake returned **`101 Switching Protocols`**.

That response established that the upgrade handshake had crossed the protocol boundary. It did not prove that every edit was durably saved on every client. Some Windows machines still showed certificate warnings or separate image-loading failures. I had also seen image-host DNS errors and HTTP `401` responses. An application homepage, its WebSocket, an attachment URL and an authenticated request are not one connection with one fate.

GitLab authentication involved another initiator again. Outline's backend had to contact GitLab's identity endpoints, and troubleshooting included `EAI_AGAIN` and `ETIMEDOUT` at different stages. A browser being able to display a GitLab login page does not prove that the Outline process can resolve or connect to the provider's userinfo endpoint. The confirmed `101` improvement could not stand in for a complete SSO or attachment recovery.

## Which external port was I actually testing?

The access models I used had overlapping terminology but different owners:

| Boundary | What I needed to distinguish |
| --- | --- |
| `ClusterIP` | An in-cluster Service destination, not an external address by itself |
| `NodePort` | A node-facing Service port and its forwarding path |
| `hostPort` | A host-port claim associated with a Pod |
| `LoadBalancer` | An external Service entry point whose implementation matters |
| Traefik `IngressRoute` | HTTP(S) routing after an appropriate entry point and TLS decision |
| `IngressRouteTCP` | TCP routing for a configured entry point; investigating it is not proof of deployment success |

That distinction mattered with Nexus too. Its management UI and Docker Registry API had different access requirements. The UI loading did not establish that `/v2/` requests, TLS identity, credentials and repository permissions all worked. I considered TCP routing for some entry points; I do not claim every proposed `IngressRouteTCP` configuration was ultimately validated.

The same `x509` text can come from different clients. A browser opening a service, K3s containerd pulling an image, and Kaniko pushing one need not share a trust store. I stopped treating “the certificate is installed” as sufficient evidence without saying **where** it was installed and **which request** failed.

## The DNS and VIP questions I left open

Not every investigation ended with a similarly reversible fix. CoreDNS reliability and intermittent MetalLB VIP reachability required more evidence. During a separate internal Service investigation, some Pods struggled to reach CoreDNS or a `ClusterIP` path. Flannel interfaces and some NAT rules existed, yet that alone could not establish how each packet passed through Service forwarding, `iptables` or `conntrack`.

I also considered whether Docker and K3s rules could interfere on the same host. That remained a hypothesis, not a confirmed explanation for every Pod-to-Service failure. It would be particularly misleading to claim that disabling ServiceLB solved later CNI, resolver and VIP anomalies. The port-contention incident and the open datapath questions crossed different failure boundaries.

In a **separate K3s startup incident**, I also recovered the iptables rule-bootstrap phase after `iptables-restore` encountered xtables lock contention. The rules were regenerated and K3s later logged `bootstrap done`. That was a completed operational recovery checkpoint—not evidence that the unrelated intermittent Pod-to-ClusterIP failure had the same cause.

## The client became my starting point

When investigating another connection failure, I now begin by asking **who made the request**. Was it a browser, a Pod, containerd, Kaniko, or a backend application calling another service? From which host or network path? Only after that can I usefully interpret a DNS error, TLS warning, connection refusal, HTTP response or missing application behavior.

The next questions follow the specific request: Did its name resolve? Was the destination reachable? What certificate did the TLS handshake actually present? Which entry point and router handled the request? Were the intended Service endpoints ready? Did the application complete a representative operation?

The confirmed checkpoints were concrete: **Traefik's presented certificate**, a `svclb-*` Pod claiming an existing host port, and an Outline WebSocket handshake changing from `400` to `101`. Each incident had a different correction or investigation path. The intermittent DNS, VIP and CNI symptoms remained separate open questions.
