When an internal application fails to open in a browser, the symptom is deceptively simple: **“the service is down.”** In practice, I had to learn how many different components could produce an identical-looking failure. The request might never resolve in DNS, reach the wrong IP, be redirected by a load balancer, negotiate the wrong certificate, or arrive at an Ingress rule with no usable endpoints.

On our on-premises K3s platform I worked with **Traefik, Kubernetes Services, NodePort/hostPort, MetalLB and internal certificate trust**. My goal was not to add layers for their own sake; it was to make service exposure more consistent and debuggable.

## 1. A single HTTP failure can originate in six places

I started separating the request path, because changing configuration at the wrong layer frequently made an incident longer.

| Stage | What it can tell me | Typical misleading symptom |
| --- | --- | --- |
| DNS | Does the name resolve to the intended destination? | “Ingress is broken,” when the name points elsewhere |
| VIP or node endpoint | Is the destination being advertised and reachable? | Browser timeout with healthy Pods |
| TCP/TLS | Is the handshake successful and certificate trusted? | Certificate warning despite apparently correct HTTP routing |
| Traefik | Does the selected entry point and router match the request? | Unexpected backend response |
| Kubernetes Service | Are the ports and endpoints correct? | 502/503 while application processes are running |
| Application | Is it ready and serving its intended protocol? | Pod is `Running` but request fails |

The table was not just a checklist: it changed the order in which I investigated a problem. For instance, if a TLS handshake returns the default certificate, editing an HTTP path rule is often irrelevant.

## 2. The TLS detail I wish I had recognized sooner

An HTTP router only receives a request **after TLS negotiation**. The server must choose and present its certificate before an application sees the HTTP `Host` header or URL path. This is why an IngressRoute may route correctly after a warning while the certificate remains unexpected.

I worked through Traefik entry-point configuration, private trust chains, HTTPS configuration and certificate-name matching. For private registries, the relevant clients also included **image builders and container runtimes**, which do not necessarily share the same certificate store as a browser.

I came to ask two separate questions: **Does the client trust the issuer?** and **Does the presented certificate identify the endpoint the client requested?** Solving the first without the second still leaves a failure.

## 3. MetalLB and the problem of a moving frontend

Load-balancer VIP behavior introduced another layer of ambiguity. An intermittent endpoint could be caused by advertisement behavior, network asymmetry, node readiness, or the service behind the endpoint. I investigated possible **VIP instability** and related symptoms, but I did not always have enough evidence to assign one final root cause.

This made me distinguish between what was observable—**a reachability change**—and what was only a hypothesis—such as address advertisement shifting unexpectedly. I wanted to correlate service endpoint health, node-level reachability and load-balancer state before proposing a permanent fix.

## 4. CoreDNS is infrastructure, not an invisible utility

I also encountered a reliability question around **CoreDNS availability**. DNS failures can make otherwise healthy services appear broken, especially when service discovery is embedded in application startup, database dependencies or background job execution.

One concern was **reliance on too little DNS redundancy**. The relevant decision is not simply to increase replicas blindly, but to check placement, node fault domains, resource pressure, upstream resolution and whether the affected applications actually use cluster DNS as expected.

## 5. Why I compared NodePort and hostPort

NodePort, hostPort and load-balancer Services change **which component owns the listening port and how the request reaches the Pod**. I studied their trade-offs when deciding where Traefik or other entry points should terminate incoming traffic.

The operational pain is that every extra path increases the number of things that can be misconfigured. The better design is the one whose **packet path and failure modes I can explain**, not necessarily the one with the shortest manifest.

## 6. TLS negotiation happens before HTTP routing

The distinction between the TLS handshake and HTTP routing became a useful mental model. A server may select a certificate based on the requested server name and the configured TLS entry point **before it sees the HTTP path**.

Consequently:

- A wrong certificate cannot always be corrected by editing an HTTP router rule.
- A trusted certificate issuer and a matching certificate name are separate checks.
- A browser, a container image builder and a container runtime can use different trust stores.
- A successful connection to a VIP does not mean the correct ingress router is selected.

This helped me avoid changing several unrelated layers at once.

### SAN, issuer and name matching

| Property | Question | Typical failure category |
| --- | --- | --- |
| Issuer/trust | Does the client trust the certificate chain? | Unknown certificate authority |
| Subject alternative name | Does the certificate identify the requested host/IP? | Name mismatch |
| TLS configuration | Does the entry point choose the intended certificate? | Default certificate selection |
| HTTP routing | Does the path/host match the intended router? | Wrong service or route |
| Backend readiness | Are there usable endpoints? | 502/503 or no response |

These checks apply to internal service endpoints and private registries, but each client may maintain trust differently.

## 7. Why Service, NodePort, hostPort and VIP are not interchangeable

They can all participate in exposing a workload, yet they select different boundaries of responsibility.

| Exposure method | What it exposes | Trade-off |
| --- | --- | --- |
| ClusterIP Service | Stable in-cluster destination | Usually not directly reachable from outside the cluster |
| NodePort | Service through a port on nodes | Node reachability and port use |
| hostPort | Pod port bound through a host networking mechanism | Placement constraints and host port conflicts |
| LoadBalancer Service | Service entry point backed by a load-balancer implementation | External advertisement/routing must also work |
| Traefik ingress | HTTP(S) routing, TLS termination, rules | Requires valid entry points and backend Services |

For a constrained cluster the best choice was not necessarily the one with the shortest Kubernetes manifest. I wanted a request path whose ownership and failure conditions I could follow.

## 8. A client-centered diagnostic sequence

For a sanitized reproducible environment, I would collect a minimal matrix of observations:

1. Resolve the name and record which address was returned.
2. Test whether the selected destination accepts a connection.
3. Inspect the certificate selected during TLS negotiation.
4. Confirm the intended ingress router matches the request.
5. Inspect the Service and its ready endpoints.
6. Send a representative request to the application and verify its response.

Changing the DNS record, the MetalLB advertisement, the ingress route and the application in a single attempt would make cause attribution almost impossible.

### Availability and path symmetry

The same URL can behave differently from two clients because they traverse different DNS caches, routers, firewalls or node paths. Comparing vantage points is useful, but it needs to be deliberate. A connection succeeding from one node cannot by itself rule out network asymmetry elsewhere.

## 9. Failure-domain questions that remained

I was particularly interested in whether CoreDNS redundancy and MetalLB behavior had become **shared failure domains** for otherwise unrelated services. Yet having one resolver Pod or seeing a VIP transition is not enough to conclude that either caused a specific outage.

A future investigation would correlate client request timestamps with resolver and endpoint observations and would explicitly record when a hypothesis did not fit the evidence. That discipline matters more than claiming a neat root cause for every connectivity symptom.

## What I kept in my notebook

I kept unresolved questions about VIP behavior and DNS as open investigations instead of writing a misleading “fixed MetalLB” headline. The things I could verify were which layer was behaving differently and which hypotheses were still plausible.
