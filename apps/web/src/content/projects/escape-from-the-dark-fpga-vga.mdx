A screen that is only 160 × 120 logical pixels does not have to contain the entire game. That was the starting point of **Escape From the Dark**, a side-scrolling escape game developed as a two-person project on a DE2 FPGA board in May–June 2023. My contribution covered the overall game design and code-generation logic; the report describes the team's implementation, rather than assigning every RTL block to me individually.

The objective was to make a world larger than the visible display, with obstacles, enemies, collectible objects, jumping and a camera that followed the player. Rendering that world directly through VGA made the project different from a software game: the display needed a color for the current scan coordinate while the underlying state continued to evolve in hardware.

> The technical account below draws on the 45-page project report dated June 20, 2023, including its Verilog listings, map, control table and result screens. The game artwork below is reconstructed on the documented logical pixel grid from the original embedded report images; the implementation diagrams explain the RTL. Neither is a new hardware capture.

## A world beyond the visible screen

The level is 540 × 240 logical pixels, with only a 160 × 120 window visible at a time. The character has three lives and must collect five keys before reaching the door. Six warders patrol platforms; four projectiles travel horizontally at two heights. Falling below the level ends the game regardless of the remaining lives. A sword can appear at one of four locations, and the player can attack after collecting it. The God Mode switch was included to make exploration and testing easier.

The DE2 controls are KEY3 (left), KEY2 (right), KEY1 (jump), KEY0 (attack), SW0 (run/reset) and SW17 (God Mode). The control table on page 5 identifies KEY0; an earlier sword description calls it KEY4, which is inconsistent with the table. The reset block is active-low, and the report describes restarting by moving SW0 to 0 and back to 1. These are the documented interface assignments, not a fresh pin-level test.

## The camera is an offset, not another copy of the map

The player position and collision checks use world coordinates. The display scan counters refer to the visible window. The two coordinate systems meet in the color-generation logic:

```text
world_x = x_count + x_map
world_y = y_count + y_map

screen_x = x_player - x_map
screen_y = y_player - y_map
```

The last two equations are a conceptual inverse transformation. In the actual comparison predicates, addition was preferable to subtracting an offset from an unsigned object coordinate.

The horizontal camera origin is bounded by 0 and 380 (540 − 160), the vertical origin by 0 and 120 (240 − 120). Reset puts the player at (10, 230) and the origin at (0, 120), so the window begins at the bottom of the world. Instead of following every change in position, the camera moves once the player crosses a small central dead zone: x = 76 or 84 and y = 57 or 63 in window-relative coordinates. The 8 × 6 span follows the 160:120 aspect ratio. It also avoids making the background move on every small change around the center.

The horizontal movement block advances the player one pixel, and moves the camera by one pixel if the corresponding boundary is exceeded and the origin has not reached the map edge. The vertical movement block handles the same relationship when rising or falling. These are incremental tracking rules, not an instantaneous recentering algorithm. The comparison uses the registered position before the nonblocking updates take effect.

A more subtle issue appeared while implementing the camera. A predicate expressed in screen coordinates could subtract a camera offset larger than the unsigned object coordinate; the result could wrap and select a completely unrelated dot. The team rewrote subtraction-based rendering conditions into addition-based comparisons. For example, a lower-bound condition can be expressed as follows, provided the operands are widened before adding:

```verilog
// Equivalent over mathematical integers; illustrative widened form.
{1'b0, x_count} + {1'b0, x_map} >= {1'b0, object_x}
```

This is not a verbatim recovered source line. It illustrates the report's actual remedy: move the subtraction to the other side of the comparison. Merely replacing minus with plus is not a general cure for overflow; the addition still needs a sufficient intermediate width. A 540-pixel world requires at least 10 bits for its horizontal coordinate. The report contains some 9-bit reset literals but does not preserve every register declaration, so I cannot confirm the final widths from those literals alone.

## Display generation and game-state transitions

The VGA controller supplies the current scan position; the pixel-generation logic uses that position together with the game registers to select color. The report's dark-region logic assigns a three-bit color value, `3'b000`, for black. The logical 160 × 120 coordinate grid is not a statement about the electrical VGA timing, the physical monitor resolution or the refresh rate. Those details would need the full VGA timing module.

The system block maintains `game_screen`, `life`, `key`, temporary immunity and key positions. It represents the start, play, failure and success screens with values 0, 1, 2 and 3. During play, collision with a warder or projectile decrements life, enables temporary immunity and starts a counter; the parity of that counter changes the character color between blue and green. At the threshold of 1100, the immunity is cleared by the condition shown in the report. The code compares the counter with greater-than rather than greater-than-or-equal, and the report calls the interval approximately one second. Without the verified base clock and initialization, that description should not be read as a measured duration.

The key pickup conditions are an ordered else-if chain. Collected keys are moved to y = 247 rather than explicitly deleted; the count increases by one. The five key coordinates are (215, 230), (445, 230), (15, 110), (435, 90) and (535, 30). The door is at (530, 230), and the success condition requires five keys and a proximity check. A fall beyond y = 245 sets life to zero. Because life and game screen are registered with nonblocking assignments, a decrement to zero and the subsequent failure transition need not occur on the same system edge. The source also shows separate success and failure conditions; their ordering matters if both evaluate true on one edge.

## One pixel per step, different clocks for different motion

A key design choice was to use **one-pixel position increments** while changing the time between them. Large integer coordinate jumps would have made movement visibly discontinuous and could have skipped narrow collision regions. The team divided the base clock using counters for the system, player movement, animation, sword, warders and projectiles.

| State domain | Divider threshold |
| --- | ---: |
| System | 30,000 |
| Horizontal player | 300,000 |
| Vertical player | 30,000 × y_speed_count |
| Player motion | 1,000,000 |
| Sword | 300,000 / sword_speed_count |
| Warder | 500,000 |
| Projectile | 200,000 |

  <figcaption>Divider thresholds in the archived RTL. Each divided clock toggles after its counter threshold; the values are not measured refresh rates.</figcaption>

The counters toggle their corresponding clock at the threshold, not on every input cycle. For an integer threshold N and a counter starting at zero, the nominal interval between rising edges is 2(N + 1) input cycles; for the variable dividers this is only a local approximation while their thresholds remain constant. The system checks run faster than horizontal movement. Warders move more slowly than the player; projectiles move more quickly. Animation is independent so the sprite does not alternate between standing and running on every movement step.

This separation made speed tuning straightforward in the original design. It also introduces a hardware concern: several internally generated clocks read state written by other blocks. The listings do not establish whether all such transfers were constrained or synchronized. A modern version would keep one clock domain where possible and use periodic clock-enable pulses, with explicit synchronization for asynchronous button inputs. That is a follow-up design choice, not a claim about the 2023 implementation.

## Approximating acceleration without moving more than one pixel

The jump starts only when the character is supported by a block. On a jump request, `jump` becomes 1, `y_speed_count` becomes 1, and the player moves upward by one pixel. While rising in free space the code subtracts one from y on every vertical update, increases the interval multiplier toward 20, then clears the jump flag at the apex. While falling it adds one to y, decreases the multiplier until 5, and holds it there as a terminal-speed approximation.

    <img src="/figures/journals/escape-05-jump.svg" alt="The documented one-pixel vertical steps, with interval multiplier increasing on ascent and decreasing on descent." loading="lazy" decoding="async" />

  <figcaption>The documented one-pixel vertical steps, with interval multiplier increasing on ascent and decreasing on descent.</figcaption>

The rising-edge interval is proportional to the multiplier, so the approximate local step rate is inversely proportional to it. The character moves quickly near the beginning of a jump, slows near its highest point, then accelerates downward. This resembles gravity visually, but it is not numerical integration of constant acceleration. The velocity changes through discrete clock-divider settings. When hitting the underside of a platform, the code moves the player down one pixel and resets the interval; the report explains that the next cycle produces a brief hesitation. There are also guards against y going below zero and wrapping.

Collision detection is based on coordinate comparisons rather than a physics library. The report expands predicates for 42 numbered platform blocks: horizontal boundary checks, vertical contact checks, and the condition that the player is outside every block. The following form summarizes the rectangle-overlap principle for centers a and b, using combined half-extents:

```text
overlap_x = (ax < bx + hx) AND (bx < ax + hx)
overlap_y = (ay < by + hy) AND (by < ay + hy)
overlap   = overlap_x AND overlap_y
```

The actual collision margins vary by object type. In the warder damage condition the horizontal combined margin is 6 + 5 and the vertical margin is 8 + 5. The block conditions include equality at specific edges, with one-pixel corrections that push the player out of a platform. The report describes a side-contact effect that lets the character cling briefly to the block. This is an effect of the discrete checks, not a separately modeled friction law. The expanded predicates are also a reason that generating repeated RTL from a level description is useful, although the original generator's input format and complete source are not retained in the report.

## A sword attached to a moving coordinate frame

The sword was a good example of why an algorithm that works for one object is not necessarily appropriate for another. The initial approach reused the vertical player mechanism, but the sword's reference point moved and could change direction. Rather than controlling its absolute displacement alone, the team introduced `sword_distance`, a distance relative to the player.

At the start screen, the spawn selector cycles through (14, 193), (364, 193), (469, 153) and (279, 233); the start event leaves one selected position. This is a deterministic cycling selector with input-dependent timing, not a cryptographically or statistically verified random generator.

Once close to the player, the sword tracks the player's y position and an x offset of ±(9 + sword_distance), with sign selected by facing direction. An attack starts when the relative distance is zero and the button and alignment conditions are met. The speed count moves from 1 toward 3 while the distance increases one pixel at a time. The `attack` flag is then cleared and the distance decreases on the return path. The divider is 300,000 divided by sword_speed_count, so the extension becomes faster as the count increases. This is deliberately the inverse relationship of the vertical player's interval multiplier.

A warder is defeated only when the attack flag is asserted and the sword overlap condition is satisfied; the corresponding warder y coordinate is set to 247. The warders otherwise patrol one pixel at a time and reverse near their platform endpoints. The first right-moving projectile pair starts at x = 0 and 270, shares y = 89, and wraps after reaching 540. The second pair travels in the opposite direction. The projectiles are not removed by sword attacks.

## Rendering darkness with coordinate predicates

The game's name refers to a restriction on visibility rather than to a lighting engine with continuous intensity. The output logic compares the world coordinate of the current scan pixel with the player's position. The report includes outer black-region predicates at approximately ±60 horizontal and ±36 vertical logical pixels. For example, `x_count + x_map >= x_player + 60` makes the corresponding pixel black during normal play.

The source also describes a gradual transition near the edge, rendered as increasingly sparse visible dots. The complete predicate for that transition was omitted from the report because of its length, so the figure shows the known outer bounds and only illustrates the intermediate stippling. It would be misleading to claim a particular radial falloff or reconstruct a numerical luminance curve from the screenshots alone. God Mode disables the darkness mask and is intended to protect the player from enemies. The archived condition `god || !god_mode` and the prose describing SW17 as enabled-high do not agree on signal polarity; the external behavior is documented, but the final internal signal mapping is not confirmed. The fall check precedes this immunity branch in the shown logic.

The other rendering issue recorded in the report was corrupted colors when nested if statements were used in the output logic. The team flattened the predicates using logical AND and observed correct output. Nested conditionals in Verilog do not inherently introduce an extra clock cycle, and the report supplies no timing slack or synthesized netlist to prove a root cause. A different priority structure, combinational depth or assignment behavior could have contributed. The reliable claim is the observed symptom, the rewrite and the reported improvement.

A game dot is not the same as a pixel in the report image. The original start, failure and success images are 752 × 504, 416 × 271 and 418 × 272 pixels; their different horizontal and vertical enlargement factors obscure the 160 × 120 logical grid. The gameplay panels are 706 × 460 and 653 × 448 pixels, and the map illustration is 1498 × 605. To restore the pixel artwork, I fitted the grid period and origin to the source color transitions and sampled cell centers, using the RGB colors of the documented three-bit output. For the small sprites, the stated dimensions constrain the reconstruction directly. Each recovered cell becomes an integer-aligned SVG region, merging only adjacent cells of the same color. The map uses the observed platform spans and the reconstructed sprite masks rather than resampling tiny copies of each character. The red circles on the result panels are report annotations, redrawn separately so that they do not become part of the game grid. These figures preserve the documented content and sharply defined logical dots, but the screenshots are not ROM dumps: isolated ambiguous cells, the exact map illustration placements and the annotation outlines remain inferred. The original team report and raw images are not redistributed here.

## What I would change in the RTL today

The report records another problem that is easy to recognize in larger designs: an early approach tried to centralize most assignments in one control always block and make adjustments in other blocks, resulting in multiple writers to the same registers. The team reorganized the logic so related state was owned together and overlap between always blocks was reduced. A cleaner version would make each register's ownership explicit, separate next-state calculation from its update, and test priority rules where simultaneous events can occur.

I would also make the level data a single source of truth for generated geometry and collision predicates, use explicit widened arithmetic, and verify boundary cases such as camera origin 380, falling below the map, hitting a platform at its edge and switching facing direction during a sword attack. Frame-consistent rendering could use a snapshot of game registers at a defined display boundary if tearing proved to be an issue. None of those improvements should be mistaken for features already verified in the archived design.

The project did produce the documented VGA game on DE2 hardware. The report preserves code excerpts and visible outcomes, but not a complete synthesizable source tree, testbench, resource-utilization table, timing-closure report or a measured frame rate. I therefore cannot reproduce the original bitstream or quantify FPGA area and timing performance. What remains useful is the way the game emerged from small arithmetic and state decisions: a moving coordinate frame, bounded integer arithmetic, controlled update intervals and the ownership of state across concurrent hardware processes.
