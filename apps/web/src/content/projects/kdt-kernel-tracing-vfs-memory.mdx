One of the moments I remember from learning Linux internals was moving from a **static explanation of scheduling** to looking at an **event timeline**. A diagram can show how a process changes state; a trace gives that transition a timestamp and context.

During KDT I used **ftrace and KernelShark** to observe kernel events and think about process execution over time. The exact event options I selected at the time are not the important part of this record; the lesson was learning how a trace becomes evidence for a specific question about the kernel.

## 1. Start with the scheduler, not with an intuition

When an application appears stuck, it is easy to say that it is “not getting CPU.” But a sleeping thread may be intentionally waiting on I/O, a lock or a timer. A runnable thread might be waiting in a runqueue; a running thread might frequently be preempted.

The scheduler portion of the course covered process states, scheduling classes, **CFS**, real-time policies, runqueues, context switching, multicore load balancing and preemption. I tried to connect these concepts to the events visible in a timeline rather than treating them as independent definitions.

| Observation | Question I learned to ask |
| --- | --- |
| Context switch | Which task stopped running and why? |
| Wake-up | What made the task runnable, and when was it scheduled? |
| Long wait | Was the task sleeping or runnable but delayed? |
| Multiple CPUs | Was load distribution or synchronization affecting progress? |
| Frequent switching | Was the switching useful, or overhead caused by contention? |

A timeline does not directly reveal a root cause. For example, an observed delay between wake-up and execution could reflect many factors; I still need the workload and relevant surrounding events to interpret it.

## 2. Interrupts and execution context

The ARM/Linux material introduced exception handling, IRQ entry/exit, timers, deferred work and the rules that differ among **process context**, **interrupt context** and **workqueues**.

This answered a question I had from embedded programming: why can't a driver simply do any useful work inside an interrupt handler? The kernel must prioritize bounded, non-blocking work in the appropriate context, and often defer more expensive operations.

Understanding these boundaries also makes traces easier to read. A long callback is not necessarily scheduled like an ordinary userspace thread; execution context changes what behavior is legal.

## 3. Virtual memory: the address is not the page

The memory-management part of KDT connected **VMA**, page tables, virtual-to-physical translation, demand paging, page faults and allocators.

The progression I found most useful was:

1. A process reads or writes an address in its virtual space.
2. The CPU uses translation structures to determine the physical destination.
3. If the mapping is absent or protection disallows the access, control enters fault handling.
4. The kernel may establish a valid mapping, load a file-backed page, or report an error.
5. The process resumes or fails depending on the fault outcome.

This explains why an application can have a large virtual address range without every page being resident in RAM. It also explains why a program's resident size, mapped files, kernel allocations and page cache cannot be treated as identical quantities.

## 4. VFS: the `open()` path hides several layers

The file-system lectures covered **VFS**, `inode`, `dentry`, `superblock`, file operations, EXT-family structures, page cache, consistency, journaling, flash translation layers and F2FS.

I started thinking of a file operation as a journey through interfaces: pathname resolution, VFS objects, a concrete filesystem implementation, caches and writeback, block I/O and the device. Each layer has its own performance and failure behavior.

The important contrast is **logical success versus physical persistence**. A successful return from a buffered write is not automatically proof of durable media state. Journaling can protect filesystem metadata consistency, but it does not give every application transaction exactly the semantics it wants.

## 5. Tracing, dump analysis and performance tools answer different questions

We studied debugging with ftrace/KernelShark, GDB, Trace32, crash utilities, kernel dumps, PMU and related monitoring concepts. I learned to associate each with the kind of evidence it can provide:

| Evidence | Best use |
| --- | --- |
| ftrace / KernelShark | Time-ordered kernel events around observable behavior |
| `perf` / PMU | Where CPU time or microarchitectural events accumulate |
| `/proc` and process views | Live state and resource accounting |
| vmcore / crash tools | A snapshot of kernel state after a failure |
| Application logs | Domain-level events and errors |

I would not use one tool as a substitute for all the others. A crash dump preserves a state snapshot; it cannot reconstruct every preceding scheduling decision without additional evidence.

## 6. The question that stayed with me

Later, while operating replicated volumes and stateful services, I often fixed the immediate symptom without being able to explain the kernel/filesystem behavior beneath it. The KDT study made that limitation visible to me.

I want to go back to these mechanisms with **small, reproducible tracing experiments**—particularly VFS-to-block I/O latency, page-cache effects and scheduler wake-up delays—and measure rather than guess.
